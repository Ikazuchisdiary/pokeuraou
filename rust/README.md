# Rust 移植：局面生成の 96.7% を占める解決器を Rust に移す

**結論**: 生成は **20〜28 倍**速くなり、**同じ乱数種で生成した対戦は 1 バイトも変わりません**。

```
3 ゲーム / 種 5      python 21.7 s -> rust 1.0 s   22.2x   試合一致 3/3
3 ゲーム / 種 1001   python 24.4 s -> rust 1.2 s   20.4x   試合一致 3/3
3 ゲーム / 種 77     python 30.2 s -> rust 1.1 s   27.5x   試合一致 3/3
```

**学習済みの価値関数でも同じです。** `data/models/*.pt` を評価軸にした生成は
GPU で **15〜18 倍**、CPU で順伝播しても **8〜10 倍**速くなり、
対戦はやはり 1 バイトも変わりません。比が hp-share より小さいのは、
解決器が速くなったあとに**残るのが torch** だからです。

```
10 ゲーム / 種 404 (cuda)  python 113.0 s -> rust 6.3 s   17.8x   試合一致 10/10
 6 ゲーム / 種 77  (cuda)  python  71.7 s -> rust 4.8 s   14.9x   試合一致 6/6
 2 ゲーム / 種 11  (cpu)   python  19.6 s -> rust 2.6 s    7.6x   試合一致 2/2
```

再現は `uv run python tools/diff_generation.py --games 3 --seed 5`、
価値関数なら `--value data/models/value-gen234.pt` を足します。

## なぜ解決器だったのか

移植先は推測ではなく実測で決めました。**カウンタで測った**生成 1 ゲームの内訳:

| | 秒 | 割合 |
|---|---|---|
| `resolve_turn` | 35.04 | **96.7%** |
| うち `damage.calculate` | 7.49 | 20.7% |
| うち `view.battler` | 3.74 | 10.3% |
| `narrow` | 0.43 | 1.2% |
| `equilibrium.solve`（LP） | 0.02 | **0.1%** |

**cProfile はこれに同意しません。** 同じワークロードで実行時間の 16% を scipy の HiGHS
オプション検証（`_highs_wrapper.check_option`）に配分します。単体ベンチでは 1 回の solve が
4.5 ms、つまり 0.1% です。C 拡張の呼び出しを歪めないほうのプロファイラを信じます。

## 推測せず拒否する

移植の契約は「**Python と同じ答え**」です。だから未対応に出会ったら推測せず `Err(reason)` を返し、
呼び出し側は Python の答えをそのまま使います。これが部分移植を「測れるだけ」ではなく
「使える」ものにします:

- Rust が解決したターンは Python の答えそのもの
- 拒否したターンは Python の時間がかかるだけ（余計な損はない）
- **拒否理由は数えられる**ので、次に実装すべきものは推測ではなく影響の大きさで決まる

実際この数えが次を順に名指ししました: `pixilate`(730) → `poisontouch`(177) →
`thawsTarget`(96) → `mustrecharge`（1 ノードの 45% のセル）→ `recharge` 疑似技 →
`electroshot`(1.5%) → `afteryou`(1.9%) → `cursedbody`(3.3%)。
**白リストは 2 つとも反転させました**——列挙するのは「Python が名指しで扱っていて、こちらが
実装していないもの」だけ:

- 揮発性状態: 以前は `disable` 1 つ。`disable` を実装したので**今は空**です。
- 状態技: Python が完全にモデル化していない技は、Python 自身も宣言的フィールドを適用して
  申告するだけです。こちらも同じことをするので、**拒否が正しいのは Python が独自コードを
  モデル化していてこちらが未実装のときだけ**。112 技が拒否から解決に変わりました。

学習済み価値関数の生成 10 ゲーム・34,959 セルで、**拒否は 0** です。

### 到達しえない局面は答えずに拒否する

`validate_position` が弾く局面（hp が 0..maxhp の外、`fainted` と hp の不一致）は
Rust 側も拒否します。2 実装が一致するのは関数が定義されている入力の上だけで、
ゲームが到達しない状態では Python 自身が負のダメージを出します。
**別の間違った答えを黙って返すより、拒否するほうが正しい。**
これはテストで見つけました——隠れ個体に勝手な SP を入れた手作りの局面で
0.095 の差が出て、原因は移植ではなくテスト側の局面でした。

**カバー率はサンプルの性質です。** 最初の 2 ゲームのサンプルでは 87.2% でしたが、
別の 10 ゲームでは同じビルドが 42.4% でした。退行ではなく、最初のサンプルに
メガサーナイトが入っていなかっただけです（`pixilate` だけで 730 ターンが拒否）。
1 つのサンプルのカバー率は、そのサンプルについての数字でしかありません。

### 1 ULP の差について

ノードの差分で、採点されたセルの 73% は**ビット単位で一致**し、残りは最大 6.7e-16 ずれます。
これは numpy の `values @ weights`（内積）と逐次加算の**加算順序の違い**です。
解決器そのものはビット単位で一致しています（局面・分岐・確率すべて）。
そして実際に読まれる答えである均衡は:

```
均衡値が動いた最大   6.7e-16
採用頻度が動いた最大 1.2e-14
```

CLI が印字する最下位桁より 12 桁下です。生成した対戦が完全一致することが、
この差が何も変えないことの実地の証拠になっています。

## 速度（交互実行・各 5 回の最小値）

絶対値は負荷で 2 倍動くので、比は必ず両側を同条件で交互に測ります。

| | Python | Rust | 比 |
|---|---|---|---|
| `damage.calculate` | 103.8 us | 1.54 us | **67.2x** |
| `resolve_turn`（狭いサンプル） | 3482.9 us | 82.9 us | **42.0x** |
| `resolve_turn`（広いサンプル） | 3378.3 us | 89.6 us | **37.7x** |
| ノード充填（24x24、2 評価軸） | 56.0 s / 25 ノード | 1.4 s | **40.3x** |
| ノード充填（学習済み価値関数 + 対照軸） | 20.7 s / 10 ノード | 2.2 s | **9.4x** |
| 符号化（`encode.py`） | 66.1 us | 3.5 us | **18.9x** |
| 生成（エンドツーエンド） | 0.59〜0.92 s/ターン | 0.026〜0.037 s/ターン | **20〜28x** |
| 生成（学習済み価値関数・cuda） | 0.99〜1.20 s/ターン | 0.067〜0.071 s/ターン | **15〜18x** |
| 生成（学習済み価値関数・cpu） | 1.11〜1.22 s/ターン | 0.115〜0.160 s/ターン | **8〜10x** |

学習済み価値関数の比が小さいのは、解決器が速くなった後に**残るのが torch** だからです。
順伝播と符号化の受け取りは Python 側の仕事で、そこは移植の対象ではありません。

### ロスレスな分岐重複排除は、速度ではなく正確さを買いました 〔9/19・IKA-10〕

同じ状態に到達した分岐を 1 本にまとめます（`Budget.merge_duplicates`、既定 on）。
Python の `_merge_live` / `_merge_branches` / `_merge_suspended` の転記で、
**両方を入れないと本番で効きません**——生成はこの移植を通ります。

実戦から記録したコールを同一入力・50 回・交互実行（各 5 回の最小値と中央値）で測ります。
**標本を 2 つ載せるのは、答えが標本で変わったからです**:

| 標本 | 分岐 | 解決時間（併合なし → あり） |
|---|---|---|
| `value-gen11L` の 955 コール | 259,950 → 185,650（**−28.6%**） | 50.0 → 43.6 us（中央値）／ 44.6 → 42.7 us（最小値） |
| `hp-share` の 1,218 コール | 310,750 → 216,350（**−30.4%**） | 39.0 → 39.2 us（**差なし**） |

分岐の削減率はどちらも 3 割で同じなのに、時間は片方で縮み片方で動きません。
**併合は減らすだけではなく、予算の当たり方も変える**からです:
`room = max_branches / pending` なので、生きている分岐が減ると 1 手あたりの解像度が上がり、
そのぶん展開が増える。浮いた時間の一部は**正確さに使われ**、`TurnResult.exact` が
false になる頻度が下がります（Python 側の実測で matrix 予算 90.5% → 96.7%）。

⚠ **`value-gen11L` 標本には 43 us と 49 us の 2 峰があります**（同じバイナリ・同じ入力・
15 回中 13 回がどちらかの峰）。原因は特定していません。上の表は峰ごとに比べても
向きが変わらないことを確認した上で載せています。`hp-share` 標本では 2 峰は出ません。

移植で 1 つだけ Python と違うのは比較の実装です。パーティは `Rc` で共有されているので、
**触っていない Pokemon は `Rc::ptr_eq` で済み**、928 バイトの `==` はそのターンに
動いた 2 体だけに走ります。`same_turn` / `same_side` は**分解束縛**（`..` を使わない
`let Turn { .. } = a`）で書いてあるので、フィールドが増えたらコンパイルが通りません。
比較から漏れたフィールドは「違う状態を同じとみなす」という唯一の壊れ方なので、
テストではなくコンパイラに見張らせています。

**併合の実装費用は測って2回削りました**（`hp-share` 標本・同一バッチ内の比、併合なしを 1 として）:

```
  最初（既定ハッシャ・Rc 高速路なし）   +8.9%
  Rc::ptr_eq を入れた                  +6.2%
  バケット鍵を FNV-1a にした            +0.5%   ← 現在
```

バケット鍵は**チェックサムではない**ので SipHash は過剰でした
（`encoded_node::leaf_key` が先に同じ結論に達しています）。取りこぼしても比較が
空振りするだけで、違う状態が併合されることはありません。

`uv run python -m pokeuraou.cli examples/scenario-turn5.json` の内訳:

| 段階 | 前 | 後 |
|---|---|---|
| import | 0.86 | 0.94 |
| build_beliefs | 0.88 | 0.92 |
| reduce_for_position | 0.14 | 0.15 |
| **joint_classes** | **4.62** | **0.05** |

| **合計** | **15.95** | **2.38** |

`joint_classes` は Rust とは無関係で、Python 側のアルゴリズムの問題でした——
`itertools.product` で 1,359,156 通りを作ってソートし、4 つだけ残していました。
各スロットが既に重み降順で結合重みが積なので、ヒープで格子を歩けば作る必要がありません。
分母も「積の和 = 和の積」で列挙不要です。同点の並びは `itertools.product` 順に揃えてあり
（報告に出るクラス名が変わらないように）、`tests/test_joint_classes.py` が総当たりと突合します。

**印字される内容は 1 行も変わりません。** 変わるのは自己申告の所要時間と、
LP の双対ギャップ（3.4e-15 対 6.2e-15、どちらも「解けた」の意味）だけです。

## 何が速いのか

**コピーです。** Python の `Pokemon.copy` は生成時間の 16% で、解決器は分岐ごと・行動ごとに
局面を複製します。だから表現をコピーのために選びました:

- 識別子はインライン（`Id`、31 バイト、**切り詰めずにパニック**する）
- ランクは固定配列、技は固定 4 枠
- 解決器が読むだけの 2 つの JSON（`abilityState`、効果の `extra`）は `Rc` の後ろ

`Position` の複製は memcpy と参照カウントの加算です。

### 複製は移植後も一番大きい

移植したあと、**Rust の解決器の中で一番大きいのも複製でした**。カウンタで測ると
1 ターンあたり 44.3 回、1 回 0.90 us——**解決器 55.2 us の 65%** です。
`cargo run --release -- clones <turns.json>` と `turns` の出力がこの 2 つを直接出します。

内訳は 2 つあり、順に潰しました:

| | 複製 1 回 | 1 ターン |
|---|---|---|
| 最初 | 0.90 us | 55.2 us |
| 控えのポケモンを `Rc` で共有（11 KB の memcpy → 参照カウント） | 0.36 us | 49.3 us |
| 文字列 5 つを `Rc<str>` に、`sides` を固定長 2 に（確保 6 回削減） | 0.22 us | 44.5 us |
| 変種が 1 つのときはターンを複製せず渡す（複製 44.3 → 31.4 回） | 0.22 us | **-3.9%** |

最後の 1 行だけ絶対値ではなく比なのは、測ったときにこのマシンが別の生成を走らせていたからです
（交互実行・各 8 回の最小値で 61.8 us 対 59.4 us）。**比は同条件で交互に測れば生きますが、
絶対値は生きません。**

1 段目は memcpy が理由でした——`Pokemon` は 928 バイトで両側 12 体。ターンが触るのは
場に出ている 2 体だけなので、`Rc::make_mut` は書いたものだけを複製します。
2 段目で複製は memcpy 律速ではなく**確保律速**に変わっていたので、確保を減らしました。
生成全体では 15.4x → 17.8x（種 404・10 ゲーム・学習済み価値関数）、
hp-share では 19.1x → 22.3x です。

共有が効いているかも数えています。1 ターンあたり複製 44.3 回に対し、
**書き込みで実際に複製されたポケモンは 38.4 体**——共有しなければ 12 体 × 44.3 = 532 体です。
1 複製あたり 0.87 体で済んでいる、というのがこの設計の成否そのものなので、
将来この比が悪化したらカウンタが先に言います。

カウンタは製品コードに残してあります。1% ほどの負担で、**次に何を直すべきかを
推測ではなく測定で決められる**ことのほうが高くつきません。
今の内訳は 1 ターン 44.5 us のうち複製 9.7 us、ダメージ計算 9.5 回で 8 us、残り 27 us です。

**そして粒子軸がありません。** CLI の行列経路は実測で 100% が n=1（`damage.calculate` の
呼び出し 3,855 件すべて）。Python が運ぶベクトル化は、この経路では幅 1 の NumPy 配列を作る
純粋なオーバーヘッドでした。

## 使い方

既定では**オフ**です。何も設定しなければ何も変わりません。

```bash
cd rust && cargo build --release

export POKEURAOU_RUST_NODE=1          # 使う
uv run python tools/selfplay.py --games 100
```

壊れていたら黙って Python に戻り、理由を 1 度だけ表示します。実行を失敗させません。

### 境界はノード単位

`batched_payoffs` はもともとこの計画のノード境界（局面と両側の行動リストが入り、行列が出る）
なので、プロセス境界を同じ場所に置けば**葉は一切渡りません**。渡るのは入りに局面 1 つ、
帰りに 576 個の float だけです。

試合を進める `resolve_turn`（exact 予算）は別扱いで、**重みだけ**を先に返して
Python 側が自分の乱数生成器で 1 つ引き、その 1 局面だけを取りに行きます。
これが「対戦がビット単位で同じ」を保つ仕組みです——
`numpy.random.Generator.choice` が乱数列そのものなので、引く回数と引き方を変えられません。

### 学習済み価値関数：渡るのは葉の「符号化」

パラメータ無しの評価軸（`hp-share`、`faints`）は Rust 側で計算され、**行列だけ**が帰ります。
学習した価値関数はそれができません——**入力が葉そのもの**だからです。
そこで境界の向きを変えて、葉を `encode.py` の配列にしてから渡します:

| | 渡るもの | 1 ノードあたり |
|---|---|---|
| 局面 JSON を渡す（却下） | 葉の局面 | 約 2,000 × 15 KB + パース |
| **符号化を渡す（採用）** | 8 本の配列 | 約 2,000 × 3.7 KB、パース無し |

**順伝播は torch に残します。** float32 の行列演算をもう 1 つ実装すれば加算順序が変わり、
勝率の下位桁が変われば利得が変わり、利得が変われば均衡が変わります。渡るのは入力だけです。
`encode.rs` は `encode.py` の移植で、9,730 局面 × 8 配列を**ビット単位で**突合済み
（`tools/diff_encode.py`）。速度は 3.5 us 対 66.1 us で **18.9x**。

折り畳みは Python のままです。Rust が返すのは「葉」と「畳み方」——
ふつうのセルは (開始位置, 重み列) の内積、途中で交代が入ったセルは `turn_leaves` が作る木
（偶然は平均、交代は選ぶ側の最大）——で、`fold_value` はすでにある関数です。

**対照軸も同じ往復に乗ります。** 解析は学習軸の隣にパラメータ無しの軸をもう 1 本置きますが、
葉は向こうにあるので**そちらで葉ごとに採点して**値を一緒に返します。
2 本目の列のためにノードごと帰すより安く、実測で 2.11 s 対 2.19 s（差はほぼ 0）。

## まだ Python にあるもの

ブリッジを入れたあとの生成の内訳（学習済み価値関数、6 ゲーム 54 ターン、2.81 秒）。
cProfile ではなくカウンタで測っています:

| | 秒 | 割合 |
|---|---|---|
| ノード充填（Rust、往復込み） | 1.68 | 59.9% |
| 試合を進める `resolve`（Rust、exact 予算） | 0.48 | 17.3% |
| torch の順伝播 | 0.28 | 9.9% |
| `narrow`（採点は Rust、合法性は Python） | 0.13 | 4.6% |
| LP | 0.11 | 4.0% |

**Python 側に残っているのは 1 割強で、その大半は torch です。**
`narrow` は移植前 15.5% でした（下）。残りを削るなら次は Rust の中です。

### `narrow` は採点だけ渡す

候補の**合法性**（`actions.py`、PP・Disable・アンコール・こだわり・拘束の 500 行）は
測ると実行時間の **0.2%** で、これを 2 重に実装する価値はありません。
高かったのは採点のほう——`score_action` は `damage.calculate` のループで、
ブリッジ後の生成の **13.9%** を占めていました。だから渡すのは候補の列と、
返るのはスコアと当たった相手の内訳だけ。網羅・並び・同点処理は Python のままです。

**スコアはビット単位で一致しなければなりません。** スコアは順序を決めるためだけに使われ、
順序がそのまま「どの手が行列に載るか」なので、最下位桁の差は別のメニュー、
別の対戦になります。許容誤差では捕まりません。16 ロールの平均は整数 16 個の float64 和
（順序によらず厳密）を 16 で割るだけなので、一致させられます——
2,951 候補すべてが一致し、採用集合も順序も内訳の文字列も同じでした。

ただし**1 粒子だけ**です。信念層は分布を持った Battler を渡してきますが、
移植側は 1 粒子なので、`battlers` を渡す呼び出しには提示しません（解析 CLI がそれです）。
生成は信念を使わないので、生成のためのものとしては十分です。

narrow は 3.8〜4.2x、生成全体では 17.8x → 19.6x（学習済み価値関数）、
22.2x → 26.8x（hp-share）になりました。

### 拒否は 0 になりました

学習済み価値関数の生成 10 ゲーム・34,959 セルで拒否 0。そこに至るまでの 3 つ:

| 理由 | 測ったときの割合 | 中身 |
|---|---|---|
| `two-turn move: electroshot` | 1.5% | 溜め技 12 種すべて |
| `status move: afteryou` | 1.9% | 状態技の白リスト反転（112 技） |
| `ability: cursedbody` | 3.3% | `disable` 条件そのもの |

拒否されたセルは Python が埋めるので答えは変わりませんが、**そのセルだけ速くありません**。
学習済み価値関数ではもう 1 つ副作用があります——拒否されたセルの葉は、
ノード全体とは別の小さな順伝播で採点されるので、float32 の行列演算が

**移植の穴が数値にも出る**ということです。埋めたら消えました。

`cursedbody` は 30% で Disable を分岐します。だから Disable 条件——どの技を止めたかを

### dlshogi から持ってこられたもの / こられなかったもの

[DeepLearningShogi](https://github.com/TadaoYamaoka/DeepLearningShogi) の `UctSearch.cpp` は、
GPU ごとに複数の探索スレッドが `QueuingNode()` で 1 つのバッチに局面を積み、
`PolicyValueCache` が局面キーで NN 出力をキャッシュし、`AddVirtualLoss()` で
同じ枝の重複探索を避ける、という構造です。この 3 つのうち:

- **バッチ化**は既にこうなっています（ノードの葉を 1 回の順伝播で採点）。
- **virtual loss** は MCTS の道具で、ここの探索は 1 プライなので出番がありません。
- **評価キャッシュ**は効きます——下の通り、葉の共有として入れました。

### ノードの葉は共有する（41.8% は「すでにある局面」）

dlshogi の `PolicyValueCache` と同じ理屈がここにもあるかを測りました。6 ノード 28,827 葉:

| ノード | 葉 | 相異なる | 重複 |
|---|---|---|---|
| 24x24 | 4,601 | 3,020 | 34.4% |
| 24x24 | 5,236 | 3,059 | 41.6% |
| 24x24 | 3,917 | 1,572 | 59.9% |
| **合計** | **28,827** | **16,789** | **41.8%** |

両者の技が両方失敗した、両方まもる、交代が同じ返しに出会った——結果の局面は同じです。
**同じ局面なら葉を 1 つにまとめます。** 正しさの根拠は `Position` の `PartialEq` で、
これは全フィールドを見ます。手前にある安いハッシュは取りこぼしても構いません——
取りこぼせば比較が空振りするだけで、**違う局面が共有されることはありません**。

幅 48 + `--rank-leaf` の 3 ゲームで測った効果:

| | 前 | 後 |
|---|---|---|
| 葉の数 | 222,593 | **107,387**（-52%） |
| パイプを渡った符号化 | 775 MB | **374 MB** |
| 充填の中の符号化 | 15.6% | **8.6%** |
| 1 ターン | 0.249 s | **0.151 s（1.65x）** |

**バッチの行数が変わると値が動くのでは、という懸念は測って否定しました**——
19,333 行と 13,277 行で、同じ行の値は CPU でも GPU でもビット単位で一致します。

### 残る 1e-8 は、ネットワークが自分と食い違っている分です

共有を入れたあと、ノード差分の最大差が 2.8e-16 から **2.98e-8** に増えました。
調べると、これは移植の誤差ではありません:

- 問題のセルは「2 分岐が同じ局面に落ちる、重み 0.5/0.5」でした。
- Python 側でその 2 分岐を確かめると、**局面は完全に同一**です。
- ところが**同じ局面を 1 つのバッチで 2 回採点すると、ネットワークは 1 ULP
  （5.96e-8）違う値を返します**——ブロック GEMM のタイル境界によるものです。
- 重複排除しない側はその 2 値を平均するので、**半 ULP ずれた値**になります。
  共有する側は 1 回しか採点しないので、float32 の値そのものが出ます。

つまり**移植側のほうが正確**で、差はそちら由来ではありません。読まれる数字は動きません:

```
均衡値が動いた最大   2.2e-15
採用頻度が動いた最大 1.4e-14
生成した対戦          決定は全て同一（記録される探索値だけが 8 桁目で動く）
```

`tools/generate_parallel.sh` は `--device cpu` を選んでいて、理由もそこに書かれています——
**「順伝播は幅 24 で 1 ゲームの 1.3%。1.3% をカードに移しても、
1 ワーカー 1 GB の CUDA コンテキストの元は取れない」**。当時は正しい判断でした。

**その 1.3% は、解決器が Python だった頃の 1.3% です。** 解決器が 20 倍速くなると、
同じ順伝播が占める割合は跳ね上がります。いま測るとこうです:

| | torch の割合 | 1 プロセスの所要 |
|---|---|---|
| 幅 24 / cpu | 26.2% | 5.55 s |
| 幅 24 / cuda | 12.6% | **3.69 s（1.5 倍速い）** |
| 幅 48 / cpu | **35.4%** | 10.68 s |
| 幅 48 / cuda | 9.4% | **4.85 s（2.2 倍速い）** |

マシン全体でも同じ向きです（幅 48、`--rank-leaf`、空きマシン）:

| | 合計 g/min |
|---|---|
| cpu 8 ワーカー | 128.7 |
| cpu 16 ワーカー | 142.5 |
| cpu 24 ワーカー | 146.3 |
| **cuda 8 ワーカー** | **263.8** |
| cuda 16 ワーカー | 295.7 |

**CUDA コンテキストが 9 個で頭打ちでも、cuda 8 ワーカーは cpu 24 ワーカーより 1.8 倍速い。**
コンテキストの制約は本物ですが、それを避ける理由がもう無くなりました。

同じ理由で `WORKERS=14` も古い数字です。「16 で 80.2 g/min に崩れる」は
移植前の測定で、いまは 16 でも 24 でも崩れません（1 ワーカーが軽くなったので）。

**教訓**: 移植は「何が速くなったか」だけでなく、**「何が相対的に高くなったか」**を
変えます。速くした部分の隣にある判断は、根拠ごと測り直してください。

### プロセス数は測って決める（誰も使っていないマシンで）

`tools/bench_workers.py` が N プロセス同時の games/min を返します。
実設定（幅 48、`--rank-leaf`、value-gen2345、seed 1000、1 ワーカー 4 ゲーム）で、
**他に何も走っていないマシン**で測った結果:

| ワーカー | cuda 合計 g/min | 1 ワーカーあたり | 効率 | cpu 合計 g/min |
|---|---|---|---|---|
| 1 | 50.4 | 50.4 | 100% | 27.6 |
| 8 | **263.8** | 33.0 | 65% | 128.7 |
| 16 | 295.7 | 18.5 | 37% | 142.5 |
| 24 | — | — | — | 146.3 |

読み取れること:

- **8 ワーカーで頭打ち**です。16 にしても合計は 12% しか増えず、
  起動だけで 157 秒かかるようになります（CUDA コンテキストが 1 つ約 1.1 GB、
  RTX 5070 の 12 GB では 9 個ほどで一杯）。**いまの 10 ワーカーで妥当**です。
- **CPU 推論に逃がす手はありません。** どのワーカー数でも cuda が 2 倍速い。
  順伝播は 1 プロセスの 10% でしかないのに、CPU にすると倍かかります。
- 8 コア 16 スレッドに対して 8 ワーカーで効率 65% なのは、
  Python と Rust が交互に動く（同時には走らない）ので 1 ワーカーが
  1 スレッドを使い切らないためです。

**前に「ワーカーを増やすのが一番安い」と書いたのは誤りでした。** その測定は
そちらの 10 ワーカーが走っている上に 2 つ足しただけのもので、
サンプルが 2 つしかありませんでした。空いたマシンで曲線を取ると頭打ちです。

### ベンチの最初の 1 回は嘘をつきます

`bench_generation.py` は評価器を 1 回空打ちしてから計測を始めます。
入れる前は、**同じコマンドが 9.17 s/game と 1.35 s/game を返していました**——
プロセス最初の順伝播が CUDA コンテキストとカーネルの準備を払っていて、
それが計測区間の中にあったからです。4 ゲームならその 8 秒が 4 で割られ、
40 ゲームなら 40 で割られます。

同じ理由で `bench_workers.py` は最初の 1 波を捨てます。
そして**ゲーム数を変えると 1 ワーカーあたりの数字も変わります**
（seed 1000 の 5〜6 ゲーム目は重い）ので、比べるときは `--games` を揃えてください。

## 差分はバイナリに対して取ります

`tools/diff_*.py` はバイナリの存在しか見ていませんでした。**編集したソースを
コンパイルする前に走らせると、古いビルドに対して「誤り 0」と報告します。**
差分が防ぐはずの失敗が、その解決策の顔をして起きる形です。

`rustnode.require_current_binary()` が、ソースのどれかがバイナリより新しければ
拒否します。通ったときは実行したバイナリの指紋を出力の先頭に書きます:

```
binary 326d6bec9c3143e6 built 2026-09-12T22:47:20
```

（`POKEURAOU_RUST_NODE_BIN` で別のものを指している場合は、それが意図なので
新旧の判定はしません。）生成側の記録に同じものが要るなら
`rustnode.binary_fingerprint()` がそのまま使えます。

## セルを全部解かない（実装済み・既定はオフ）

ここまでは**同じ仕事を速くする**話でした。残っている一番大きいものは、
**仕事そのものを減らす**ほうにあります。

幅 48 のノードは 2,304 セルを全部解いています。しかし**均衡を求めるのに
全セルは要りません**——ある手が「より良い応手ではない」ことを示すのに必要なのは、
相手の混合戦略が重みを置いている列だけです。その台は普通 1〜5 本しかありません。

これは double oracle（列生成）として知られた方法で、**収束したときに
「これは全体の均衡である」が証明済み**になります。近似ではありません。

### どれだけ減るか（`tools/cells_needed.py`）

充填済みの行列に対して double oracle を再生し、必要だったセルを数えます。
本番の評価関数（value-gen2345、幅 48、`--rank-leaf`）:

| 種 | 必要だったセル | 値の差 | 打ち方が同じ |
|---|---|---|---|
| 404（8 ノード） | 2,498 / 12,240 = **20%** | ≤ 4.4e-16 | 7 / 8 |
| 77（6 ノード） | 1,622 / 7,232 = **22%** | ≤ 1.1e-16 | 6 / 6 |

台は 1x1 〜 5x5、収束は 3〜10 ラウンド。**値は厳密に一致します。**

hp-share でも測ると 17% ですが、**打ち方が同じなのは 8 中 5** でした。
学習した評価関数のほうが値がばらけるので均衡が一意になりやすく、
実際に使う側のほうが条件が良い、という向きです。

### 端から端で 2 倍前後（見積もり）

ノードに紐づく仕事は 1 走行の約 70%（充填の解決 49.6%、符号化 8.6%、
torch 9.4%、パイプ 2.3%）。これが 5 分の 1 になるので:

```
0.30 + 0.70 × 0.20 ≒ 0.44  →  約 2.3 倍
```

LP は 48x48 を 1 回から 2x2〜5x5 を 3〜10 回に変わるので、**むしろ安くなります**。

### 代償: 同値の別の均衡を選ぶことがあります

値は厳密に同じですが、**均衡が複数あるとき、どれを選ぶかが変わりえます**
（14 ノード中 1 つ）。この計画は均衡から手を抽出するので、
**生成される対戦は変わります**。

これは「どちらが正しいか」ではありません。いま選んでいるのも HiGHS が返した
任意の 1 つです。ただし**これまで守ってきた「対戦が 1 バイトも変わらない」は
成り立たなくなります**。過去の生成と再現しなくなるので、これは移植の判断ではなく
そちらの判断です。

### 入れたもの と 実測

`src/pokeuraou/node_solver.py`、`search(..., solve_sparsely=True)`、
`tools/bench_generation.py --solve-sparsely`。既定はオフです。

```
生成（幅 48、--rank-leaf、cuda、6 ゲーム）
  行列を全部埋める   2.839 s/game   19〜21 games/min
  均衡だけ証明する   1.755 s/game   34〜40 games/min     1.6〜2.0 倍
  1 ゲームあたりの決定 14.5、ターン 12.0 — どちらも同じ
```

**5 倍にはなりません。** セルは 5 分の 1 でも、ラウンドごとに往復と順伝播を
払うので、19,000 葉を 1 バッチで流すほうが 700 葉 × 6 バッチより葉あたりは安い。
両側の質問を 1 往復にまとめて 1.8 → 2.0 倍にしたのが効いた分です。
開始を上位 1 手から上位 6 手に広げるのは効きませんでした（1.9〜2.2 倍、誤差）。

**ループは Python のままです。** ラウンドが必要とするのは LP と学習した葉で、
どちらも意図的に Python 側にあります——LP を Rust で書けば**均衡の実装が 2 つ**になり、
同値の別頂点を選んで乖離します。渡るのは葉で、それは学習葉を使う限り避けられません。

### 正しさ: 解かなかったセルについても確認済み

`tools/diff_solve_node.py` が、**全行列に対して** exploitability を測ります
（どちらかの側に、settle した値を上回る応手が残っていないか）:

```
8 ノード 幅 48    2,498/12,240 セル = 20%    3〜10 ラウンド
exploitability   ≤ 7.7e-08   ← 一度も解かなかったセルを含めてこれ
値の差           ≤ 4.0e-08
```

ブリッジの有無でも答えは同じです
（`tools/diff_generation.py --solve-sparsely`: 決定は全て一致、記録される探索値のみ 1.2e-07）。

### 代償は「どの均衡か」だけ、ただし再生より頻繁です

打ち方が変わったのは **8 ノード中 6**。`tools/cells_needed.py` の再生では 8 中 1 でした。
再生は**同じ行列**に両方式を当てていて、実装はラウンドごとに別バッチで採点します。
**同じ局面を 1 バッチ内で 2 回採点するとネットワークが 1 ULP（5.96e-08）違う値を返す**ので、
その塵がほぼ退化した LP を同値の別頂点に動かします。

つまり差の出どころは方式半分・float32 半分です。**どちらも正しい均衡**で、
値は 4e-8 以内。ただし**過去の生成とは再現しません。**

### 列生成のあと、時間は Python 側の「呼び出し回数」に移りました

3 ゲーム・幅 48・`--rank-leaf` で、往復の中身を分けて測ると:

| | 行列を全部埋める | 均衡だけ証明する |
|---|---|---|
| 往復の回数 | 315（8.3/ターン） | **560（14.7/ターン）** |
| 中で解決 | 45.7% | 22.5% |
| 中で符号化 | 10.1% | 3.5% |
| **往復そのもの** | 14.0%（3.94 ms/回） | 14.0%（**1.63 ms/回**） |
| 返ってきたバイト | 621 MB | 213 MB |

**局面の JSON は 0.1% でした** — 固定費の正体はそこではありません。
そして sparse では**時間の 60% が往復の外**にあります。内訳:

```
torch の順伝播   34.2%   221 回   ← 1 回 6 ms、ほぼ起動と転送の遅延
narrow           37.7%   116 回   ← 葉順位付けはまだ全セル埋めている
LP                6.6%   107 回
```

探索担当が測った **GPU 51.6 W / 使用率 76%** と同じ事実です。使用率は
「カーネルが 1 つ以上走っていた時間の割合」で、計算能力の消費ではありません。
**列生成はバッチを小さく多くするので、この壁を悪化させます**——
セルは 5 分の 1 になったのに速度が 2 倍止まりなのはこれです。

次に効くのは「1 回あたりを大きくして回数を減らす」方向で、候補は 2 つ:
葉順位付けの充填と解の第 1 ラウンドを 1 回にまとめる、
またはノード内でセルを跨いで葉の値をキャッシュする。どちらも未実装です。

**device の再測定が要ります。** sparse で cpu が cuda より速く出ましたが、
そのとき GPU では対戦が 8 ワーカー走っていました。**比が汚染されているので
結論にはできません**——空いているときに測り直してください。

### 列生成を入れると、device の選択が効かなくなります

前の節の「device の再測定が要ります」への答えです。空いている機械で、
4 構成を同じ波の中で回し、最初の波は捨てて最小を取りました。

1 プロセス（幅 48、`--rank-leaf`、value-all）:

| | 行列を全部埋める | 均衡だけ証明する |
|---|---|---|
| cuda | 1.303 s/game | **0.747 s/game** |
| cpu | 2.228 s/game | 0.898 s/game |
| cuda の優位 | **1.71 倍** | **1.20 倍** |

生成が実際に走らせる 8 ワーカーでは（3 波の最良、games/min）:

| | 行列を全部埋める | 均衡だけ証明する |
|---|---|---|
| cuda | 307.9 | 342.0 |
| cpu | 190.6 | **349.5** |
| cuda の優位 | **1.62 倍** | **なし**（cpu が 1.02 倍） |

**行列を埋める限り cuda が正しく、列生成を入れると引き分けになります。**
バッチが小さく多くなるほど GPU は起動遅延を隠せなくなる、という同じ話が
並列度の上でもう一度起きているだけです。単独で 1.20 倍だったものが、
8 プロセスが 1 枚のカードを奪い合うと消えます。

実務上の意味は「cuda をやめろ」ではなく **「sparse なら選べる」** です。
cpu 推論はワーカーあたり約 1.1 GB の VRAM を返すので、12 GB のカードが
生成のワーカー数を決めなくなります——ただし 8 ワーカーで既にスケーリングは
59〜61% なので、増やして買えるものは多くありません。空いた VRAM は
学習を同時に回すために使うほうが筋が良さそうです。

再現:

```
uv run python tools/bench_workers.py --workers 8,8,8 --games 4 --limit 48 \
    --rank-leaf --solve-sparsely --device cuda --value data/models/value-all.pt
```

### 並列のさせ方のほうに、まだ 2 つ残っています

**1 枚目: ワーカーごとに固定本数を配っている。** 実際の生成ログから
（完了時刻はファイルの mtime、開始は作成時刻）:

| run | ワーカー | 対局 | 所要 | 待ち時間 | 遊んだコア |
|---|---|---|---|---|---|
| gen2345/50 | 14 | 7,000 | 4.18h | 10.4m | 1.4% |
| gen6/60 | 12 | 7,008 | 0.53h | 8.7m | 16.4% |
| gen7/71 | 12 | 11,156 | 1.86h | 97.6m | 21.1% |

gen7 の 21.1% は 2 つの話が混ざっています。**seed7108 と 7112 は死んでいました**
——1,098 本のうち 126 本と 50 本しか書いていません。7112 のログに理由があります:

```
[rustnode] falling back to Python: the Rust node sent 0 of 64219920 bytes:
```

64 MB の返信が届かなかった。これは `RESTARTS_ALLOWED` を入れた版より前の挙動です。
この 2 つを除いた健全な 10 ワーカーでも、最初と最後の完了差は 28.4 分、
**遊んだコアは 10.5%** あります。固定分割で 1,098 本ずつ配れば、
1 本あたり 8 倍のばらつきは平均化されずに端に溜まります。

共有キューにすれば両方が直ります。遅いワーカーは少なく引き、
**死んだワーカーの残りは他が引き取る**ので、gen7 で失われた約 2,100 本は出ません。

**2 枚目: GPU の 1 回あたりの費用が、行数にほぼ依存しない。**
`from_encoded` を行数を変えて測ると:

| 行数 | cuda ms/call | cpu ms/call |
|---|---|---|
| 8 | 1.50 | 0.78 |
| 64 | 2.21 | 2.45 |
| 256 | 2.12 | 7.97 |
| 1024 | 2.20 | 28.4 |
| 2048 | 2.12 | 60.1 |

**cuda は 8 行でも 2,048 行でも 2.1 ms です。** 2,048 行まで全部が固定費で、
行あたりの計算は見えません。cpu は逆に 29〜32 us/行 の実計算です。

これで今までの測定が全部つながります。1 プロセスなら cuda が速いのは
2.1 ms が cpu の 8 ms に勝つから。8 ワーカーで互角になるのは、
**その 2.1 ms が CPU 側の起動費用で、8 プロセスが 8 コアで別々に払う**から。
探索担当の GPU 51.6 W も同じ——カードは待っているだけです。

推論を 1 プロセスに集めて 8 ワーカー分を 1 回のバッチにすると:

| 各 n 行 | 別々に 8 回 | まとめて 1 回 | 削れる |
|---|---|---|---|
| 64 | 17.64 ms | 2.21 ms | 87% |
| 256 | 16.95 ms | 2.12 ms | 87% |
| 512 | 17.68 ms | 3.59 ms | 80% |

torch は sparse なプロセスの 34.2% なので、その 87% は**プロセスの約 30%**、
**1.4 倍**にあたります。ただし配管そのものの費用は別で、
そして 64 MB のパイプが 1 本死んでいる前科があるので、共有メモリで渡すべきです。

配管なしで同じ方向に効く手も 2 つあります（どちらも未実装）:
葉の順位付けの充填と解の第 1 ラウンドを 1 回にまとめる、
ノード内でセルを跨いで葉の値をキャッシュする。**呼び出し回数そのものを減らします。**

### キューは 1.21 倍で、待ちは 43% から 10% になりました

240 局・8 ワーカー・幅 48・cuda を、固定分割とキューで交互に 3 回:

| | 所要 | 完了差 | 遊んだコア |
|---|---|---|---|
| 固定分割 | 429.3s / 415.6s | 329s / 306s | **44.1% / 43.1%** |
| キュー | 375.4s / 343.0s | 59s / 47s | **11.4% / 9.8%** |

**1.21 倍**（415.6 → 343.0）。ただし 1 ワーカー 30 局という小さい配り方なので、
実運用の 1,000 局よりかなり誇張されます——**実ログの 10.5〜16.4% のほうが実勢値**です。

3 回目の固定分割は測れませんでした。**ワーカーが 1 つ、1 局も書かずに死んだ**からです
（240 局のうち 210 局）。この節が存在する理由そのものが、測っている最中に起きました。

### 葉順位付けの費用は、記録の 1.6% ではなく 1 決定あたり 9〜15% でした

`TODO.md` は「幅 48 ではほぼタダ（0.245 → 0.249 s/turn）」と書いています。測り直すと
違います（`tools/bench_generation.py`、6 局、同一シード、cuda、value-all）:

| | s/game | 決定/game | **s/決定** |
|---|---|---|---|
| 葉順位 on・行列を埋める | 1.857 | 13.3 | 0.1396 |
| 葉順位 off・行列を埋める | 1.567 | 12.2 | 0.1284 |
| 葉順位 on・sparse | 1.352 | 13.3 | 0.1017 |
| 葉順位 off・sparse | 1.077 | 12.2 | 0.0883 |

**単位が効きます。** 葉順位を付けると**対局が 9% 長くなる**（13.3 対 12.2 決定）ので、
1 局あたりで見ると費用が水増しされます:

```
  行列を埋める : 1局あたり +18.5%   1決定あたり  +8.7%
  sparse      : 1局あたり +25.5%   1決定あたり +15.2%
```

`narrow` の中身を計ると、**どちらの基準でも払うダメージ採点は 1.4〜3.3%**、
**葉順位そのものが 19.1%（full）／24.4%（sparse）** です。`_bridged_scores` は移植済みで
安く、高いのは葉順位が `pool × references` セルを実際に解いているほうでした。

sparse の取り分は 1 決定あたり **1.37 倍（葉順位あり）／1.45 倍（なし）**——
**葉順位はほとんど頭打ちの原因になっていません。** 探索担当の 8 ワーカーでの 1.14 倍とは、
コア律速で圧縮された分だけ差があります。

この節は 3 回書き直しました。1 回目は `narrow` の 37.7% を葉順位固有と読み、
2 回目はコードだけを見て「どちらでも払っている」と訂正し、どちらも部分的に誤りでした。
**位相の名前も、コードの形も、費用の測定ではありません。**

### 共有推論プロセスは、sparse のときだけ価値があります

「1 回あたりを大きくして回数を減らす」を実際に設計する前に、**誰が何回呼んでいるか**を
数えました（4 局、幅 48、cuda、`--rank-leaf`）:

| | torch 呼び出し/決定 | バッチ中央値 | torch の割合 |
|---|---|---|---|
| 行列を全部埋める | **1.00**（+ 順位付け 2.00） | 1,819〜2,306 | **7.7%** |
| 均衡だけ証明する | **6.07**（+ 順位付け 2.00） | 33〜54 | **33.9%** |

**呼び出し回数の問題は、列生成が作っています。** 行列を埋めるなら 1 決定に 1 回、
2,000 行のバッチで、torch は 7.7% しかありません。

そして**行列を埋める側では、ワーカーを跨いだまとめ売りに意味がありません**。
すでに 2,300 行あるものを 8 つ束ねると 18,400 行で、2,048 行の平坦域を抜けています——
`8 × t(2306) ≈ 17.6 ms` に対して `t(18448) ≈ 16 ms`。ほぼ何も減りません。

```
  行列を埋める + 葉順位 : torch 7.7%  → まとめても約 1.0 倍
  sparse + 葉順位      : torch 33.9% → 87% 回収できれば約 1.41 倍
```

**`SOLVE_SPARSELY=0` が既定である限り、共有推論プロセスを書く理由はありません。**
逆に sparse を戻すなら、これが sparse の残りの費用をそのまま叩きます——
1 プロセスで 1.37 倍、8 ワーカーで 1.14 倍に潰れているぶんが、ここです。

### 制限ゲームを大きく始めても、仕事は減りません

ラウンドは 1 回ずつが往復と順伝播なので、`solve_node` の開始点を 1×1 から広げれば
ラウンドが減って安くなるはず——と思って測りました:

| seeded | s/game | ラウンド/ノード | 解いたセル | 行列の |
|---|---|---|---|---|
| 1 | 1.118 | 4.34 | 210 | 16.2% |
| 2 | 1.228 | 3.73 | 218 | 16.8% |
| 3 | 1.182 | 3.44 | 218 | 16.8% |
| 4 | 1.167 | 3.15 | 213 | 16.4% |
| 6 | 1.120 | 2.78 | 222 | 17.1% |

**ラウンドは 36% 減り、解いたセルは動きません。** 時間も動きません（波ごとのばらつき
11% のほうが設定間の差より大きい）。費用はラウンドの回数ではなく**最良応答の走査**
——全行 × 生きている列、全列 × 生きている行——にあり、ラウンドが減れば 1 回あたりの
走査が広がるだけでした。`seeded` は据え置きます。

### 順位を良くすると幅が半分になり、幅は二乗で効きます

ここまでの改善はどれも数％から 1.4 倍でした。**幅だけは `limit**2`** です。
幅 48 を使っているのは `narrow` の順位が当てにならないからで、
**順位が良くなれば幅を下げられる**——これは誰も測っていませんでした。

記録局面 200 で、幅 W に狭める代償を測りました（`tools/width_vs_ranking.py`）。
狭めた側は自分の均衡を打ち、**幅 48 側はメニュー全体から最良応答**で返します
（現実の相手はこちらのメニューに留まる義務がないので）:

| 幅 | ダメージ順の代償 | **葉順位の代償** | ダメージ順の落ちた重み | 葉順位の落ちた重み |
|---|---|---|---|---|
| 8 | 0.0473 | 0.0291 | 0.519 | 0.365 |
| 12 | 0.0340 | 0.0194 | 0.358 | 0.194 |
| 16 | 0.0249 | **0.0127** | 0.282 | 0.123 |
| 24 | **0.0141** | 0.0069 | 0.174 | 0.064 |
| 32 | 0.0088 | 0.0046 | 0.104 | 0.040 |

**葉順位はどの幅でもダメージ順のちょうど半分の代償です。** そして幅を跨いで読むと:

```
  葉順位の幅 16（0.0127） < ダメージ順の幅 24（0.0141）
  葉順位の幅 12（0.0194） < ダメージ順の幅 16（0.0249）
  葉順位の幅 24（0.0069） < ダメージ順の幅 32（0.0088）
```

**同じ代償なら幅が 1.5 倍下げられ、行列はその二乗で安くなります**（16/24 なら 0.44 倍）。
`--rank-leaf` の費用が 1 決定あたり 8.7% であることを思い出すと、
**8.7% 払って行列を半分以下にする**取引になります。これは今まで見たどの取引より良い。

ただし、ならして良くなっただけで**裾は直っていません**。葉順位の最悪値は
**幅 8 から 32 まで 0.3476 で動きません**——同じ 1 局面が、どの幅でも同じだけ損をして
います。その局面では決定的な手が葉順位でも 33 位以下にあり、**幅を広げても順位の失敗は
直らず、費用だけが二乗で増えます。** 幅ではなく順位を直すべきだ、という主張の一番強い形が
これだと思います。

**まだ測っていないのは端から端までの速度**です。行列は `limit**2` でも、
`narrow` の採点と葉順位付けは pool に比例して幅に依存しないので、
幅を半分にしても全体が 4 分の 1 になるわけではありません。空いた機械で測ります。

そして最終的な判定は Elo です。ここで測った代償は**相手が幅 48 を持っている**前提の
最良応答差で、生成では両側とも同じ幅なので実際の損はこれより小さくなります。

### 幅を下げるのは 2 倍。ただし「順位で幅を買う」取引は速度的には引き分けです

幅の速度は**対局では測れません**。幅がメニューを変え、メニューが手を変え、手が対局を
変えるので、幅ごとに違う局面集合を測ることになります。1 局の費用は 8 倍ばらつくので、
6 局の違いは測りたいものを飲み込みます——実際 1 決定あたりに正規化しても
**幅 24 が幅 48 より遅い**という答えが 3 波とも再現しました。決定そのものが違うからです。

なので局面を固定しました。記録局面 60 を、各幅・各順位で検索します（ms/検索）:

| 幅 | 葉順位 | ダメージ順 | 差 |
|---|---|---|---|
| 12 | 29.04 | 12.81 | 16.2 |
| 16 | 33.05 | 18.03 | 15.0 |
| 24 | 44.01 | 30.82 | 13.2 |
| 32 | 57.06 | 46.31 | 10.8 |
| 48 | 89.16 | 76.31 | 12.9 |

**葉順位の費用は幅によらず 11〜16 ms でほぼ一定**です。pool に比例して幅に依存しない、
という読みがそのまま出ています。だから幅が小さいほど**割合としては重くなり**——
幅 48 で +16.8%、幅 24 で +42.8%、幅 16 で +83% です。

結果、**「順位を良くして幅を下げる」は速度的には引き分け**になります:

```
  葉順位の幅16（33.05 ms）対 ダメージ順の幅24（30.82 ms）   0.93倍（やや遅い）
  葉順位の幅24（44.01 ms）対 ダメージ順の幅32（46.31 ms）   1.05倍（ほぼ同じ）
```

勝率では葉順位のほうが安いので**取引としては損ではありません**が、
**二乗の得は順位付けの固定費に消えます。** 前節でここを「8.7% 払って行列を半分」と
書いたのは誤りでした——8.7% は 1 局あたりの数字で、1 検索あたりでは幅 24 で 42.8% です。

**本当の取り分は、幅そのものを下げることのほうでした:**

```
  幅48 葉順位 → 幅24 葉順位   2.03倍   代償 0.0069
  幅48 葉順位 → 幅16 葉順位   2.70倍   代償 0.0127
```

### 幅を下げるなら、sparse は切ってください

同じ表から:

| 幅 | 葉順位・行列を埋める | 葉順位・sparse |
|---|---|---|
| 16 | 33.05 | 43.87 |
| 24 | 44.01 | 48.86 |
| 32 | 57.06 | 52.88 |
| 48 | 89.16 | **60.12** |

**sparse は幅 48 では 1.48 倍ですが、幅 24 と 16 では逆に遅くなります。**
ラウンドと小さいバッチの固定費が、小さい行列では償却できないからです。
**幅を下げることと列生成は代替であって、足し合わせるものではありません**——
そして幅を下げるほうが大きい（2.03 倍 対 1.48 倍）。

### 選出 book は決定を重くしません。重いのはチームの引きです

探索担当から「book 選出の局面は 1 決定あたり 4.4 倍重い」（40 戦ずつ、11.00 対
2.51 s/game、試合の長さは同じ）という測定が来ました。**再現せず、逆向きに出ます。**

同じ比較を 8 戦ずつ、同一シード・同一モデルで回すと **book 1.85 / 一様 21.68 s/game**
——11.7 倍の逆向きです。決定数は両方 111 でしたが、先発 6 匹は 0/8 一致でした。

**局面を固定すると差が消えます。** gen-8（book）と gen-7（一様）の記録局面 60 ずつを、
同じ幅・同じ葉で検索:

| | ms/検索 | 合法手ペア | 葉/検索 |
|---|---|---|---|
| 一様 | 139.36 | 42.4 | 2,767 |
| book | 143.29 | **36.0** | **1,877** |

**1.03 倍。しかも book の局面は合法手ペアも葉も少ない**——構造的に軽いほうです。

100 戦ずつ × 4 シードで 1 決定あたりを測ると、なぜ 40 戦で答えが出ないかが分かります
（比なので対数で扱います）:

```
  book     141, 641, 211, 242 ms/決定   設定内のばらつき 4.5倍
  uniform  954, 228, 488, 228 ms/決定   設定内のばらつき 4.2倍

  book / uniform = 0.66倍   95% CI [0.15, 2.96]
    1.00倍 は区間の中 / 4.40倍 は区間の外
```

**設定内のばらつきが、設定間の差（1.51 倍）より大きい。**
変動しているものが、変えているものではないときの見た目です。

原因はチームです。1 局の費用は 8 倍ばらつき、book は相手の 6 匹を**解いたクラス**から、
一様は**大会フィールド**から引くので、**両者が同じチームを見ることは原理的にありません。**
40 戦はそれを見通すには足りませんでした。

**「試合の長さが同じだから、残るのは局面が重いという事実」は閉じない消去法です。**
同一シードだと乱数列の消費パターンが揃うので長さは揃いやすく、チームは揃っていません。
こちらの 8 戦でも決定数はぴったり 111 で一致し、先発は 0/8 一致でした。

### 幅は中盤の梃子です。再開生成には効きません

探索担当が再開生成（記録局面から決着まで、0.18 s/game）を入れたので、
**このファイルの結論が終盤でも成り立つか**を測りました。ここまでの測定は全部
`load_positions` の既定であるターン 3 以降、つまり中盤の局面です。

まず局面の形が違います:

| 標本 | 生存 | 合法手ペア |
|---|---|---|
| 中盤（ターン3以降） | 5.58 | **43.2** |
| 終盤（ターン10以降） | 3.50 | **16.9** |

**終盤の合法手ペアは 16.9**——つまり**プールが幅より小さい**。`narrow` は無いものを
返せないので、幅 48 も幅 24 も同じメニューを返します。

ms/検索（50 局面、葉順位、同一モデル）:

| 標本 | 幅 | 行列を埋める | sparse |
|---|---|---|---|
| 中盤 | 16 | 39.52 | 59.79 |
| 中盤 | 24 | 56.13 | 68.41 |
| 中盤 | 48 | 109.41 | 86.06 |
| 終盤 | 16 | 26.88 | 34.33 |
| 終盤 | 24 | 29.08 | 29.52 |
| 終盤 | 48 | **35.55** | 30.38 |

梃子の効き方:

```
  中盤   幅48→24  1.95倍    幅48→16  2.77倍    sparse@48  1.27倍   sparse@24  0.82倍
  終盤   幅48→24  1.22倍    幅48→16  1.32倍    sparse@48  1.17倍   sparse@24  0.99倍
```

**幅を下げる 2 倍は中盤の話で、終盤では 1.22 倍しかありません。**
プールが幅を下回っているので、下げる幅が残っていないからです。

逆に言えば、**再開生成は幅の設定に関係なく速い**（終盤 35.55 ms 対 中盤 109.41 ms、
3.1 倍）。そちらの 0.18 s/game はこれです。**幅を調整する価値はそこにはありません。**

葉の数だけは逆を向きます。中盤の幅 48 は 2,824 葉 / 2,304 セル = 1.23 葉/セル、
終盤は 621 葉 / 約 289 セル = 2.15 葉/セル。**終盤のセルはよく枝分かれします**
（KO 境界の振れが多い）——ただしセルの数が桁で少ないので、合計では軽いままです。

### 均衡は 2.5 手しか打ちません。幅 48 はすべて順位付けの穴埋めです

裾が幅では直らないという話（葉順位の最悪値が幅 8〜32 で動かない）の先を測りました。
**順位が完璧だったら幅はいくつで足りるのか。** 完璧な順位は「均衡の重みそのもので並べる」
——事前には知りようがない（知ることは解くこと）ので、これは**どんな順位付けでも
超えられない天井**です。`tools/policy_ceiling.py`、記録局面 150（両側で 300 標本）:

```
  幅48 の均衡が実際に打つ手の数   平均 2.5   中央値 2   p90 4   最大 6      （48 のうち）
```

**2.5 手です。** 2,304 セルを解いて、2.5 手の台を見つけています。

| 幅 | 完璧な順位 | p90 | 最悪 | 葉順位 | p90 | 最悪 |
|---|---|---|---|---|---|---|
| 2 | 0.0221 | 0.0716 | 0.374 | 0.0571 | 0.1823 | 0.4993 |
| 4 | 0.0010 | 0.0000 | 0.078 | 0.0455 | 0.1287 | 0.7685 |
| **6** | **0.0001** | **0.0000** | 0.017 | 0.0389 | 0.1204 | 0.7685 |
| 8 | 0.0001 | 0.0000 | 0.017 | 0.0279 | 0.0975 | 0.4993 |
| 16 | 0.0001 | 0.0000 | 0.017 | 0.0127 | 0.0451 | 0.2100 |
| 24 | 0.0001 | 0.0000 | 0.017 | 0.0083 | 0.0271 | 0.1797 |

**完璧な順位なら幅 6 でタダです**（0.0001、p90 はちょうど 0）。
葉順位が幅 48 でようやく届くところに、幅 6 で届きます。行列は 2,304 対 36 セル、**64 分の 1**。

つまり **`limit` は精度の設定ではなく、順位付けの誤りに対する保険料**でした。
ここまで「幅 48 → 24 で 2 倍」と測ってきたものは、保険を半分にしただけで、
**保険そのものを要らなくする道がこの表です。**

いくつか但し書きがあります。

- **完璧な順位は手に入りません。** 学習した方策がどこまで近づけるかは未知で、
  この表はその上限でしかありません。
- **幅 48 はそもそもあまり narrow していません。** 中盤の合法手ペアは平均 43.2
  （p90 70）なので、平均的な局面では**幅 48 = 全合法手**です。だから「48 のうち上位 6」は
  「全体のうち上位 6」とほぼ同義で、方策が解く問題はこの表が示すとおりのものです。
- **完璧でも裾は 0 になりません**（最悪 0.017）。ただし葉順位の 0.7685 とは桁が違います。

列生成（sparse）が同じ事実の別の使い方であることも、ここで繋がります。台が 2.5 手なら
セルの 5 分の 1 で証明できる——測ったとおりです。ただし証明には**全行 × 生きている列**を
走査する必要があり、そこが 1.37 倍で頭打ちになる理由でした。
**順位が当たれば走査そのものが要りません。**

### 安い特徴では葉順位に届きません。届かせるものが何かは分かりました

天井（幅 6 でタダ）に向けて、記録済みの均衡から順位付けを学習しました。
**新しい自己対戦は要りません**——記録された各決定が `ownActions` と `ownPolicy`
（均衡混合）を持っているので、gen-7 だけで 85,228 決定あります。

`tools/policy_dataset.py` で 3,000 局から 57,741 決定・203 万行を取り出し、
`tools/policy_train.py` で学習しました。特徴は 38 個——手の形（移動か交代か、
技スロット、対象、メガ、両スロットが同じ相手を狙っているか）、局面の要約（生存数、
HP、ターン）、そして**ダメージ採点**（`narrow` がどちらの順位でも計算するので無料）。

保留した 11,549 メニューで、均衡の重みが上位いくつに入るか:

| 上位 | 無作為 | ダメージ順 | **学習** | 葉順位 |
|---|---|---|---|---|
| 1 | 5.9% | 15.4% | 21.1% | **38.6%** |
| 4 | 22.8% | 40.1% | 45.2% | **66.1%** |
| **6** | 30.4% | 47.9% | **53.5%** | **73.9%** |
| 8 | 35.6% | 55.2% | 60.2% | **79.6%** |
| 16 | 53.3% | 70.5% | 77.3% | **90.7%** |

**学習はダメージ順を 5.6 ポイント上回り、葉順位に 20.4 ポイント負けました。**
与えた唯一の局面依存の信号（ダメージ採点）よりは良いので、何かは学んでいます。
ただし**葉順位の優位は「次に何が起きるか」を実際に評価していること**から来ていて、
手の形と要約統計はそれを再現しません。

**これは方向が否定されたのではなく、位置が特定されたということです。**
安い特徴が足りないなら、必要なのは**エンコーダの配列そのもの**——価値関数が既に
使っている表現に方策の頭を足す——であって、手作りの要約ではありません。

費用の見積もりもはっきりしています:

```
  葉順位          11〜16 ms/検索   pool × references を実際に解く
  方策の頭         約 2 ms         プール 43 行の順伝播 1 回（曲線より）
```

**葉順位と同等に並べられる方策は、それ自体が 6 倍安く、さらに幅を下げられます。**
幅 6 相当まで届けば行列は 64 分の 1、幅 16 相当でも葉順位の幅 48 より良い。

現状の到達点（学習 53.5% 対 葉順位 73.9%、上位 6）は、幅に直すと
**葉順位の幅 12〜16 相当**です。まだ足りません。

### 手の同一性を与えると、方策は葉順位を上回ります

前節の 38 特徴は「技スロット 2 番」しか知らず、**それはポケモンが変われば意味を持ちません**。
そこで**同一性**を足しました——誰が動くか、どの技か、何に交代するか、誰を狙うか。
`Encoder` の語彙（種 357、技 514）をそのまま索引に使い、埋め込みます。

6,000 局から 115,687 決定・407 万行。保留メニュー 23,138 で、均衡の重みが上位に入る割合:

| 上位 | 同一性なし | **同一性あり** | 葉順位 |
|---|---|---|---|
| 6 | 53.5% | **65.7%** | 73.9% |
| 16 | 77.3% | **87.7%** | 90.6% |
| 24 | 87.2% | **94.5%** | 95.3% |

差は 20.4 → 8.3 ポイントに縮みました。**ただしこの指標は代理です。**
本当に知りたいのは「狭めたときの代償」なので、天井測定に方策を差しました。

**gen-8（学習に使っていない生成）の記録局面 150 で:**

| 幅 | 完璧 | 葉順位 | **学習** |
|---|---|---|---|
| 4 | 0.0014 | 0.0524 | 0.0545 |
| 6 | 0.0004 | 0.0439 | **0.0371** |
| 8 | 0.0012 | 0.0336 | **0.0301** |
| 12 | 0.0003 | 0.0210 | **0.0160** |
| 16 | 0.0004 | 0.0176 | **0.0114** |
| 24 | 0.0001 | 0.0091 | **0.0037** |

**幅 6 以上のすべてで葉順位に勝っています**（幅 24 では 2.5 倍良い）。
上位 k の重みでは負けていたのに代償では勝つ、というのは矛盾ではありません——
台を外しても**良い代替**が入っていれば、最良応答に対する損は小さいからです。
**代償のほうが本来の指標**です。

### 共有推論プロセスを作るなら、バッチの大きさを固定してください

推論を 1 プロセスに集めるという依頼が来ました。根拠はメモリで、そちらが測っています——
対戦ワーカー 1 つが commit 4.0 GB・VRAM 1.5 GB（葉を 2 つ持つため）で、
**8 本が 31.1 GB / 12.2 GB の機械に入りません。**

集約は**バッチを詰める**ことで成り立ちます。そして依頼の制約 1 が
「同じ局面には同じ答えを返すこと」（アンサンブルの logit 平均が 1.9e-06 違うと均衡が動く）。
**その 2 つが両立するかを先に測りました。**

同じ 1 行を、いろいろな入れ方で通します:

| | cuda | cpu |
|---|---|---|
| 同じ行をひとつのバッチに 2 回 | 一致 | 一致 |
| 単独 対 8 行のバッチ | **5.96e-08** | 一致 |
| 単独 対 64 行 | **8.94e-08** | 一致 |
| 単独 対 2048 行 | **5.96e-08** | 一致 |
| 同じ大きさ・違う中身 | 一致 | 一致 |

**cuda の答えはバッチの「大きさ」で変わり、「中身」でも「位置」でも変わりません。
cpu はどれでも厳密に一致します。**

つまり**バッチを可変長で詰める cuda サーバは、構成上その制約を満たせません。**
ワーカーの組み合わせ次第でバッチ長が毎回変わるからです。

**ただし「大きさだけ」なら、固定すれば直ります。** 2048 に固定して、
中身を 4 通り変えて同じ 1 行を読み戻すと**差は 0**。そして曲線どおり、
固定の費用はほとんどありません（**符号化済み配列**に対する順伝播のみ）:

| 実際の行数 | そのまま | 2048 に詰める | |
|---|---|---|---|
| 34 | 2.577 ms | 2.912 ms | 1.13倍 |
| 446 | 2.837 ms | 3.204 ms | 1.13倍 |
| 1024 | 3.381 ms | 3.255 ms | 0.96倍 |

**1.13 倍**です。torch は行列を埋める生成プロセスの 7.7% なので、**全体では約 1%。**

（最初この費用を 4.7 倍と測りました。`evaluate(positions)` を使ったせいで、
**詰めた 1,602 局面を Python で符号化していた**からです。サーバが受け取るのは
Rust が符号化済みの配列なので、詰めるのはテンソルであって局面ではありません。
このファイルで 5 回目の同じ間違いです——**測っているものが動いているものと同じか。**）

### ただし、速度のためにやる話ではありません

torch は**行列を埋める生成ワーカーの 7.7%**（幅 48、葉順位、葉 1 つ、実測）。
対戦ワーカーは葉を 2 つ持つので倍としても 15% 程度で、**集約で取れる上限はそこまで**です。

**やる理由はメモリで、そこは確定しています。** 速度は副産物と考えてください。

### 推論サーバ: 葉を 1 プロセスに集め、ワーカーからは torch ごと消しました

`src/pokeuraou/inference.py`、`tools/inference_server.py`、`--inference`。

**まとめません。** 探索担当の判断で、サーバはワーカーを跨いでバッチを合流させません。
合流させると「バッチの大きさが誰と一緒になったかで変わる」ので制約（同じ局面に同じ答え）
が壊れ、固定長で直せるものの見返りは torch の 7.7% の一部——**メモリの利得は合流と無関係**
だからです。要求は届いた行数のまま流れ、**答えは今日と 1 ビットも変わりません。**

そのぶん検査が「だいたい同じ」ではなく**同一**にできます:

```
  同じ種・同じ設定で 6 局、サーバ経由と直結
    決定列が完全一致   6/6
    所要               直結 15.6s   サーバ経由 13.2s（0.84倍）
```

**サーバ経由のほうが速い**のは、ワーカーが torch の import と CUDA コンテキスト作成を
払わなくなるからです。

### ワーカーの重さ（自プロセスの `PrivateUsage`、実測）

| | 直結 | サーバ経由 |
|---|---|---|
| bare python | 7 MB | 7 MB |
| + numpy | 523 | 523 |
| + レギュレーション・prior・standings・roster | 541 | 541 |
| + エンコーダ | 542 | 542 |
| + import torch | **1,410** | — |
| + モデル読み込み | 1,447 | — |
| + cuda へ移す（コンテキスト） | **1,741** | — |

**サーバ経由のワーカーは 542 MB で止まり、torch を import しません**（検査で確認）。
探索担当の見積もり 0.55 GB とほぼ一致しました。直結はここから探索を始めると
torch のアリーナがさらに乗り、対戦ワーカーは葉を 2 つ持つので実測 4.0 GB です。

### 運び方

**符号化済み配列は共有メモリ、制御行だけソケット。** 生成は毎秒約 900 MB の葉を運ぶので
ソケットに載せる量ではなく、この計画にはパイプを 1 本 64 MB で失った前科があります。
ワーカーごとに 1 つ共有バッファを作り、サーバはそれを覗いて結果を同じバッファに書きます。

バッファに入らないバッチは**分割せず拒否**します。分割はバッチの大きさを変え、
**cuda の答えはバッチの大きさで変わる**からです。

**接続が切れたら、そのワーカーのバッファを閉じて次へ進みます。**
キューの `release()` と同じ性質で、ワーカーの死がサーバを道連れにしません。

### サーバの二つのバグは、どちらも「アンサンブルのときだけ」出ました

探索担当が見つけました。両方ともこちらの落ち度で、**単体ネットの検査では踏めない**種類です。

**1 本目: 平均の経路を二本にしていました。**

```python
  BatchedValue._mean_logit   stack_module_state + vmap → .mean(0)
  inference.ensemble_model   torch.stack([net(batch) for net in nets]).mean(0)
```

同じ量に二つの経路があり、**4e-08 違い**ました。メニューも台も引いた行動も一致して、
混合だけがずれます。**`value.py` のコメントが、まさにこれを測って
「速い経路と参照経路の二本は持たない」と書いてあります。** 読んでいませんでした。

直し方は「慎重に複製し直す」ではありません——最初の版も慎重で（同じチャンク境界 8192、
同じ sigmoid、同じ dtype）、それでも違ったので。**`BatchedValue.from_encoded` に委譲**して、
構成上同じものにします。

**2 本目: `functional_call` はスレッド安全ではありません。** モジュールのパラメータを
その場で差し替えるので、同じ base に二スレッドが入ると負けたほうが meta を見ます。
サーバは接続ごとにスレッドを立てるので、これは常に起きます。

### ロックは外せますが、外す価値がありません

聞かれたので測りました。446 行 × 2 本アンサンブル、calls/s:

| スレッド | 共有 base + ロック | スレッドごとの base、ロック無し | 共有 base、ロック無し |
|---|---|---|---|
| 1 | 381.2 | 383.7 | 400.1 |
| 4 | 412.8 | **418.5** | **失敗** |
| 10 | 403.2 | **419.4** | 466.7（たまたま通った） |

**外せます。** スレッドごとに base と vmap を持てば、答えは同一で落ちません。
ただし `copy.deepcopy(template)` ではだめで、**`functional_call` が一度でも触った base は
BatchedTensor を抱えている**ので、実モジュールから `.to("meta")` で作り直す必要があります。

**そして外す価値がありません。** 10 スレッドで 419 対 403、**4%**。
torch はワーカーの 7.7% なので**全体で 0.3%** です。

**もっと大事なのは、スレッド数でスループットが動かないこと**です——1 スレッドで 381、
10 スレッドで 403〜419。**カードは 1 スレッドで飽和しています。**
スレッドが買っていたのはソケットとコピーの重なりであって、前向き計算の重なりではない、
という探索担当の読みが実測で確認されました。**サーバが単一の供給口に見えるのは
ロックのせいではありません。**

もう一つロックを残す理由があります。**ロック無しで落ちると共有 base が壊れたまま残ります**
（BatchedTensor を抱えた状態）。以後そのアームは誰に対しても壊れます。
ロックはこれも防ぎます。

### 検査の穴は「交差」でした

探索担当の指摘がそのまま教訓です:

```
  並行の検査        あった。ただし単体ネット   → functional_call に到達しない
  アンサンブルの検査  あった。ただし単一呼び出し → 二スレッドが中に入らない
  本番              その両方
```

**どちらの軸も覆われていて、交差だけが空いていました。**

### ロックの 0.3% は、測った領域が違いました

11 通目で「ロックを外しても 4%、全体で 0.3%」と書きましたが、**本番では律速でした。**
探索担当が待ち時間と保持時間を分けて測ると:

```
   6 ワーカー    7.44 ms 待ち,  5.63 ms 保持
  14 ワーカー   32.04 ms 待ち,  6.36 ms 保持     保持は動かず、待ちが 4.3 倍
```

**飽和したロックであって、遅いロックではありません。** そして本数を増やすと悪化する
（91.0 → 64.2 → 63.5 → 59.7 局/分）の正体がこれでした。外して 14 ワーカーで 1.63 倍。

**こちらの測定は 446 行**で取っていました。**本番の平均は 2,104 行**です。
446 行ならロックは空いていて、測っていたのは**能力**でした。
そして `calls/s` は飽和しても頭打ちの値を返すだけなので、**待ちと保持を分けないと
飽和は見えません。** 中央値（446）で測って平均（2,104）の挙動を語ったのが誤りで、
この分布は歪んでいる——**呼び出しの 18.3% が行の 74.8% を運ぶ**——と自分で測っていました。

### ワイヤの int64 化は要りませんでした。**拡幅そのものが不要です**

`rustnode` が到着時に 4 配列を int32 → int64 に広げていたので、
「ワイヤで int64 を出せば拡幅が消える」という依頼でした。測ると第三の道がありました:

```
  nn.Embedding は int32 を受け取り、答えは完全に一致    索引参照に算術がないので当然
```

**どこでも広げる必要がありません。** ワイヤは狭いまま、到着時の再構築も消えます。

そして依頼の周辺を測ったら、**もっと大きいものがこちらのコードにありました**
（2,104 行、本番の平均）:

| | ms/呼び出し |
|---|---|
| 4 配列の拡幅 int32 → int64 | 0.058 |
| **共有メモリへ `tobytes()` 経由（コピー 2 回）** | **1.028** |
| 共有メモリへ view 経由（コピー 1 回） | 0.196 |
| （比較用）順伝播そのもの | 2.651 |

**`RemoteValue` が `tobytes()` で配列をもう一度作り、その代入でもう一度コピー**していました。
view を張れば 1 回で済み、**0.83 ms/呼び出し**——拡幅の 14 倍です。
順伝播の 31% にあたる量を、運ぶためだけに使っていました。

両方直して、**同じ種の 6 局で決定列は完全一致**のままです（2 回確認）。

### 「分割しない」も間違いでした

`RemoteValue` がバッファを超えるバッチを「分割すると CUDA の答えが変わる」として
拒否していましたが、**`BatchedValue.from_encoded` は最初から 8192 ごとに分割しています。**
直結経路は 100 万葉のノードを 128 個に切って黙って評価していました。
**拒否は何の答えも守らず、1 チャンクを超えるバッチを禁じていただけ**です。
正しい不変量は「分割しない」ではなく「**`BatchedValue` と同じ境界で分割する**」でした。

### サーバが無言で死んだ原因は、こちらが 100 万局面を一度に符号化していたことでした

伸びの調査を回したら、**サーバがログに 1 行も残さず死に**、ワーカーからは接続が切れた
だけに見えました。落ちた場所は `_do_self_switch_node`——**自己交代ノードの 1,048,576 葉**です。

`BatchedValue.__call__` は**符号化の前に分割**します:

```python
  for start in range(0, len(positions), self.batch_size):
      chunk = positions[start : start + self.batch_size]
      encoded = self.encoder.encode_positions(chunk)     # 一度に 8,192 行まで
```

`RemoteValue.__call__` は**全部を先に符号化**していました。100 万局面なら約 3.9 GB を
一度に作ることになり、直結経路が 30 MB ずつ作るところを一息に要求します。
**機械が尽きて、巻き添えでサーバが死にました。** サーバが間違っていたのではありません。

`BatchedValue` と同じ場所で分割するように直したら、**バッファを 128 MB から 64 MB に
減らしたうえで** 120,000 行まで通ります:

```
    1,000 行  ok      8,192 行  ok      20,000 行  ok
   40,000 行  ok    120,000 行  ok      （バッファ 67 MB）
```

**不変量は「分割しない」ではなく「`BatchedValue` と同じ境界で分割する」でした。**
1 チャンクが 8,192 行 ≒ 30 MB なので 64 MB で足り、14 ワーカーで 0.9 GB 浮きます。

### 伸びは Python の中にありません

`tools/worker_growth.py`（探索担当作）を 50 局、サーバ経由で:

```
   局   working set   commit   tracemalloc   gc オブジェクト
    1      185 MB    1102 MB       0 MB        58,285
   50      236 MB    1154 MB       0 MB        58,284
```

**約 1.0 MB/局で育つ**（そちらの 0.9 MB/局と一致）、**しかし tracemalloc も gc の数も
平ら**です。型別の増分も +62 が最大で、50 局ぶんの伸びではありません。

**Python が確保して保持しているものは増えていない**ので、伸びているのは
その下——numpy の配列データや CRT ヒープのように tracemalloc が見ない層です。
そして数字が単調でない（213 → 209 → 229 → 215 → 236）のは、
**高水位であって保持ではない**形に見えます。

高水位なら頭打ちになり、保持ならなりません。

### numpy も持っていません。そして頭打ちになります

`tracemalloc` には**numpy の配列データが見えません**（numpy は自前の割り当て器を使い、
PyMem を通りません）。そして gc の**個数**が平らでも、**一定個数の入れ物が育つ配列を
持つ**ことはできます。つまり上の 2 つの計器は同じ死角を共有しています。

そこで到達可能な ndarray の `nbytes` を直接数えました（80 局、サーバ経由）:

```
   局   working set   numpy が保持   配列の数
    1       163 MB       0.0 MB          2
   40       181 MB       0.0 MB          2
   60       184 MB       0.0 MB          2
   80       190 MB       0.0 MB          2
```

**numpy は何も抱えていません**（配列 2 個、0.0 MB）。そして working set は
**0.34 MB/局で始まり、40 局あたりで平ら**になります——高水位の形です。

サーバ側も測りました。**16,799 要求・250 万行を通して CUDA の予約は 0.54 GB で一定**、
使用中 0.01 GB。**サーバは育ちません。**

### 計器そのものの費用

`tracemalloc` を有効にすると、同じ 80 局が **working set 163 MB → 239 MB** で始まります。
26 MB を自分で確保し、新しい確保場所を見るたびに増えます。
**伸びを `tracemalloc` の下で測ると、一部は `tracemalloc` を測っています。**
（探索担当の道具は roster や standings を読んだ*後*に開始するので影響は限定的ですが、
0.9 MB/局 と 0.34 MB/局 の差の一部はここかもしれません。）

### 無言の死は、まだ説明できていません

調査中にサーバが 3 回、**ログに 1 行も残さず**死にました。分かったこと:

```
  Python の例外ではない     ハンドラが握りつぶす形跡がない
  ネイティブの落ち方でもない  faulthandler を入れても何も出ない
  → 外から終了させられている（コミット枯渇による OS の終了が最も近い）
```

**こちらのコードで 80 局を回した限り再現しません**（サーバ健在、CUDA 予約も一定）。
死んだのはどれも**分割前の `RemoteValue`** を使った経路で、そこは
100 万局面を一度に符号化して約 3.9 GB を要求します。
**`53b7750` を取り込んだ後に再発するかどうかが、この仮説の検査になります。**

## ブリッジが落ちたときに何が起きるか

生成 7 で 2 ワーカーが落ち、こう出ていました:

```
[rustnode] falling back to Python: the Rust node sent 0 of 64219920 bytes:
```

ヘッダは届いていて（バイト数が読めている）、本体の最初の read が即 EOF、
**stderr は空**。つまりノードはヘッダを書いた直後に黙って死んでいます。

原因はまだ再現できていません（幅 48 の 46.6 MB のノードを 6 プロセス並列で
240 回送っても落ちません）。ただし**この症状を作っていた側**は直しました:

- **黙って死ぬのをやめました。** `node.rs` の書き込みエラーは全部 `break` で、
  プロセスは正常終了し stderr は空になっていました。**証拠を消していたのは
  こちらです。** いまは理由を stderr に書いてから止まります。
- **1 リクエストの panic でプロセスを落とさない。** `catch_unwind` で包んで、
  そのノードだけ拒否として返します。呼び出し側は拒否を Python で埋められます。
- **本体を作らずに流す。** 40〜60 MB の `Vec<u8>` を配列とは別に組み立てていました。
  このプロセスが確保する最大のものが、元の配列のコピーだったわけです。
  64 KB の窓で直接書くようにして、大きいノードのピークがほぼ半分になりました。
- **1 回の失敗でブリッジを諦めない。** これが一番効きます。以前は最初の失敗で
  そのプロセスは残り全部を Python で回していました（20 分の 1 の速度）。
  ノードはリクエスト間に状態を持たないので、**新しいプロセスを起こすだけ**です。
  3 回までやり直して、それでも駄目なら諦めます
  （`POKEURAOU_RUST_NODE_RESTARTS`）。`tests/test_rust_node.py` がノードを
  kill して、答えが変わらないことと諦めていないことを確認します。

**まだ分かっていないこと**: なぜ書き込みが失敗したのか。次に出たときは
stderr に理由が載るので、そのログを見せてください。

## 環境の注意

このマシンには C ツールチェインがありません（MSVC も Windows SDK も無く、PATH の
`link.exe` は coreutils のもの）。`x86_64-pc-windows-gnu`（rustup がリンカごと配る）で
解決しています。**この道では PyO3 拡張は作れません**——CPython は MSVC ビルドなので、
拡張も MSVC で作るのが筋です。だから境界はプロセス（JSONL over stdio）で、
これは既存の sim-bridge と同じ形でもあります。

`-gnu` の std には `profiler_builtins` が無いので、PGO は `x86_64-pc-windows-gnullvm` で作ります
（`rust/pgo.sh`、上の「target-cpu=native」の IKA-100 の段）。
