# 測ったが入れていない変更

速くなりそうに見えて**入れなかった**もの。捨てるとまた誰かが同じものを書くので、
パッチと測定結果を置いてあります。

## `inline-position.patch` — 局面の中の小さい `Vec` をインライン／`Rc` にする

`Side` の `active`（2 スロット）、`pokemon`（6 体）、`slotConditions`、`megaCapableSlots` を
インライン配列か `Rc` にします。前 2 つは複製のたびに必ず確保が走っていたもの、
後ろ 2 つは解決器がそもそも書き換えないものです。

**正しさは問題ありません**: 往復 6,200 局面一致、ターン差分 6,341 件すべて一致・拒否 0。
確保は **557.6 → 380.9 回/ターン（-32%）**。

### 結論: 遅くなります。入れません。

最初に測ったときは「速い時は 26% 速く、遅い時は 2.5 倍遅い二極化」に見えました。
**それは測定の側の問題でした**——当時このマシンでは生成が 10〜11 プロセス走っていて、
どのコアに乗るかで 2 倍変わっていたのです。

誰も使っていないマシンで測り直すと、二極化などありません:

```
base   41.2 41.7 41.4 42.0 41.4 43.4 us/turn
inline 78.5 79.3 78.7 80.1 79.2 79.9 us/turn      ← 1.9 倍遅い
```

交互実行 14 組でも同じで、**やっている仕事は完全に同一**です
（複製 21.2、ダメージ 7.1、強制コピー 26.1、Battler 48.7——すべて一致）。
確保を 32% 減らしてなお 1.9 倍遅いので、遅いのは確保ではなく**このパッチのコード**です。
心当たりは 2 つ:

- `Party` の添字は `self.slots[index].as_ref().expect(...)`。
  `mon_at` はこの移植で一番よく通る経路で、そこに毎回 `Option` の分岐が増えます。
- `Position` が 464 → 528 バイトになるので、複製も move も毎回その分多く運びます。

**確保の回数を減らすこと自体は正しい方向です**（1 ターン 429 回 × 18〜28 ns）。
ただしこのやり方ではありません。次に試すなら、添字に分岐を増やさない持ち方
（長さを別に持たない固定長、あるいは `Option` を使わない番兵）から測ってください。

### 測るときの教訓

**最初の 1 回は必ず速く出ます**（base も inline も）。CPU がアイドルから
ブーストする分で、これを 1 サンプルとして扱うと二極化に見えます。
そして**他のものが走っているマシンで取った絶対値は、比であっても信用できません**——
このパッチの「26% 速い」は、そうやって生まれた幻です。
