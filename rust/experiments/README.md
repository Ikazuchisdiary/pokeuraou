# 測ったが入れていない変更

速くなることは示せたのに**入れられなかった**もの。捨てるとまた誰かが同じものを書くので、
パッチと測定結果を置いてあります。**再現するなら、他に何も走っていないマシンで。**

## `inline-position.patch` — 局面の中の小さい `Vec` をインライン／`Rc` にする

`Side` の `active`（2 スロット）、`pokemon`（6 体）、`slotConditions`、`megaCapableSlots` を
インライン配列か `Rc` にします。前 2 つは複製のたびに必ず確保が走っていたもの、
後ろ 2 つは解決器がそもそも書き換えないものです。

```bash
git apply rust/experiments/inline-position.patch
cd rust && cargo build --release --features count-allocations
./target/release/pokeuraou-damage turns \
    ../configs/regulations/gen9championsvgc2026regmb.json turns-wide.json 3
```

**正しさは問題ありません**: 往復 6,200 局面一致、ターン差分 8,769 件すべて一致・拒否 0。

| | 確保/ターン | 1 ターン |
|---|---|---|
| 現行 | 557.6 | 45 us（安定） |
| このパッチ | **380.9**（-32%） | **35 us または 87 us** |

**二極化するので入れていません。** 同じバイナリがプロセス起動ごとに速い側か遅い側かに
落ち着き、10 回中 4 回が速い側でした。現行ビルドは 35 回測って一度も遅い側に落ちていません。
`Position` が 464 バイトのときも 528 バイトのときも起きるので大きさそのものではなく、
ヒープがどこに載るか（ASLR）に依存しているように見えます。

確かめるべきこと:

1. アイドルなマシンで 20 回ずつ交互に測り、二極化が残るか。
2. 残るなら、速い側と遅い側で何が違うか（`Vec<Live>` の確保アドレス、L1 のセット競合）。
3. 消えるなら、あれは私が測っていた間ずっと走っていた別の生成の影です。

`Party` 型そのものは素直な作りなので、二極化の原因が別だと分かれば
そのまま使えます。
