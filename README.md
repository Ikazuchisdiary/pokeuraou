# pokeuraou

Pokémon Champions (VGC 2026 Reg M-C) ダブルバトル検討ソルバ。

同時手番・確率的・不完全情報ゲームなので、出力は「最善手1つ+評価値」ではなく
ポーカーソルバ形式（均衡混合戦略・採用頻度・EV損・相手の配分事後分布）。

ダメージの乖離もターンと同じ flagged / silent の 2 分類にしました。閾値を合計に掛けると
「申告をやめれば数字が下がる」ことになるので、掛けるのは無警告のほうです
（現在の flagged は親子愛＝メガガルーラで、1 発が 2 発になる構造変化なので倍率では表せず、
計算器は申告する側を選んでいます）。

ダメージのサンプル数が 2,261 → 1,731 に減ったのは、**メガが初手前に発動したターンを
スキップする**ためです（下記のとおりメガが初めてサンプルされるようになった）。

解決器の乖離は 2 種類に分けて数えています。**flagged** は解決器が「これは未実装」と
先に申告したうえでズレたターン（既知の穴）。**silent** は何も言わずにズレたターン
（表示する数値を黙って壊しうる唯一の種類）。閾値は silent に掛けています。

原因の特定は目視ではなく統計です。`tools/diverge_report.py` が、各効果について
`P(効果 | 無警告乖離) / P(効果 | 一致)` を出します。lift が高く件数もある効果が原因、
lift が 1 付近なら単に頻出しているだけ。加えてダメージ乖離を比率でバケット化するので、
「1.3倍が抜けている」のように修正子名まで絞れます。

### 使用率データがメガ形態を落としていた（種族 201 → 220）

「マフォクシーに使用率データが無いのは変」という指摘から出てきた、この回いちばん重い欠陥です。
使用率データはメガを**独立した種族として記録**します（バトルログがそう呼ぶため）。
`Delphox-Mega` は team-legal ではないので読み込み時に捨てられ、**マフォクシーに人が振っている
配分が丸ごと消えていました**（使用率 12.75%、1,873 配分、道具はデルフォックスナイト 100%）。

1体の話ではありません。**75 のメガ形態**が同じ理由で落ちていて、
Champions は構築の主軸がメガなので、**環境の中心をピンポイントで失っていた**ことになります。
時々メガらずに使われる種族は「メガらなかった側の記録」だけが残り、配分の偏った標本になっていました。

→ メガ形態は `changesFrom` で**実際に持ち込む種族に畳む**（生の出現数で加重マージ）。
2 つだけマージしない項目があります:

- **特性**: メガ後の特性はメガ前には非合法で、チームシートに出るものでもないので落とす。
  それで合法な特性の観測が 0 になった 19 種族は「合法な特性の一様分布」にし、
  `abilities_unobserved` として**名前を出して報告**する（測定ではなく仮定なので）。
- **道具**: メガエントリの道具はメガストーンで、これは正しく、
  「マフォクシーがデルフォックスナイトを持つ」ことを事前分布が知る唯一の経路。

### メガが初めてサンプルされて出てきた 5 つの実バグ

差分テストは「使用率からチームをサンプルする」ので、メガが落ちている間はメガの経路に
**到達できていませんでした**。復活させた直後に無警告乖離が 2.9% → 5.6% に上がり、
原因を順に潰して 2.7% に戻りました。

| バグ | 内容 |
|---|---|
| **フェアリーオーラの二重適用** | オーラは場全体に効くので `field_abilities` から足していたが、保持者が攻撃側自身のときは通常の特性経路でも足されていた。Showdown は `move.auraBooster` で**最初の保持者だけ**に絞る。メガフラエッテのフェアリー技が 1/3 高くなっていた |
| **オーラブレイクが未実装** | オーラを打ち消すのではなく `3072/4096` = **0.75倍に反転**させる |
| **あまのじゃくが未実装** | `onChangeBoost` で保持者への全能力変化を反転。**メガムクホークが持つ**ので、インファイトの自己ダウンが上昇になる。lift 7.6 で `closecombat` の boosts 7 件と同じ原因 |
| **サンパワーの日照りダメージが未実装** | 1.5倍のほうは入っていたが、毎ターン最大HPの 1/8 を失うほうが抜けていた。リザードンは環境 27% で半分がサンパワー。かんそうはだ・あめうけざら・アイスボディも同じ形なので併せて実装 |
| **やどりぎのたねが回復先を間違えていた** | 「最初の生存している相手」に返していたが、Showdown は `getAtSlot(sourceSlot)` で**植えた個体**に返し、その個体が居なければ誰も回復しない。lift 36（5回中3回ずれていた） |
| **はたきおとすがメガストーンで威力上昇していた** | 1.5倍は `TakeItem` が通ることが条件で、メガストーンは持ち主から**離れない**。65 のまま、しかも何も落とさない |

### 実装済みと申告しながら何もしていなかった特性（とびだすハバネロ）

差分テストが 1 件の無警告乖離として出したものです。メガスコヴィランの特性
**とびだすハバネロ（Spicy Spray）** は Champions 独自で、本家は

```js
onDamagingHit(damage, target, source, move) { source.trySetStatus('brn', target); }
```

**接触判定も確率もなく、ダメージを受けたら攻撃側を必ず火傷させます**（ムーンフォースでも）。
これが「ダメージ計算に影響しない特性」の集合に入っていて、計算器としては正しいのに
**解決器では完全に無視**されていました。申告もしないので無警告乖離です。

静電気・ほのおのからだ（1/3、申告する側）と違って**確定発動なので実装できます**。
修正後、無警告乖離は **2.68% → 1.82%**（440 ターン）。

なお `MAX_TOTAL_DIVERGENCE` の per-seed 判定は外しました。1 シードは約 50 ターンなので
1 件が 2 ポイント動き、集計値と同じ閾値を課すと「使用率サンプラがどのチームを引いたか」を
測っていることになります。**無警告率は per-seed でも厳しく**保ち（申告漏れは標本に関係なく退行）、
総乖離の厳しい判定は 440 ターンの大標本テストに置いています。

### SP → 能力値を「実機の表示値」と照合（36/36 一致）

これまで能力値は Showdown（＝再実装）とだけ照合していました。`configs/teams/` の実チームは
**実機のステータス画面に出ていた最終能力値**を `shownStats` として持っているので、
`teams.verify_shown_stats` がそれを再計算して突合します。6体 × 6能力 = **36/36 一致**。
ゲーム本体に対する検証はこれが唯一の箇所です（`tests/test_teams.py`）。

### 相手プールは実際の大会エントリー（394 チーム）

**結論から**: 相手プールの一次資料は大会結果です。環境は少数アーキタイプの混合であり、
ペアの同時採用モデルは**混合を原理的に表現できません**（どのペアが同居するかしか言えないので、
誰も持ち込んでいない 6 匹を平気で作る）。そして 394 の実エントリーがあれば
**アーキタイプという抽象自体が不要**で、1 つ一様に引けばそれが大会分布です。

出典: [Reportworm standings API](https://standings.reportworm.com/2026/worlds)
（`/api/v1/2026/worlds`）。使用率データと同じ扱いで、手動取得・ローカルキャッシュ・
User-Agent 明示・再配布なし（`data/standings/` は gitignore）。

```bash
uv run python tools/fetch_standings.py 2026 worlds --usage
uv run python tools/standings_report.py
uv run python tools/selfplay.py --games 1500 --opponents worlds --limit 16
```

**データ品質**: 395 エントリー中 394 が 6 匹完備、**386 がレギュレーションに完全適合**。
特性・性格・道具・4技すべて有り。取り込み時に落ちたのは 2 件だけです:

- 1 エントリーがチーム未提出
- `Charizard: Drought` × 2 — メガリザードンY の**メガ後**の特性。チームシートに出るのは
  メガ前なので、これは「不明」にして使用率から引く（使用率データがメガの特性を落としていたのと
  同じ問題の裏返し）。名前を出して報告する

**SP が無いのは欠損ではなく正しい**: Champions のオープンシートは性格を見せて努力値を隠します。
だから配分は使用率から、**シートが示す性格で条件付けて**引きます
（信念層が検討時にやっているのと同じ条件付け。実測で 3.2 倍のシャープ化、厳密）。

### 大会構築の一覧を使用率で監査する（`tools/archetype_audit.py`）

キュレーションの失敗は「単に足りない」ことで、一覧自身は何も教えてくれません。
そこで関係を逆にして測ります。環境がアーキタイプの混合なら

```
usage[種族] = その種族を含むアーキタイプの重みの和
```

が種族ごとに 1 本の式になるので、非負最小二乗で解けます。**残差が欠落を名指しします。**

11 アーキタイプ（当時）で測った結果:

- 周辺分布（使用率）の **67.9%** は説明できる
- **ペア質量は 36.3% しか説明できない** ← キュレーションの弱点はここに出る
- 未説明ペアの上位が全部同じ核: `ガオガエン+ヤバソチャ 15.9%→0`、`ガオガエン+オオニューラ 13.8%→0`、
  `オオニューラ+ヤバソチャ 12.1%→0`

→ **ヤバソチャ（使用率 26.1%）がどのアーキタイプにも入っていなかった**。
実チームプールに差し替えたのでこの穴自体は解消しましたが、監査は残してあります
（次のレギュレーションでも同じ測り方ができる）。

なお**当てた重みをアーキタイプ頻度として使ってはいけません**。
アーキタイプ同士がメンバーを大きく共有しているので分解が一意に定まらず、
`big6` の当て値 1.1% と順位表での 3/10 は矛盾しません。監査の価値は残差であって重みではない。

### かつての相手プール（アーキタイプ 11 個 → 同時採用構造）

「勝率が高すぎる」「よくある編成を確認すべき」という指摘から出てきた欠陥です。
まず**実測で切り分け**ました:

| 仮説 | 実測 | 判定 |
|---|---|---|
| 相手のセットが壊れている | 攻撃技を1つも持たない個体が **2.3%**。該当ゲームで相手の勝率は 12pt 落ちる（全体では約 1pt 分） | 一因だが主因ではない |
| 相手がメガを持っていない | 相手の4体にメガストーンがあるゲームは **92.8%** | 該当せず |
| 相手の配分が薄い | 攻撃技のある種族で攻撃 SP が 8 未満なのは相手 19.5〜28.7% / 自陣 33.1〜33.6% | **相手のほうが薄くない** |
| **相手の編成が環境と違う** | 使用率上位 24 種のうち **78 ポイント分がプールに存在しない** | **これが主因** |

11 アーキタイプが使う種族は**全部で 28 種**（使用率データは 220 種）。
そして **Sneasler（使用率 31.4%、5位）と Sinistcha（26.1%、7位）が1つも入っていません**。
つまり価値関数は「誰も使っていない環境」に対して校正されるところでした。

→ 修正は**推測ではなく実測から**。chaos ファイルの `Teammates` 表を使います。

この表は無記載ですが、**同時採用の加重生数**だと読めます。根拠は2つで、両方
`tools/cooc_report.py` が毎回印字するので解釈が腐っても気づけます:

- `sum(Teammates) / 5 / usage` が**全種族で 6,934.3**（ばらつき 6.7e-04）。
  1チームの他メンバーがちょうど 5 体なので、値が「両方を含むチーム数」ならこうなるほかない。
  そしてこの共通値が総加重チーム数そのもの。
- **行列が対称**（質量加重 1.4e-04、上位2000ペアで最大 8.3e-02）。数え上げは対称、条件付き確率は非対称。

保持するのは **lift** `P(a,b)/(P(a)P(b))`。1.0 が偶然どおり、それ以上が本物の組み合わせです。

```
kingambit + sneasler      同時採用 20.2% of teams   lift 1.36x
garchomp  + charizard     同時採用 20.1%            lift 2.19x
incineroar + sinistcha    同時採用 15.9%            lift 1.82x
```

サンプラは「選んだメンバーに対する lift × 使用率」で次を引く**対等な pairwise モデル**です。
データがペアしか記録していないので、これがデータの支持する唯一の形です。
そして**近似なので誤差を測ります**（`tools/cooc_report.py`、5,000 チーム）:

- 使用率周辺分布との**全変動 4.5%**
- 個別の比は Kingambit 0.96x、Sneasler 0.95x、Incineroar 0.86x、Swampert 1.24x
- 記録のないペア（4.9%）は 0 にせず、**表の分解能（加重0.5チーム）で上限を与える**

`--opponents metagame | archetypes | mix` で選べます。既定は `mix`（半分ずつ）で、
アーキタイプは**出典のある実チーム**として残しています（同時採用プールには識別名も作者もない）。

### 相手の行動が最適化されていなかった（`tools/asymmetry.py`)

もう一つの指摘の検証です。両側とも同じ `narrow` → 同じ LP なので**コード上の非対称はありません**。
しかし両側とも 8 手に絞っていて、**絞り込みの損失はチームによって同じではない**。
同一シード・同一チームで予算だけ変えて 300 ゲームずつ:

| 自陣 x 相手 | 自陣勝率 |
|---|---|
| 8 x 8 | 77.3% |
| 8 x 16 | **61.7%** |
| 8 x 24 | 61.3% |
| 16 x 8 | 86.0% |
| **24 x 24** | **74.3%** |

読み方は 2 段階で、**最後の行が結論を変えます**。

- **片側だけ増やすと巨大に効く。** 相手を 8 → 16 手にするだけで自陣勝率が 15.6pt 落ち、
  自陣を 16 手にすると 8.7pt 上がる。そして 16 → 24 でほぼ動かない（61.7 → 61.3）ので、
  **片側の探索は 16 手で飽和**する。1 ターン先読みの浅い探索でも、候補を 8 に絞ることの
  損失はこれだけ大きい。
- **両側同時に増やすとほとんど動かない**（8x8 で 77.3%、24x24 で 74.3%）。
  つまり **8x8 は相手を我々より不利に扱っていたわけではない**。

したがって「勝率が高いのは相手を過小に探索していたからだ」という説明は**成立しません**
（一度そう書いたので訂正しておきます）。対等な予算での実勢はおおむね 74〜77% で、
残る説明候補は:

- **測定済み**: 相手プールが環境ではなかった（上記、修正済み）
- **測定済み**: 攻撃技を持たない相手 2.3%（修正済み、寄与は約 1pt）
- **未測定**: 4/6 選出を一様に引いていること。自陣は「どの4体でも機能する」ように
  組まれた実チームだが、アーキタイプの多くは特定メンバーが揃って初めて機能する
  （雨構築からペリッパーが抜けるなど）。ここは選出を解くまで分離できない
- **未測定**: 周辺分布からのセットは技構成として整合しない（攻撃技1つだけが相手 25.5%
  対 自陣 17.0%）

これは学習データの前提も変えます。**ラベルは探索予算に依存する**ので、
各ゲームに `searchLimit` を記録し、第1世代は 16x16 で生成しています
（片側 16 手が飽和点なので、両側 16 が現状の妥当な設定）。

### 両方直しても勝率は動かなかった（第1世代の途中集計）

修正後の条件（**16x16 / 実測の同時採用プール / 攻撃技の制約あり**）で 5,272 ゲーム:

```
全体                        75.7%
うち metagame プール        75.0%   ← 220 種から実測構造で生成した相手
うち rain-perish            84.2%
うち staraptor-delphox      68.8%
```

修正前が 72.4%（8x8 / アーキタイプのみ）だったので、**実質的に変わっていません**。
2 つの欠陥はどちらも実在し、どちらも直りましたが、**どちらも勝率の説明ではなかった**
ということです。残っているのは上に挙げた未測定の 2 つ（4/6 選出の一様抽出、
周辺分布サンプリングによる技構成の非整合）と、
「1 ターン先読み同士ならこのチームは実際にこの相手プールに強い」という可能性です。

勝率が 50% から離れているぶん学習信号は薄くなりますが、
**それがこの組み合わせの実際の分布**なので、勝率を報告して回す方針は変えていません。

### 自己対戦のチーム分布

価値関数はそれを学習した分布でしか校正されないので、チームの出どころは 3 つに分けて
混ぜないようにしています。**発明という 4 つ目の出どころは置きません。**

| 出どころ | 何が正確か | 何を埋めるか |
|---|---|---|
| **実チーム**（`configs/teams/`） | SP・性格・技・道具すべて実機から転記 | 何も埋めない。null は読み込み時に拒否 |
| **構築**（`configs/archetypes/`） | 6体構成は出典どおり。数値が出ている個体はセットも出典どおり | 記事が書いていない欄 |
| **使用率事前分布** | 実測 | 上の「書いていない欄」 |

構築名が「メガ○○」と名指ししている個体は、**出典がメガだと言っている**のでメガストーンも
stated 扱いにします（事前分布に任せると、メガリザードンY 軸の構築にこだわりスカーフの
リザードンが出てきて構築の identity が消える）。
使用率データに載らないほど珍しい種族を含む構築は**除外して理由を報告**します
（WCS2026 の 11 構築のうち 9 が使用可能。マフォクシーの 2 構築は使用率データが無いため除外）。

選出は 6 → 4 で、**選出の意思決定はモデル化していません**（`pick_four` は 6 から一様）。
実分布ではない（人は相性で選ぶ）ので、そう明記します。採用理由は「根拠が説明できる唯一の
規則」であることと、15 通り全部を覆うのでどの 4 体でも使えることです。

### 観測による事後更新（M2）

隠れているのは配分だけなので、観測は**それを直接絞る**。4 チャネル:

| チャネル | 何を絞るか | 尤度の性質 |
|---|---|---|
| `damageTaken` 自分が受けた**正確な**ダメージ | 相手の攻撃側能力値 | 16 ロールのうち一致する本数 / 16。**最強** |
| `damageDealt` 相手の **% の変化** | 相手の防御側能力値 | 両端が帯なので弱い。帯の中は平均 |
| `movedFirst` 同優先度での行動順 | 素早さ | 速ければ 1、同速 1/2、遅ければ 0 |
| `fractionalLoss` 残留ダメージの % 変化 | **最大 HP** | 0 か 1。他の能力値に一切依存しない |

実測（例の局面、Sneasler の事前 802 パーティクル）:

```
p2[0]  候補 802 → 410（エントロピー +0.17 bit）  closecombat が 188 ダメージ
p2[1]  候補 1314 → 1314（エントロピー +0.00 bit）  行動順（相手が 100% 速いので情報なし）
p2[1]  候補 1314 → 1314（エントロピー -0.25 bit）  やけど 1/16 で 56% → 50%
```

**ダメージ 1 個で候補が約半分**になる。一方エントロピーは +0.17 bit しか動かない
（質量が既に 1 個に 70% 乗っているため）。**候補数とビットの両方**を出すのはこのため。

尤度の計算コスト: `damageTaken` 9.5 ms / 802 パーティクル、`movedFirst` 15.2 ms、
`fractionalLoss` 0.05 ms。

### 自己対戦の予算（`tools/selfplay_budget.py`、1 ゲーム 12 ターン / 50,000 ゲーム）

| 探索サイズ | セル数 | 1 局面 | 1 ゲーム | 1 コア | 16 コア |
|---|---|---|---|---|---|
| 6×6 × 1 クラス | 36 | 0.024 s | 0.29 s | 4.1 h | **0.3 h** |
| 8×8 × 1 クラス | 64 | 0.042 s | 0.50 s | 7.0 h | **0.4 h** |
| 12×12 × 1 クラス | 144 | 0.092 s | 1.11 s | 15.4 h | 1.0 h |
| 24×24 × 4 クラス（検討用の既定） | 576 | 1.45 s | 17.4 s | 242 h | 15.1 h |

**「M3 の自己対戦には解決器を 100 倍にする必要がある」というのは私の誤った見積りでした。**
1 局面のコストは `行 × 列 × 同値類` のセル数に比例するので、支配的なのは探索サイズです
（片側 24 手 → 8 手で 9 倍安い）。自己対戦は根を厳密に解くだけでよく、検討用と同じ
サイズである必要はないので、**8×8 × 1 クラスなら 16 コアで 0.4 時間**。
現状の解決器で M3 は回ります。

内側のループを配列化して得られるのは「同じ予算での深さ」で、それは M4（同時手番 MCTS）
の話です。プロファイルで見えた残りの内訳は `_hit_target` 49% / ターン中の素早さ再ソート
22% / `Position.copy` 12% で、素直な最適化で稼げるのはあと 1.5〜2 倍程度。
3.4% の無警告乖離を守りながら書き換える価値が出るのは、深さが足りないと分かってからです。

分岐は 1 ターン中の全ヒットの**積**なので、完全列挙は指数的になります。
`max_branches` は「生成後に間引く」のではなく**世代を作る前に解像度を落とす**ので、
時間もメモリも上限で押さえられます（これを入れる前は `Budget.exact()` が 20 GB /
9 分に達しました）。行列を埋めるのは `Budget.matrix()`（乱数 1 点）、注目したセルだけ
濃い予算、という使い分けです。ダメージの分布自体は計算器が 16 乱数まとめて返すので、
ランキングのためにターンを分岐させる必要はありません。

## 重要な事実（実測で確定済み。依頼時の前提から訂正されたもの）

- Showdown の champions mod は `set.evs` を **SP そのもの**として扱う
  （`base + SP + 75` / `base + SP + 20`）。**SP↔努力値の変換層は不要。**
  `evLimit = 66`、1ステ上限 32 は validator が強制し、`32/32/2`（合計66）も合法。
- Champions のオープンチームシートは **性格も公開する**
  (`sim/battle.ts` の `showOpenTeamSheets` が champions を特別扱い)。
  隠れ情報は **SP 配分 6 次元のみ**。
- Showdown には中立性格が5つ残っている（Hardy/Docile/Bashful/Quirky/Serious）。
  本家に無い4つを弾くのは**我々の責務**。0SP セットは Hardy に差し替えて渡す。
- テラスタルは `canTerastallize() → null` で無効。ギミックはメガのみ、1試合1回/陣営。
- 上位K個の「配分アーキタイプ」は成立しない。Incineroar は 10,154 通りの配分を持ち、
  上位8個の完全能力値ベクトルで質量の 28.7% しかカバーしない。
  → 信念は**全パーティクル**で保持する。
- **エントロピーは更新で増えることがある。**事前分布が 1 個の配分に 70% 乗っていて、
  観測がそれと食い違えば、事後分布は平らになる。ベイズ更新として正しい挙動なので、
  「情報量」ではなく**エントロピー減少量**として符号つきで出す。
- **瀕死は等式ではなく不等式。**倒れたときプロトコルが報告するのは「そこにあった HP」で
  ロールではない。等式として扱うとオーバーキルする配分（＝投資の重い配分）を全部
  排除してしまう。きあいのタスキで軽減された一撃も同じ。
  → `DamageTaken(capped=True)` で `P(roll >= observed)` を使う。
  これは実オラクル往復テストが見つけた。
- **相手は自分の配分を知っている。**行列を信念で平均してから解くと、「相手も自分の
  投資量を知らずに手を決める」という別のゲームを解くことになり、**自分の均衡値を
  過大評価する**（情報は持っている側を損させない）。正しくは片側private情報つきの
  ベイズ型ゼロ和ゲームで、`value(x) = Σ_k w_k · min_j (x'M_k)_j` は凹な区分線形関数
  なので**依然 1 本の LP**で解ける（`equilibrium.solve_bayesian`）。
  補助変数がクラスごとに 1 個増えるだけ。実例では平均 0.25 に対し真値 0.0 になる。
- **「局面依存の無損失同値類で縮約する」という設計方針は外れた。**実測 **1.02倍**
  （30局面/60体の中央値、最大 2.45倍）。通常のダブル局面では 6 個の能力値のうち
  4 個が何かに読まれるので、パーティクルは本当に区別可能で、厳密な縮約は効かない。
  → 実際に効いているのは (1) **チームシートが公開する性格での条件付け**（3,126 → 974、
  中央 3.2倍・厳密）と (2) **上位クラスへの切り詰め**（近似）。
  切り詰めは覆う質量が中央 22.5% しかないが、**均衡値はほぼ動かない**
  （4→16クラスで最大 0.0016）。ただし**採用頻度は動くことがある**（最大 23.7pt）ので、
  頻度を読む前に `--stability` で確認する。質量の被覆率は妥当性の代理指標にならない。

### Showdown API / 仕様の落とし穴（すべて差分テストで踏んだ）

- `Battle.fromJSON` は**引数オブジェクトを破壊的に書き換える**。必ず文字列を渡す。
- `serializeBattle` は `state.log = battle.log` で log 配列を**参照共有**する。
- `log.length - sentLogPos > 1000` で `Error: Infinite loop`。clone 後にリセット。
- ダブルで `target: normal` の技は選択文字列に**対象が必須**、全体技は**対象を付けると拒否**。
- 選択エラーは `send` 経由なので log には出ない。`side.choice.error` を読む。
- Protean の「発動済み」は volatile ではなく `effectState`。局面に `abilityState` が必要。
- Transform は HP 以外の能力値をコピーする。SP から再計算すると誤る。
- Cloud Nine / Air Lock の天候無効化は**場全体**。味方が持っていても効く。
- **交代は控えとパーティ位置を入れ替える**（`side.pokemon` の要素ごと）。
  入れ替えは `if (oldActive)` の中にあり、**瀕死かどうかは見ていない**ので
  瀕死の入れ替えでも起きる。したがって `side.active` は常に `[0, 1]`。
  `switch N` の N はこの位置を数える。
  （※ 以前ここに「瀕死のときだけ入れ替えない」と書いていたのは**誤り**でした。
  ターン中に瀕死の交代は起きないので、ターンの差分テストではこの分岐に到達できず、
  交代フェーズの差分テストを作った初回に乖離率 100% で露出しました。）
- **瀕死のポケモンは控えに戻る際に状態異常が消える**
  （`if (oldActive.fainted) oldActive.status = ''`）。場にいる間は `'fnt'`。
- **しろいハーブは残留だけでなく 4 箇所で発動する**:
  `onAnySwitchIn`（優先度 -2、つまり登場特性の後）・`onAnyAfterMove`・
  `onAnyAfterMega`・残留 29。しかも `onAny*` なので**場の全保持者**を毎回見る。
  残留だけで実装すると、いかくで下がった攻撃をそのターン中ずっと引きずり、
  交代フェーズ（残留が無い）では永久に引きずる。
- **gen 8 以降、行動のたびに素早さを再計算してキューを再ソートする**
  （追い風・素早さダウン・持ち物消失が残りの行動順を変える）。
- 残留効果は「持続を減らす → 0 なら**効果を実行せず終了**」の順。
  砂嵐の最終ターンはダメージが入らない。
- Protect は連続使用で失敗率が上がる（`stall` カウンタ、n 回目は `(1/3)^(n-1)`）。
  **カウンタを見る技は `stallingMove` フラグで決まる**（M-C では みきり・まもる・
  ニードルガード・キングシールド・トーチカ・こらえる）。設定から読むこと。
- **ワイドガード / ファストガードは `stallingMove` を持たないが `stall` を付ける**。
  自分は必ず成功するのに、次のターンの まもる を 1/3 にする。両者とも Protect と同じ
  `onTry: !!queue.willAct()` ゲートを持つ。
- こらえる・きあいのタスキ・がんじょうは `effect.effectType === 'Move'` を見るので、
  **砂嵐・反動・いのちのたまでは発動しない**。こらえる（`onDamagePriority -10`）が
  タスキ（-40）より先に走るので、こらえた一撃でタスキは消費されない。
- **きあいのハチマキはタスキとは別物**。`randomChance(1, 10)` で HP 満タン不要、
  消費もしない。同じ扱いにすると確定発動になる。
- **ほろびのうたは満了時に効果が「走る」**（`onEnd` で瀕死）。天候のように
  満了で handler を飛ばすと、ゲームが倒したポケモンが生き残り、
  以降そのバトルの全ターンが誤った局面と比較される。残留順は 24。
- **Champions は HP 表示ルールも独自**（`getHealth()` が champions を特別扱い）。
  `Math.floor(100 * hp / maxhp) || 1` なので**切り上げではなく切り捨て**、
  生存中は最低 1%。さらに **20% と 50% ではバーの色が 1 ビット追加情報**を持つ
  （`hp*5 > maxhp` で y/r、`hp*2 > maxhp` で g/y）。
  つまり「相手は 62%」は数ではなく**幅 1〜3 の帯**（幅 ≒ maxhp/100）。
  `round(maxhp * 0.62)` は表示され得ない値になることがあり、確定数がこの幅で反転する。
- 反動・吸収は `Math.round`、猛毒は `trunc(maxhp/16) * stage`（積の切り捨てではない）。
- 反動・いのちのたま・技自身の `self` 効果は**1 回の技につき 1 回**。全体技で
  対象ごとに適用すると 2〜3 倍になる。
- Sucker Punch は「相手が攻撃を選んでいるか」ではなく
  「相手が**まだ動いていない**か」で判定する。
- Protect は `!!queue.willAct()` でも判定する。**キューに何も残っていなければ失敗**。
- ため技の最中は**行動が固定される**（`[from] lockedmove`）。選択は無視される。
  ため技のブースト（エレキドリフトの特攻+1）は雨で溜めを飛ばしても適用される。
- 猛毒のカウンタは**交代で戻ると 0 にリセット**される（`tox.onSwitchIn`）。
- さめはだ・ゴツゴツメットは `onDamagingHit` なので、**その一撃で倒れても発動する**。
- 片側が全滅した瞬間にキューは破棄される。以降の行動は起きない。
- あばれる（Unnerve）は**相手のきのみ全般**を食べさせない。
- 技の `heal` は gen 5 以降 **四捨五入**（切り捨てではない）。
- `selfBoost` は `self` とは別のフィールド。3 技（クランゴンの鳴き声など）だけが使う。
- ぼうおん（Soundproof）は `target !== source` 条件つき。**自分に撃つ音技は防がない**。
- 半減きのみは「実際に軽減した一撃」でしか消費されない（オッカなら**炎かつ抜群**のとき）。
  オボンのみ系の「ピンチで回復」とは条件が別。
- どくびしは**地上の毒タイプが吸収して消す**。鋼タイプは無効だが消さない。
- トリプルアクセル / トリプルキックの威力は `20 * ヒット数` / `10 * ヒット数`。
  宣言威力をそのまま使うと 3 発当たりで実ダメージの 1/3 になる。

## 出力（M1 の 1ターン検討ツール）

```bash
uv run python -m pokeuraou.cli examples/scenario-turn1.json --stability
uv run python -m pokeuraou.cli examples/scenario-turn5.json   # 観測つき（事後分布）
```

出力は「最善手1つ + 評価値」ではなく、**両者の均衡混合戦略・採用頻度・EV損・
相手の配分分布**。加えて、その数値がどこまで信用できるかを数値自身が申告する:

- 評価軸の**式**と、その軸が**見ていないもの**
- **これは勝率ではない**という明示（勝率は学習した価値関数が必要で M3）
- 相手の配分は**事前分布**であること（観測による更新は M2）
- 行列が覆った同値類の**質量**と、切り詰めを倍にしたときの**頻度の動き**
- 絞り込みが**落とした選択肢**（あれば）
- 解決器が申告した**未実装効果**（この行列に混ざっているもの）

評価軸は無パラメータのものだけを用意した（`hp-share` / `faints`）。
「KO は HP 何点分」のような重みは根拠が出せないので置かない。2 軸は逆方向に失敗する
（`hp-share` は削りを過大評価、`faints` は倒れるまで何も見ない）ので、両方で解いて
**支持集合が一致するかを報告する**。一致しないならそれはこの局面の情報で、欠陥ではない。

## 観測の与え方

局面 JSON に `observations` を付けると事後分布になります（`examples/scenario-turn5.json`）:

```json
"observations": [
  {"type": "damageTaken", "attacker": [1,0], "defender": [0,1],
   "move": "Close Combat", "damage": 188},
  {"type": "movedFirst", "first": [1,1], "second": [0,1],
   "firstMove": "Matcha Gotcha", "secondMove": "Flare Blitz"},
  {"type": "fractionalLoss", "slot": [1,1], "fraction": [1,16],
   "before": "56%", "after": "50%g", "reason": "burn"}
]
```

制約を 2 つ明示しています。**尤度は与えられた局面で評価する**ので、観測時と天候や
ランクが違うならその局面の JSON に付けて別に流す必要がある。そして**隠れ個体同士の
行動順**は結合制約になり独立な再重み付けに分解できないので、適用せず申告する。

観測が全パーティクルで確率 0 になったときは**正規化せず報告**します。それは観測か
局面の入力が間違っているという意味で、黙って正規化すると「根拠のない自信のある分布」
ができてしまう。

## 自己対戦（M3 のデータ生成）

```bash
uv run python tools/selfplay.py --games 3000 --seed 1 --limit 8
```

**教師は勝敗そのもの**です。プロキシを教師にした価値関数はプロキシのバイアスを学習し、
それ以上には決してならないので、「勝率」というラベルを正当に付けられません。
そこから 3 つの制約が出ます:

- **決着まで回す必要がある** → 交代フェーズを決定ノードとして実装した理由
- **決着しなかったゲームはラベルを付けずに捨てる**（件数は報告）。
  打ち切りにプロキシを入れるのは、却下した教師を裏口から戻すこと
- **手を選ぶ探索は、学習する対象ではない**。価値関数がまだ無いので葉は `hp-share` で
  評価する（つまり第0世代は弱い）。**ラベルは実際の勝敗なのでそれでも正しい**。
  各ゲームに `searchObjective` を記録している

局面には**両者の配分が入っています**。隠れ情報は価値関数の**外**で扱う設計です
（検討時は信念層が行列をパーティクルで平均するので、価値関数は
「ここから誰が勝つか」だけ答えればよい）。

### 偏りの切り分け（実測）

初回の勝率が 92% だったので、データを作る前に原因を切り分けました。

| 実験 | side 0 勝率 |
|---|---|
| 自陣ミラー（同じチーム同士） | 56.8%（37戦） |
| 自陣 side 0 vs 構築群 | 56.0%（25戦） |
| **構築群** side 0 vs 自陣 side 1 | 18.5%（27戦） |

ミラーが 50% 近傍なので**機械側の偏りではない**。実チームが、周辺分布からセットを引いた
相手プールに対して単純に強いだけです（1ターン先読みの浅い探索同士なら妥当）。
勝率が 50% から離れているぶん学習信号は薄くなりますが、**それがこの組み合わせの実際の分布**
なので、勝率を報告して回すほうを選びました。探索が強くなる世代で 50% に寄るはずです。

コスト: 1.14 秒/ゲーム、13.0 決定点/ゲーム（片側 8 手、`Budget.exact()` で解決）。

### プロキシがすでにどれだけ当たっているか（M3 の余地の実測）

`tools/selfplay_analyse.py` は、価値関数が**倒すべき相手**を先に測ります。探索は葉を
`hp-share` で評価していて、各決定点にその値と最終結果の両方が入っているので、
「プロキシがどれだけ勝者を当てるか」がデータから直接出ます。

信頼度曲線（プロキシを8分位に切って、各バケットの実際の勝率）:

      0.362..0.457            29.7%
      0.457..0.504            56.0%
      0.504..0.543            76.0%
      0.543..0.590            87.5%

      0.669..0.826            97.8%

|---|---|---|---|
| 1 | **0.769** | 0.512 | **72.4%** |

### フォルム名は合成する

Showdown の ja 図鑑はフォルム種を `baseSpecies` + `forme` の 2 つに分けて持ち、
`name` は無フォルム種だけです。`name` しか読まないと種族被覆が **68.9%** に見え、
ルガルガン・イダイトウ・全メガが未訳扱いになります（最初そうなっていました）。

優先順: 完全な訳 → 訳された base + 訳された forme → 訳された base + **英語の** forme → 英語名。

3 番目が要点です。`lycanrocdusk` は「**ルガルガン (Dusk)**」になります。
素の「ルガルガン」に落とすと**別のポケモン（種族値も素早さも違う）と同一視**されます。

メガは「メガ+基本名」を適用します（メガスコヴィラン・メガユキメノコ・メガカイリュー・
メガプテラ・メガマフォクシー）。これは発明ではなく、**引用した日本語の大会レポートが
一貫して使っている表記**です。一方**メガストーンの日本語名は基本名から導けない**ので、
`configs/names/ja-extra.json`（生成物とは別ファイル、再生成で消えない）に手で入れる形にしています。
空文字なら英語名にフォールバックするので、途中まで埋めた状態でも安全です。

### 技の対象はスロット番号ではなくポケモン名

`ねっぷう → 相手1` は読む側に何も伝えません。`ねっぷう → ガオガエン` にしています。

これは行動オブジェクト単体では解決できません。choice 文字列の対象は**指す側から見た相対値**
（正 = 相手スロット、負 = 自分側スロット）なので、`相手1` は誰が指しているかで別のポケモンを
指します。そこで `target_names(pos, side_index)` が側ごとに解決子を作り、
`describe` がそれを受け取ります。自陣の表と相手の表で別の解決子を渡しています
（逆にすると出力の全行が誤ったラベルになるので、テストで両方向を確認しています）。

- 種族制約があるので、片側の中で名前は一意になります
- 空きスロット（瀕死・不在）は**番号にフォールバック**します。名前を付ける対象が無いので
- 味方対象は `味方ガオガエン` と側を残します。ねこだましを味方に撃つのと相手に撃つのは
  まったく別の行動で、名前だけではどちらか分からないため

```
+2.000  アイアンヘッド → オオニューラ | フレアドライブ → ヤバソチャ
+1.789  ドゲザン → ヤバソチャ | フレアドライブ → オオニューラ
予算不足で落ちた選択肢: slot1 まもる, slot1 交代 → イダイトウ, slot2 すてゼリフ → オオニューラ
```

### `--json` は英語のまま

機械向けインターフェースなので、表示フラグで `"Heat Wave"` が `ねっぷう` に変わってはいけません。

## 選出（6→4）は順序付きの別のゲーム

### 先発がチームファイルの順序で決まっていた（実バグ）

`pick_four` は4匹を一様に引いたあと**パーティ順**で返し、`position_from_sets` が先頭2匹を
場に出していました。つまり**先発を決めていたのは乱数ではなくチームファイルの並び順**です。
生成済み 4,539 ゲームを数えたら:

```
先発ペア: 15通りのうち 6通りしか出ていない
  1775 (39%)  フシギバナ+リザードン
   914        ガブリアス+フシギバナ
   ...
ガオガエン・ドヒドイデ は一度も先発していない（ファイル上で 4,5 番目なので、
選ばれた4匹の中で必ず後ろ2匹になる）
```

**ねこだまし先発が訓練データに1件も存在しませんでした。** ダブルで最も基本的な先発の1つです。

これが重いのは、**ターン1の局面＝選出そのもの**だからです。プロキシが最も弱く価値関数の
余地が最も大きいのがターン1（AUC 0.71〜0.77、終盤は 0.96）なので、
**データセットは「それを改善するために作られた唯一の領域」で体系的に壊れていました**。
既存の第0世代・第1世代データはこの点で使えないので破棄して作り直しています。

### 行動空間は 15 ではなく 90

1・2匹目は場に並ぶので、3・4匹目とは別の選択です。
したがって **C(6,2) 先発ペア × C(4,2) 控えペア = 90 通り**。

ペアの中の順序は取っていません。ダブルでは両先発が両相手に隣接しているので slot1/slot2 の
違いは機構的にほぼ無く、控えは交代時に自由に選べるので 3/4 の順序も意味を持ちません。
だから「ペア＝集合」で 90 が**空間の全体**（サンプルではない）です。

`all_selections()` がこの 90 を列挙します。テストで先発 15 通り全部と 6 匹全員が
先発しうることを検査しています（ファイル順に依存した抽出は即座に落ちる）。

### 選出リゾルバ（`src/pokeuraou/selection.py`）

```bash
uv run --group learn python tools/selection.py --place 1
uv run --group learn python tools/selection.py --mirror       # 正当性検査
uv run --group learn python tools/selection_check.py --place 1 --games 300
```

90×90 のベイズ型ゼロ和ゲームとして厳密に解きます。相手は自分の配分を知っていて我々は
知らないので、ターン解決器と同じ `solve_bayesian`（配分クラスごとに別の行列、相手はクラス
ごとに別戦略、我々は1つ）。8,116 局面を 2.9 秒。`resolve_turn` は使いません —
価値関数が「ここから誰が勝つか」に既に答えているので、ターンを解き直すのは
90×90×256 倍のコストで劣る問いを立てることになります。

**正当性の担保が2つ。**

- **ミラーは厳密に 50.0%**（誤差 0、双対ギャップ 1.11e-16）。同じ6匹・同じ配分なら行列が
  `M[i][j] = 1 - M[j][i]` を満たすので値は強制されます。向きの取り違えを検出する唯一のテスト
- **反対称性の実測** 2.98e-08。価値関数の構造的性質が配線まで届いているかの検査

優勝構築（ヤマザキ選手）相手:

```
自陣の勝率 44.2%（全体平均 61% に対して）
  52.06%  ガブリアス+ニンフィア / ドヒドイデ+ガオガエン
  47.94%  ガブリアス+ニンフィア / リザードン+ガオガエン
最も損な選出: フシギバナ+ドヒドイデ / リザードン+ニンフィア（-31.7 ポイント）
```

**選出だけで勝率が 31.7 ポイント動きます。** ターン内のどの判断より大きい。

### 「先発はじゃんけん」か、はしごか（`cyclic_share`）

均衡が純戦略を返したので、それが信用できるかを行列の形から測ります。対称ゲーム（ミラー）
なら一意に分解できます:

```
A - 0.5 = T + C     T[i][j] = t[i] - t[j]（t は行平均）
```

`T` は「はしご」（各先発に強さがあり強い方が勝つ）、`C` が残りで、じゃんけんは純粋な `C` です。

| | 推移的 \|T\| | 巡回 \|C\| | 巡回の割合 |
|---|---|---|---|
| 強い4匹の先発6通り | 0.600 | 0.017 | **0.1%** |
| 6匹すべての先発15通り | 2.097 | 0.324 | **2.3%** |

3すくみは1つも存在しません。**誤差の向きが重要です** — セルのノイズは巡回成分を*増やす*側に
働くので、0.1% は上限であり、ノイズで巡回が消えたのではありません。

強さ順も人間の目に素直です:

```
+17.96  ガブリアス+ガオガエン    ← ねこだまし + スカーフガブ
+10.63  フシギバナ+ガオガエン
  ...
-22.93  ニンフィア+ドヒドイデ    ← 受け2枚
```

**ただし結論ではありません。** この価値関数は hp-share を葉にした深さ1の方策が指したゲームで
校正されています。じゃんけんは「読みを咎められる相手」がいて初めて成立する構造なので、
浅い相手に対して1つの先発が支配していても不思議はない。つまりモデルは**自分の生成方策の
ゲームを正しく記述している**だけかもしれません。

→ **巡回の割合を世代ごとに追う指標**にしました（リゾルバが毎回印字）。第2世代で増えれば
じゃんけんは実在して「強さとともに現れる」構造だったことになります。

### 探索が解いていた行列はゼロサムではなかった（実バグ）

ミラーで「均衡選出 vs 一様選出」を測ったら、**一様 vs 一様が 59.1% ±5.8**（276ゲーム）でした。
ミラーで両側が一様なら**対称性から 50%** になるはずで、区間 53.3〜64.9 は 50% を除外します。
field vs field は 50.2% で正常だったので、違いは「ミラーは両側の素早さが完全に同値になる」こと。

原因を1つの近似に特定しました:

```
                  budget  max |M[i][j]+M[j][i]-1|  符号付き平均  branches  ms/cell
           matrix() そのまま                 0.0417      +0.0052       1.0     1.19
                 + 同速を分岐                 0.0000      -0.0000       5.0     4.05  ← これだけ
                 + 急所を分岐                 0.0417      +0.0052       1.0     1.38
                 + 命中を分岐                 0.0417      +0.0052       1.0     1.03
               + 追加効果を分岐                 0.0417      +0.0052       1.0     0.88
                 exact()                 0.0000      +0.0000    1545.8   648.09
```

**同速だけが反対称性を壊していました。**他の近似はすべて対称です。

なぜ side 0 有利になるか: LP は1つの行列から row に maximin、col に minimax を読みます。
これが整合するのは行列がゼロサムのときだけで、ミラーなら `M[i][j] + M[j][i] = 1` が要件です。
同速を片方向に決めると、**正典順で先に来る側は「同速に必ず勝つ」前提で計画し、
もう一方は「必ず負ける」前提で計画**します。現実は 50/50 なので side 1 だけが過度に守りに入る。
これが11ターン積み上がって 59.1% になっていました。

修正: `Budget.matrix()` が同速を分岐（`max_branches` も 1 → 16、でないと切り捨てられる）。
`Budget.deterministic()` は**触っていません** — 差分テストが Showdown の固定乱数方策と
一致させる必要があり、そちらは意図的に非分岐です。

コストは**実戦で 1.06 倍**。同速の発生率を 25,000 決定点で測った結果:

| | 割合 |
|---|---|
| 同速なし | 94.2% |
| 1組が同速 | 5.6% |
| 2組が同速 | 0.2% |
| **少なくとも1組** | **5.8%**（生の素早さ基準 6.2%） |

ミラーだけが 3.4 倍になる最悪ケース（全ペアが同速）です。
なおこの 5.8% は**使用率からサンプルした配分**での数字なので、実戦（人が同速を意識して調整する）
より低く出ているはずで、下限とみるべきです。

**既存の学習済みモデルは作り直していません。**理由: 実際の1手は `Budget.exact()` で 50/50 に
分岐しているので**ラベル（勝敗）は汚染されておらず**、歪んでいたのは探索の見立てだけ。
影響も同速が起きた 5.8% のセルに限られ、そして第2世代は価値関数を葉に入れるので
どうせ全部再生成します。修正はそこに無料で乗ります。

回帰テストは「ミラーで `M[i][j] + M[j][i] = 1` が厳密成立」の形にしました
（`tests/test_resolve.py`）。LP が同じ行列から両者の答えを読む前提そのものなので、崩れたら落ちます。

### 選出リゾルバの助言は実際に勝てるのか（`tools/selection_check.py`）

セルの推定誤差を最適化が拾う（optimiser's curse）のは実在の危険なので、指させて測りました。
優勝構築相手、各300ゲーム、同一シード:

| 自陣 vs 相手 | games | 勝率 |
|---|---|---|
| **均衡 vs 一様** | 264 | **61.0% ±5.9** |
| 一様 vs 一様 | 263 | 44.5% ±6.0 |
| 均衡 vs 均衡 | 260 | 38.8% ±5.9 |

**助言の価値 +16.5 ポイント**、区間が重ならないので実在の効果です。optimiser's curse は
出ていません。

**ただし主張した均衡値の校正は判定できていません。** 44.1% に対し実測 38.8% ±5.9 で、
区間 32.9〜44.7 は 44.1 を含みます。点推定は 5.2 低いものの、260ゲームでは 38 と 44 を
区別できず、校正を言うには片側 2,000 ゲーム必要です。

そして**3本すべて上記の同速バイアスの下で走っています**（修正前に起動したプロセス）。
マッチアップが違うので影響は 5.8% のセルに限られますが、第2世代で測り直す対象です。

### ドヒドイデの評価 — 仮説は外れた

「深さ1の探索はどくどくを打てない（見返りが未来なので）」という仮説を立てて測ったら**外れ**でした。
ドヒドイデが場にいた 64,447 の決定点で、均衡が実際に指したもの:

```
まとわりつく  40.0%      どくどく      13.1%
トーチカ      23.5%      ワイドガード  12.4%      交代 6.8%
```

技構成が全部位置取りで、探索はちゃんと使っています。ただ**順序に葉の性質が出ています** —
即座に少し削るまとわりつく（威力20＋拘束）が最多で、遅延して大きく削るどくどくが 13%。
hp-share は即時の HP しか見ないので、この偏りは機構から予測できます。

打ち切りの生存者バイアスは想定より小さい（30ターン超は 0.22% 対 0.12%）。ただし
**打ち切り群（全体の 10.7%）は尾ではなく別のレジーム**です — 完走ゲームの 30ターン超が
0.2% しかないのに打ち切りが 10.7% あるので、「膠着したら解けない」局面が別に存在します。
その構成は現データからは見えません。

選出は近似で埋める穴ではなく、**同じ形の別のゲーム**です。両者のチームシートが公開されていて
同時に選ぶので、**90×90 の同時手番ゼロ和ゲーム**で、各セルの値は「その先発同士のターン1局面から
の勝率」— つまり価値関数がまさに埋めるべき行列です。

コスト見積り: 8,100 セル。`resolve_turn` は不要（ターン1局面を作って評価するだけ）なので
符号化 8,100 件（約 2.8 秒）＋ forward 1回（約 100 ミリ秒）。厳密に解けます。

順序:

1. 価値関数で 90×90 を埋める
2. LP で選出の均衡混合戦略を解く（M1 と同じ機構、既にある）
3. その均衡から選出を引いて次世代のデータを作る
4. 現実的な選出分布の局面で価値関数を再学習

ニワトリと卵ですが、一様選出から始めて均衡に寄せる形は正当です。
なお**古いデータで選出リゾルバを作っても意味がありませんでした** —
価値関数が見たことのある先発ペアが 15 のうち 6 しかなく、残り 9 は外挿になるためです。

## 価値関数（M3）

```bash
uv sync --group learn                                  # torch は任意グループ
uv run --group learn python tools/encode_dataset.py --dir data/selfplay-gen1
uv run --group learn python tools/train_value.py --data data/selfplay-gen1-encoded.npz
```

`torch` は既定の依存に入れていません。ソルバ・解決器・差分テストは 3GB の CUDA wheel なしで
入るべきで、かつ**検討側の経路が torch に依存し始めないため**の分離でもあります。
（RTX 5070 は Blackwell / sm_120 なので既定の PyPI wheel には該当カーネルがなく、cu128 ビルドを使う）

### 符号化（`encode.py`）

局面は `(B, 2, 4, ...)`。**side 軸を潰さない**のが要点です。

種族・特性・道具・技は埋め込み（レギュレーションダンプから id 順で語彙を作る）、
数値は 1 体あたり 88 次元（HP 割合、**実能力値6**、SP6、ランク7、状態異常7、
在場/場所/瀕死/メガ済/メガ可能/拘束/交代直後 8、タイプ18、PP4、技無効4、volatile 25+1）。
side が 27 次元（場の状態11、メガ使用/残存、生存率、チーム HP 率、スロット条件12）、
field が 24 次元。

**能力値は計算して渡します。**素早さは行動順を決め、行動順がその後のほとんどを決めるので、
実機と照合済みの厳密な式を種族埋め込みから再発見させる理由がありません。

3 つの性質を「祈る」のではなく**検査可能**にしています:

- **反対称性**: `mirror()` は side 軸を反転するだけ。side に属する量が `field` に紛れ込めば
  「局面の左右を入れ替えて符号化＝鏡像」というテストが落ちます
- **レギュレーション固定**: 語彙の指紋を重みと一緒に保存し、不一致なら**読み込みを拒否**。
  M-B の重みを M-C で読むと同じ整数が別のポケモンを指す
- **リークなし**: 同じ局面は、それが属するゲームの勝敗によらずビット単位で同一に符号化される

不明な volatile は「何も起きていない」ではなく `other` ビットを立てて**名前ごとに計数**します
（第0世代のデータでは未知は 0 件）。

### モデル（`value.py`）

1体ごとの MLP → **在場/控えを分けた masked mean と max** でプーリング → side ベクトル。
mean だけでは「1体だけ耐えられる」を表現できず、max だけでは残存量を失います。

出力は `head([我々, 相手, 場]) - head([相手, 我々, 場])` の差。
これで **`V(x) + V(鏡像 x) = 1` が厳密に成立**します（初期化時 1.2e-07、学習後 1.2e-07）。
ゼロサムなので学習で覚えさせるのは容量の無駄で、しかもデータの薄い局面でこそ破れます。
副作用として**ミラーマッチはちょうど 0.500** を返し、これはテストになっています。

学習は勝敗そのものに対する BCE。**分割は決定点ではなく必ずゲーム単位**です
（1ゲームの13決定点は同じラベルの13コピーなので、決定点で分けると検証値が暗記を測る）。

40.6 万パラメータ、第0世代 140,593 決定点で 1 epoch 1.5 秒（RTX 5070）。

### 結果（第0世代 10,852 ゲーム、ゲーム単位で 15% を検証に）

| | AUC | log loss | Brier |
|---|---|---|---|
| **学習した価値関数** | 0.9073 | **0.3664** | **0.1134** |
| hp-share プロキシ | 0.9093 | 0.4735 | 0.1546 |
| 常に 0.679 と答える | -- | 0.6273 | 0.2178 |

**校正では大差で勝ち、順序付けでは互角**です。これは正直に書いておきます。

信頼度曲線はほぼ対角線に乗ります（プロキシは乗りません）:

```
学習した価値関数                    hp-share プロキシ
予測 0.022 → 実際  5.8%            予測 0.203 → 実際  5.6%
     0.550 →      54.4%                 0.481 →      56.7%
     0.927 →      85.2%                 0.566 →      86.1%
     0.999 →      99.7%                 0.740 →      97.7%
```

ターン別（`--min-turn-rows 200`）:

| ターン | model AUC | proxy AUC | model 平均 | proxy 平均 | 実際 |
|---|---|---|---|---|---|
| 1 | 0.767 | 0.780 | 0.692 | 0.511 | 72.5% |
| 3 | 0.869 | 0.867 | 0.745 | 0.550 | 73.3% |
| 5 | 0.909 | 0.913 | 0.736 | 0.598 | 70.7% |
| 9 | 0.951 | 0.952 | 0.633 | 0.578 | 61.1% |
| 13 | 0.951 | 0.961 | 0.583 | 0.550 | 57.6% |

序盤のレベル（プロキシ 0.511 に対し真値 72.5%）は**直りました**。
序盤の順序付け（0.767 対 0.780）は**まだプロキシに負けています**。
つまり前回見つけた「序盤の余地」は、その大半が**校正の余地**でした。

交代ノードだけは順序付けでも勝っています（0.8821 対 0.8657）。

### 学習曲線 — 飽和していない（`--curve`）

「順序付けが伸びなかったのは構造の限界か、データ不足か」は逆の結論になるので測りました。
学習**ゲーム**数を変え、検証ゲームは固定:

| 学習ゲーム | 決定点 | AUC | log loss | turn-1 AUC |
|---|---|---|---|---|
| 576 | 7,309 | 0.7974 | 0.5066 | 0.6872 |
| 1,153 | 14,554 | 0.8604 | 0.4923 | 0.7106 |
| 2,306 | 29,534 | 0.8766 | 0.4302 | 0.6959 |
| 4,612 | 59,525 | 0.8903 | 0.3936 | 0.7325 |
| **9,224** | 119,368 | **0.9162** | **0.3409** | **0.7648** |
| プロキシ | -- | 0.9093 | 0.4735 | 0.7798 |

倍にするごとに AUC が +0.026、turn-1 AUC が +0.03 前後で伸び続けています。
**データ量がレバーであり、モデルを大きくする話ではありません。**
（分数は決定点ではなく**ゲーム**単位。決定点を間引くと残りが互いに近似重複なので、
曲線が間違った理由で平らになる）

なお第0世代のデータには上で見つけた欠陥がそのまま入っています
（アーキタイプのみのプール、8x8 の探索、攻撃技のない相手 2.3%）。
第1世代は **16x16 / `--opponents mix` / 攻撃技の制約あり**で生成中です。

## 将来の前提変更に対する見通し

### チームシートが無い場合（相手の6匹だけ分かる）

隠れ情報が「SP 配分 6 次元」から「セット全体」に広がります。壊れる場所:

| 層 | 今の前提 | 必要な変更 |
|---|---|---|
| `setup.py` | 相手の性格・技・道具・特性は既知として要求 | すべて省略可にし、信念が埋める |
| `belief.py` | パーティクル = 配分のみ（性格で条件付け） | パーティクル = セット全体 |
| `narrow.py` | 相手の合法手は既知の技から列挙 | 相手の**行動集合自体がタイプ依存**になる |
| `equilibrium.py` | — | **すでに対応済み** |

均衡層が既に対応しているのが大きい。`solve_bayesian` は**クラスごとに列数が違って
よい**ので、「タイプごとに別の行列を渡す」だけで、技が非公開でも同じ LP で解けます
（観測頻度の周辺分布だけが定義できなくなり、それは結果が `None` で申告する）。

本当の障害はデータ側です。Smogon chaos は特性・道具・技は**周辺分布**しか持たず、
セットの同時分布を持ちません（同時分布があるのは (性格, SP) だけ）。
「こだわりハチマキ型は配分が違う」という相関が事前分布から出てこないので、独立と
仮定すると実在しないセットを大量に生成します。ここは別のデータ源
（リプレイからのセット復元など）が必要で、独立仮定で誤魔化すと出力が作り話になります。

加えて、**選出フェーズが射程に入る**（現在スコープ外）。6匹から4匹の選出は、
相手のセットが分からない状態での意思決定なので、上のベイズ型定式化と同じ形になります。

### HP が % しか見えないことの帰結

`hpdisplay.py` が表示ルールを持ち、CLI は帯を同時クラスの一因子として列挙します
（帯の中は等確率。区別する情報がないためで、出力に明記）。M2 に向けての要点:

- **% の変化そのものが最大 HP の情報になる。**「78% → 41% になった」は与えたダメージと
  合わせて maxhp を絞り込む。逆算は HP 空間ではなく**パーセント空間**で行う必要がある。
- ある配分の maxhp では観測された % が**そもそも出せない**ことがある。
  `hpdisplay.band` はそれを例外にする（クランプしない）。そのままパーティクルの棄却に使える。

## 第2世代は第1世代より強いのか（実測 +4.5 ポイント）

**世代間は検証 AUC で比較できません。** 世代ごとに指し方が変わる＝生成される局面の分布が
変わるので、AUC が上がっても「判定しやすい局面を作っただけ」かもしれない。交絡しないのは
**直接対戦**だけです（`tools/generation_match.py`）。

葉が違えば行列が2つになるので、両者は共通のゲームを解くのをやめ、**それぞれが自分の行列から
自分の側の戦略を取る別のエージェント**になります。エージェント同士の対戦とはそういうものです。

| 席 | games | gen2 勝率 | 95%（Wilson） |
|---|---|---|---|
| gen2 = side 0 | 713 | 66.6% | [63.1, 70.0] |
| gen2 = side 1 | 724 | 42.4% | [38.9, 46.0] |
| **合計** | **1,437** | **54.4%** | **[51.8, 57.0]** |

席差 24 ポイントは**席の有利ではありません**。side 0 は常に自陣、side 1 は常に大会チームなので、
入れ替えているのは「どちらの世代がどの席に座るか」だけ。自陣の勝率を R、新世代の上積みを a とすると

```
席A: 自陣+gen2 vs 大会+gen1 → R + a
席B: 自陣+gen1 vs 大会+gen2 → (1 - R) + a
平均                        → 0.5 + a
```

なので**両席の平均が a の推定量**で、差から R が復元できます。

→ **R = 62.1%、a = +4.5 ポイント。** そして R は独立測定の自陣 vs 大会（13,395 ゲームで
60.9%）とほぼ一致していて、これは**実験構成そのものの検算**になっています。

+4.5pt は「効くが小さい」。価値関数がプロキシに対して AUC +0.012 / log loss -0.11 だった差が
勝率に化けた大きさとしては順当で、**深さ1では葉の質が効く範囲に限りがある**ことも意味します
（M4 が必要な理由のひとつ）。

なお第2世代の価値は勝率だけではありません。葉が勝率になったので**各ノードの均衡値が勝率**に
なり、選出リゾルバの数字が正当化されます。

## 学習データの範囲と、その先（汎用 AI への分岐）

第1世代 13,395 ゲームの構成:

| | |
|---|---|
| 自陣の4匹 | **15 通り**（1つの6匹から） |
| 相手の4匹 | **1,622 通り**（394 の6匹から） |
| 相手側に登場した種族 | 82 |
| 1回しか出ていない相手の4匹 | 265 |

**相手は環境全体を見ていますが、自陣は固定**です。これは意図的な割り切りで、
「あなたのチームの検討ツール」という目的に対して容量とデータを全部そこに使う設計
（チーム条件付き価値関数）。コストは3つ:

1. チームを変えたら再学習が必要（レギュレーション変更と同じ扱い）
2. **大会チーム同士の対戦は分布外** — 訓練データに「自陣以外 vs 自陣以外」が1件もない
3. 自陣側は選出集合が 15 通り止まり（先発の違いは見ている）

架構上は自陣が side 1 に来ても扱えます（`head([我々,相手]) - head([相手,我々])` なので
自陣のベクトルは学習中に両方の引数位置に現れる）。問題は**ペアの分布**であって側ではありません。

→ **将来の分岐**: field × field を混ぜれば汎用の価値関数になり、任意のチーム同士を評価できる
「最強ポケモン AI」の方向。自陣の精度は薄まるので、混ぜる前に**分布外の劣化量を測る**
（大会チーム同士のゲームを少数生成して実際の勝敗でラベルし、AUC / log loss を比較する）のが
判断材料になります。当面は自陣固定。

## この機械での並列度（実測）

生成が唯一のボトルネックなので（11 コア時間 対 学習 11 秒）、ワーカー数は測る対象です。
8 物理コア / 16 スレッドで、**16 スレッドは 16 コア分のスループットにはなりません** —
純 Python の仕事では HT の上積みは 20〜30% 程度なので、CPU カウンタが 98.5% でも
「飽和」ではなく「互いに奪い合っている」だけのことがあります。最大化すべきは
**games/min であって使用率ではありません**（`tools/bench_scaling.py`）。

| | 1プロセスあたり | 備考 |
|---|---|---|
| hp-share 葉 | 2.61 s/game | 第1世代 |
| 価値関数 葉 / CUDA | 3.78 s/game | 1プロセス約 1 GB の CUDA コンテキスト |
| 価値関数 葉 / CPU | 4.09 s/game | **8% 遅いだけ**。GPU 制約が消える |

### ワーカー数（`tools/bench_scaling.py`、価値関数の葉 / CPU）

| workers | games/min | 1ワーカーあたり | 対 4ワーカー |
|---|---|---|---|
| 4 | 48.0 | 12.0 | 1.00x |
| 8 | 83.3 | 10.4 | 0.87x |
| 10 | 97.1 | 9.7 | 0.81x |
| 12 | 104.7 | 8.7 | 0.73x |
| **14** | **112.3** | 8.0 | 0.67x |
| 16 | 80.2 | 5.0 | **0.42x** |

**16 で崩壊します**（112 → 80）。16 論理スレッドに 16 ワーカーを載せると OS 自身や
他のプロセスに残るコアがなくなって全体が破綻するので、**「論理コア数＝ワーカー数」は誤り**。
14 が最適で、そこでも 1ワーカーあたりは 0.67x — 8 物理コアなので HT の上積みは
4→14 で 2.3 倍（理想の 3.5 倍ではない）。

**CPU 推論のほうが総スループットで勝ちます。** CUDA だと 12 GB のカードで 9 プロセスが
上限ですが、CPU なら CPU の並列度を使い切れます。forward は1葉あたりコストの 3% しか
ないので、GPU に乗せる意味がほとんどありません。

**`torch.set_num_threads(1)` が必須です。** torch は既定でプロセスごとにマシンサイズの
スレッドプールを作るので、14 プロセス × 8 スレッドが 8 コアに乗って
**並列のほうが遅くなります**。`--torch-threads`（既定 1）で、単一プロセス実行のときだけ上げる。
