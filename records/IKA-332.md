## 1. 入れたもの

### 1.1 エンジンの口（`deepen.Step`・`progress=`）

* `deepen_root(..., progress=None)`・`deepen_belief(..., progress=None)`: コールバックを渡すと、`Step` を
  深さ 1 の答えで 1 回（`start`）、歩ごとに 1 回（`refine`・`refused`・`widen`）、終わりに 1 回（`done`、返す答えそのもの）呼ぶ
* `Step` は数（予算・使った量・セル・埋め・精緻化・深化したセル・段・読めなかったセル・オラクルの探り・入れ・抜き、その歩のセルと段）と、**根への生の参照**。
  コールバックはその場で読み、書かない。直列化はしない（調整役の指示）
* 深化しないノードも同じ形で報告する: `announce_depth1`（開いたノード）・`announce_belief_depth1`（裏の残るベイズ型のノード）が `start` と `done` を出す。
  `search(progress=)`・`belief_solve(progress=)` がそれを呼ぶ（深さ 1 の全行列だけ。深さ 2 と `solve_sparsely` では止まる）
* **既定では何も変わらない**: コールバックが無ければ、足した行はすべて `if announce is not None` / `if progress is not None` の比較だけ。
  あっても、探索は同じ仕事を同じ順でする（読むだけ）。数えの時計の局は、コールバックの有無でバイト一致（§3）

### 1.2 読み取り（`progress.Reader`・`progress.Recorder`・`progress.Snapshot`）

`Reader` が `Step` を AI の側から読んで `Snapshot`（numpy の配列の写しと Python の値）にする:

* AI の混合（メニューの順、f64）と各手の期待値の損、ラベル（`describe` の日本語、対象は名前で）
* 値: 側 0 の単位（記録の `searchValue` と同じ数）と AI から見た値
* 相手の混合: 裏が見えないときは**裏の決定化ごと**（信念の重み、その裏に置く種族、その裏なら相手がどう打つか、その裏での値）と、重みでの平均
* 収束の目安 `read`: 均衡の組の確率（x_i·y_j、裏が見えないなら w_k·x_i·y_kj）のうち、葉より深く読んだセルの分。LP の双対ギャップも添える。
  メニューの中の NashConv は LP の答えなので 0 で、目安にならない。値と混合の歩ごとの動きは画面が折れ線で見せる
* 読み筋（§1.3）

`Recorder` はコールバックの本体: 最初（`start`）と最後（`done`）は必ず、その間は `interval_ms`（既定 100 ms）より詰めては読まない
（読むのに少し費用がかかるので。10 回/秒で見るには十分）。呼ばれた回数（`calls`）と送った回数（`sent`）を数える。

### 1.3 読み筋の形（確率の付いた木）

```
  根（今のターン）
  ├─ 組: p = x_i·y_j（裏が見えないなら w_k·x_i·y_kj と裏の決定化 k）  AI の手 × あなたの手  → 値（根の値との差）  [読んだ | 葉の値 | 読めない（葉の値）]
  │   ├─ 偶然の枝: 重み（ターンの結果の上位 sub_branches を正規化したもの）  何が変わったか  → 値（組の値との差）
  │   │     何が変わったか = 両側の HP の変化（最大 HP に対する %）・ひんし・状態異常・登場。決着した枝は「決着（葉の値）」
  │   │   └─ 次のターン: そのノードの値、AI の混合の上位 3 手、あなたの混合の上位 3 手
  │   │       ├─ 組 …（同じ形で、深化で読んだ深さまで）
  │   │       └─ 組 … 葉の値
  │   └─ 偶然の枝 …
  └─ 組 … 葉の値
```

* 根は重い組を 4 つ（`PV_PAIRS`）、下のノードは 2 つ（`PV_PAIRS_BELOW`）、6 段（`PV_LEVELS`）まで。確率 0.5% 未満の組は出さない。6 段より下を読んだノードは「この先も読んだが省略」
* すべて深化の木（`_Node.children`）にあるものを読むだけ。新しくターンを解いたり葉を呼んだりはしない。
  偶然の枝の説明は、木が持っている枝の局面と親の局面の差から作る（急所・命中・乱数の名前は port が返さないので、結果で書く）
* 値はすべて AI から見た値。画面では「+0.012」のように親との差を色で付ける

### 1.4 対局の器（`humanplay` の `listener`）

`humanplay.play(..., listener=, interval_ms=)` と `HumanGame` に口を足した。`listener(kind, payload)` に Python のオブジェクトを渡す:

```
  sheets   選出の前: 両方の 6 体（種族・持ち物・特性・性格・SP・技、日本語）、席、AI の葉、1 手の秒・時計・コア
  select   人に選出を聞く前
  board    各決定の前と終局: 人から見える盤面（自分は実数の HP と PP、相手は表示の %、見ていない裏は数だけ、場・天候・壁）
  think    AI が move を考え始めた: 予算の配分（MovePlan）、裏の決定化の数、メニューにかかった ms
  step     progress.Snapshot（上）
  answer   AI の答え: 混合・値・秒・深化の報告・呼ばれた/送った数。引いた手はまだ出さない（人が選ぶ前に見えてしまうので）
  prompt   人に聞く: 合法手の文字列と、各手の 1 体ずつの選択肢とラベル
  turn     ターンの結果: AI の手とあなたの手（ラベル）、メニューの外の手だったか
  end      終局: 勝敗・理由・ターン数
```

`listener` が無ければ前と同じ（`if self.listener is not None` の比較だけ）。

### 1.5 画面（`liveview` と `web/live.html`）

* **サーバ**は標準ライブラリだけ（新しい依存なし）: `http.server` がページを出し、`/ws` を WebSocket（RFC 6455 のうちブラウザが使う部分:
  分けないフレーム、テキストとバイナリ、ping と close）に切り替える。`LiveServer.listener` を `humanplay.play` に渡す
* 後から繋いだページには、それまでの局を送る（出来事すべてと、終わった各手の最後の歩、考え中の手の歩すべて）
* **人の入力**: ページはテキストのフレーム `{"line": "..."}` で答えを送り、`WebPerson` が台本の行と同じ形で読む（読めない行は画面に返して聞き直す）。
  選出は 4 体を順に押す（先の 2 体が先発）。行動は 1 体目・2 体目の順に選び、2 体目の選択肢は 1 体目と合う合法手だけに絞る
* **ページ**（1 枚の HTML と JS、外部の読み込みなし）:
  * 盤面: 両側の HP の棒・状態・能力変化・持ち物・場、AI の持ち時間
  * 読みの量: 経過・歩・読んだセル・深化したセル・段・埋め・精緻化・幅（AI × あなた）・台の大きさ・深く読んだ重み・裏の決定化の数・入れ/抜き、予算の配分
  * 値の推移: 考え始めてからの ms を横軸にした折れ線（AI から見た値）
  * AI の混合戦略: 手ごとの確率の棒と期待値の損（使わない手は損の小さい 3 手だけ）
  * あなたの手の読み: 相手の混合の棒（裏の決定化の重みで平均）と、裏の決定化ごとの表（信念の重み・その裏に置く種族・値・その裏ならの上位 3 手）
  * 読み筋: `<details>` の木。開いた枝は更新しても開いたまま
  * 「自分の手を入れるまで読みを隠す」: 読みには AI の裏の種族（交代先）が出るので、公平に打つなら入れる。既定は見せる（眺めるのが段 1 の目的）
  * 見出しに「最善手 1 つと評価値」は出さない（cli.py と同じ方針）
* 起動: `tools/play_human.py --view`（`--person web` で画面から打つ、`--live-out` で記録）。`tools/live_view.py` が記録を画面で再生する・JSON 行にして出す

### 1.6 送る形と記録の形（選んだ形と理由）

三つの段で形を変えた。

| 段 | 形 | 理由 |
|---|---|---|
| エンジン → 器（同じ過程） | コールバックに `Step`（数と根への参照）。`Reader` が numpy の配列の写しと Python の値にする | 直列化の費用を払わない。読むのは送るものだけ（`interval_ms` で間引いた歩だけ） |
| 器 → 画面 | WebSocket のバイナリのフレーム（`Wire`）。歩は固定の並びの little-endian の数値。文字列は表にして初出の 1 回だけ（STRINGS フレーム）、以後は u32 の番号。1 ターンに 1 回ほどの出来事（盤面・選出・入力の問い・結果）は小さな JSON のテキスト | 大きいのは歩の流れ（最大 10 回/秒 × 手ごとの秒）。手のラベルは 1 本 30〜60 字で、毎回送ると歩の大半になる。低頻度の出来事は 1 局で数十回なので読みやすさを取った |
| 記録 | 同じフレームを、長さ（u32）と開始からの秒（f64）を付けて並べたファイル（`FileSink`） | 画面が読むものそのものなので、再生（`Replay`）も解析（`Decoder`、JSON 行への書き出し）も同じ読み手で済む |

歩のフレームの並び（little-endian）:

```
  u8 3 | u8 kind | u16 段 | u32 決定 | u32 ターン | u32 歩 | f32 ms | u32 予算 | f32 使った量 | u32 セル | u32 埋め | u32 精緻化
  | u32 深化したセル | u32 読めない | u32 探り | u16 入れ | u16 抜き | f64 値（側 0） | f64 値（AI） | f32 深く読んだ重み | f32 双対ギャップ
  | u16 AI の手の数 n | u16 相手の手の数 m | u16 裏の決定化の数 K
  | u32[n] ラベル | f64[n] 確率 | f32[n] 損 | u32[m] ラベル | f32[m] 確率（平均） | f32[m] 損（平均）
  | K × (f32 重み | f32 値 | u32 裏の種族の名前 | u32 裏の種族の id | f32[m] 確率)   名前と id は " ／ " で区切った 1 本の文字列
  | 読み筋: u8 組の数, 組 = (u32 AI の手 | u32 相手の手 | i16 裏の決定化 | u8 読み | f32 p | f32 値 | u8 枝の数, 枝…)
            枝 = (f32 重み | f32 値 | u32 説明 | u8 旗: 1 決着・2 ノードあり・4 省略あり [| f32 値 | u8 n, (u32, f32)… | u8 m, (u32, f32)… | 組の並び])
```

AI の確率だけ f64 にした: 最後の歩が記録の方策とビットで一致することを、画面側の数でも確かめられるように（§4.2 のテスト）。

### 1.7 画面へ送るデータの形（デザイナー向けの表）

ページは 4 つのファイルに分けた（`src/pokeuraou/web/`）。**データの半分**と**見た目の半分**が別なので、デザインは上の 3 つを差し替えればよい。
9/26 にデザイナー（別の担当、`C:/tmp/ika332d/design/`）の 3 つに差し替えた（§1.8）。

```
  live.html      骨組み（要素の id、画像の取得元の meta）。             デザイナーの版
  live.css       見た目（:root の CSS 変数と配置、ライト/ダーク）。     デザイナーの版
  live-view.js   描く部分。                                              デザイナーの版に、下のデータの形への合わせを足した
  live-data.js   データの部分（socket・フレームの読み・文字列の表）。  そのまま使う。描かない
```

`live-data.js` の口: `LiveData.connect({onEvent(e), onStep(s), onOpen(), onClose()})` と `LiveData.send(line)`（人の答え）。
`onEvent` には下の出来事がそのまま（JS のオブジェクト）、`onStep` には歩（文字列の番号はもう文字列に戻してある）が来る。

**出来事（`onEvent(e)`、`e.type` で分ける）**

| `classes` | {weight, value, bench, benchIds, p}[] | 人の裏の決定化ごと: 信念の重み、その裏での値、裏に置く種族（`bench` 日本語の str[]、`benchIds` dex の id の str[]。見ていない裏が無ければ []）、その裏なら人がどう打つか（`theirs` の順の確率）。裏が尽きていれば [] |

| 　pair | {ours, theirs, oursSlots, theirsSlots, klass, read, p, value, branches} | AI の手・人の手（ラベルと枠ごと）、裏の決定化の番号（`classes` の添字、-1 はなし）、"deep"/"leaf"/"refused"、組の確率、組の値、偶然の枝 |

## 4. テスト（`tests/test_liveview.py`、8 件。port を使う。torch・CUDA・data は要らないので CI の skip の予算は変えない）

プールは test_humanplay と同じ M-B のロスタの 2 変種、hp-share を port で採点。ローカルで 8 件 約 25 秒（1 コア）。

* **口を付けても局は変わらない**: 数えの時計で、`listener` ありと無しの局の行が同じバイト。陽性対照: その局でコールバックが深化の歩（`refine`）を受け、ベイズ型の根（裏の決定化あり）を読んだ
* **各手の最後の歩が答え**: 手ごとに最初が `start`・最後が `done`。最後の歩の AI の混合が `answer` の方策と記録の `foePolicy` にビット一致、`value0` が記録の `searchValue` に一致、AI から見た値は 1 − 側 0 の値
* **深化した `search` はコールバックの有無で同じ配列**（方策・損・行列・`Deepened`）。呼ばれた回数 = 深化したセル + 読めなかったセル + 2。
  側 1 から読むと列の戦略が AI の混合になる（行と列の戦略が違う局面で確かめる。同じだと入れ替えが見えないので、列のメニューを逆順にした）。
  読み筋の「読んだ」組は木の子と一致し、偶然の枝の重みは木の重みと 1 つずつ一致。2 枝以上ある組がある（陽性対照）。深化しないときは `start` と `done` だけで、組はすべて「葉の値」。深さ 2 では止まる
* **間引き**: 間隔を大きくすると `start` と `done` の 2 つだけ送り、呼ばれた回数は数える
* **読み筋**: 組は重い順、確率の和 ≤ 1、読んだ組の枝の重みの和は 1、枝の説明がある、ノードに開く枝がある
* **フレーム**: 局の出来事と歩をすべて `Wire` で詰めて `Decoder` で読み戻す。AI の混合は f64 でビット一致、ラベル・数・読み筋の形が一致、文字列は各 1 回
* **記録のファイル**: 長さと秒の付いたフレームを読み戻す
* **サーバ**: ページと `live-data.js` を出す。WebSocket の台本の人（テストの中の最小のクライアント）が、選出の読めない行（「1 1 2 3」）で `error` を受け、正しい行で進み、各問いに最初の合法手で答えて終局まで打つ。
  `done` の歩の混合が `answer` と一致。**その人の答えを台本にして打った局が同じバイト**
* **後から繋いだページ**: 終わった局の出来事と、各手の最後の歩（`done`）だけを受ける

**陽性対照（故障注入、`C:/tmp/ika332/mutate.py`、戻したことをハッシュで確認）: 7 通りの壊し方がそれぞれ落ちる** ——
`listener` があると局の乱数を 1 つ引く、最後の歩を出さない、側 1 が行の戦略を読む、読み筋の枝を 1 本に切る、ベイズ型の根の値を側 1 で反転しない、
混合を f32 で詰める、後から繋いだページに経緯を送らない。最初の版では「側 1 が行の戦略を読む」と「枝を切る」が落ちなかった
（テストの局面で両側が同じ添字の純粋戦略だった・読んだ組がどれも枝 1 本だった）ので、上の 2 つの確かめ方を足した。
