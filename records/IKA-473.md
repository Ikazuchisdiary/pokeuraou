# IKA-473: 推論サーバとの往復と待ちを減らす

課題: Notion の Issues（ID IKA-473）。ブランチ `ika473-served`。9d68df3 の上で作って測り、そのあと origin/master d39ca78（IKA-469・470 まで）の上に rebase した（§3.5）。計測の道具と生の出力は `C:/tmp/ika473/` に置き、コミットしていない。

## 0. 要点

* 21 ワーカーの生成で、ワーカー 1 つの 1 局の実時間 610 ms のうち、推論サーバの答えを待つ時間は 117 ms（19%）だった。内訳は葉が 84 ms（1 局 25.8 回）、Q が 33 ms（1 局 8.9 回）である（§2）。
* 葉の依頼の 58% は 1〜3 行だった。小さな依頼は 21 ワーカーの負荷の下で行の数によらず 1 回 2.7 ms ほど待つ（§2.2）。小さな依頼の大半は交代の局面で、裏の決定化 1 つごとに 1 回ずつ送っていた。
* 交代の局面の葉を、サーバの graph の桶が変わらない範囲で 1 つの依頼に束ねた（§3.1）。1 局の葉の依頼は 25.8 回から 12.6 回に減った。局は変わらない。
* 推論サーバの Q を CUDA graph で回すようにした（§3.2）。Q の答えは eager の答えとビット一致する。サーバの中で 2,077,517 セル（約 208 万セル）を比べ、違うセルは 0 だった。graph の道が失敗したときは eager の道で答える。
* 2 つを合わせた exe と master の exe を、生成の形の ABBA で 2 回比べた（§4）。局/分は +6.7% と +4.3%、1 局の CPU は −3.3% と −2.9% だった。2 回の ABBA の 16 回すべてで、新しい exe の 1 局の CPU は master の exe の 8 回のどれよりも低かった。局は 8,000 局でビット一致した。
* 21 ワーカーの生成で、この過程の木が使う論理コアは 11.4〜13.5 だった。各回の前に測った機械の負荷は 16.5〜58.6% だった（§2.3）。待つ間にほかの仕事を進めても、CPU が空かなければ局/分は上がらない。ワーカーを 28 にした ABBA は、局/分が −2.8% で、上がらなかった（§5）。
* キューのサーバの backlog が 5 で、28 ワーカーが同時に接続すると 1 つが拒まれて生成が止まった。backlog を 256 にした（§3.3）。

## 3. 変えたもの

### 3.1 交代の局面の葉を束ねる（局は変わらない）

`replacephase.rs` の交代の局面は裏の決定化 1 つごとに葉を符号化して 1 回ずつサーバに送っていた。この変更で、すべての決定化を先に符号化し、葉ごとに `replacenode::score_jobs` で送る。

* 続く決定化のどれもが同じ graph の桶に入り、行の和もその桶に入る間は、それらを 1 つの依頼にまとめる（`packs`）。サーバは依頼を桶の graph で回す。行の値はその行の入力と graph だけで決まるので、各決定化の値は前と同じになる。実際にまとまるのは 64 行の桶（1〜64 行）だけである。
* 1 局の葉の依頼は 25.8 回から 12.6 回に減った（陽性対照、m21 と p21 の計数）。
* 一致: 6 ワーカー・300 局（種 47331）で、master の exe と束ねた exe の局が 300/300 一致した（決定 3,619/3,619）。対照として種 47332 の局とは 0/300 だった。
* 桶の判定の対照: 推論サーバに同じ 10 行を、単独で（64 行の桶）と、もっと多い行の依頼の先頭に置いて送り、値をビットで比べた（`C:/tmp/ika473/probe/test_zz_bucket_probe.py`、コミットしていない）。

| 依頼の行（10 行を含む） | 網 1 本の arm で 10 行中ビット一致 | 網 2 本の arm で 10 行中ビット一致 |
|---|---|---|
| 64（同じ桶） | 10 | 10 |
| 65 | 6 | 4 |
| 128 | 6 | 4 |
| 129 | 5 | 6 |
| 1,024 | 7 | 9 |
| 1,025 | 3 | 7 |
| 4,096 | 3 | 3 |

* 桶が変わると値の最後の桁が変わる（最大差 2.4e-7）。同じ桶の中では、ほかの行があっても値は変わらない。
* 局での対照として、桶の判定を外して 4,096 行まで束ねる exe（計数の build の `POKEURAOU_PACK_IGNORE_BUCKET`）で 300 局を打った。局は 300/300 一致し、葉の依頼の数も 3,581 回で、判定のある exe と同じだった。この 300 局では 1 つの交代の局面の葉の行の和が 64 を超えなかったと読む（依頼の数が同じだったことからの読みで、行の和そのものは数えていない）。このため、桶の判定が局を守っていることは局では示せていない。
* `POKEURAOU_REPLACEMENT_PACK=0` で、前のように決定化 1 つごとに送る。`1` か未設定で束ね、ほかの値では局面が fault で止まる。このフラグは意図して既定の build に残した。CI のテストが既定の build で使い、`0` にしても依頼が増えるだけで局は変わらないからである。`tests/test_replacement_pack.py` は代役のサーバで 12 局を両方で打ち、記録が一致すること、束ねた方の依頼が少なく行の和が同じことを確かめる。

### 3.2 Q を CUDA graph で回す（局は変わらない）

Rust の推論サーバの Q は 1 局面ごとに約 55 個の kernel を eager で起動していた。この変更で、Q の網を 3 つに分けて graph にした（`infer_gpu.rs` の `QSlot::item_graphs`）。

* 局面の配列を決まった場所（`q_fixed`）にコピーし、胴の graph を回す。胴の graph は網ごとに 1 本である。
* 各側の行動と対の射影は、（網、側、候補の数）ごとに graph を持つ。まだ graph の無い候補の数が来たら、1 回 eager で回してから取り込む。1 スロットの側の graph は 256 本まで（`Q_SIDE_GRAPHS`）で、それを超えた候補の数は eager で回す。
* 両側の行列は eager の kernel 1 個のままにした。
* 取り込みが失敗した胴や側は、その形の graph をやめ、以後は eager で回す（失敗の数は `q_stats` の `captureFailed`、初めの 5 回はサーバのログに書く）。取り込みのたびに eager と取り込みをやり直すことはない。
* それ以外で graph の道が失敗した依頼は、eager の道で答え直す。答えには `note` を付け、サーバの報告の行に数を出し、初めの 5 回はサーバのログに書く。port の側にも Python の側にも、`note` を読む所は無い。
* `POKEURAOU_Q_GRAPHS` は既定の build にも残した。`0` は build し直さずに eager の道へ戻すため、`check` はカードの上で 2 つの道が同じ答えを出すことを見るためである。未設定か `1` で graph、ほかの値ではサーバが起動のときに止まる。
* 依頼 `q_stats` は比べたセル・違うセル・eager で答え直した数・取り込んだ graph の数を返す。

| 確かめ | 結果 |
|---|---|
| `check` で比べたセル（ワーカー 1 つ・40 局、qchk1） | 2,077,517 セル、違うセル 0 |
| `check` で比べたセル（6 ワーカー・300 局、rcC。サーバ 0 と 1 の最後の報告の行の値） | 7,262,212 と 8,242,497 セル、違うセル 0 |
| 対照 1: `check` のまま、graph の答えの最初のセルに 1 ULP を足す（`POKEURAOU_Q_GRAPH_FAULT=ulp`、qchk2） | 2,044,078 セル中 320 セルが違う。`check` は eager の答えを返すので、局は 40/40 一致する |
| 対照 1 の局: graph の道のまま 1 ULP を足す（qgf、rcU） | 40 局中 4 局、300 局中 28 局が master と違う |
| 対照 2: 側の graph を候補 1 つ少なく取り込む（`POKEURAOU_Q_GRAPH_FAULT=shape`）。`check` で（rcS。サーバ 0 と 1 の最後の報告の行の値） | 7,345,167 と 7,860,966 セル中、235,594 と 266,789 セルが違う（合わせて 502,383） |

| graph の道（既定）の局と master の局（ワーカー 1 つ・40 局、種 47301） | 40/40 一致 |
| `tests/test_rust_inference_server.py`・`tests/test_q_rank.py`（CUDA、Q の値を torch と比べる） | すべて通った（skip 0） |
| `test_the_q_graphs_answer_what_the_eager_road_answers`（CUDA、`check` で違うセル 0・取り込み 1 本以上） | 通った。対照 2 の故障を入れた exe では `differ` 5,894 で落ちた |

* ワーカー 1 つでは Q の 1 依頼の GPU の時間は graph でも 1.16 ms で、eager の 1.18〜1.21 ms とほぼ同じだった。21 ワーカーの ABBA の B の窓では 1.08〜1.63 ms で、master（m21）の 2.52〜2.64 ms より短い。窓が違うので、この差は参考にとどめる。

| ax2B2 | 28 | 1,819.5 | 0.380 | 11.5 |

* 平均は 21 ワーカーが 2,006.0 局/分・0.3757 秒、28 ワーカーが 1,948.9 局/分・0.3792 秒だった（−2.8%、+0.9%）。ワーカーを増やしても局/分は上がらなかったので、既定の 21 は変えていない。
* 計測の前の負荷は 20.3〜40.5% だった。
* 同じ組の前の試み（aw、`find.exe` を止める前）は、aw2B2 がキューの backlog で止まったので使わない（§3.3）。

## 6. 入れなかったもの

| 案 | 理由 |
|---|---|
| 推論サーバを 1 つにする・スロットを 8 にする | 下見（8 回、1 回ずつ）は、1 回目がこの担当の build と重なり、ほかの回も外の負荷が 25〜45% あったので、比べに使えなかった。ABBA はしていない |
| サーバの待ちを spin や yield にする | ワーカー 1 つの 40 局で、葉の 1 依頼の GPU の時間は blocking sync が 1.62 と 1.18 ms、spin が 1.52 ms、yield が 1.54 ms で、差が揺れの中だった。spin と yield はサーバの CPU を使い、21 ワーカーでは CPU を取り合うので入れていない |
| 決定の葉を、fill を進めながら分けて送る（パイプライン化） | 待つ間に fill を進めても、CPU が空かなければ局/分は上がらない（§5）。分けると依頼の桶が変わり、局も変わる |
| GEMM を TF32 にする | 値が変わり、局も変わる。大きな依頼の GPU の時間は減るはずだが、測っていない |

## 7. 確かめていないこと

* §2.1 の「実時間から CPU と待ちを引いた残りは CPU の順番の待ち」という読み。
* 外の負荷の無い機械での ABBA。使った窓では、各回の前に測った負荷が 16.5〜58.6% あった。
* GPU のメモリの増え方。`*-gpu.csv`（nvidia-smi、0.5 秒ごと、カード全体）で、各回の始めから最大までの増えた量は、A の 8 回が 2,531〜2,948 MiB（平均 2,685）、B の 8 回が 2,815〜3,345 MiB（平均 3,024）だった（§4 の ab と ac）。B の方が平均 340 MiB 多い。サーバ 2 つの合計で、ほかの過程の使う分も含む。graph の本数の上限（1 スロットあたり側の graph 256 本と胴 1 本）は、この計測の後に入れた。2,000 局より長い生成での増え方は確かめていない。
* 対戦評価（`match_queue.py --pool --served`）の速さ。局が変わらない変更なので、SPRT は回していない。
* 人と打つ道具・検討が使う `q_batch` の速さ。graph の道を通るが、測っていない。
