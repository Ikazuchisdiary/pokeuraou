# IKA-340: データ生成の記録に、使った Q のファイルと sha256 を書く

IKA-338 の別課題。M-C のデータ生成（`generate_queue.py --pool` → `selfplay.py --pool` →
`poolplay.generate_pool`）は、葉の順位付けを Q（既定は `data/models/q-mc0.pt`）で行うのに、
局の記録には Q が何も書かれていなかった。分かるのはワーカーのログの echo（`Q: q-mc0.pt (the q arm on …)`）だけ。
対戦評価の記録（`pool_match.py`）には `qModel`（ファイル名のリスト）があったが、中身の指紋は無かった。
同じ名前で学び直した Q（q-mc1 を q-mc0 の名前で置くなど）とは区別できない。

## 変えたこと

局の中身は変えない。足したのは記録の欄だけ。

* 記録の形は、対戦評価の記録の `qModel` に揃えた。どちらも最上位の欄で、次の 2 つ。
  * `"qModel": ["q-mc0.pt"]`: 今までと同じ `qrank.describe_installed` の形。名前付きの Q は `NAME=file`。
  * `"qModelSha256": ["3944d4ba…"]`: 各ファイルの sha256（全 64 桁）。`qModel` と同じ順。
  * Q で順位付けしない実行（`--rank-fill refs2`、葉の順位付けなし）では、どちらの欄も書かない。
* データ生成の記録では、この 2 欄を `pool` の後、`gameIndex` の前に置く。
  データ生成の記録は `provenance` を持たない（無いことが自己対戦の意味。`provenance.SELF_PLAY`）ので、
  `provenance` の塊は作らず、対戦評価と同じく最上位に置いた。
* 対戦評価の記録（`pool_match.py`）にも `qModelSha256` を足した（`qModel` はそのまま）。
* sha256 はファイルを持っている側で計算する。
  * 推論サーバの Q（`--q-arm`、データ生成の本番の経路）: サーバが読み込むとき（`load_q_arms`）に計算し、
    `describe_q` の返事に `sha256` として載せる。ワーカー（`RemoteQ.digests`）はそれを受け取る。
  * ワーカーが自分で読む Q（`LocalQ`）: 読み込むときに計算する。
  * 1 ファイル 1 回で、局の間には何もしない。

| ファイル | 変更 |
|---|---|
| `src/pokeuraou/qrank.py` | `file_sha256`、`record_fields(models)`（`qModel` と `qModelSha256` の dict、Q が無ければ空）、`LocalQ.digests`・`RemoteQ.digests`、`served_q` に `digests`、`load_q_arms` が sha256 を計算 |
| `src/pokeuraou/inference.py` | `describe_q` の返事に `sha256` を 1 つ足す（推論サーバの他の部分には触れていない） |
| `src/pokeuraou/poolplay.py` | `generate_pool(q_record=…)`: 各記録の `pool` の後に書く |
| `tools/selfplay.py` | `--pool` の `_install_q` が `record_fields` を返し、`generate_pool` に渡す |
| `tools/pool_match.py` | `_install_q` が `record_fields` を返し、記録に `**q_record`（`qModel` は今までと同じ値） |
| `tests/test_q_record.py` | 新規（下の 5 本） |
| `tests/test_shipped_rank_fill.py` | `FakeQ` に `digests` を足す（新しい経路が呼ぶため） |
| `tests/test_q_rank.py` | torch のテスト 1 本に、サーバとワーカーの sha256 がファイルの sha256 と一致する確認を足す |

`generate_queue.py` は変えていない（Q のパスはこれまでどおり推論サーバに渡り、ハッシュはサーバが計算する）。
IKA-363 が推論サーバの周りを触っているため、`inference.py` の変更は `describe_q` の返事への 1 行に留めた。

## 一致の確認（スモークテスト）

本番の形を小さくして回した。`generate_queue.py --served --servers 1 --workers 6 --games 12 --seed 7701 --limit 12
--value value-mc1.pt --q-model q-mc0.pt --pool regmc-matchupweb --hide-bench --max-worker-failures 0 -- --rank-leaf`。
master（A）とブランチ（B）を順に回し、選出 book は条件ごとに別の空のディレクトリにした。どちらも workers.json の失敗は 0。
B のワーカーのログは `Q: q-mc0.pt (the q arm on 127.0.0.1:…)` と `fill q-nocover` を出しており、Q の経路を通っている。

| 比較 | 局 | 一致 |
|---|---|---|
| A 対 B（`qModel`・`qModelSha256`・`engine`・`searchSeconds` を除く、gameIndex ごと） | 12 | 12 |
| 対照: A の局 i 対 局 i+1 | 11 組 | 0 |

* 違う欄は `engine`（ソースのハッシュ。コードが違うので当然）と `searchSeconds`（実時間）だけ。
* B の 12 局はすべて `qModel = ["q-mc0.pt"]`、`qModelSha256 = ["3944d4ba6e96cd67…"]`。後者は `data/models/q-mc0.pt` の sha256 と一致する。
* 記録を読む道具:
  * `encode_dataset.py`: A と B を gameIndex の順に 1 ファイルにまとめ、`--engine rust`・`--engine python` の両方で符号化した。
    16 の配列（130 行）は 4 通りすべてで一致し、meta の違いは `source_dir` と `engines`（ソースのハッシュ）だけ。
    port の `encode-games` は知らない欄を読み飛ばす（serde の既定）。
  * `queue_restart.py`: `gameIndex` を `json.loads` で読むだけで、欄が増えても影響しない（import と `--help` で確認）。
  * `agent_drift.py --check`・`port_gate_audit.py --check`・`port_coverage.py --check`・ruff は通る。
  * `sprt.py`・`luck.py` は対戦評価の記録を `"provenance":` から後ろで読む。`qModelSha256` は `write_game` の extra として
    `provenance` より前に入るので、その読み方は崩れない。

## 残したこと・別課題の候補

* `encode_dataset.py` の meta（npz の `meta_json`）に、学習データに入った Q（`qModelSha256` ごとの局数）を数えて出す。
  今は `engines` だけを数えている。世代をまたいで Q が混ざったとき、学習データの側で見える。
* 評価モデルも名前だけで記録されている（データ生成は `searchObjective: "value:value-mc1"`、対戦評価は `describe()` のファイル名）。
  同じ理由で sha256 を足す価値がある。Q と同じ `describe`/`digests` の形で足せる。
* `time_match.py`・`play_human.py` の `qModel` は、パスやファイル名だけのまま。揃えるなら `record_fields` を使う。
