# IKA-471: ターンの解決を速くする

課題: Notion の Issues（ID IKA-471）。ブランチ `ika471-resolve`。計測の道具の出力と exe は `C:/tmp/ika471/` に置き、コミットしていない。

## 0. 要点

* 標本採りの道具を作り直した。別のスレッドが主スレッドを止め、Windows の x64 の unwind 表（`RtlVirtualUnwind`）でスタックをたどる（feature `sampler`）。生成の形のワーカーでは主スレッドの標本の 41% が ntdll に当たった。そのうち推論サーバの待ちを除いた分は、ほとんどがヒープの関数だった（§1.3）。
* mimalloc は windows-gnu で起動処理が走っていなかった。起動処理は MSVC の `#pragma const_seg` で登録する TLS コールバックから呼ばれる。GCC はこの書き方を無視するので、mimalloc は「preloading」の状態のまま動いていた。この状態の mimalloc は呼ぶたびに環境変数を読み、ページを OS から直接取って返す（§2）。IKA-462 で mimalloc が生成を速くしなかった理由の候補だが、起動処理のない形とある形を ABBA で比べてはいない。`fill-bench` では、起動処理のない mimalloc でも前の allocator の 0.796 倍の時間で、起動処理を呼ぶとさらに 0.945 倍だった。
* `main` の先頭で `_mi_auto_process_init` を呼び、mimalloc を既定にした。2,000 局の ABBA（21 ワーカー、8 回）で、1 局の CPU が 0.3910 秒から 0.3257 秒（−16.7%）になり、局/分が 1,927.7 から 2,179.0（+13.0%）になった。局は 4,000 局すべてで前の exe と一致した（§3）。
* 局を変えない高速化をさらに 3 つ入れた（§4）。fill のターンだけを解き直すベンチ（`fill-bench`）での時間の比を下に示す。
  * 局面の複製で、変わらないリストを共有する（`Shared`）: 0.914 倍
  * fill の中で、同じ局面から同じ行動を解くのは 1 回にする（`fill_cache`）: 0.932 倍
  * 行動ごとのコピーを減らし、場の特性を inline で持つ: 0.987 倍
* 3 つをまとめて、mimalloc だけの exe と ABBA で比べた。1 局の CPU が 0.3213 秒から 0.3085 秒（−4.0%）になり、局/分が 2,533.4 から 2,640.8（+4.2%）になった。局は 4,000 局すべてで一致した（§5.1）。
* origin/master（d39ca78）の上に rebase した exe を、origin/master の exe と ABBA で比べた。1 局の CPU が 0.3103 秒から 0.2550 秒（−17.8%）になり、局/分が 2,640.2 から 3,053.3（+15.6%）になった。局は 4,000 局すべてで一致した。`fill-bench` では時間が 0.598 倍で、答えの hash が一致した（§5.2）。
* 規則の正しさは変えていない。`tools/diff_turn.py`（200 戦）の数字は、origin/master の exe とこのブランチの exe で同じだった（1,486 ターン中 1,409 が一致、乖離 5.182%）。
* ダメージ計算のメモ化は入れていない。同じ fill の中で入力が重なる呼びは 75% あったが、標本ではダメージ計算の自分の時間は 2.5〜3.2% だった。キー（Battler 2 体と場）を作って比べる費用は、計算と同じくらいになる（§6）。

## 1. 数え（課題の手順 1）

### 1.1 fill のターンを解き直すベンチ

feature `dump-fills` の exe で生成の形を 60 局打ち、belief plan の fill の要求を 3 つに 1 つ書き出した（種 47101、4 ワーカー、687 fill、セル 44,755）。`fill-bench` は書き出した fill のセルを、`encoded_node::fill` と同じ順で解く。中断したターンは `resume_all` と同じ形で再開する。符号化はしない。1 回の繰り返しで解くターンは 93,514 回で、うち 48,759 回が中断からの再開だった。

`--digest` は、各セルの答えを FNV で hash する。hash に入れるのは、枝の重み、局面の Debug 文字列、注記、中断と再開の答え、拒否の文である。2 つの exe の答えが同じかを、この hash で比べる。対照として、規則を壊す feature `ika210-control` の exe では 687 fill のうち 580 の hash が違った。

時間を比べるときは、同じ dump を 2 回ずつ繰り返す回を A B B A の順に 3 組か 4 組回し、組ごとの比（B の 2 回の和 ÷ A の 2 回の和）を出した。ほかの担当の仕事と機械を分けて回したので、ターンあたりの µs の値そのものは回ごとに 10〜42 µs と揺れた。そのため µs の値は比べに使わず、組ごとの比だけを使う。

## 2. mimalloc が windows-gnu で起動していなかったこと

libmimalloc-sys 0.1.49 の `prim/windows/prim.c` は、既定で `MI_WIN_INIT_USE_CRT_TLS` を選ぶ。この形では `_mi_auto_process_init` を呼ぶ TLS コールバックを `#pragma const_seg(".CRT$XLB")` で置く。GCC はこの pragma を無視するので、コールバックは登録されない。`os_preloading` を偽にするのは `_mi_auto_process_init` だけなので、mimalloc は終わりまで preloading の状態で動く。preloading の間、mimalloc は次のように動く。

* arena を使わず、ページを OS から直接取る（`arena.c` の「use OS only while pre loading」）。
* 設定を DEFAULTED にしないので、呼ぶたびに環境変数を読み直す。

`main` の先頭で `_mi_auto_process_init` を呼ぶ形にした（windows-gnu だけ）。`_mi_auto_process_init` は mimalloc の公開 API ではなく、コールバックが呼ぶ内部の関数である（libmimalloc-sys 0.1.49、mimalloc 3.3.2）。版は `Cargo.lock` が決めている。名前が変われば link で止まるが、名前が同じで中身が変わると止まらない。版を上げるときは `init.c` と `prim/windows/prim.c` を読み直し、`fill-bench` と ABBA を回し直す（`main.rs` のコメントにも書いた）。

スレッドの終わりも同じコールバックが知らせるので、終わるスレッドは自分で知らせる必要がある。推論サーバの接続ごとのスレッドと、`encode-games` のファイルごとのスレッドは、終わりに公開 API の `mi_thread_done` を呼ぶ（`main.rs` の `thread_done`、windows-gnu だけ）。ほかのスレッド（セルの pool、推論サーバの報告）は過程が続く間生きる。

mimalloc 2.x（mimalloc クレートの feature `v2`）も試した。起動処理を呼んだ形どうしの `fill-bench` で、3.x の時間は 2.x の 0.844 倍だったので、3.x のままにした。この比較は line-tables 付きの標本採りの exe どうしで回した。

| `fill-bench` の比較（A → B） | 組 | B/A（組の平均） | 組の範囲 |
|---|---|---|---|
| 前の allocator → mimalloc（起動処理なし） | 4 | 0.796 | 0.689〜0.946 |
| 前の allocator → mimalloc（起動処理あり） | 4 | 0.701 | 0.669〜0.738 |
| mimalloc（起動処理なし）→ mimalloc（起動処理あり） | 3 | 0.945 | 0.932〜0.969 |
| mimalloc 2.x → 3.x（どちらも起動処理あり） | 3 | 0.844 | 0.809〜0.897 |

## 4. 局を変えない高速化

### 4.1 局面の複製で、変わらないリストを共有する（15d71fc）

ターンの解決は分岐と行動ごとに局面を複製する。局面の中の Vec（場の状態、並び、裏の Rc の並び、場全体の状態など）は、複製のたびに確保していた。これらを `position::Shared`（Rc の中の値。書くときに `Rc::make_mut` でコピーする）に替えた。読む側と書く側のコードはそのまま動く。`Debug` と `==` は中の値のものなので、`--digest` の hash も変わらない。ほかに次の 2 つで確保を減らした。

* 終わりの処理の速さの順で、種族名を String にせず参照で持つ。
* 場の状態と場全体の状態の残りターンは、数えるものがあるときだけ作り直す。

性格の表を FNV と inline の id の表にした変更（0eeb26a）も、`fill-bench` ではこの比較に入っている。

### 4.2 fill の中で、同じ局面から同じ行動を解くのは 1 回にする（0eeb26a）

`resolve::fill_cache` は、fill の間だけ、行動を解いた結果を局面と行動の組で持つ。2 回目からは持っている結果のコピーを返す。`execute` が読むのは局面と行動と予算だけなので、答えは変わらない。キーでは `same_turn` の欄に加えて、`same_turn` が比べない欄（注記と、解いている技の記録）も比べる。経過を記録するターン、交代で場に出るときの引き（`draws`）の途中のターン、1 本の道を引くターン（IKA-469 の `sample_turn`）は持たない。`same` は `Turn` を `..` なしで分解するので、`Turn` に欄を足すと、`same` で扱うまで build が止まる。

持つ局面は動いた枠の数で限った。`fill-bench --max-acted` で比べた結果を下に示す。

| 比べ（A → B） | 組 | B/A（組の平均） | 組の範囲 |
|---|---|---|---|
| 持たない → 動いた枠 1 つまで | 3 | 0.932 | 0.918〜0.940 |
| 1 つまで → 0（動く前だけ） | 3 | 1.032 | 1.029〜1.034 |
| 1 つまで → 2 つまで | 3 | 1.015 | 1.002〜1.027 |

既定は 1 つまでにした。

### 4.3 行動ごとのコピーを減らし、場の特性を inline で持つ（4684685）

* `run_queue`: 行動 1 つの結果のリストを、作り直さずにそのまま使う。重みは同じ積である（浮動小数の掛け算は順を入れ替えても同じ値）。並べ直した列をコピーせず、先頭を取り出して残りを使う。最後の結果には残りの列をコピーせずに渡す。次の世代のリストは初めから大きさを取る。
* `FieldState` の場の特性と、特性を守る道具を持つ Pokemon の特性を、2 つまで inline で持つ（`battler::Abilities`）。`field_state` は当たりと並べ直しのたびに呼ばれ、空にならない 2 つのリストで毎回 2 回確保していた。

### 5.3 `fill_cache` の対照とテスト

feature `ika471-cache-control` の build は、`fill_cache` のキーと `same` から `attacks`（Sucker Punch の読む欄）を除く。この build では、`attacks` だけが違う局面に、前の局面の結果が返る。

| 確かめ | 既定の build | 対照の build |

`tests/test_fill_cache.py` は、Rust のワーカーで同じ種の 6 局を 2 回打つ。1 回はキャッシュを入れたまま打ち、もう 1 回は `POKEURAOU_FILL_CACHE=off` で切って打つ。2 回の記録が同じであることを確かめる。プールは `tests/fixtures` の 2 つの構築で、team_a には Sucker Punch を持つ Pokemon が 2 体いる。推論サーバはテストの代役なので、GPU は要らない。ワーカーは終わりに `fill cache: N lookups, M hits, K kept` を出す。テストは、入れた回で hits と kept が正であることと、切った回で 3 つとも 0 であることも確かめる。test_rust_worker のプール（`rizabanadohido` を並べ替えた 3 つ）には Sucker Punch が無く、対照の build でもテストが通ったので、プールを替えた。

本番の道で当たった数は、§5.4 の生成で数えた。

## 6. 入れなかったもの

| 案 | 理由 |
|---|---|
| ダメージ計算のメモ化 | 呼びの 75% は同じ fill で前に出た入力だった（§1.2）。しかし `fill_cache` のあとでは、ダメージ計算はターンあたり 1.39 回で、標本の自分の時間は 3.2% だった。キーは Battler 2 体（各 352 バイト）と場（536 バイト）と技の文脈で、作って比べる費用が計算と同じくらいになる |
| Battler を作る回数を減らす | ターンあたり 23 回で、標本では約 8%（`from_pokemon` を含む標本）。Pokemon は書き込みのときに同じ Rc の中で変わることがあるので、ポインタをキーにして作った Battler を探せない。中身をキーにすると、作るのと同じくらいの費用になる |
| `attacks` を除いたキーで `fill_cache` を引く | 前に出た入力が execute の時間の 39.2% から 44.7% に増える（§1.2）。Sucker Punch のほかに `attacks` を読む所が無いことを、すべての技の道で確かめる必要がある |
| 終わりの処理（`residual_forks`）の結果も fill の中で持つ | 同じ fill で前に出た局面は、終わりの処理の時間の 21.8% だった。終わりの処理は解決の時間の約 20% なので、見込みは 4% 以下で、結果をコピーする費用を引くとさらに減る |
| IKA-462 §5 のセルの共有（作り直し） | `fill_cache` が、同じ局面から同じ行動を解く所を共有する。セルの途中までの分岐を明示的に共有する作り直しは、残りの見込みが小さいので行わなかった |

### 7.2 確かめていないこと

* `mi_thread_done` が、推論サーバの接続のスレッドのページを実際に返しているか。接続が過程の間続く生成では、§5.4 のとおりサーバの主記憶は増え続けなかったが、接続が何度も替わる使い方では測っていない。
* 人と打つ道具・検討（全コアのスレッドの pool）での速さ。`fill_cache` は pool のスレッドでは働かない（キャッシュは fill を呼んだスレッドにだけある）。mimalloc のほうは pool のスレッドでも使われる。
* 対戦評価（`match_queue.py --pool`）の速さ。局が変わらないので、強さを比べる必要はない。
* Linux の build で `_mi_auto_process_init` を呼ばない形（`cfg(windows, target_env = "gnu")`）が CI で通るか。CI は push の後に走る。
* 標本採りの道具の正しさの対照。どの標本も `main` までたどれたこと、mimalloc の起動処理の有無で `mi_os_prim_free` などが出たり消えたりしたことは見たが、既知の時間の関数を入れた対照は回していない。
