# 実時間の読みの後の読みが、前の読みの文脈で読まれた塊を混ぜる（仮名 ladder-fill-leak）

課題番号は調整役が振る。ブランチ `fix-ladder-fill-leak`（master 818a902 から）。

## 結論

**本番の不具合**。テストの読み方の問題ではない。

ワーカーの塊の送り側（`ladder._Pool.cells` / `deep_cells` / 3 つ目の送りループ）が、前の読みが捨てた塊の中にまだいるワーカー（orphan）に、新しい読みの塊を送ることがあった。
そのワーカーには新しい読みの文脈（`begin` の "read" メッセージ。行・列の候補、局面、部分ゲームの表の世代）がまだ届いていない（orphan の塊が戻ってから送る）。
塊は前の読みの文脈と表の世代で読まれ、答えは新しい読みのものとして受け取られる。

原因の行: 送りループは `min(out, key=len(out[k]) + (orphan なら POOL_DEPTH))` で一番空いているワーカーを選ぶが、送るかどうかは素の `len(out[i]) >= POOL_DEPTH`（=2）で決めていた。全ワーカーが orphan で、選ばれたワーカーの残りが 1 つ（POOL_DEPTH 未満）のとき、罰の付いた負荷が 3 でも送ってしまう。

- CI と同じ落ち方をローカルで再現した。テストを 4 並列で繰り返し、直す前は 80 回中 2 回、120 回中 1 回（合計 200 回中 3 回、1.5%）落ちた。値も CI と同じ（0.4215827934475901 対 0.4301653535640189、`again` の work は subgames 8 / cells 116、`serial` は 9 / 132）。落ちた回はどれも 3 局面のうち 2 番目（pos 1）で、実時間の読みが d3 の段の途中で予算切れになった回だった。落ちた回の直後に同じ読みをもう一度すると `serial` と一致した（読みの状態が汚れたのは 1 回だけ）。
  - ログ: `C:/tmp/fillleak/evidence/base.0.4.log`, `base2.1.11.log`
- 落ちた回の時刻付きの記録（部分ゲームの表の put / hit、塊の開始と終了、読みの始まり）: `C:/tmp/fillleak/evidence/ci_like_failure_trace_wall.6.0.txt`。
  - 落ちた `again`（表の世代 10）の塊 task=110（d2 の 1 セル）がワーカー 0 に送られたのは、そのワーカーが前の読み（世代 7）の深い塊 task=91 を 480 ms 読んでいる最中だった。task=110 は task=91 の後、文脈 gen=10 より前に届き、`tablegen=7` で読まれた（同じ記録の他の塊は tablegen=10）。世代 7 の表に前の読みの部分ゲームが入っており、そこから `claim-hit` した値が入った。
- 別の落ち方も 1 回見た: 0.4240634422353869（subgames 15、cells 192）。同じ原因の別の現れ（古い文脈の塊が読んだセルの組が違う）と見ている。ただし、この回の記録は取っていない（確かめていない）。
- 陽性対照（遅れを入れる）: ワーカーの深い（d3）塊の答えを 400 ms 遅らせる一時的な細工（コミットしていない）で、実時間の読みの次の読みを続けて 2 回、3 局面 × 3 回 × 2 並列（54 組）。塊の開始のとき、その塊が新しい読みのものなのに表の世代が古い（=古い文脈で読まれた）回数を数えた。
  - 直す前: 612 塊のうち 108 塊（`evidence/delay400_unfixed_check.txt`）
  - 直した後: 612 塊のうち 0 塊（`evidence/delay400_fixed_check.txt`）

- テストでの陽性対照: `test_no_chunk_goes_to_a_worker_still_in_an_earlier_reads_chunk`（本物のパイプにワーカー無しで `_Pool` を作り、全ワーカーが orphan で残り 1 つずつの状態で `cells` を回し、どのパイプにも何も送られないことを確かめる。空いているワーカーが 1 つあればそれには送られることを対照にする）。直した後は通る。`cells` の送り判定を素の `len(out[i])` に戻すと落ちる（`assert not True`）。
- 直した後の元のテスト（`test_a_filled_budget_ends_at_the_budget`、[env] と [ladder]）: 4 並列 × 50 回 = 200 回で 0 回落ちた（直す前は 200 回で 3 回。直った確率の下限は弱く、0/200 だけでは、1.5% の落ち方が消えたと言い切れる程度ではない: 1.5% なら 0 回の確率は約 5%）。決め手は上の遅れの陽性対照とテストの対照。出力: `C:/tmp/fillleak/fixed_run.txt`。

## 直し

`_Pool._load(worker)` を足し（残りの数 + orphan なら POOL_DEPTH）、3 つの送りループで選ぶキーと「いっぱいか」の判定の両方に使う。orphan のワーカーには、その塊が戻って文脈が届くまで送らない。全ワーカーが orphan のときは、`wait` で答えを待つ（答えが戻れば `cells` の受け取りが文脈を送り、orphan を外す）。

`deep_cells` と 3 つ目の送りループにも同じ式があったので同じ直しを入れたが、テストは `cells` にだけ付けた（確かめていない）。

## 確かめなかったこと

- 本番と同じ全コア・数秒の実時間の読みを続けた再現はしていない（`humanplay` の経路）。遅れの陽性対照は 2 ワーカーの test プールで行った。
- `deep_cells` と 3 つ目のループのテスト。
- 別の落ち方（0.42406…）の記録。
- 生成の経路（`--served` など）では、実時間の読みを捨てない（読みが最後まで走る）ので、この不具合は出ないはずだが、生成の局が変わらないことは測っていない（送りの選び方は、orphan のいない読みでは前後で同じ）。
