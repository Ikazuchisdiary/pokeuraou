## 1. 測り方

`tools/legal_moves_cost.py`（新規）。記録済みの局面を読み、各段の **このスレッドの CPU 時間** を 1 呼び出しずつ測る。

* 局面: `data/selfplay-mc0`（M-C gen-0、読むだけ）の 26 個のワーカーのファイルから均等に move の決定の局面を取り、混ぜて
  **4,000 局面 × 両側 = 8,000 本**。種 319
* 深さ 2 の部分ゲームの局面（`--children`）: 上の根で幅 12 のメニューを両側に作り、セルを一様に 1 つ選んで port で 1 ターン
  解き（`Budget.matrix()`）、確率の高い順に 3 本の終わっていない枝の局面（`search._refine_cells` が `narrow_many` に渡すもの）。
  **4,000 局面 × 両側**。本物の精緻化は根の上位のセルを選ぶので、セルの混ざり方は同じではない
* 時計: `QueryThreadCycleTime`（スレッド自身のサイクル、1 呼び出しごとに読む）を busy loop で ns に較正。Windows の
  `thread_time` は 15.6 ms 刻みなので、合計の照合にだけ使った。**照合**: 同じ合法手の仕事を 1 本のループで回し、1 呼び出しずつの
  サイクルの和 2,868 ms ／ `thread_time` 2,938 ms（根）、1,911 ／ 1,797 ms（部分ゲーム）。2 秒と 4 秒の busy loop では
  1,817 ／ 1,781 ms・3,647 ／ 3,703 ms（`C:/tmp/ika319/clockcheck.py`）
* `side_actions`・`drop_dead_actions`・並べ替え・覆いは 3 回ずつ測って中央値。port への要求は 1 回目だけ（答えの保持
  `hold_positions` は off で、同じ要求でも port はもう一度解く）
* `narrow` の中は、`narrow` の本体を段ごとに書き出して各段の前後で時計を読む。**各段を直接測っていて、差し引きでは出していない**。
  書き出した本体の答えは、全 8,000 本 × limit 8・12・48 で `narrow` 自身と一致（残した手・点・detail・覆えなかった選択肢・
  `by_kind`）。**不一致 0**（根・部分ゲームとも）。段の和（limit 12）1.347 ms に対し `narrow` を丸ごと測ると 1.469 ms
  （差は `Narrowed` の組み立てと呼び出しの分）
* port への往復は 5 つに分けた: 要求の dict（`_position`＝`to_json` と `dump_action`）・JSON の 1 行（`_payload`）・往復
  （書き込み・子の仕事の待ち・`readline`）・答えの `json.loads`・答えのほどき。port の子の CPU は子のプロセス時間を要求ごとに
  読んだ和（15.6 ms 刻みの標本の和）
* 順位付け（`rank=`、葉の充填と順伝播）は走らせていない。IKA-32 では別の段（`rust.fill`・`serve.wait`）に出ている

**混雑の注意**: この測りは IKA-274 が 16 コアの専有で教材を生成している最中（機械の負荷 100%）に、heavy.py `--cores 1` で回した。
サイクルは奪われた時間を数えないが、SMT の相方と共有キャッシュの取り合いで 1 サイクルあたりの仕事は遅くなる。**だからここの ms は
空いた機械の値より大きい（上限）**。IKA-32 の `d2.menus`（深さ 2・裏非公開、空いた機械、1 手 130.7 本のメニュー）と照らすと、
`narrow` の自分の時間は IKA-32 28.3 ms／手 に対しこの測りで 130.7 × 0.296 = 38.7 ms（1.37 倍）、段の外の Python
（`narrow_many` の合法手と detail）は 16.0 ms に対し 27.5 ms（1.7 倍）。**混雑の倍率はおよそ 1.4〜1.7**。下の「空き」の列は 1.5 で割った見積もり。

## 5. port へ移すべきか

**合法手の生成だけを移すのは勧めない。**
* 取れるのは 1 手の 1〜3% が上限（空きなら 0.1〜2%）
* port が合法手の列を返すなら、Python はそれを JSON から読んで `SideAction` を作り直す（今の答えのほどき＋`json.loads` が 3 KB で
  0.1 ms。53 本の列なら同じ桁）。`narrow` の次の段（順位付けの葉・メニュー・記録）は Python の `SideAction` を使うので、
  作る費用が読む費用に置き換わるだけ
* 規則は約 500 行（技の使用可否・対象・拘束・固定・メガ・交代先・Imprison 等）で、Showdown と一致させる面が増える

**移すなら `narrow` ごと**（IKA-303 の「部分ゲームの narrow」）:
* 要求は局面（`hold_positions` で 1 決定 1 回の文字列）と `limit` だけ、答えは残す ≤8〜12 本の手（と、要るなら点）。
  消えるもの: 候補の JSON（要求の 18 KB の大半、0.2〜0.3 ms）、覆い（0.23〜0.52 ms）、並べ替え、合法手と効かない手、
  候補の点のほどき。残るのは局面を送る費用と残した手を読む費用
* 見積もり: `narrow` 1 回の Python が 0.8〜1.35 ms から 0.2 ms 前後へ。**d2h で 1 手 50 ms 前後（混雑下。空きで 33 ms、1 手の 14%）、
  h48d2 で 90 ms（空き 60 ms、9%）**。深さ 1 で閉じられるのは `rank` なしの 2 回だけで、1 手 2.3 ms（空き 1.5 ms、d1h の 3%）
* ただし葉で順位付けする `narrow`（根のメニュー、1 手 2 回）は `rank` が Python の葉を呼ぶので、port で閉じるのは
  `rank` なしの `narrow`（`leaf_ranking` の返し手と `narrow_many` の部分ゲームのメニュー）。深さ 2 の費用はほぼこちら

**port に移す前に Python の中で取れるもの**（局は変わらない）:
* detail の文字列（`narrow` の 14%）: 記録と `cli` が読むときに作る（遅延）。同じ文字列を同じ順に作るので記録はバイトで同じ
* 覆い（39%）: `_slot_key` を候補ごとに 1 回だけ作り、`uncovered` の判定を整数の集合にする。選ぶ候補の順は同じ

### Showdown との一致をどう保証するか（port に移すとき）

1. **port 対 Python の差分（移す前の基準）**: 記録の局面（この測りの 8,000 本＋部分ゲームの 8,000 本）で、port の合法手の列と
   `side_actions` の列が **順まで** 同じこと（`to_choice()` の列）。順は `narrow` の覆いの `needed` の順と、順位付けの葉の並びに
   効くので、集合の一致では足りない。`drop_dead_actions` の後の列も同じく
2. **port 対 Showdown（request と比べるテスト）**: `tests/test_actions.py::test_enumeration_agrees_with_showdown_over_whole_battles`
   と同じ形で、合法手を port から取る版を足す。Showdown の対局を乱数で進め、各決定で
   * port の全ての手を Showdown に `probe` し、全部受け付けられること
   * 近い外れ（`_near_misses`: 使えない技・同じ交代先・メガ 2 つ・拘束中の交代など）を `probe` し、全部断られること
   * 枠ごとの技の集合が request の `active[slot].moves` の `disabled` でないものと等しいこと（`_cross_check_against_request`）
   * 交代先が request の `side.pokemon` の生きている控えと等しく、`trapped`/`maybeTrapped` の枠は交代が無いこと、`canMegaEvo` の枠だけに
     メガがあること
   加えて `tools/diff_turn.py` の 1,600 対局の各決定で、port の列と request から作った列を比べる広い確認
3. **陽性対照**: port に故障を入れた exe（Imprison を無視する、メガを 2 枠に許す、など）で 2. が落ちることを、直す前の exe で示す
4. **局の一致**: 移した後の生成を家の規則の ABBA（600 局）でバイト一致させる（合法手の順が同じなら `narrow` の答えも同じ）
