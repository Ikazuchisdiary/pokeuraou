# IKA-462: port の exe を速くする

課題: Notion の Issues（ID IKA-462）。ブランチ `worktree-agent-a679ed2523463a124`。計測の道具と生の出力は `C:/tmp/ika462/` に置き、コミットしていない。

## 0. 要点

* 生成の形で、ターンの解決を入力ごとに数えた。同じ入力で 2 回目以降の呼びは全体の 4.9% だった。同じ決定の別の fill どうしが 4.7%、局をまたぐ分が 0.2%、同じ fill の中と決定をまたぐ分は 0% である。ターンの解決のキャッシュで減らせるのは多くても約 5% なので、入れていない。
* 標本採りのプロファイラを自作した。対照で誤りが分かったので、結果を使っていない（§2.3）。
* 代わりに、段ごとの時計で内訳を測った。ワーカー 1 つ・100 局では、ワーカーの CPU のうち、ターンの解決が約 55%、LP が約 18%、符号化と縛りの列が約 20% だった（§2.2）。熱い関数は 1 つに絞れず、広く薄い。
* 速くなった変更は見つからなかった。`mimalloc` を global allocator にした exe を試した。局は変わらない（種 46281〜46284 の 2,000 局ずつ、計 8,000 局で記録が前の exe と一致）。定常状態の窓が取れる 2,000 局の ABBA（21 ワーカー、4 組 16 回）では、局/分が 2,202.1 対 2,178.1（−1.1%）、1 局の CPU が 0.3851 対 0.3839 秒（−0.3%）で、速くなっていない。4 組のどれでも mimalloc の局/分が前の exe より 1.0〜1.2% 低い（§3.2）。ここでの「1 局の CPU」は、推論サーバを含む port の exe の過程すべての合計である。
* 同じ試作を 600 局で測った 2 回の ABBA（各 8 回）は、局/分が +2.0% と +2.0% だった。これらの窓は 12〜14 秒で、計測の道具が「定常状態でない」と警告していた。2,000 局で取り直すと再現しなかったので、600 局の値は参考にとどめる（§3.4）。
* `mimalloc` の feature は残し、既定では off にした。局が変わらないので、使うかどうかは決めてよい。
* PGO は使えない。windows-gnu の rust-std に profiler runtime が無い（§4）。`target-cpu=native` は +0.7% で、揺れの内なので入れていない。

## 2. 計測

### 2.1 重複の数え（`count-resolves`）

`resolve_turn_logged` の入口で、局面の Debug 文字列と、両側の行動と予算の Debug 文字列を hash する。1 回の呼びを 32 バイトで `POKEURAOU_RESOLVE_LOG` の下に書く。局の番号・局の中の決定の番号・決定の中の fill の番号も持つ。8 ワーカー・600 局（種 46202）。

| 数え方 | 回数 | 全呼びに対する割合 |
|---|---|---|
| ターンの解決の呼び | 1,288,867（1 局 2,148） | |
| 同じ fill の中で入力が重なる分 | 0 | 0.0% |
| 同じ決定の別の fill どうしで重なる分 | 60,603 | 4.7% |
| 同じ局の別の決定にまたがる分 | 0 | 0.0% |
| 別の局にまたがる分 | 2,335 | 0.2% |
| 合計（2 回目以降の呼び） | 62,938 | 4.9% |

* 局は（ファイル、局の番号）で区別した。最初の数え方は局の番号だけで区別して、別のワーカーの局を混ぜていた。直して数え直した。
* 実際に打つターンの解決は 5,148 回で、全体の 0.4% である。局面は同じ決定の fill のどれかと一致するが、予算が違う（打つ側は exact の予算）。そのため入力は重ならない。
* 1 決定の呼びは中央 181 回、1 決定の fill は中央 5 回だった。
* この数えには対照が付いていない。入力が同じなのに別と数える誤り（Debug 文字列に入らない欄があれば重なりを見逃す）と、別なのに同じと数える誤り（hash の衝突）を、別の手段では確かめていない。hash に入っているのは局面、両側の行動、予算で、`resolve_turn_logged` の引数 `events` は入っていない。`events` を真にして呼ぶのは診断の `turn` コマンドだけで、生成の道は `resolve_turn`（偽）を呼ぶ。数えは `resolve_turn_logged` の入口で行う。

### 2.2 内訳（`phase-report` と `profile`）

ワーカー 1 つ・100 局（種 46231）。ワーカーが決定ごとに足した時計を、報告に出す。時計は 1 回 25 ns ほどかかるので、呼び数の多い行は少し大きく出る。単位は 1 局あたりの µs。ワーカーの実時間は 1 局 約 200 ms、CPU は約 157 ms である。157 ms は、同じ構成の別の run の値（exe の合計 0.172 秒、種 46241 の 60 局）から、推論サーバの CPU 約 0.015 秒（種 46221 の run）を引いた概算である。実時間との差は推論サーバの待ちである。下の割合は、この 157 ms で段の µs を割った値で、profile の時計が足されているので少し大きい。

| ターンの解決（fill の分と、打つターンの分） | 約 86,000 | CPU の約 55% |
| 　うち打つターン（exact の予算） | 約 16,000 | 1 局 約 8.8 手（move node 884 を 100 局で割った値）で、1 手 約 1.8 ms |

### 2.3 標本採りの試みと対照（結果は使わない）

`SuspendThread` で worker の主スレッドを 0.5 ms ごとに止め、命令ポインタとフレームポインタをたどる標本採りを作った。走っている時だけ数える。この方法は、ntdll のヒープ関数（割り付けと解放）に標本の約 24%（ntdll 全体で約 33%）が当たると報告した。この 24% は、mimalloc の前の exe で数えた値で、その時の生の出力は残っていない。

対照として `mimalloc` を入れた exe で同じ標本採りを回した。ヒープ関数の標本は 24% から約 2% に減った。しかし 1 局の CPU は変わらなかった（ワーカー 1 つで 0.173 秒 対 0.183 秒）。標本採りの帰属が実際の CPU とずれているので、この道具の関数ごとの数字は使わない。原因は調べていない。道具は master に入れない。

## 5. 局が変わる案、深い作り直しが要る案（入れていない）

* 打つターンの exact の解決は 1 局 約 16 ms（約 8%）。全分岐を作ってから 1 つ引いている。重みだけで引ける形にすると、分岐の順と足し順が変わりうる。
* LP は 1 局 約 28 ms（約 14%）。HiGHS の設定（presolve など）を変えると、縮退した問題の解が変わり、局が変わる。同じ費用の対戦評価で判定する。
* 符号化は、leaf どうしで同じ `Rc` を共有する Pokemon を再符号化している可能性がある。符号化の結果が Pokemon だけで決まるかを、`encode.rs` で確かめる必要がある。
* fill のセルどうしで、自分の行動の組が同じで相手の 2 つめの行動だけが違うものは、途中まで同じ分岐を持つ。共有するには resolve の作り直しが要る。
* 同じ決定の別の fill どうしで重なる 4.7% は、`beliefplan` の dirty fill の入力どうしである。fill をまたぐ小さなキャッシュで減らせるが、見込みは 5% 以内。
