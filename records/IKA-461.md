# IKA-461: 推論サーバを Rust に移す

## 0. 要点（2026-11-27、評価モデルの腕まで）

* 評価モデルの腕を Rust の推論サーバが答える。`generate_queue.py --rust-server`（既定 off）で選ぶ。今の Python のサーバの道は変えていない。
* 実行系は `cudarc` 0.17.8（実行時に CUDA を読む）。網の kernel は自前で、NVRTC が起動時に作る。新しい取得物は crate 2 つ（`cudarc`・`libloading` の固定）だけ。
* 値は torch と float32 の誤差の内に収まる。記録の局面 6,000 で最大 1.07e-6、99 分位 5.1e-7。
* 生成の形（21 ワーカー・サーバ 2・600 局）の ABBA で、1 局あたりのサーバの CPU は 0.1228 秒から 0.0534 秒（−57%）。1 局の CPU 合計は 0.4775 秒から 0.4172 秒（−12.6%）。
* 局/分は決まらなかった。組ごとの差の向きが逆で、機械の負荷の幅が差より大きい（§4.3）。
* Q の腕は Python のまま残る。Python の Q 専用サーバが Q の依頼を受け、Rust のサーバは行ごとそのまま渡す。段 4 で Q を Rust に移す。

### 1.2 実行系の比較

この機械の条件は次のとおり。

* Rust の toolchain は `x86_64-pc-windows-gnu`（MinGW）。port は windows-gnu のままにする。
* 設計時の CUDA Toolkit は 11.1 だけで、RTX 5070（sm_120）には使えなかった。実装の途中で Toolkit 12.8.1 と MSVC 14.44 が入った。
* `.venv` の torch 2.11+cu128 が、`torch/lib` に CUDA 12.8 の `cublas64_12.dll`・`nvrtc64_120_0.dll` を持つ。

| 案 | build（windows-gnu）| 配布・依存 | CPU の見込み | 評価 |
|---|---|---|---|---|
| ONNX Runtime（`ort`、CUDA EP）| `load-dynamic` なら build できる。ONNX の書き出し（2 本平均を含む）が要る | `onnxruntime-gpu` の DLL 数百 MB と CUDA 12・cuDNN 9 の DLL | 形ごとの CUDA Graph を EP の外から扱えない | 重い |
| TensorRT | NVIDIA の配布物（数 GB 級）。形ごとにエンジンを作る | 重い | 速いが、小さい MLP には過剰 | 見送り |
| libtorch（`tch`）| MSVC 版のみ。windows-gnu に繋がらない。MSVC が入ったあとも、推論サーバだけ別の target にする必要がある | 約 2.5 GB | op ごとの dispatcher の費用が残る。tch に CUDA Graph の捕捉の包みが無い | 目的（CPU を減らす）に合わない |
| candle | CUDA 版は nvcc 12 と MSVC が要る | crate は小さい | kernel は結局自前 | `cudarc` を直接使うほうが薄い |
| 自前の FFI（`LoadLibraryW`）| crate が要らない | torch か Toolkit の DLL | Graph を直接呼べる | `cudarc` が同じ物を提供するので、保守の少ない `cudarc` に譲る |
| **`cudarc`**（採用）| windows-gnu で build できた（下記）| crate 2 つ。DLL は実行時に読む | Graph 1 起動で依頼を処理する | 採用 |

`cudarc` の確かめ（`C:/tmp/ika461/cudarc-try`、windows-gnu のまま）:

* `cudarc` 0.17.8（features: `driver`・`nvrtc`・`cublas`・`dynamic-loading`・`cuda-12080`）が build できた。ソースは約 8.3 MB。
* `libloading` を `=0.8.5` に固定した。新しい版は `windows-link` を使い、これが `raw-dylib` で kernel32 を繋ぐため、windows-gnu では `dlltool` が PATH に要る。`cmake` を 0.1.54 に固定した理由（`rust/Cargo.toml` の注記）と同じ。0.8.5 は `windows-targets` を使い、import library が crate で届く。`rust/Cargo.toml` に理由を書いた。
* 実行時に PATH の `nvrtc64_120_0.dll`・`cublas64_12.dll` を読み、NVRTC で sm_120 の kernel を作り、cuBLAS の sgemm と、`cuStreamBeginCapture` による CUDA Graph の捕捉と起動が動いた。
* 注意: `cudarc` が既定で付ける stream をまたぐ event の追跡は、Graph の捕捉を「別の stream の未捕捉の仕事に依存した」として止める。`disable_event_tracking` で切る（スロットごとに stream を 1 本持ち、バッファを共有しないため）。

DLL の置き場:

* 順に、`--dll-dir`、環境変数 `POKEURAOU_CUDA_DLLS`、`CUDA_PATH_V12*` の `bin`、`%ProgramFiles%` の Toolkit の `v12*\bin`。見つからなければ PATH のまま読む。生成の道具は、これらが無いときだけ `.venv` の `torch/lib` を `--dll-dir` に渡す。
* 起動時に、ドライバ・NVRTC・cuBLAS の版と GPU の名前を stderr に出す。NVRTC か cuBLAS の主版が 12 でなければ止まる。DLL が見つからないときは、対処を書いた誤りで止まる（`cudarc` の panic を捕まえて言い換える）。
* 今の機械の起動の行: `GPU NVIDIA GeForce RTX 5070 (compute 12.0), driver 13.3, NVRTC 12.8, cuBLAS 12.8.4`。Toolkit の DLL でも torch の DLL でも、同じ行になる（どちらも 12.8）。

nvcc と MSVC が入った前提の見直し（調整役の依頼）:

* kernel を nvcc で前もって build して起動時の NVRTC をやめる案: 起動時の NVRTC の時間は 0.2 秒ほどで、4 スロット × 28 本の Graph の捕捉を含む起動全体が 0.4〜1.3 秒に収まる。前もって build すると、nvcc 12 が build の条件になり、CUDA の無い Linux の CI でも cubin の生成が要る。得るものが無いので、NVRTC のままにする。
* MSVC が要る crate: 要る物が無い。推論サーバは port と同じ exe の部分コマンドなので、target を分ける費用も払わない。
* 変わらないので `cudarc` のまま進めた。

### 1.3 重みの渡し方

* 学習は `.pt` のまま。`tools/export_rust_net.py`（学習側の道具、`src/pokeuraou/rustnet.py`）が `.pt` を `.rnet` に書き出す。
  * 形は、マジック `RNET0001`、見出しの長さ、見出しの JSON（網の大きさ、読む列の範囲、移動 id の置き場、各テンソルの名前・形・位置、元の `.pt` の名前と sha256）、64 バイトにそろえた float32 の生の値。
  * `attention`・`move_properties`・`width_groups` が 1 でない・`head_layers` が 2 でない網は、書き出しが止まる。本番の value-mc7 には当たらない。
* 評価モデルの腕は `--arm 名前 a.rnet b.rnet ...`。2 本以上は、ロジットの平均を取って sigmoid にかける（今と同じ）。
* 生成の道具は、`.pt` から `.rnet` を作り（元の sha256 が同じなら作り直さない。`--out` の下の `rnet/`）、サーバに渡す。生成の道具は `--value` に 1 ファイルだけ取る（2 本平均の腕は、この道具では未配線）。
* Q の腕は次の段。`qhead.py` の網は評価モデルと同じ胴体を持つので、同じ `.rnet` の形に載せる予定である。

### 1.4 取り決め（今のサーバと同じ）

* 同じ取り決めで答える。ソケット（1 行 1 JSON）と共有メモリ（`inference.ARRAYS` の順、64 バイト整列、numpy の dtype 文字列）、腕の名前、`ping`・`describe`・`score`・`score_segments`（1 つのブロックとして採点する）。port（`served.rs`）と Python（`RemoteValue`）の呼び手は変えていない。
* 整数の配列は `<i4`（port）と `<i8`（Python のエンコーダ）を受ける。浮動小数は `<f4`。
* 共有メモリの名前は、呼び手が作った Windows の名前付きファイルマッピングを `OpenFileMappingW` で開く（`shm.rs` と同じ）。
* テスト用に `stages` を足した。同じ依頼で、最初の網の各段の中身（特徴・Pokemon ごとの MLP の出力・プール・側のベクトル・頭の入力・頭の隠れ層・勝率）を共有メモリに返す。
* Q の依頼（`q`・`q_many`・`q_batch`・`describe_q`）は、`--q-forward 住所` の Python サーバへ、行ごとそのまま渡して答えを返す。`--q-forward` が無ければ、Q の腕が無いと名指しで断る。

### 1.5 依頼のまとめと、スレッドの組み方

* 接続ごとに 1 スレッド。依頼を読み、共有メモリからスロットのピン留めメモリへ写し、Graph を起動し、blocking sync の event で眠って待ち、結果を共有メモリに書く。
* スロット（stream・cuBLAS の handle・入出力のバッファ・Graph）は既定 4 個。空いたスロットを 1 つ借りる。空きが無ければ Condvar で待つ（CPU は使わない）。
* CUDA Graph は、行数を切り上げた桶（64 行刻みで 1,024 行まで、256 行刻みで 4,096 行まで）ごとに 1 本、計 28 本。起動時にすべて捕捉する。H2D のコピー・全 kernel・D2H のコピーを 1 本にする。4,096 行を超える依頼は 4,096 行ずつに切る。
* 桶に切り上げた余りの行は、前の依頼の行で埋まり、結果を捨てる。値は行数に左右されうるが、実測では 600 局の 2 回が一致した（D どうし、§4.2）。
* 複数ワーカーの依頼を 1 回にまとめる案は入れていない。1 依頼の GPU 時間は 1.5〜2.2 ms で、スロットの空き待ちは 0.00〜0.01 ms だった（§4.3）。`records/IKA-390.md` 段 B でも、まとめて実時間は変わらなかった。

* Rust のサーバの 1 依頼（種 46101、サーバ 2 台、600 局の別の 1 回 `rep1`、報告の行から。後半 5 秒ごとの値）: 全体 1.75〜2.5 ms、うち GPU の待ち 1.46〜2.17 ms、写し 0.27〜0.35 ms、スロット待ち 0.00〜0.01 ms。過程の CPU は 7,280 依頼で 5.2 秒（起動を含む）。1 依頼あたり約 0.7 ms。Q の転送は 2,563 件。
* 比べ: IKA-458 §12 の Python のサーバは、1 依頼約 5 ms、2 台で 79 秒。今回の A の側のサーバの CPU は、局あたり 0.1228 秒（600 局で約 74 秒）。
* GPU のメモリ: Rust のサーバ 1 台（4 スロット）で約 1.1 GB（nvidia-smi の全体の差）。
* 起動: スロット 4 × 28 本の Graph の捕捉を含み、0.4〜1.3 秒で準備が済む。

### 4.4 確かめていないこと

* 局/分の差（上記）。同じ負荷の窓での再計測は、していない。
* 600 局より長い生成（数万局）で止まらないこと、メモリが増えないこと。
* 対戦評価（SPRT(−10, 0)）。指示どおり、調整役の判断を待つ。
* Linux の build と CI。CI 上の 16 本は skip になる設計（`cuda` 24、`torch` 36）で、実際の CI は走らせていない。
* 2 本平均の腕で生成を回すこと（`generate_queue.py` が 1 ファイルしか取らない）。テストでは 2 本平均の値を torch と比べた。
* `score_segments` の依頼（深さ 2 の読み）を Rust のサーバに向けること。値の取り決めは同じにしたが、本物の生成で通したのは `score` だけ。
* 複数ワーカーの依頼のまとめ。入れていないので、効果は測っていない。
* Q の腕。
* 1 局の記録の探索値の差（9.5e-7〜1.6e-6）が、選ぶ手を変える確率の見積もり。実測で 600 局に 1 局が違った（上記）。
