## 1. 設計（2026-11-27、実装の前）

### 1.2 実行系の比較

この機械の条件は次のとおり。

* Rust の toolchain は `x86_64-pc-windows-gnu`（MinGW）。MSVC は無い。
* CUDA Toolkit は 11.1 だけが入っている。RTX 5070（sm_120）には使えない。
* `.venv` の torch 2.11（CUDA 12.8）が、`torch/lib` に `cublas64_12.dll`・`nvrtc64_120_0.dll`・`cudart64_12.dll`・`cudnn64_9.dll` を持つ。
* ドライバの `nvcuda.dll` はシステムにある。

| 案 | build（windows-gnu）| 配布・依存 | GPU 待ち | 固定費・CUDA Graph | 評価 |
|---|---|---|---|---|
| ONNX Runtime（`ort` crate、CUDA EP）| `load-dynamic` なら build できる。ONNX 書き出し（vmap の 2 本平均を含む）が要る | `onnxruntime-gpu` の DLL 数百 MB と CUDA 12・cuDNN 9 の DLL（取得元は PyPI か pyke の CDN）| EP の内部で決まる | EP の CUDA Graph は形が固定のときだけ。形ごとの切り替えが難しい | 重い。依頼の形の数だけ捕捉が要る |
| TensorRT | NVIDIA の配布物が要る（数 GB 級）。形ごとにエンジンを作る | 重い | 同上 | 速いが、この網（小さい MLP）には過剰 | 見送り |
| libtorch（`tch`）| MSVC 版の libtorch しかなく、windows-gnu に繋がらない | 約 2.5 GB | torch と同じ | torch の CUDA Graph を使える | build できない |
| candle | CUDA 版の build に nvcc（12.x）と MSVC の `cl` が要る | crate は小さい | — | 自前の kernel | build できない |
| 自前の薄い CUDA 呼び出し（`nvcuda.dll`・NVRTC・cuBLAS を実行時に読む）| crate を足さない。FFI は `LoadLibraryW`・`GetProcAddress` だけ（`shm.rs` と同じ流儀）| 実行時に `torch/lib` の DLL（学習用の `uv sync --group learn` で入る）を読む。新しく取る物は無い | `cuEventSynchronize` を blocking sync の event で待つので、CPU を手放す | 網は埋め込み 4 つ・Linear 数個・LayerNorm・GELU・プールだけ。kernel は NVRTC で実行時に作る。CUDA Graph は `cuStreamBeginCapture`・`cuGraphLaunch` を直接呼べる | 推奨 |

推奨は最後の案である。理由は次のとおり。

* 網が小さい（約 42 万個の重み、1 行あたり約 120 万 MAC）。必要な演算は、埋め込みの引き、行列積、LayerNorm、GELU、マスク付きのプールだけである。
* 行列積は torch と同じ cuBLAS の `cublasSgemm`（fp32、TF32 なし）を使うので、値の差は小さいはずである。
* 新しい crate も新しい取得物も要らない。Cargo.lock は変わらない。
* 依存は `torch/lib` の DLL で、学習側の依存と同じ場所にある。DLL の置き場は `--dll-dir` と環境変数で指せるので、CUDA 12 の DLL が別の場所にあってもよい。
* 見送った案の再検討: 将来 ONNX Runtime に移したくなったときは、下の重みファイルから ONNX を書き出せる。

### 1.3 重みの渡し方

* 学習は `.pt` のまま。`tools/export_rust_net.py`（学習側の道具）が `.pt` を `.rnet`（Rust が読む 1 ファイル）に書き出す。
  * 形は、1 行目がマジック、2 行目が JSON の見出し（網の大きさ、読む列の範囲、各テンソルの名前・形・位置、元の `.pt` の名前と sha256）、残りが 64 バイトにそろえた float32 の生の値。
  * 注意（サポートしない設定）: `attention`・`move_properties`・`width_groups` が 1 でない・`head_layers` が 2 でない網は、書き出しが止まる。本番の value-mc7 には当たらない。
* 評価モデルの腕は `--arm 名前 a.rnet b.rnet ...`。2 本以上なら、ロジットを平均してから sigmoid を取る（今と同じ。torch は float32 で平均）。
* 生成の道具（`generate_queue.py --rust-server`）は、`.pt` から `.rnet` を作り（元の sha256 が同じなら作り直さない）、サーバに渡す。
* Q の腕は次の段。今の Q の網（`qhead.py`、胴体は評価モデルと同じ作り）を同じ `.rnet` の形に載せる予定である。

### 1.4 取り決め（今のサーバと同じにする）

* 同じ取り決めで答える。ソケット（1 行 1 JSON）と共有メモリ（`inference.ARRAYS` の順、64 バイト整列、numpy の dtype 文字列）、腕の名前、`ping`・`describe`・`score`（`score_segments` も同じ扱い）。port（`served.rs`）と Python（`RemoteValue`）の呼び手は変えない。
* 理由: `RemoteValue`・`served.rs`・段 3 の各 `*_core` が同じ住所に話しかけているので、差し替えだけで済む。違う形にする必要は見つからなかった。
* 答えの形は同じ。`{"ok": true, "rows": n}` で、値は共有メモリの `result_offset` に float64 で書く。
* 評価モデルの腕だけを Rust で答える段では、Q の依頼（`q`・`q_many`・`q_batch`・`describe_q`）を、起動時に指した Python の Q 専用サーバへ行ごとそのまま渡す（`--q-forward 住所`）。呼び手は同じ住所だけを知っていればよい。Q の腕を Rust に移した段で、この転送を外す。
* 共有メモリの名前は、呼び手が作った Windows の名前付きファイルマッピングを `OpenFileMappingW` で開く（`shm.rs` と同じ）。

### 1.5 依頼のまとめと、スレッドの組み方

* 接続ごとに 1 スレッド（今の Python と同じ）。依頼を読み、共有メモリから固定のピン留めメモリへ写し、GPU に渡し、GPU を blocking sync の event で待ち（CPU を手放す）、結果を共有メモリに書く。
* GPU 側の作業場（stream・cuBLAS の handle・活性化の置き場・入出力のピン留めメモリ・CUDA Graph）は、スレッドごとではなく「スロット」単位で持つ。既定は 4 個。依頼を処理するスレッドが、空いたスロットを 1 つ借りる。空きが無いスレッドは待つ（CPU は使わない）。
* CUDA Graph: 行数を切り上げた「桶」ごとに 1 本。64 行刻み（1,024 行まで）・256 行刻み（4,096 行まで）で約 28 本。起動時にすべて捕捉する（依頼の途中で捕捉しない）。入力のコピー（H2D）・全 kernel・出力のコピー（D2H）を 1 本の Graph にし、依頼ごとの CPU は Graph の起動 1 回にする。端の余りの行は直前の依頼の値で埋まり、結果は捨てる。
  * 今の Python は依頼の行数ごとに捕捉していた（今回の 600 局で 393〜796 本）。桶にしたことで、同じ依頼でも行数が切り上がり、値が torch と 1 ULP ほど違う余地が生まれる。ビット一致は求めない方針なので、これを選ぶ。
* 4,096 行を超える依頼は 4,096 行ずつに切る（今は 8,192 行）。
* 複数ワーカーの依頼を 1 回の順伝播にまとめる案は、最初の実装に入れない。理由は 2 つ。
  * 今のボトルネックは GPU でなく CPU で、1 依頼の順伝播は GPU で数百 µs の見込みである。まとめる前に、1 依頼あたりの CPU が小さくなるかを見る。
  * `records/IKA-390.md` 段 B で、まとめても同じ段までの実時間は変わらなかった。
* スロット数・まとめの効果は、最初の実装の後に計測で決める。
