# IKA-454: 段の CPU を Windows でサイクル数で数える

課題: Notion の Issues（ID IKA-454）。枝 `worktree-agent-aaa2bc1abb3961f16`。起点は 9c227ce。駆動スクリプトと生の出力は `C:/tmp/ika454/` に置き、コミットしていない。

## 0. 要点

問いは、Windows で段の CPU を `thread_time` の代わりにスレッドのサイクル数で数えると、IKA-452 で見えた偏りがなくなるかである。

* `timing.py` に、スレッドの CPU 秒を返す関数 `thread_cpu` を 1 つ置いた。`time.thread_time()` を直接呼ぶ所は残っていない（テストで確かめた）。
* Windows で計時が on のときは、`QueryThreadCycleTime` のサイクル数を、起動時に測った周波数で割る。それ以外は `time.thread_time` のままである。
* 周波数は、5 ms の空回しを 20 回行い、いちばん速い回を採る。空回し中に別の過程へ譲った回は、サイクル数が少なく出るからである。
* 校正の誤差は、空いた機械で +0.1%、21 過程で全コアを埋めた状態で +0.1%（最悪 +0.2%）だった。IKA-452 と同じ 0.3 秒の空回しは、負荷時に最悪 +65% 外れた。
* 本番の生成の形で 1,500 局を回すと、CPU が実時間を 5% 以上上回る行は 0 だった。IKA-452 の 600 局の回に新しい検査を当てると、LP の行（CPU 1.938 ms 対 実時間 1.745 ms）など 8 行が上がった。
* 計時が on のときの CPU 負荷は、600 局の 2 回ずつの組で +0.7%（過程木の CPU）だった。実時間の差は雑音を超えず、決められない（§5）。

## 2. 校正

`C:/tmp/ika454/cal.py`・`cal2.py`・`cal3.py`・`ratio.py`。機械は 8 物理・16 論理コア。レジストリの `~MHz` は 4,691。

### 2.1 サイクル数の進み方

3 秒の窓で、サイクル数を `thread_time` の秒（刻み誤差 15.6 ms ÷ 3 s = 0.5%）で割った。

| 状態 | サイクル数 ÷ CPU 秒（MHz、窓ごと）|
|---|---|
| 空いた機械 | 4,679・4,705・4,681 |
| 16 過程で全コアを埋めた状態 | 4,712・4,664・4,811・4,717・4,795 |

負荷時に周波数が下がるなら、値は下がるはずである。下がらなかった。この機械では、サイクル数は一定の周波数で進む計数として扱える。

### 2.2 周波数の決め方 3 通り

「真の値」は、空いた機械の長い窓の 4,680 MHz とした。各 20 回の誤差を出した（`cal3.py`）。

| 決め方 | 費用 | 空いた機械（中央値の誤差、最悪）| 21 過程で全コアを埋めた状態（中央値、最悪）|
|---|---|---|---|
| 0.3 秒の空回し 1 回（IKA-452 の形）| 0.3 s | −0.0%、+0.3% | −3.9%、**+65.2%** |
| 10 ms を 10 回、最速を採る | 0.1 s | +0.1%、+0.1% | +0.0%、+1.2% |
| 5 ms を 20 回、最速を採る（採用）| 0.1 s | +0.1%、+0.2% | +0.1%、+0.2% |
| レジストリの `~MHz` | 0 | +0.24%（固定）| +0.24%（固定）|

* IKA-452 で CPU が実時間を 1 割上回った原因は、0.3 秒の空回しが、負荷時に別の過程へ譲られた分を CPU と見て周波数を低く出したことだと考える。表の最悪 +65% と向きが同じである。差し替え中の周波数は記録していないので、確かめてはいない。
* レジストリの値はこの機械で近いが、TSC と公称周波数が違う機械の保証はない。`QueryPerformanceFrequency` は 10 MHz のタイマーの周波数で、サイクル数と関係がないので、試していない。
* 新しい時計で、空回しの区間の「CPU ÷ 実時間」を出した（`ratio.py`、各条件で別過程が起動時に校正する）。5 ms の区間 400 個と 100 ms の区間 30 個を測った。

| 状態 | 起動時の周波数（MHz）| 5 ms 区間の CPU/実時間（中央値、95 分位、最大）| 100 ms 区間（中央値、最大）|
|---|---|---|---|
| 空いた機械（5 過程）| 4,690〜4,691 | 0.9988〜0.9990、0.9997〜1.0000、1.0001〜1.0007 | 0.9981〜0.9984、0.9989〜0.9992 |
| 21 過程で全コアを埋めた状態（5 過程）| 4,688〜4,690 | 0.9902〜0.9969、0.9995〜1.0001、0.9999〜1.0007 | 0.3853〜0.9874、0.9879〜0.9991 |

* 負荷時の 100 ms 区間が 1 を下回るのは、別の過程へ譲った時間が実時間に入るからで、時計の誤差ではない。最大が 1.0007 を超えない点が、校正の誤差の上限である（+0.07%）。
* 負荷時の測定は 8 本回した。起動の import が 1.2 秒以上かかった最初の 5 本を負荷時とした。残り 3 本は import が 0.16 秒に戻っていて、負荷が終わったあとの測定なので、表に入れていない。
* 本番の形（`C1`、21 ワーカーが同時に校正する）で、報告に残った周波数は、ワーカー 21 本が 4,668〜4,691 MHz、推論サーバ 2 本が 4,690 と 4,691 MHz だった。空いた機械の 4,690 に対して、最大 −0.5% である。この分だけ CPU 秒は高く出る（最悪 +0.5%）。
* 許容は 5% にした。校正の誤差（最悪 +0.2%）の 20 倍あり、IKA-452 の 1 割（+8〜12%）より小さい。

### 5.1 新しい時計の表（`C1`、1,500 局、ワーカーの段の CPU）

IKA-452 §12.3 の旧い表と比べた。`GT` は 600 局の `thread_time`、`GX` は 600 局の差し替えのサイクル数（0.3 秒校正）。`percall.py`（`C:/tmp/ika452b/`）と `shares.py` で、ワーカーの借り行でない段の CPU に対する割合を出した。

| 項目 | GT（`thread_time`）| GX（差し替え）| C1（今回）|
|---|---|---|---|
| 待ちの行 7 行の CPU の和（1 局あたり）| 72.5 ms | 24.0 ms | 21.0 ms |
| 同、段の CPU に対する割合 | 20.6% | 5.9% | 6.7% |

* LP と信念の補完は、GX では実時間を上回っていた（1.938 対 1.745、11.093 対 10.616）。今回は実時間より小さい（1.638 対 1.754、9.163 対 10.328）。

* 1 局あたりと 1 回あたりは、同じ局（種 45201）の別の局数の回である。1 回あたりの値は、行ごとの CPU ÷ 呼び出し回数。

### 5.2 計時 on の負荷（`thread_time` との ABBA）

一時的に環境変数で `thread_time` に戻せる版を作り、ABBA で回した。環境変数の分岐はコミットしていない。

| 局数 | 新（サイクル）の実時間 | 旧（`thread_time`）の実時間 | 新の過程木の CPU | 旧の過程木の CPU |
|---|---|---|---|---|
| 600 | 44.9 s・46.5 s | 42.5 s・43.0 s | 462.6 s・464.5 s | 458.3 s・462.1 s |
| 1,500 | 119.4 s・121.3 s | 141.3 s・115.0 s | 1,079.4 s・1,075.4 s | 1,080.3 s・1,057.1 s |

* 過程木の CPU: 新が旧より 600 局で +0.7%、1,500 局で +0.8%。段の入り口の増分（1 局 1〜2 ms）は 0.3% 以下になるはずで、残りは校正 0.1 秒 × 約 25 過程（2〜3 CPU 秒）と合う（600 局で 0.5%、1,500 局で 0.2%）。局数が増えると、割合は下がるはずである。1,500 局の +0.8% はこの説明より大きい。
* 実時間は、新が旧より 600 局で +6.8%（2 回ずつの平均）。旧の 1 回（1,500 局の `D1`）は、起動の行が 344.7 s（他の 3 回は 44〜54 s）と外れていて、他の過程の影響が疑われる。この回を除くと、新 120.4 s、旧 115.0 s で +4.7%。
* 増える費用の見積もり（0.1〜0.2% と校正の固定費）より、実時間の差のほうが大きい。原因は見つけていない。雑音（同じ側の 2 回の差は、600 局で 3.5%・3.5%、1,500 局で 1.6%・23%）を超えるかどうかは、この回数では決められない。
* 本番の生成は計時を on にしない。off のときは時計が `time.thread_time` のままで、`POKEURAOU_TIMING` が無い限り何も変わらない。

## 6. 確かめていないこと

* 他の機械（周波数が違う、ハイブリッド CPU）で、サイクル数が一定の周波数で進むこと。この機械の 3 秒窓 8 本だけで確かめた。
* IKA-452 の差し替えの校正値が、負荷時に低く出たという推定。当時の値は保存されていない。
* 5.2 の実時間の差（+4.7〜6.8%）の原因。過程木の CPU の増分は +0.7〜0.8% で、これは見積もりの 2〜4 倍である。
* `tools/ci_skip_audit.py` の本体の実行（junit を作る全体の実行）。Linux の CI で skip 理由が分類に当たることは、正規表現の一致の目視までである。
* スレッドが多い推論サーバでの時計の読み取り。サーバの報告も `cpu_clock: thread_cycles` と出るのは `C1` の JSON で確かめた（サーバ 2 過程）が、サーバの行の CPU の正しさの検査は行っていない。
* 計測の途中で、他の過程が無いことの確認。`G1` の前は、python と pokeuraou-damage が 0 本、CPU 使用率 26.6% だった。ABBA の各回の前は、確認の呼び出しが拒否されたので、確かめていない。`D1` の外れは、他の過程のせいかもしれない。
