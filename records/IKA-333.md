## 1. 道具（`tools/time_match.py`・`src/pokeuraou/timematch.py`）

```
python tools/time_match.py --out DIR --arm long:seconds=1 --arm short:seconds=0.1 \
    --pairs 300 --sprt 0 10 --parallel 2 [--start N --resume]
python tools/time_match.py --out DIR --arm c10:seconds=10,clock=count --arm c1:seconds=1,clock=count \
    --pairs 200 --sprt 0 10 --parallel 4 --cpu-sets none          # ノード時間: 専有は要らない
```

* **条件**は `名前:キー=値,...`。キーは `seconds`（必須）・`threads`・`cores`・`clock`（wall|count）・`oracle`（sall|none|s<W>）・`levels`（深化の柵。0 は
  `deepen.MAX_LEVELS` で記録なし）・`width_only`・`width`（固定の幅。規則の代わり。`width_only` と合わせて対戦評価の `d1@W`）・`child_q`。
  書かないキーは `tools/play_human.py` が旗なしで打つ既定（IKA-343 の人と打つ打ち手。柵は IKA-342 の 16）。評価モデル（`play_human.DEFAULT_VALUE`）・候補集合（q-nocover、Q が無ければ止まる）・裏の推定も同じ。
  ノード時間の条件だけはスレッドの既定が 1（ノード時間の局はスレッド数で変わらない、IKA-343 §4.1。1 局 1 スレッドなら局を多く並べられる）。
  **1 つ目の --arm が検定側**（Elo はその側の、SPRT の H1 は「その側が elo1 以上強い」）
* **1 局**は `humanplay.play` の局で、人の席をもう 1 つの打ち手にした `TimedGame`:
  * 行動: 両席とも `HumanGame._agent_move` を自分の側から、自分の条件で読む（自分のスレッド・自分の裏の推定。相手の裏について持つ情報は、人と打つ打ち手と同じ公開の情報）
  * **両席を 1 つの過程で順に読む**。読む側はその過程のコアを独り占めし、もう片方は待つ。同時に読ませると、短い側は読みの全部を相手と L3・メモリ帯域・GPU で取り合い、
    長い側は読みの最初の一部だけなので、実時間で公平にならない（人と打つときも AI のコアは考えている間 AI のもの）
  * 交代（ひんしの後）: 両席とも裏の決定化の上の Bayes のゲームを解く（`HumanGame._replacement_mixture` に切り出した。AI 側の解き方そのまま）。持ち時間の外
  * 技の効果の交代: 両席とも AI の選び方（`selfplay._do_self_switch_node`）。持ち時間の外
  * 選出: 2 つのシートの解（`humanplay.solve_entry`）を組ごとに 1 回解き、各席が自分の側の純粋な均衡から 4 体を引く。持ち時間の外で、両条件とも同じ選出
  * ponder（IKA-344）は使わない（ユーザーの判断 9/27）。`Agent(..., ponder=False)` を明示して渡す（agent_drift のため）
* **組**: 構築プールから引いた 1 組の構築で 2 局、条件の側を入れ替え、種と選出の引きは同じ。組の点は検定側の 0・1/2・1（`sprt` の単位）。勝者の無い局（ターンの上限）を含む組は点にせず、理由を残す
* **並列**: `workqueue.run_workers` で組を `--parallel` 個の過程に配る（1 過程 1 局ずつ）。各過程は論理コアの取り分に固定（既定は機械を等分。`--parallel 2` で 0-7 と 8-15 = 物理 4 コアずつ、
  人と打つ既定の 4 スレッドの大きさ。ノード時間では `--cpu-sets none`）。過程が起こす先読みのワーカーも同じ取り分を継ぐ
* **失敗**: 過程が落ちたら最初の 1 つで止まる（`workers.json`、IKA-336）。先読みのワーカーが死んだ過程と、**メモリの見張りが 1 手でも深化を止めた過程**も、その組を書いた後に非 0 で終わる
  （その手は条件どおりの打ち手ではない。`--allow-memory-stops` で続ける）。局の行に読みが答えを出せなかった数（`fallbacks`）・メモリで止めた手（`memoryStops`）・メモリの最大（`peak`）
* **SPRT**: 組の番号の順に、キューが解決した組だけを読む（`match_queue` の StopWhenDecided と同じ形）
* **区切り**: `--resume --start N` で同じ `--out` に続きを打つ（設定が違えば止まる。SPRT は前の組から順に数え直して続ける。前の区切りの `logs`・`workers.json` は `logs.<n>`・`workers.<n>.json` に残す）
* **記録**: `settings.json`（局を決めるものすべて、最初の局の前に。`chunks` に区切り）、`games-worker<k>.jsonl`（1 局 1 行: 側ごとの条件・結果・各手の時計の行 = 秒・計算予算との比・幅・深さ 1 のセル・
  深化のステップ・深さ・セル・最善応答オラクルの問い合わせ）、`logs/`（各過程が起動時に自分の設定を echo）、`sprt.json`、`summary.json`（Elo と区間、条件ごとの分布）
* **OpenMP**: 入口で `openmp.quiet_wait()`（IKA-360、torch より前）
* **drift の検査**: `tools/agent_drift.py --check` に、`timematch` の `Agent(...)` が `play_human` の `Agent(...)` と同じ引数を渡すこと、条件の既定が play_human の旗の既定と同じこと、を足した
  （テストで両方の形に故障を入れて落ちることを確かめた）

### 1.1 humanplay・deepen に足したもの（人との局は変えない）

* `HumanGame._replacement_mixture(pos, options, side, shown, leads)`: `_replacement` の中の Bayes の解きを、どちらの側からでも呼べる形に切り出した（IKA-352 の `replacement_matrix` はそのまま）。`replacement_options` も同様
* `play(..., entry=None, make_game=None)`: 選出の解を渡せる（組の 2 局で 1 回解く）、`HumanGame` の代わりの局を作れる
* `Agent.width`・`plan_move(..., width=)`: 固定の幅（既定 None = 規則）
* `deepen.workers_alive(reg)`: 先読みのワーカーの生きている数

## 3. 途中で見つけたこと

### 3.1 torch の OpenMP の待ち回し（→ IKA-360、master に取り込み済み）

実時間の実行の最中にユーザーが「計算資源の使い方が変だ」と指摘した（過程の system 時間が 4 割超）。スレッドごとの CPU と起点の DLL を測ると、torch の Intel OpenMP（libiomp5md）の 7 スレッドが、
並列領域の後の 200 ms（`KMP_BLOCKTIME` の既定）ずっと yield しながら回っていた（本体で user 2.2 + sys 1.9 s / 5 s、先読みワーカーで各 1.0 + 1.8 s / 5 s）。
`KMP_BLOCKTIME=0` で人の局は同じバイトのまま CPU 175 s → 40 s、実時間 −17%。データ生成には効かない（推論サーバ経由）。詳細は records/IKA-360.md。
t01・aa・c01 はこの直しの前の実行なので、実時間の打ち手はその分だけ遅かった（両条件とも同じ過程で同じだけ）。

### 3.2 GPU の上限超え

c01 の 2 本目（6 過程、非専有 `--gpu`）の終わり 13:45〜13:52 に、カード全体の使用が 11.1 GB に達し（私の過程 6 本 + 他の常駐分）、メモリの見張りが 31 組（組 160〜199）で計 912 手の深化を止めた。
その組は数から外した（§2.1）。これを受けて、1 手でもメモリで止めた過程は実行ごと止める形にした（§1）。ノード時間の並列は 4 過程に下げた（w36w8 の最大 9.2 GB）。

### 3.3 IKA-344 の ponder の口

途中まで ponder の条件（後に読む席が、先の席の使った単位まで読み続ける）を作ったが、ユーザーの判断（ponder は使わない）で外した。

### 3.4 試験の揺れ

`tests/test_humanplay.py::test_a_pondering_agent_reads_until_the_person_chooses_and_replays`（IKA-344）が、`-n 4` で機械が混んでいるとき 1 回落ちた（1 秒考える人の間に読みが予算を越えることを見る試験で、
混むと越えない）。単独では通る。別課題の候補（§7）。

## 5. テスト（`tests/test_timematch.py`、8 件。port を使う。torch・CUDA・data は要らないので CI の skip の予算は変えない）

* 条件の既定が人と打つ打ち手（`humanplay` の既定）、書き方の誤りは止まる、ノード時間はスレッド 1
* time_match の打ち手が play_human の打ち手（`agent_drift.play_agent_drift` が空）。故障注入 2 つで落ちる: 条件の既定を play_human からずらす（`default_threads` を 7 に）、`Agent(...)` から `halt` を抜く
* 組は条件の側を入れ替え、各決定に両側の手の行が 1 つずつ、各行の計算予算はその側の条件のもの、代わりの手 0。陽性対照: 秒の多い条件の深化の計算予算が大きい
* ノード時間の組は 2 回打ってバイト一致（実時間の欄を除く）、種を変えると別の局（比較の感度）、深化が走った局で比べている
* 人の席の交代は Bayes で解く（選択肢が 2 以上の交代を人の席が解いたこと）
* 組の点（0・1/2・1、勝者の無い局を含む組は外す）、番号の順の先頭、区間
* 固定の幅が規則の代わりになる（36 と 8 の行、規則なら 36 を選ばない局面での対照）
* `tests/test_openmp.py` の入口に `tools/time_match.py` を足した
