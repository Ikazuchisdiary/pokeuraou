## 1. 縛りの定義（段 1）

縛りは port のダメージ計算から作る（`rust/src/bind.rs`）。場の 2 体と相手の 2 体の、向きのある 8 組を技ごとに判定する。控えは含めない。

| 項目 | 決めたこと |
|---|---|
| 1 撃 | 急所なしの 16 乱数のうち、相手の今の HP を削り切る乱数の割合。必中急所の技（willCrit）は急所で計算する。命中は読まない |
| 範囲技 | 当たる相手が 2 体以上なら 0.75 倍で、両方の相手に当てる。味方にも当たる技（allAdjacent）は、味方が生きていれば 0.75 倍 |
| 耐える効果 | きあいのタスキ・がんじょう（HP 満タン）と、ばけのかわは計算器の扱いのまま |
| 連続技 | 最小回数（スキルリンクは最大回数）で、同じ乱数が毎回出るとみなす。タスキとがんじょうは効かない |
| 先手 | 技の優先度（いたずらごころ・はやてのつばさ・グラススライダーを含む）、次に実効の素早さ（おいかぜ・まひ・スカーフ・天気の特性）。トリックルームでは逆にする。同速は 0.5 |
| 相手の技 | 分からないので優先度 0 とみなす |
| 止まる先制技 | サイコフィールドで地面にいる相手と、ビビッドボディ・じょおうのいげん・テイルアーマーの側への先制技は、倒せないものとして数える |
| 使える技 | PP が残り、かなしばりでない技。こだわり・アンコール・あばれる・溜め技で固定された体は、その技だけ |

組 (X, Y) の値は、技 m ごとに「先手（1・0.5・0）× 1 撃の割合」を出し、その最大を bind(X, Y) とする。先手を問わない最大を ko(X, Y) とする。

符号化の列（revision 4）は次のとおり。どれも 1/2048 の倍数で、float32 で正確に表せる。

| 列 | ブロック | 値 |
|---|---|---|
| `bind_out` | 1 体 | この体が縛っている相手の bind の和 / 2 |
| `bind_in` | 1 体 | この体を縛っている相手の bind の和 / 2 |
| `ko_out` | 1 体 | この体が倒せる相手の ko の和 / 2 |
| `ko_in` | 1 体 | この体を倒せる相手の ko の和 / 2 |
| `foes_bound` | 側 | 相手の各体について、自分の体の bind の最大をとった和 / 2 |
| `double_bind` | 側 | 相手が 2 体いるときの、その最大の小さいほう（両縛り） |
| `secure_bound` | 側 | `foes_bound` のうち、縛り手が相手に縛り返されていない分 |
| `spread_double` | 側 | 1 体の範囲技 1 発で相手 2 体をともに縛る強さ |
| `spread_ally_ko` | 側 | その範囲技が味方を倒す乱数の割合 |
| `spread_wide_guard` | 側 | 範囲技の両縛りに対し、相手がワイドガードを持つ |
| `spread_fake_out` | 側 | 範囲技の両縛りに対し、相手のねこだましがその体を止められる |

* 控えの行の 4 列は 0 にした。こうすると 1 体の行は場の体と場の状態だけで決まる。`beliefnode._patched` が控えの行を別の局面の符号化から写しても、値は正しいまま残る。
* 両縛りは、縛られた相手の数が 2 のときに数える。縛る側は 1 体でも 2 体でもよい。1 体の範囲技による両縛りは、まもるで 1 体を守っても、もう 1 体が倒れる。そこで `spread_double` を別に持つ。
* ねこだましの判定: その体が場に出て最初の行動で、範囲技より先に動ける（優先度が高い、または同じ優先度で速い）。相手がゴースト・せいしんりょく・りんぷん・おんみつマントのときは止められない。
* 縛りを解く技は `bind.rs` の `RELEASE_*` に 1 か所でまとめた。ワイドガード、ねこだまし、このゆびとまれ・いかりのこな、まもる系（まもる・みきり・ニードルガード・キングシールド・トーチカ・スレッドトラップ・かえんのまもり・ブロッキング）。列として読むのはワイドガードとねこだましだけで、ほかは技の埋め込みで網が読む。

## 2. 両方の符号化の一致の扱い

* 1 ターンの解決とダメージ計算は port だけが持つ。縛りの列も port だけが計算する。
* 学習の配列は port の `encode-games` が作る。探索の葉も port が符号化する。
* Python の `Encoder.encode_positions` は計算器を持たないので、port に `bind` 要求で局面を送り、答えの列を自分の配列に書く。選出の 8,100 局面は 900 の先発 4 体の組でできているので、場の体・場の状態・気絶数のオブジェクトが同じ局面は 1 回だけ問う。
* `beliefnode._patched` は控えの行だけを読むので、`bind=False` で問わない。
* port の側は、葉ごとに全部を計算すると重い。そこで、体（HP は計算器が読む旗だけ）・場・組ごとのダメージ乱数を正確なキーで覚える（`BindCache`）。倒せる乱数の割合は、葉ごとの HP で数え直す。

## 4. 費用（段 1）

### 4.1 葉 1 つあたり（`C:/tmp/ika429/fillbench.py`）

gen-4 の記録から 300 局面を取り、幅 12 のメニュー（`narrow`）と `Budget.matrix()` で node を埋めた。port の子が header に書く時間（`resolveUs`・`encodeUs`・`bindUs`）を葉の数で割った。キャッシュの作りを変えながら測った。

| 版 | 縛りの列（µs/葉） | 縛り以外の符号化（µs/葉） | 解決（µs/葉） | 組のキャッシュの当たり |
|---|---|---|---|---|
| キャッシュなし（局面ごとに全部を計算） | 5.4 | 2.5 | 19.6 | |
| 組のキャッシュ、体のキーに HP を含める | 5.6 | 2.5 | 19.1 | 61% |
| 体のキーは計算器が読む HP の旗だけ | 3.4 | 2.4 | 17.7 | 82% |
| 体と場もキャッシュから引く、KO の数え方を直接に（今の版） | 2.5 | 2.2 | 16.5 | 82% |
| 今の版、同じ node を 2 回目に埋めたとき（全部当たり） | 1.5 | 2.6 | 19.3 | 100% |

* 1 回目の値は 300 局面がばらばらの局から来るので、当たりが少なめに出る。実際の生成では同じ局の node が続く。
* 記録の判断局面（9,091）だけを `bind-bench` で計算すると、縛りの列は 1 局面 11.2〜12.9 µs、符号化は 5.2〜7.1 µs だった。判断局面どうしは状態が違うので、キャッシュはほとんど当たらない（当たり 5%）。

### 4.2 生成 1 局あたり（`tools/profile_stages.py generation`、48 局、CPU の葉）

本番と同じ形（プール regmc-matchupweb、裏は非公開、幅 12、`--rank-leaf`、`--rank-fill q-nocover`、value-mc4st x1、q-mc4st、選出は `data/selection-solved/value-mc4st`）で、葉だけ CPU にして 4 worker で 48 局を打った。port の子が数える時間は葉をどこで順伝播しても変わらない。

| 段 | 48 局の計（秒） | 1 局あたり |
|---|---|---|
| port の解決（`rust.child.resolve`） | 4.9 | 102 ms |
| port の符号化（`rust.child.encode`、縛りを含む） | 1.3 | 27 ms |
| 　うち縛りの列（`rust.child.bind`） | 0.6 | 12.5 ms |
| Python から port への `bind` 要求（Q の根の符号化） | 0.1 | 2 ms |

* port が符号化した葉は 1 局 4,045（194,196 / 48）。縛りの列は 1 葉 3.1 µs だった。
* 本番の生成の 1 局は CPU 0.894 秒（IKA-427 §5 の B 腕）。足される分は約 14.5 ms で、+1.6% と見積もった。
* 選出の解き（1 組 8,100 局面）の符号化は、縛りの列を含めて 0.248 秒、含めずに 0.183 秒（3 組、A B B A の平均、`selbench.py`）。1 組あたり +0.065 秒になる。

### 4.3 正確さのキャッシュの確かめ

* `--features bind-verify` の build は、葉ごとにキャッシュありとなしの両方で縛りの列を計算し、違えば止まる。gen-4 の別の 600 局面（175,077 葉）で止まらなかった。
* 対照: `--features bind-verify,ika429-cache-control`（キャッシュのキーから HP の旗と HP を抜いた build）は、最初の局の 2 ターン目の葉で止まった。比べが差を見つけられることを示した。

## 5. 出現率と勝敗（段 1）

### 5.1 出現率（gen-4 の 24 ファイル、20,000 局、168,727 の手番）

「確定」は、先手が確実で 16 乱数すべてで倒せることを指す。「乱数込み」は bind が 0 より大きいこと（乱数の一部で倒せる、または同速）を指す。

| 状態 | 確定 | 乱数込み |
|---|---|---|
| どちらかの側に縛りがある手番 | 66.8% | 77.0% |
| 側が相手を 1 体以上縛る（側ごと） | 41.5% | 50.2% |
| 両縛り（側ごと） | 8.1% | 12.3% |
| 　うち 1 体の範囲技 1 発による | 0.9% | 1.4% |
| 　うち 2 体による | 7.2% | 10.9% |

* 範囲技による確定の両縛りは 3,068 の側にあった。そのうち相手がワイドガードを持つのは 6.6%、相手のねこだましで止められるのは 8.0%、範囲技が味方を倒しうるのは 2.1% だった。

### 5.2 縛りの差ごとの勝率

縛りの差は、側 0 が確定で縛る相手の数から、側 1 が確定で縛る相手の数を引いたもの。

| 差 | 手番（gen-4） | 勝率（gen-4） | 探索の値との差（gen-4） | 手番（IKA-427 B 腕） | 勝率（B 腕） | value-mc4st x2 の予測との差（B 腕、se） |

| −2 | 8,621 | 28.6% | −0.9 点 | 4,457 | 30.6% | −3.6 点（0.5） |
| −1 | 38,072 | 35.1% | −0.5 点 | 18,914 | 36.6% | −1.5 点（0.3） |
| 0 | 74,913 | 49.5% | +0.0 点 | 36,967 | 50.9% | +0.9 点（0.2） |

| +2 | 8,797 | 69.1% | −0.4 点 | 4,440 | 70.8% | +4.8 点（0.5） |

* gen-4 の「探索の値との差」は、記録の `search_value`（生成の探索が出した値）と勝敗の差の平均。探索は 1 ターン先の葉を読むので、縛りの差ごとにも勝率とほぼ合う。

* 差 0 の行でも +0.9 点あり、B 腕の局では側 0 の勝ちが予測より多い。縛りの傾きはこの水準のずれとは別に見える。
