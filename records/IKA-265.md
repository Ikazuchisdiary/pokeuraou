# IKA-265: LP を HiGHS に直接渡して 2.2 倍速く、belief の span の平均をまとめて計算 —— 局はビット一致。ワーカーの CPU は 1 局 0.043 秒（11%）減ったが、全体では 1.02 倍にとどまる

2026-09-25。担当 IKA-265（worker）。master 8199f94 から切った `ika-265-lp-belief`。測定は 8199f94 どうしの前後（A = master、B = この枝）で、報告の直前に master（317fcc0、IKA-264 入り）を取り込んだ。

答えた問い: **局を変えずに（前後で局がビット一致、LP は同じ頂点）、ワーカーの Python の LP（solve_bayesian）と belief の span ループをどこまで削れるか。そのとき 1 局の CPU 秒と局/分はどう動くか。**

## 1. 結論

* **LP**: `scipy.optimize.linprog(method="highs")` の前後処理（入力の検査・整形・結果の組み立て）を飛ばし、同じ HiGHS に同じモデル（同じ列順の疎行列・上下限・選択肢）を渡すようにした（`equilibrium._lp`）。作り方が同じなので、返す頂点はビット単位で同じになる。**lp 段の CPU は 1 局 0.079 → 0.035 秒（−55%）**
* **belief**: `belief_payoffs` の span ごとの `float(values[idx] @ w)` を、`spanmean.SpanTable` でまとめて計算するようにした。**同じ double を返す**: OpenBLAS の `ddot` は長さ 16 未満では「fma を順に重ねる」ループなので、それを列ごと・全 span まとめて、fma を正確に模して計算する（下の 3）。長さ 16 以上（2.6%）と、模し方が合わない機械ではこれまでどおり 1 span ずつ `@` で計算する。**belief 段の CPU は 1 局 0.065 → 0.058 秒（−11%）**
* **足し順は変えていない。** 前後で 1,200 局・14,137 決定が searchValue の最後の桁まで一致し、本番の `data/selfplay-mc0` の gameIndex 0〜1199 とも一致した（取り込み後も同じ）
* **全体は小さい**: ワーカーの CPU は 1 局 0.398 → 0.355 秒（−0.043、B の 8 本はすべて A の 8 本より小さい）。合計の CPU 秒/局は 1.141 → 1.114（−2.4%）、局/分は 730.6 → 746.5（+2.2%）。見込みの 1.08 倍には届かない。理由は二つ
  * belief 段の 0.064 秒のうち、span ループは一部でしかなかった（1 本で測ると span ループは 1 局 約 9 ms）。残りは `_patched`・`_stacked` の配列の写しなど（6 の候補 5）
  * `port._encoded` のループはまとめても速くならなかった（1 fill あたり平均 100 span で、1.03 倍）ので、元に戻した。port.py は変えていない
* port（子）とサーバのコードは前後で同じ。port の CPU 秒/局は本ごとに ±0.02 揺れ（A 0.567〜0.600、B 0.583〜0.609）、それが局/分のばらつきの大半になる

## 2. LP: 何を使い、どれだけの大きさを何回解くか

* `solve_bayesian` は 1 回で LP を 2 つ（こちらの maximin と相手の minimax）解く。どちらも scipy 1.18.1 の `linprog(method="highs")`（HiGHS の双対単体法、presolve あり）
* 数（60 局・1 ワーカーで全部の入力を写した。`C:/tmp/ika265/cap`）: **1 局 22.6 回（段の数えでは 22.9 回）、LP は 45.8 回**。同じ入力の 2 度目は 0/1,358
  * 型（クラス数 K）: K=1 が 608 回、3 が 386、6 が 341、4 が 15、10 が 8
  * こちらの手の数 m: 12 が 868 回、1 が 239、2 が 120、それ以外が少し。いちばん大きいのは 12 手 × 6 クラス × 12 手（制約 72 本、変数 18 個）
* 1 本（競合なし）で測った 1 回の LP: linprog 860 µs、直接の呼び出し 290 µs。そのうち HiGHS の `run` が 170 µs、`_Highs()` の生成が 33 µs、モデルの組み立てが 57 µs。solve_bayesian 1 回は 2.0 ms → 0.8 ms
* **同じ頂点であること**:
  * 写した 1,358 回（LP 2,716 本）で、solve_bayesian の出力の全部の欄（value・両者の戦略・EV・duality_gap）が master とビット一致
  * `solve` も、乱数の行列 700 個（うち 200 個は値を 1/4 に丸めて同点を作ったもの）でビット一致
  * 手で組んだ列順の疎行列は、`csc_array` が作るものと indptr・indices・data が一致（300 問 × 2）
  * **正の対照**: 同じ HiGHS でも presolve を切ると、2,716 本中 465 本で x がビット単位で変わる。比べ方は違いを見分けられる
* 成否の判定は linprog と同じ: HiGHS が optimal を返し、そのうえで linprog 自身の残差の検査（`_check_result`、tol 1e-9）を通すこと。scipy の非公開の場所（`_highspy._core`・`_linprog_util._check_result`）が動いたら import が失敗し、linprog に戻る（テストで両方の道を比べる）

## 3. belief: span の平均を同じ double で

* span の長さ（60 局・311,468 span）: 1 が 42%、2 が 29%、4 が 9%、3 が 5%、6 が 4% …、16 以上が 2.6%（16 がほとんど）
* **numpy の 1 次元 float64 の `@` が何をしているか**（`C:/tmp/ika265/ddot_probe.py`、長さごとに 300 組）: この機械の OpenBLAS 0.3.34（DYNAMIC_ARCH、Haswell のカーネル）では、
  * 長さ 1〜15: `dot = fma(x[k], w[k], dot)` を k の順に重ねたものと 300/300 一致。丸めた積を順に足すものとは 2 で 251/300、15 で 200/300 しか一致しない
  * 長さ 16 以上: どちらとも合わない（ブロックに分けた別の道）
* そこで長さ 16 未満の span は、長い順に並べて「k 列目」を全 span で同時に進める。fma は倍精度だけで正確に模す（Dekker の正確な積と Knuth の正確な和、その尾を「奇数への丸め」にしてから 1 回丸める。Boldo・Melquiond の方法）。有理数で計算した真の fma と 28,572 組中 28,572 組一致
* 列 1 つにかかる numpy の呼び出しは span の数によらず約 20 回、span を 1 つずつ `@` で読むのは 1 回あたり約 4 回ぶん。そこで 1 回ごとに「何列目までまとめるか」を安いほうに選び、それより長い span は 1 つずつ読む。どちらを選んでも同じ double になり、変わるのは速さだけ
* 守り: 値か重みが大きすぎる・小さすぎる（2^900 以上、または 2^-900 未満の 0 でない値）か、有限でないとき、またはプロセスの最初の確かめ（長さ 1〜15 を各 64 組、`@` そのものと比べる）が合わないときは、全 span をこれまでどおり 1 つずつ `@` で読む
* 写した実物（20 局で 682 表）で旧ループと比べた。行列はすべてビット一致、速さは 1 本・競合なしで
  ```
    どこ                          表   span/表  読んだ span/表   旧        新        比

    belief の汚れセル（まとめて）    109   447.2     447.2          744 µs    345 µs    2.2 倍
    port._encoded                  413   100.1     100.1          170 µs    165 µs    1.03 倍（戻した）
  ```

## 9. 追記（同日）: spanmean は外した。入れるのは LP だけ
