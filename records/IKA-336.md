# IKA-336: worker が落ちても局がそろってしまう —— worker の失敗を数えて名前と理由を出し、計時と対戦評価は最初の失敗で止める。生成は worker の 4 分の 1 まで続け、それを超えたら止める。サーバの OOM は worker に `ServerOutOfMemory` として届く

2026-09-26。担当 IKA-336（worker）。master be59cb3 から切った `ika-336-worker-failures`。
出力は `C:/tmp/ika336/`（コミットしない）。$M/data は読んだだけ。

## 1. 何が起きていたか

* 生成（`generate_queue.py`）と対戦評価（`match_queue.py`）は、`workqueue.run_workers` で局を配る。
  - worker が落ちると、握っていた局は列の先頭に戻る。残りの worker がそれを打ち直す。
  - 局は番号で種が決まるので、打ち直した局はバイト単位で同じになる（IKA-77。`queue_restart.py` で 600/600 一致）。
  - そのため局はそろう。落ちた worker は、終わりの 1 行の「N worker(s) failed」と終了コード 1 にしか出なかった。
* 計時の道具 `profile_stages.py` は、駆動の終了コードが 0 でなくても「the run exited 1」と 1 行出すだけだった。表を出し、summary.json を書き、**自分は 0 で終わった**。
  - ABBA の駆動（C:/tmp の run.py・abba_run.py の形）は `profile_stages` の終了コードしか見ない。そのため worker が死んだ本もきれいな本として読まれた。
  - IKA-307 の値段の本（d1@18〜40）では、24 のうち 18〜23 の worker が OOM で落ちた。それでも 300 局がそろい、CPU/局と壁時計だけが黙って汚れた。
* worker に届くサーバの OOM は `RuntimeError: inference failed: OutOfMemoryError: ...` で、ほかの失敗と区別がつかなかった。
  - サーバの側も、OOM を返したことをログに残していなかった（返答の `error` に入れるだけ）。

## 3. 直したこと

### 3.1 `workqueue.run_workers`

* worker が 0 以外で終わると、その場で次の 3 行を出す。
  ```
    WORKER FAILED: worker 1 exited with 1 after 2s (1 failed so far, 283 job(s) unclaimed)
      out of memory: RuntimeError: inference failed: OutOfMemoryError: CUDA out of memory. 3.26 GiB allowed
      log: ...\logs\worker1.log
  ```
  - 理由の行は worker のログの末尾 64 KiB から取る（`worker_error`）。
  - traceback の最後の例外の行を探す。stdout は traceback の後で flush されるので、最後の行とは限らない。
  - OOM の行（`out of memory` / `OutOfMemory`）があれば、それを先に出す。
  - Windows の異常終了（NTSTATUS）は 16 進でも出す。
* 失敗の数が `max_failures` を超えると、SPRT の停止と同じ止め方をする。
  - 列を閉じて、それ以上配らない。握っている局は打ち終えて書く。
  - 既定は 0（最初の失敗で止める）。`None` は止めない。
* 走りごとに `out_dir/workers.json`（`RUN_RECORD`）を書く。きれいな走りでも書く。
  - 中身: 失敗の数、OOM の数、失敗ごとの worker・終了コード・秒・理由・OOM か、止めた理由、終えた局、打たずに残った局、放棄、落とした局、打ち直し、SPRT の停止、サーバの OOM 返答の数、秒。
  - 始めに 1 回、失敗のたびに 1 回、終わりに 1 回書き直す。長い生成の途中でも、今の数が読める。
  - bytes で書くので LF。
* 終わりの echo には、0 も含めて「, N worker(s) failed」を必ず出す。
  - 0 のときに黙ると、数えない道具と見分けがつかないため。
  - 止めたときは `STOPPED FOR A FAILED WORKER: ...` を出す。止めずに続けたときは「its wall clock is not the configured run's」を出す。
* 呼び出し側は `outcome` に同じ dict を受け取れる（match_queue が SPRT の行に使う）。
* 終了コードの規則は前と同じ（残り・放棄・失敗・monitor の故障のどれかで 1）。

### 3.2 サーバの OOM（`inference.py`・`inference_server.py`・`qrank.py`）

* サーバの `_Handler` は、例外が OOM なら返答に `oom: true` と `capGb`（`--cuda-memory-gb`）を付け、`server.note_oom` を呼ぶ。
  - OOM かどうか: 型名が `OutOfMemoryError`、または文字列に "out of memory" がある。
  - `note_oom` は数え、stderr に `out-of-memory reply #N to a 'score' request (cuda memory cap: 3.5 GB, IKA-334): <error>` を 1 行出す。
  - 目印 `workqueue.SERVER_OOM_MARK` を駆動と共有する。駆動は `server_logs` の中のこの行を数えて `serverOutOfMemory` に入れる。
* worker の側（`RemoteValue` の 2 か所、`RemoteQ._ask`）は `inference.request_failed` で例外を作る。
  - OOM なら `ServerOutOfMemory`（`RuntimeError` の子）で、文言は `inference failed: the inference server ran out of CUDA memory (its cap: 3.5 GB, --cuda-memory-gb, IKA-334) -- OutOfMemoryError: ...`。
  - OOM でなければ前と同じ `RuntimeError("inference failed: ...")`（文字列まで同じ）。
* サーバの挙動（答え・上限・ゲート）は変えていない。OOM のときに返答へ 2 つの鍵が増え、ログに 1 行増えるだけ。

### 3.3 生成の既定をどうしたか（止めるか、印を付けるか）

**4 分の 1 までは続ける。それを超えたら止める。局には印を付けない。**

* 印を付けない理由: 打ち直した局は、落ちた worker が書いたはずの局とバイト単位で同じ（局の種は番号で決まる、IKA-77）。局の中身は失敗で変わらず、印を付けても区別する中身が無い。
  失敗が壊すのは速さと、その走りの時間の数字だけである。それは workers.json と echo に残る。
* 最初の 1 つで止めない理由: 数時間の生成（IKA-331）が夜中の 1 つの失敗で止まると、誰かが見るまで機械が空く（「空いた機械は黙った失敗」）。落ちた worker は局を 1 つも失わない。
* 4 分の 1 を超えたら止める理由: そこまで落ちるなら、失敗は事故ではなく走りの状態（上限が足りない OOM、壊れた局）である。速さも 4 分の 3 を切る。
  - 止め方はこうである: 握っている局は書き、`queue_restart.py where` で最初の欠けを出して再開する。
  - 同じ局が 3 回 worker を殺すと、前からその局は放棄される（`MAX_ATTEMPTS`）。
* 失敗は 1 つめから、その場で `WORKER FAILED` と理由を出し、workers.json に書く。監視（Monitor の grep）は `WORKER FAILED` を見ればよい。
* 計時として生成を回すときは、`profile_stages` が 0 を渡すので、最初の失敗で止まる。
  `generate_queue.py` を直接計時に使う駆動は、`--max-worker-failures 0` を付けること。

## 5. 限定と別課題の候補

* 本物の GPU で、サーバの上限を超えさせた OOM の端から端までの確かめはしていない（GPU は他の担当が専有中）。
  サーバの OOM の判定は、torch の `OutOfMemoryError` の型名で行う。torch 2.11 の CUDA の OOM はこの型である。
* worker を立て直す（落ちた worker の代わりを起こす）ことはしていない。生成は 4 分の 1 までは速さを落として続く。
* 別課題の候補:
  - **サーバの OOM を worker が待って再試行する**。上限は答えを変えないので、少し待って同じ要求を送り直せば同じ答えが返る。
    生成と対戦評価は落ちずに済む。計時の本では再試行の回数を数えて失敗扱いにする必要がある。
  - **静的に割る並列の道具**（`q_teach.py`・`endgame_exact.py`・`deep_targets.py`・`refine_signals.py`・`rank_fill_menus.py`・`bench_workers.py`、tools/*.sh）。
    打ち直しは無いので黙ってそろうことは無いが、失敗の理由を名前つきで出す形はそろっていない。
  - 列の終わりの競争: 他の worker が全部抜けた後に落ちた worker の局は、列に戻っても打つ者がいない。「left unplayed」で終了 1 になる（前からの挙動。テストの初版で見えた）。
