## 3. 機械は CPU で頭打ち（GPU ではない）

* この機械は 8 物理コア・16 論理コア（SMT）。定常の busy は 12.7〜13.1 論理コアで、物理コアは埋まっている。
  タスクマネージャの「CPU 100%」はこれ
* **同じ局を 1 ワーカー・1 サーバで打つと（o1、60 局、競合なし）CPU 秒/局は半分**: 合計 0.591（ワーカー 0.201・
  port 0.311・サーバ 0.079）。24 本では 1.18。SMT と競合で同じ仕事の CPU 秒が約 2 倍になる。割合は同じ（34/53/13%）
* 局/分 ≈ busy ÷ CPU 秒/局 で読める。**正の対照**: d1（CPU 1.495）の予測 514 局/分に対し実測 526、s1（1.256）の
  予測 611 に対し 608。だから「CPU 秒/局を f だけ削れば 1/(1−f) 倍」で見積もる（GPU に当たるまで）
* GPU は 56% 前後（n・t の 4 本）。1 本の中で局/分と比例するとすれば、GPU で頭打ちになるのは約 1,150 局/分。
  **そこへ届くには CPU 秒/局を 1.19 → 0.67 まで、約 44% 削る必要がある**
* 本番の「ワーカー 51%・port 39%・サーバ 10%」（開始 43 分の累計）は、定常（34/51/15%）に選出の解（ほぼ全部が
  ワーカーの Python、下の 6）2,145 回分が乗った値。定常の数で本番の 43 分を足すと、ワーカー ≈ 19,000 s（本番 18,761）・
  サーバ ≈ 4,100 s（3,620）で合う

### IKA-109（価値関数を Rust の子の中で回す）との関係

* 消えるのはサーバ（14.8%）とワーカーの serve.copy/serve.wait の CPU（2.4%）、子→ワーカーの配列の受け取り（rust.body・

* 代わりに子が順伝播を CPU で払う。**機械は CPU で詰まっているので、子の中の順伝播が 1 行あたり約 4 µs（1 本の値）より
  重ければ生成は遅くなる**。GPU は空くが、今の頭打ちは GPU ではない
* 候補 1・2・4（葉の数・行の数を減らす）は、IKA-109 の前でも後でも効く。先にやるほど IKA-109 の損益分岐は楽になる
