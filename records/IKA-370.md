# IKA-370: 全コアの段を積む読みで機械を使い切る —— 内訳を数えた。16 スレッドで頭打ち（実時間あたりのノード時間 3.5〜4.0 倍）の主因は、推論サーバが Q（子の候補集合の順位付け）の依頼を 1 つずつ順に捌くことと、その Q のために port が子の局面ごとに特徴量を作ること。Q を使わない条件では 16 スレッドで 5.56 倍まで伸びる。段の終わりを先読みで埋める・予算を使い切る・ワーカーを増やす、はどれも倍率を上げなかった（既定 off で残した）。予算を使い切ったときに 8 s の読みが 17 s まで延びた不具合は直した

2026-09-28。担当 IKA-370（worker）。master ac59a6d から切った `ika-370-use-all-cores`。
駆動と出力は `C:/tmp/ika370/`（コミットしていない）。

用語は用語集どおり（推論サーバ・評価モデル・候補集合・条件・実行・スモークテスト・ノード時間・実時間・裏）。
「段」「ワーカー過程」は IKA-364・367 の語。「先読み」は、段の終わりにワーカー過程が次の段のセルを読むこと（lc0 の prefetch と同じ考え）。「予算を使い切る」は、実時間の読みで予測に関係なく次の段を始め、予算で打ち切ること。

## 0. 問いと答え

1. **どこで待っているか（§2）**: ワーカー過程の時間は、16 スレッド（ワーカー 15）で python の CPU 15%・port 待ち 28%・推論サーバ待ち 28%・遊び 27%（うち段の終わり 20〜24%）。8 スレッドでは 25%・38%・20%・16%。
   - 同じ機械で、互いに待たない 1 スレッドの読み手を 8・16 並べると、合計 4.98〜5.56 倍・6.23〜6.65 倍。ワーカー過程の組より 1.5〜1.7 倍多い。
   - ワーカー過程の 1 ノード秒あたりの「働いた時間」は、独立の読み手と同じ（1.57 対 1.60 ワーカー秒）。差は遊びとワーカー数（N−1）から来る、と最初は読んだ。
2. **遊びを埋めても速くならない（§3）**: 段の終わりに次の段のセルを先読みすると、遊びは 29% → 13〜17%（16 スレッド）に減った。しかし倍率は 3.67〜3.82 → 3.17〜3.35 に下がった（8 スレッドでも 3.51〜3.56 → 2.95〜3.36）。
   - 先読みはセル 1 つずつの依頼で、推論サーバの往復が 1 ノード秒あたり 47 → 71〜81 回に増え、サーバ待ちが 28% → 38〜44% に増えた。先読みしたセルの 2〜3 割はどの段にも使われなかった。
   - ワーカーの数を 7・8・15・16・24 と振っても 3.4〜4.0 で平ら（同じ条件の 2 回で 3.68 と 3.36。揺れは ±5% 程度）。24 では推論サーバの往復が 43 ms に延びる。
3. **律速は推論サーバ（§4）**: 往復の時間は、依頼の数に対して 1 つの待ち行列（1 依頼 約 4.2 ms、上限 約 236 依頼/秒）とよく合う（8 スレッドで 141 依頼/秒・10.5 ms、16 スレッドで 189 依頼/秒・22.5 ms）。
   - サーバの過程の優先度を上げても変わらない（22.5〜25.5 ms 対 23.2〜29.1 ms）。IKA-364 の推論サーバ 2 つでも 28 ms。CPU の取り合いではなく、カードへの順の依頼が詰まっている、と読む。
   - サーバの中の内訳（16 スレッド、7 局面）: Q の依頼 2,411 回が 1 回 42 ms（スレッドの時間の合計 102 s）、価値の依頼 3,166 回が 1 回 14 ms（44 s）。価値の塊は CUDA graph（512 行以下）が 2,295 回、eager が 871 回（行数の中央 2,101）。
   - **対照: Q を使わない条件**（子の候補集合を損傷順 `n` にした L5）では、推論サーバの往復が 1 ノード秒あたり 23〜30 回、port の読みが 44〜66 回（Q ありは 470〜580 回）に減り、倍率は 1 スレッド 1.23 → 8 スレッド 3.73 → **16 スレッド 5.56**。16 が 8 を上回るのはこの条件だけ。
   - つまり、Q のための port の特徴量（子の局面ごとに 1 回の port の往復）とサーバの Q の順伝播（eager、1 回 42 ms）が、ワーカー過程の時間の半分近くを占める。
4. **予算の使い残し（§5）**: 予測で次の段を始めないため、8 s の読みは予算の 55%（開いた）・61%（裏あり）で止まっていた。最初の深さ 3 の段の予測が実際の 5〜9 倍（a priori の見積もりは数えた費用の 80〜400 倍）。
   - 実時間の読みで予測に関係なく段を始め、予算で打ち切る形（`FILL_WALL`）を作った。開いた 24 局面のうち 12、裏あり 17 局面のうち 6 で 1 段以上先まで完了した。
   - 局面集の損失は動かない: 開いた deep −0.0014（se 0.0024）、R24 +0.0031（0.0021）、裏あり deep −0.0012（0.0012）、R24 +0.0011（0.0007）。進んだ先は深さ 3・4 の段で、今の基準では採点できない（IKA-364・367 §6 と同じ）。
   - 打ち切った段の仕事は答えに入らず捨てる（答えは最後に完了した段）。開いた 24 局面の打ち切った段のセルは 3,000 のうち 1,019（34%）を読んでいた。
   - 既定は off。深さ 4 まで読む基準（IKA-369）ができたら、30〜45 s で判定し直す。
5. **予算で止まらない不具合（§5）**: 予算を使い切る形で、8 s の読みが 8.1〜17.0 s（予算の 101〜212%）かかった。読み手が、打ち切った段のまだ返っていない塊を待っていたため（深さ 2 の塊は最後まで、深いセルは子の読みの区切りまで止まらない）。
   - 待たずに返し、返事は次の読みの初めに受け取るようにした。そのうえで、次の読みの初めにもまだ読んでいるワーカーは待たず、返るまで割り当てから外す。
   - 直した後は 8 局面すべて 8.00〜8.02 s で返った。これは IKA-364 の呼び手の止め（検討の画面の停止）にも効く。
6. **数えた時計は前と同じ（§6）**: master と比べて、1 スレッドと 16 スレッドの数えた時計の読みが 7/7 局面ずつバイト一致（時計の欄と新しい記録の欄を除く）。対照: 1 スレッドと 16 スレッドは 0/7（推論サーバの塊の大きさで最後の桁が変わる、IKA-364 と同じ）。

### 5.2 既定

予算を使い切る形は既定 off。いまの基準では良くなった証拠がなく、深さ 4 の最初の段は IKA-364 で deep の損失を上げている。30〜45 s の手と深さ 4 の基準（IKA-369）で判定し直す。止め方の直し（待たない）は既定で入る。

## 8. 参考にした作り（調整役の依頼。WebSearch・WebFetch で短く、コードは見ていない）

* **KataGo**（設定の説明 `cpp/configs/gtp_example.cfg`）: 1 過程の中で探索スレッド（`numSearchThreads`）が順伝播を依頼し、NN サーバのスレッドがそれを `nnMaxBatchSize` までまとめてカードに送る。カードを満たすには、コア数より多いスレッドが要ることがある（「コア数はあまり関係ない」と説明している）。同じ枝に集まらないよう仮想損失を使う。
  - この課題への当てはめ: いまの詰まりは、推論サーバへの依頼の数（1 秒 約 236 回で頭打ち）と Q の eager の順伝播。KataGo の形は依頼を 1 過程の中でまとめ、1 回の大きな順伝播にする。**採る方向**: 依頼を大きく・少なくする（Q を段ごとにまとめる、Q と価値を 1 往復にする、Q の順伝播を CUDA graph にする）。
  - 1 過程の中のスレッドにする形は、今は**採らない**。Python の GIL と port が別の過程なので、そのままでは移せない（port を同じ過程に入れる課題と一緒に考える）。
* **Leela Chess Zero（lc0）**（UCI の選択肢の説明）: `minibatch-size` でまとめ、まとめが足りないときは `max-prefetch` で近く要りそうな局面を先に評価してキャッシュに入れる。
  - 当てはめ: 段の終わりの先読み（§3.1）と同じ考え。**試して、既定では採らない**。ここでは先読みがセル 1 つずつの依頼になり、詰まっている推論サーバをさらに詰まらせた。lc0 の先読みは、まとめに余裕があるときに同じ依頼に混ぜる。こちらも、先読みを別の依頼にせず、段の最後の塊に混ぜる形なら効く見込みがある（推論サーバの詰まりが解けた後）。
* **Stockfish の Lazy SMP**（Chess Programming Wiki）: 全スレッドが同じ根を読み、共有の置換表だけで同期する。助けのスレッドは深さや手の順をずらし、反復の終わりで待たない。
  - 当てはめ: 段の memo が置換表に当たる。**待たない考えは採る**（先読みと、止めるときに待たない直し）。**深さをずらして並べる形は採らない**。答えは完了した段だけ（深さの混ざった答えの呪い、IKA-362）。
  - 物理コアとスレッド: HT の相手どうしは得が小さいと言われる。こちらの測りでも、8 と 16 の差は Q ありで小さく、Q なしでは 3.73 → 5.56 と伸びた。HT の壁より推論サーバの詰まりが先に来ていた（IKA-364 の「8 物理コアの壁」の読みを改める）。
* **不完全情報のもの**:
  - DeepStack は探索も GPU で、葉の評価をまとめて GPU で行う。Pluribus は CPU だけ（ポーカーの実時間の探索に 2 CPU）。
  - 並列 CFR の最近の論文（arXiv 2605.19928）: CFR の 1 回を段に分け、情報集合と木のノードで並べる。葉の評価は 1 回の GPU の順伝播に積み、CPU の枝と同時に走らせて GPU の時間を隠す。
  - 当てはめ: こちらは行列ゲームの LP で、同期は段の LP だけ。葉を 1 回に積むのは既にある（`STACK`）。**CPU（port）と GPU（順伝播）を重ねる**のは採る候補。1 つのワーカー過程の中で、python → port → 推論サーバが順に待ち合っている（§2）。次の塊の port を、前の塊の順伝播の間に進めればよい。
  - ReBeL の論文は PDF を読めなかったので、書いていない。OpenSpiel は見ていない。
* **(c) スレッド数の決め方**: KataGo は「カードを満たすまで増やし、benchmark で決める」、Stockfish は「物理コア数」。こちらは 7〜16 ワーカーで平ら（§3.2）で、決め手は推論サーバの依頼の上限。Q の詰まりを解くまでは 8 スレッドで十分（残りを検討の読みなどに空けられる）。

## 9. 残り・別課題の候補

* **（第一）ladder の Q を安くする**: Q ありの読みの律速（§4）。
  - (a) 子の局面の Q の特徴量を 1 回の port の往復でまとめて作る（今は子の局面ごとに `rustnode.qfeatures`、1 ノード秒 420 回）。Rust に複数局面の `qfeatures` を足す。
  - (b) 推論サーバの `q_batch` を CUDA graph にする（今は eager で 1 回 42 ms、Q の依頼が推論サーバの時間の 7 割）。
  - (c) Q を段ごとに 1 回に積む（IKA-363 §8。塊ごとに Q を頼むので、塊が小さいほど依頼が増える）。
  - 見込み: Q なしの対照で 16 スレッド 5.56 倍（今の 1.4〜1.5 倍）。判定は同じ実時間の倍率と、Q の候補集合が前と同じか（(a)(b) は同じ答えのはず、(c) は IKA-367 の `q_groups` の約束を変える）。
* **段の値段の当てはめ直し**: 深さ 3 以上の a priori の見積もりが数えた費用の 80〜400 倍。予算を使い切る形を入れないなら、せめて予測を正しくする（予算の 55〜61% で止まっている）。
* **打ち切った段の途中の答え**: 前の段と同じ形の段（長方形を広げるだけ）なら、読み終えた行と列の長方形で答えを作れる。打ち切った段のセルの 21〜34% は今は捨てている。
* **ワーカー過程の中で port と順伝播を重ねる**: python → port → 推論サーバの順の待ちを、2 つの塊を交互に進めて重ねる（並列 CFR の CPU と GPU を重ねる形）。
* **先読みを段の最後の塊に混ぜる**（lc0 形）: 推論サーバの詰まりが解けた後に。
* **IKA-369 の基準づくり（予算なしで全段読む形）**: Q ありの ladder なので、同じく推論サーバの Q で詰まっているはず（8 コアで CPU 24%・GPU 20% は、この課題の 8 スレッドの Q ありの形と同じ傾向）。このブランチの既定は倍率を変えないので、効くのは上の Q の課題。
