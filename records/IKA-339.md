# IKA-339: q-nocover のデータ生成で 1 局の CPU の内訳を測った —— 0.66 秒/局は、ワーカーの Python 52%・port 35%・推論サーバ 14%。GPU の形をした仕事はほとんど残っていない。Q の行列の均衡を両側で 2 回解いていたのを 1 回にした（局はバイト一致）。512 行を超える塊の CUDA グラフは、大きさが 3,357 種類に散るので入れない。profile_stages の定常状態の揺れは、局のファイルを毎回開き直していたのが原因だった

2026-09-27。担当 IKA-339（worker）。master 765ad63 から切った `ika-339-cpu-breakdown`。途中で master 91683b5（IKA-345）と befbe7c（IKA-350、port との行き来の JSON を外した）を取り込んだ。
内訳（§2）は 765ad63 の上で測った数で、ABBA（§7）は befbe7c を A にした。
出力は `C:/tmp/ika339/`（コミットしない）。$M/data は読んだだけ。

答えた問い: **q-nocover が本番になった後（IKA-338）の M-C のデータ生成で、1 局の CPU（約 0.65〜0.8 秒）はどこに行っているか。GPU（使用率 5 割弱）に移せる仕事はあるか。**

## 0. 答え

* **1 局の CPU は 0.660 秒**（計器なし、1,200 局）。内訳は次のとおり（§2）:
  - ワーカーの Python: 351 ms（52%）
  - port: 234 ms（35%）
  - 推論サーバ: 92 ms（14%）
* **GPU の形をした仕事はほとんど残っていない**。残りの CPU は、port の分岐の多いシミュレーション、Python の畳み込みと LP、プロセス間の行き来で、GPU の形をしていない（§3）。
* 候補は 6 つあった。調整役の判断で、この課題では A だけを入れた（§3）:
  - **A: Q の行列の均衡を両側で 2 回解かない**。裏が見えている局面では、両側の順位付けが同じ行列から来る。2.86 回/局の LP が減り、局はバイト一致（§4）。
  - **B: 512 行を超える値の条件の塊を CUDA グラフにする**案は入れない。eager の順伝播 6,240 回の大きさは 3,357 種類に散る。答えは呼び出しの行数で動くので、行を詰めて大きさをそろえることはできない。当たりが 100% でも上限は 1 局の CPU の 3.7%（§5）。
* **profile_stages の定常状態の揺れ（IKA-300 の ±15%）の原因**は 2 つで、どちらも直した（§6）:
  - 進みを読むたびに局のファイルを開き直していて、それが最大 7 秒止まった。IKA-300 の読みの間隔 1.2〜8.6 秒は psutil ではなくこれだった。
  - 300 局の実行は 1 ワーカー 12 局しかなく、最初の局が波になって終わる分が窓に残っていた。
* 計器（既定で off）: Q の要求の段、推論サーバの段、スレッドごとの CPU 秒、port の要求の種類ごとの時計。計器の有無で局はバイト一致（1,200/1,200）。

## 3. GPU に移せる候補（効き＝CPU/局）

```
  候補                                             効き               局              費用   判断

  B 512 行を超える値の塊を CUDA グラフに           上限 −25 ms（3.7%）、 バイト一致      中     入れない（§5）
                                                   現実には 1% 前後
  C Q のグラフの道の後半と pin_memory を減らす     −10〜15 ms（−2%）   同じ kernel なら一致 中   この課題では手を付けない
  D Q の均衡を GPU の反復解法で                    −52 ms（−7.7%）     変わる          大     別課題（強さを確かめる形）
  E qfeatures を JSON から二進に                   −8〜10 ms（−1.4%）  バイト一致      中     別課題（調整役が起票）
  F belief の畳み込みを配列でまとめて              65 ms の一部        加算の順が壁    大     この課題では手を付けない
```

* 本当の意味で「GPU に移す」候補は B と D だけ。B は §5 のとおり割に合わない。D は HiGHS と答えが変わるので局が変わる。
* port との行き来の Python 側（約 84 ms）と E は、「JSON である必要はない」の方針に沿う。調整役が別課題として起票する。

## 4. A: Q の行列の均衡を 1 回だけ解く

* `qrank.prefetch` は、1 つの要求に対して両側が同じ行列を受け取るとき（裏が見えている局面では 1 要求で両側）、両側に同じメモ（dict）を渡す。先に順位付けした側が解いた均衡をそこに置き、後の側はそれを読む（`q.solve.shared` を数える）。
* 解けなかったとき（EquilibriumError・ValueError）も、「解けなかった」ことをメモに置く。後の側は、前と同じく平均の順位に落ちる。
* 両側が 1 つの均衡を共有するので、返す配列は各側でコピーする（値は前と同じ）。
* 数え（1,200 局、計器あり）: `lp.q` の呼び出し 16.1 → 13.2 回/局、共有した解 2.86 回/局、順位付け 16.06 回/局は同じ。
* テスト `tests/test_q_rank.py::test_a_matrix_both_sides_rank_from_is_solved_once`: 裏を見せた 2 局で、メモありとメモなし（対照）の局が同じこと、LP の回数が順位付けの半分だけ減ることを確かめる。直す前の src では 18 − 18 = 0 で落ちた（陽性対照）。

## 5. B: 512 行を超える塊の CUDA グラフ —— 入れない

1,200 局（計器あり、非専有）で、推論サーバの eager の順伝播を大きさごとに数えた（`server.eager.rows.<行数>`）:

```
  6,240 回（5.2 回/局）、大きさは 3,357 種類
  帯             回数の割合   大きさの種類   前に出た大きさの再来
  513〜1,024      18.6%          440          62%
  1,025〜2,048    25.7%          775          52%
  2,049〜4,096    27.6%        1,122          35%
  4,097〜8,192    28.0%        1,020          42%（8,192 ちょうどが 509 回）
```

* グラフは大きさごとに 1 本要る。行を詰めて大きさをそろえると答えが変わる（CUDA の答えは呼び出しの行数で動く。IKA-291）ので、バイト一致のままではそろえられない。
* 本番の 20,000 局では、大きさは 7,680 通りに散る。GRAPH_CACHE 512 の LRU では当たりは 1 割に届かない見込み。キャッシュを広げると、グラフ 1 本あたりホストに 0.65〜0.86 MB（IKA-107）なので、サーバごとに GB 単位になる。
* 当たりが 100% でも、上限はサーバの eager の CPU 25 ms/局（1 局の CPU の 3.7%）。
* 小さな探り（`C:/tmp/ika339/graphmem.py`、評価モデル 2 本のアンサンブル、上限 3.5 GB、600〜8,000 行の 8 通り）:
  - グラフの答えは eager とビット一致した。
  - カードの予約は 8,000 行まで捕まえて 1.73 GB（最大 1.84 GB）。上限の中に収まる。
  - 1 回の CPU は thread_time の刻み（15.6 ms）より小さく、eager とリプレイの差は読めなかった。大きな塊では pin_memory と転送が行数に比例するので、リプレイでも CPU はあまり減らない見込み。
* 調整役の判断で、B は入れない。8,192 行ちょうどの塊だけをグラフにする案（0.42 回/局、効きは約 2 ms/局 = 0.3%）も採らない。

## 6. profile_stages の定常状態

IKA-300 は、300 局の実行の定常状態の局/分が、同じ設定で 953〜1,350 と揺れると書いた。原因は 2 つあった。

1. **局のファイルを読むたびに開き直していた**。CPU の読み（約 95 プロセス）と同じループで `GamesWritten` を呼んでいた。on1 では、0.25 秒ごとの進みの読みに 1 秒を超える間隔が 18 回あり、最大は 7.5 秒だった。進みの読みを別のスレッドに分けた後も、止まったのはファイルを開く方だった。ファイルを開いたまま読むようにすると、on2 では進みの点が 24 → 205 になった。プロセスの読みは Process オブジェクトを使い回し、1 回 0.02 秒（中央値）になった。
2. **300 局は 1 ワーカー 12 局**。24 ワーカーが同時に最初の局を始めるので、局は波になって終わる。窓に入る波が 1 つ多いか少ないかで、局/分が動く。

直したこと:

* 進みを 0.25 秒ごとに別のスレッドで読む。
* 局/分は、窓（最後の数の 10〜90%）の中の最小二乗の傾き。1 局の CPU は、各 CPU の読みの時刻に補間した局数への傾き。
* 窓の中が 1 ワーカー 25 局未満なら、`short` として定常状態を読まない。
* 読みにかかった時間を表に出す。

```
  実行    局     壁時計   全体の局/分   窓の傾き   両端の差   進みの点   short
  off1    1,200   68.5     1,051          1,164      1,158       169       -
  on2     1,200   73.7       976          1,086      1,091       205       -（計器あり）
  s300c     300   24.4       737          1,050      1,050        54       yes（窓の中は 1 ワーカー 9.9 局）
  s300d     300   23.2       775          1,050      1,044        56       yes（10.2 局）
```

300 局の実行は、窓の傾きでも 1,200 局より 1 割低い（波の分）。だから読まない。

## 7. 局の一致と速さ（ABBA）

## 10. Notion のコメント案

> IKA-339: q-nocover のデータ生成（本番の 2 サーバ / 24 ワーカー、1,200 局）で、1 局の CPU 0.66 秒の内訳を段ごとに測った。
