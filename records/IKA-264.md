# IKA-264: port とのやり取りの二度呼びを 1 回にした —— 局はビット一致のまま、CPU 秒/局 −6.1%・局/分 +6.5%。葉の行の 20% の二度送りは、重ねると値が変わるので残した

2026-09-25。担当 IKA-264（worker）。master 8199f94 から切った `ika-264-exchange-dupes`。出発点は `records/IKA-258.md` の 5（二度呼び）と 8（候補 3・7・8）。

答えた問い: **M-C の生成（IKA-258 と同じ形・同じ 1,200 局）で、同じ決定の中の二度呼びはどの呼び手から来ているか。
局を変えずに 1 回にすると、CPU 秒/局と局/分はどれだけ動くか。**

## 1. 二度呼びの出どころ（呼び手つきの数え、master の src＋計器）

`timing.repeat_where` を足した（`POKEURAOU_TIMING_DUPES` のときだけ）。呼び手は、やり取りの自前のモジュール
（timing・rustnode・port・position・inference）の外で最初の 3〜4 フレーム。1,200 局・14,137 決定（d-a）:

```

  position.json    118,344 (54.7%) play_game（needed）>> narrow._bridged_scores（_menus の本体 narrow）       9.5%
                                   _do_replacement_node.matrix >> 同じ（控えの対ごとに同じ局面）              8.7%
                                   _bridged_scores（leaf_ranking の応手 narrow）>> search.rank の fill         4.8%
                                   _bridged_scores（応手 narrow）>> beliefnode._gather_dirty の fill            4.8%
                                   play_game（needed）>> play_game（決定の記録の to_json）                   4.7%
                                   _advance_turn（weights）>> _advance_turn（branch）                        4.7%
                                   play_game（needed）>> 応手 narrow・rank・belief の fill ほか              約 17%
  port.position    104,759 (52.1%) 上と同じ組（記録の to_json を除く）
  port.score        10,054 (24.5%) 本体の narrow と leaf_ranking の応手 narrow が同じ側・同じ局面・同じ pool   12.4%＋12.2%
```

* **局面の二度書きは全部「同じオブジェクト」**: `(id, text)` で数えた `position.json.object` も 54.7% で、
  中身が同じ別オブジェクトから来るものは無い。だからオブジェクトごとの覚えで全部取れる
* `port.resolve` の二度目は 0 と出ていたが、`_advance_turn` の `weights`（select なし）と `branch`（select あり）は
  **同じ exact のターンを子に 2 回解かせていた**（要求の `select` だけ違う。局面の 4.7% がこれ）
* 葉の行の 20.3% のうち 16.9% は **同じ 1 要求の中**（`leafrow_request`）: belief_payoffs が完成形ごとに
  積むブロック（参照と patched、dirty の fill）で同じ行が重なる

## 2. やったこと（どれも局を変えない）

* **局面の JSON を決定の間だけ覚える**（`rustnode._position`・`_payload`）: 同じオブジェクトを 2 度目に送るときは、
  最初に書いた JSON の文字列を要求の行に差し込む（`json.dumps(request)` と同じバイト列。テストで確認）。
  決定の区切り（`timing.decided`、計器が off でも走る `timing.on_decided` の鉤を足した）で忘れる
* **同じ `score` 要求は同じ決定の中で 1 回**（`_answered`/`_keep`）: 行のバイト列が同じなら最初の答えを返す
* 両方とも **`rustnode.hold_positions()` を呼んだプロセスだけ**。書き換えた局面を同じ決定でまた送る道具やテストが
  古い文字列を送らないように、既定は off。`tools/selfplay.py`（生成のワーカー、pool と roster の両方）だけが on にする。
  生成は送った局面を書き換えない（局面は port の答えか copy から新しく作る。grep で確認）
* **port が直前の `resolve` のターンを覚える**（rust/src/node.rs の `resolve_one`、`LAST_RESOLVE`）: 局面・手・予算が
  同じなら解き直さず、`select` の位置だけ返す。覚えるのは 1 つ（直後の要求用。間に別の要求が来れば置き換わる）。
  **port の命令は足していない**
* **realpath**: `regulation.repo_root` に `functools.cache`。`rustnode.available()` の `exists()` は一度見つかった
  exe を覚える（`_binary_found`）

足さなかったもの:

* **葉の行を重ねてから送る**（課題の案）。**重ねると値が変わる**。本番の葉（value-gen11L、サーバ経由、CUDA）で
  決定の局面 557 個を、20% の重なりを入れた要求と重ねた要求で比べると、40 回中 37 回で行の 44〜70% が違った
  （最大 5.7e-7、合計 6,371/13,356 行）。行の値が要求の行数で変わるため（`inference.py` の注記どおり）。
  ビット一致の条件の下では取れない。別課題の候補 1
* 子に局面を覚えさせる（ハッシュで引く）: 下の 3 のとおり、残る二度送りは子のパース（`rust.child.parse`、
  fill の中で子の時計の約 2%）が主で、Python の側は 1 で取れた。命令を足すほどの見込みが無いので見送り（候補 2）

## 7. 別課題の候補

1. **葉の行の二度送り 20%（うち 17% は同じ要求の中）**: 重ねると行の値が変わる（2）。取るには、サーバで要求を
   固定の行数に詰める（inference.py の注記では 1.13 倍の順伝播）か、「重ねた値」を正とする局の変更として盤で確かめる。
   belief_payoffs の中の重なり（完成形の patched ブロックで控えに届かない行）は、行を作る前に Python の側で
   「同じ行か」を決められれば送る前に落とせるが、それも行数が変わる
2. **子に届く同じ局面 49.6%**: 子が直前の数個の局面を文字列のハッシュで覚えればパースが消える。子の時計の parse は
   fill の中で約 2%。port の命令を足すことになるので、IKA-265/268 の後に子の内訳を見てから
3. 決定の記録（`Decision.position = pos.to_json()`）と `needed` の同じ局面の二度書き（決定 1 つで 1 回、0.0006 CPU 秒/局程度）
