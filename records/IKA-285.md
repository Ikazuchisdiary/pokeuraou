# IKA-285: heavy.py を 16 コアの貸し借りにし、計時の本だけが機械を専有するようにした（9/25 13:53 に差し替え済み）

2026-09-25。調整役が持つ機械の鍵 `C:/tmp/pokeuraou-machine/heavy.py`（リポジトリの外）の改修。

## 何が困っていたか

今の heavy.py は、`--cores` が 2 以上ならどれも同じ 1 つの鍵（`lock` ディレクトリ）を取る。IKA-254 の 8 コアの計測が 12:17 から 50 分以上鍵を持ち、そのあいだ 8 コアのビルドと 16 コアのテスト一式が待たされた（log.tsv 4736 行目・4763 行目。4763 行目の `broken` は、IKA-254 のプロセスが消えたあとで待ち手が鍵を壊した行）。

## 新しい heavy.py（`C:/tmp/ika285/heavy_new.py`）

- **コア数で配る:** `--cores N` は 16 のうち N を借りる。合計が 16 以下なら並んで走る。空きの無い本は待つ。空いたら入れる本から入る（先着順ではなく first fit）。`--cores 1` は今までどおり借りず、待たず、ログにだけ `start1`・`end1` で書く。
- **専有:** `--cores 16`（以上）と新しい旗 `--exclusive` は専有にする。
  - 専有の本は、借り手が 0 になるまで待つ。
  - 専有の本が待っているあいだ、それより後に来た本は入れない。専有どうしは先着順。
  - 専有の本が走っているあいだ、ほかは入れない。
  - 専有の本のログ行は、why の頭に `[exclusive] ` を付ける。
- **状態:** `cores.json`（seq、借り手の一覧、待ち手の一覧）に次を持つ。
  - 借り手: pid・create_time・コア数・専有か・開始時刻・agent・why・cmd・包んだ子の pid
  - 待ち手: 同じ項目と到着順の seq

  読み書きは必ず `cores.lock` ディレクトリ（mkdir を排他の小さな鍵にする。持つのは数ミリ秒）の中で行い、書くときは一時ファイルから os.replace する。`cores.lock` の中には持ち主の pid を置く。30 秒より古く、持ち主が死んでいれば壊す（ログに `broken cores.lock`）。
- **後始末:** heavy.py の pid と包んだコマンドの pid が両方消えた借り手は、次に来た呼び手が返す（ログに `broken`。形は旧版の broken 行と同じ）。pid は create_time で照合するので、pid の使い回しに引っかからない。heavy.py だけが殺されて子が走り続けている間は、コアを返さない。
- **互換:**
  - 引数は `--agent`・`--cores`・`--why`・`--wait-max`・`--` のまま。`--exclusive` だけを足した。
  - 終了コードは、包んだコマンドの値か 75（`--wait-max` を過ぎた）で、今と同じ。
  - log.tsv は 7 欄で、start/end/start1/end1/broken の形も今と同じ。借りたコア数は 5 欄目。
  - `lock/owner.json` を読む道具を探したが、heavy.py 自身のほかには見つからなかった。C:/tmp の py・ps1・sh と、tools・src・メモリを探した。procs.py（7 版すべて同じ中身）はプロセスの一覧を見るだけで、lock を読まない。
- **切り替えのあいだ:**
  - 旧版が取った `lock`（owner.json の pid が生きているもの）は、専有の借り手として数える。持ち主が死んでいれば旧版と同じく壊す。
  - 新版は、借り手がいるあいだ自分の `lock/owner.json` を置く（`"mirror": true`、pid は生きている借り手の 1 つ、why に借り手の一覧）。これで、差し替えの前から待っている旧版の待ち手も、新版の借り手が全部終わるまで待つ。
- **見える化:** `heavy.py status`（`--status` でもよい）が、貸したコア数と借り手・待ち手を 1 行ずつ出す。

## 試験（別の状態ディレクトリ `C:/tmp/ika285/runs/<場面>-<時刻>/` に heavy.py を複写して、偽のコマンドで）

偽のコマンドは `fake.py`（開始と終了の時刻を trace に書いて眠る）。表の「ピーク」は、trace から数えた「同時に走っていたコア数の最大」。道具は `C:/tmp/ika285/drive.py` と `stale_mutex.py`。

**陽性対照:** `_mutex()` を何もしない版（`make_nomutex.py` が作る `heavy_nomutex.py`）で同じ 20 本を同時に流すと、ピークが 60 コアになった。読み・判定・書きの窓を 0.05 秒広げた版では 90 になった。同じ 0.05 秒を入れて mutex を残した版（`heavy_widen.py`）は 16 のまま。上限が守られているのは mutex のおかげで、試験がたまたま通ったのではない。

## 差し替え

**2026-09-25 13:53:57 に差し替えた**（ユーザーが `C:/tmp/ika285/swap.py` を実行）。旧版は `C:/tmp/pokeuraou-machine/heavy.py.bak-ika285`（5,459 バイト）に残っている。スクリプトの中身は次のとおり。

1. 旧版の `lock` が無いことを確かめる。
2. `heavy.py.bak-ika285` を残す。
3. 同じディレクトリの一時ファイルから os.replace で 1 回で置き換える。
4. 置き換え後の中身がバイト単位で一致し、CR が無いことを確かめる。

担当のセッションでも調整役のセッションでも、実行は権限の判定（共有資源の変更）で止められた。回避はせず、ユーザーが実行した。

差し替えの直前（13:25）の機械: 旧版の lock は無く、2 コア以上の旧版の待ち手もいなかった（`--cores 1` の本だけが走っていた）。`--cores 1` の旧版は lock に触らないので、走っていても差し替えてよい。

差し替えたあとの確かめ（13:54、調整役）: 本物の heavy.py は heavy_new.py とバイト一致。`heavy.py status` は `lent 0/16; 0 borrowers, 0 waiting`。`--cores 1` と `--cores 2` で短い本を 1 回ずつ流し、log.tsv に start1/end1（IKA-285-check、1）と start/end（同、2）が 7 欄で書かれた。終わった後の status も空で、残ったのは `cores.json` だけ（`lock` も `cores.lock` も無い）。

## 残したこと・注意

- 専有でない本は first fit なので、12 コアの本は、4 コアの本が次々に来る間は待たされうる。いま困っている形ではないので、入れていない。
- ポーリングは 2 秒（旧版は 10 秒）。待ち手が 20 本いても、1 回の mutex は数ミリ秒で済む。
- 子の子（cargo の下の rustc など）の生死は見ていない。heavy.py と直接の子が両方消えたときにだけ返す。
- 機械時間: 試験はすべて眠る偽のコマンドで、`heavy.py --cores 1` で包んだ。log.tsv の IKA-285 の行は、31 秒・43 秒・35 秒と stale_mutex の数秒。これとは別に、burst を 3 回くり返した分（計 36 秒、ほとんど眠り）を包まずに流した。
