# 生成の局の勝率の飛びと、解き直した読みの HTML（課題番号なし）

10/1。対象は data/selfplay-mc3/games-b07-worker3.jsonl の 5 局目（局番号 140133、value-mc2 x1・幅 12・裏非公開・
q-nocover（q-mc2）の生成の局）。ユーザーの問い: (1)「T3 から T4 で突然勝率が変わったのがよく分からない」、
(2)「HTML に均衡の読みの対象が無いのが不便」。

## 問い 1: T3 0.665 → T4 0.267

### 方法

- 局を打ち直した（C:/tmp/spreads/replay.py）。生成と同じ設定（seed 40002、局番号 140133、value-mc2、幅 12、
  q-nocover・q-mc2、選出は生成の選出の保存（C:/tmp/ika402/store-gen を複写）から）。評価モデルは CPU。
  13 の決定すべてで、局面・候補集合（3 決定は並びだけ違い、集合は同じ）・選んだ手が一致した。
  両席の混合と値の差は最大 1.5e-6。つまり下の数字は、記録の局そのものの中身。
- 打ち直しのときに `belief_solve` を横取りし、T3 の解きの中身（裏の決定化ごとの行列・重み・相手の手の読み）を取り出した。
- T3 で実際に打たれた手の組（自: まもる＋ハイパーボイス、敵: しおふき＋マフォクシーへの交代）について、
  3 通りの決定化それぞれで厳密な枝（`Budget.exact()`）をすべて出した。各枝で評価モデルの値を取り、
  T4 の手番を生成と同じ形（`_menus` と `belief_solve`）で解き直した（C:/tmp/spreads/analyze_t3.py）。
  対照: 実際の T4 局面で解き直すと 0.26731。記録の値と同じ。
- 実際の T4 局面から、同じ設定の自己対戦を 200 局打った（C:/tmp/spreads/rollout.py）。

### 結果

| 敵の手は読みどおり（しおふき＋交代、100%） | 0.574 | 0 |

- 評価モデルの値と T4 の探索値は、枝をまたいで強く相関する（相関 0.89〜0.91）。ずれは局面の型ごとの片寄り。
- 自己対戦 200 局（実際の T4 局面から）: 勝率 0.135 ±0.047。評価モデルの 0.54 は大きく外れていて、T4 の探索の 0.267 の方が近い。

### 不具合の疑いの確認

- おもてなし: ヤバソチャを出す交代の手番で 0.669 → T3 の行動の手番で 0.665。回復（61→104 = +43 = 174/4）は
  3 通りの決定化すべての局面に入っている（決定化は裏の 1 枠だけを置き換え、場は記録どおり）。
- 信念: T2 の組の重み（マフォクシー＋ヤバソチャ 0.4122、ヤバソチャ＋オオニューラ 0.5713、ヤバソチャ＋イッカネズミ 0.0043）を
  ヤバソチャが見えた条件で正規化すると、T3 の 0.4173 / 0.5784 / 0.0044 にぴったり一致する。
- T3 の値は、決定化ごとの値の信念の重みでの平均になっている（上の (a)）。
- 設計の注: 信念は「見えたポケモン」と先発だけで条件づける。相手がどの裏を先に出したかは証拠に使っていない
  （例: T3 の交代でヤバソチャを出したことは、残りの裏の重みを動かさない）。仕様どおり。
- 評価モデルの鏡像（席を入れ替えた局面で 1 − v になるか、C:/tmp/spreads/antisym.py）: T4 局面 0.54059 と 0.45941（和 1.0000000）、
  T3 局面（本当の裏）0.67991 と 0.32009（和 1.0000000）。入力の配線の片寄りではない。

### 結論

探索と信念の計算に不具合はない。飛びの 7 割（−0.274）は、評価モデル（value-mc2）が T3 の後の局面を高く見すぎていたこと。
T3 の 0.665 は、深さ 1 の探索が「1 ターン打った後の局面の評価モデルの値」を平均したもの。T4 では探索がさらに 1 ターン先まで
読んで、その局面が実は 0.27 前後（自己対戦では 0.13）だと分かった。残りは、裏がマフォクシーだった分（−0.091）と、
自分の混合から引いた手と乱数（あわせて −0.034）。

ユーザーへの言葉の案:「T3 の 67% は『この 1 ターンを打った後の局面を評価モデルがどう見るか』の平均でした。裏がマフォクシーだった分で
57% に下がり、乱数と自分の混合でさらに 54% になりました。ところが T4 では探索がもう 1 ターン先まで読み、その局面は実は 27% だと
気づきました。T4 から同じ設定で 200 局打ってみると勝率は 13% ほどです。評価モデルがこの形を高く見すぎていた、というのが飛びの正体です。
読みの計算（信念・平均）はおかしくありません。」

課題の案: 評価モデルと 1 ターン先の探索のずれを測る。生成の局面で「評価モデルの値 − 1 ターン先の探索の期待」の分布を出し、
ずれの大きい局面（今回は +0.26）の型を集め、学習の目標で直せるかを見る。

## 問い 2: 解き直した読みを HTML に出す（`show_game.py --html --reread`）

### 変えたもの

- `tools/reread.py`（新規）: 生成の記録（裏非公開）の行動の手番を、`play_game` と同じ形で解き直す。形は次のとおり。
  - 記録の局面を使う。
  - 両側の裏の決定化の重みは、記録の `ownSelectionMixture` / `foeSelectionMixture`（`all_selections` の 90 通り）を、
    記録の `shownIdentities` と T1 の先発で条件づけたもの。
  - 候補集合は記録の順位付け（`rankView`・`rankFill`・`searchLimit`）で `_menus` から作る。
  - 解きは `belief_solve`。
  - 両席の候補集合が記録と同じ集合で、両席の混合（手ごと）と値が記録と `TOLERANCE` = 5e-5 以内のときだけ「一致」とする。
    一致した手番は、各席の読みを `timematch.read_summary` の形で返す（自分の混合、相手に見た混合、手ごとの値、読みの値）。
  - 一致しない手番は読みを返さず、理由を返す。
  - 扱えない設定は止める: open の局、deepen・benchDrop・depth・knockouts、席ごとに違う順位付け、方策の順位付け。
  - `load_inputs` は、記録の名前（`searchObjective`・`qModel`・`pool.id`）から、評価モデル・Q・プールの 6 体を
    `--models` / `--pools` の下で探す。探したものは次の値と照らし、合わなければ止める。
    - Q: `qModelSha256`
    - プール: `pool.sha256`
    - 評価モデル: 名前（`value:<stem>` または `value:<stem>x<N>`）
- `tools/game_page.py`: `selfplay_line(..., rereads)` を足した。
  - 一致した手番: 各席の読みを解き直しのものにする。ページは対戦評価の局と同じ表（選んだ手に対する相手の手の値、相手の読み）を出し、
    席の見出しに「解き直した読み（記録の混合と一致を確かめた）」と書く。
  - 一致しない手番: 記録の混合だけを出し、「解き直しが記録と一致しなかったので、解き直した読みは出していません（理由）」と書く。
  - 見出しの帯に「一致した手番 / 行動の手番」の数を書く。
- `tools/show_game.py`: `--reread`（`--html` と一緒）、`--models`、`--pools`、`--value`、`--q-model`、`--device`（既定 cpu）を足した。
  `--reread` を付けないときの出力は変わらない。
- テスト `tests/test_selfplay_reread.py`（4 本）: 短い裏非公開の局（hp-share の評価）を打ち、解き直す。
  - すべての行動の手番が一致すること。裏の決定化が 2 つ以上ある手番を含むこと（信念の経路を通った陽性対照）。
  - 相手に見た混合の和が 1 で、読みの値が記録の値と同じであること。
  - ページは一致した手番だけに解き直しの表を出すこと。解き直しなしのページには出ないこと（対照）。
  - 記録の混合を 0.01 動かした手番は不一致になり、表を出さず理由を書くこと（比べが落ちうることの対照）。
  - 扱えない設定と、6 体が記録と違うときは止まること。
