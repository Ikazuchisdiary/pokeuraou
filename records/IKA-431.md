## 1. 測り方

* 測る道具は `C:/tmp/ika431/watch.py`。命令を起動し、そのプロセスの木を 0.5 秒ごとに psutil で読み、プロセスごとの private と WS を CSV に書く。役割はコマンドラインで分ける（`inference_server` は推論サーバ、`pokeuraou-damage` は port の node、`--queue`・`--worker` はワーカー、`generate_queue`・`match_queue`・`q_teach` は起動役）。
* 表の「中央値」は、起動後 20 秒以降の標本の中央値を各プロセスで取り、同じ役割のプロセスの中央値を取ったもの。「最大」は全標本の最大。
* 段ごとの内訳は、1 プロセスの中で段ごとに private と WS を読むスクリプトで測った（`imp.py`・`server_stages.py`・`cudafirst.py`・`dlls.py`・`wddm.py`）。
* 前の条件（A）は master 9073b19 の木（`git archive` で `C:/tmp/ika431/master` に展開）、後の条件（B）はこのブランチ。両方とも同じ exe（`C:/tmp/ika431/pokeuraou-damage.exe`、このブランチで build、sha256 301c1487…）を `POKEURAOU_RUST_NODE_BIN` で使う。Rust は変えていない。
* 生成の形は IKA-427 §5 と同じで、評価モデルは value-mc4st x1、Q は q-mc4st、`--rank-fill q-nocover`、幅 12、裏非公開、選出は `data/selection-solved/value-mc4st/` のコピー。run seed は 43100。

## 2. ワーカーの内訳

1 プロセスで import を順に行い、各段の後の private と WS を読んだ（MB）。

| 段 | private（既定） | WS（既定） | private（`OPENBLAS_NUM_THREADS=1`） |
|---|---|---|---|
| Python の起動直後 | 9 | 17 | 8 |
| `import numpy` | 500 | 29 | 18 |
| `import scipy` | 502 | 31 | 19 |
| `import pokeuraou.search`（scipy の OpenBLAS を読む） | 1,018 | 76 | 53 |
| `import torch`（ワーカーは読まない） | 1,857 | 521 | 852 |

* numpy の OpenBLAS（`libscipy_openblas64_`）と scipy の OpenBLAS（`libscipy_openblas`）が、読み込みのときに約 490 MB ずつ commit する。WS はほとんど増えない。
* 推論サーバを使うワーカーは torch を読まない。IKA-430 の Q の教材作りのワーカー 1 本の読み込み済み DLL を読むと（読むだけ）、torch・CUDA は無く、OpenBLAS が 2 つと HiGHS があった。生成のワーカーの DLL は読んでいない。生成のワーカーの private（局の途中の中央値 1,073 MB）は、上の表の 1,018 MB に数十 MB を足した大きさだった。
* レギュレーション、構築プール、選出 book、符号化器など、このプロジェクトが読むデータは合わせて数十 MB だった（上の表の 53 MB と、OpenBLAS を 1 スレッドにした生成のワーカーの中央値 109 MB）。共有や上限を足す大きさではない。
* port の node は、生成で private の中央値 16 MB、WS 25 MB だった。Q の教材作りでは private の中央値が約 160 MB、最大 460 MB だった。IKA-430 の port の node 1 本の DLL を読むと、OpenBLAS は無かった。port の node のキャッシュに上限を足す理由は見つからなかった。

## 3. 推論サーバの内訳

### 3.1 起動の段（value-mc4st x1 と q-mc4st、要求なし、既定の環境）

| 段 | private | WS |
|---|---|---|
| `import pokeuraou.inference`（numpy の OpenBLAS を含む） | 504 | 34 |
| `import torch` | 1,342 | 481 |
| レギュレーションと符号化器 | 1,346 | 485 |
| CUDA のコンテキスト | 1,620 | 600 |
| 評価モデルと Q の読み込み | 1,646 | 622 |
| 最初の順伝播（cuBLAS などの kernel の読み込み） | 2,386 | 1,145 |
| 値の CUDA graph 512 本（1〜512 行） | 2,902 | 1,488 |
| 600〜8,192 行の eager の順伝播 | 3,313 | 1,494 |

* torch の読み込みの約 840 MB は、torch が `torch/lib` の DLL をすべて読むことで生じる。DLL を 1 つずつ読んだときの private の増え方は、cufft 262 MB、cublas 233 MB、torch_cpu の依存 102 MB、nvperf_host 77 MB、curand 28 MB、計 755 MB だった。cufft と curand は推論サーバでは使わないが、torch の読み込み処理が読む。
* CUDA graph は 1 本あたり約 1 MB の private と 0.65 MB の WS を取る（IKA-107 の測りと同じ大きさ）。生成の推論サーバは 3,000 局で値の graph を 512 本、Q の graph を 258 本作った。
* Windows の WDDM では、CUDA のアロケータがカードに確保した量がそのまま private に数えられる。1 GiB をカードに確保すると private が 1,026 MB 増え、WS は変わらなかった。`empty_cache` で戻した。

### 3.2 試して入れなかったもの

| 試したこと | 結果 | 判断 |
|---|---|---|
| `PYTORCH_CUDA_ALLOC_CONF=garbage_collection_threshold:0.2` | 生成の推論サーバの private の中央値が 3,573 MB から 3,566 MB | 効果なし |
| 報告ループで 1 秒ごとに、カードの確保が前回の解放から 0.25 GB 増えたら `empty_cache` | 3,000 局で 146 回解放し、報告の reserved は 0.8 GB から 0.3〜0.4 GB に下がった。private の中央値は 3,560 MB で変わらない | 効果なし。差分は `C:/tmp/ika431/trim-attempt.patch` |
| `OMP_NUM_THREADS=1`・`MKL_NUM_THREADS=1`・`CUDA_MODULE_LOADING=LAZY` | torch の読み込みの private は 852〜853 MB で変わらない（torch 2.11 は既に lazy） | 効果なし |

* 推論サーバの private のうち、torch の DLL（約 0.84 GB）、CUDA のコンテキスト（約 0.27 GB）、最初の順伝播の kernel（約 0.74 GB）は、1 本の推論サーバに 1 回ずつかかる固定費で、合わせて約 1.9 GB ある。graph（約 0.8 GB）を減らすと、captureし直しの CPU が増える（IKA-291）。このため、この課題の範囲で推論サーバを半分以下にする手は見つからなかった。
* 推論サーバの本数を減らせば固定費は本数分だけ減る。本番の生成は `--servers 2` で、1 本にしたときの速さは測っていない。

### 5.2 速さ（生成の ABBA）

| A1 | 0〜2,499 | 130.7 | 2,102 |

* B2 の途中の約 2 分、この課題の比較の道具（`idcmp.py`、1 コア、2,500 局の JSON を読む）が専有の窓の中で走った。heavy.py を通さずに起動した自分の誤りで、B を遅く見せる向きに働く。このため 2 組目を 1 回の専有の中で B、A の順に打ち直した。

* 判断の材料: 5 組の比は 0.984〜1.021 で、A/A の差 1.5% と同じ幅に入る。B が遅いとは言えない。OpenBLAS のスレッド数は局の答えを変えず（10,000 局が一致）、ワーカーの CPU 秒も同じ幅で動いた。打ち直しの 2 区切りも A と B の局が 2,500 / 2,500 で一致した。
