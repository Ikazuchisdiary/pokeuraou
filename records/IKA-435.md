# IKA-435 master の CI が 10/3 から落ちている

## 要点

失敗は 5 つあった。どれもテストの前提か、テストの道具の側の問題で、コードの不具合ではない。変えたのは tests/ と `.github/workflows/ci.yml` だけで、本番の局は変わらない。

| 失敗 | 始まった取り込み | 原因 | 直し |
|---|---|---|---|
| suite ジョブの skip 監査（torch の skip が予算 26 を超えた） | ce18e3e（IKA-425 段 2a） | 学習の群が無いと全体が skip するテストファイルが 8 本増えたのに、予算を上げていなかった | `ci.yml` の予算を 26 から 34 にした |
| `test_deepen_ahead` と `test_deepen_batch`（IKA-427 の run では 6 本、IKA-429 以降は 2 本） | 26bbeb6（IKA-427、符号化 revision 3） | 疑似の葉の値は符号化の列の関数で、列が増えると同じ予算で広げるセルの数が変わった | 残った 2 本の `deepen=300` を `1000` にした |
| `test_port_threads` の `fill: the headers differ` | 27b6046（IKA-429、縛りの列） | ヘッダに新しい時計 `bindUs` が入った。`fills` の節点の `bindCache` は、どのスレッドが解いたかで変わる累積の数である | `bindUs` を時計の一覧に足し、`fills` の節点の `bindCache` だけ比べない。1 節点の `bindCache` は比べ続ける |
| learn ジョブの停止 その 1: `test_inference.py` の 2 本 | 27b6046（IKA-429） | 「ワーカー」をスレッドで作るテストで、符号化がポートに縛りの列を頼む。2 本のスレッドが 1 本のポートの子プロセスを共有し、答えが入れ替わって止まる | 各スレッドで `rustnode.own_node` を使う |
| learn ジョブの停止 その 2: `test_vocab_order.py` の 3 本 | 27b6046（IKA-429） | M-B の局面を M-C の符号器に渡している。ポートは別の形式の局面を拒み、`port.ask` がその拒否で子プロセスの再起動を繰り返して終わらない | 局面を M-C の形式で書き直して渡す（`_in_format`） |

## 切り分け

### torch の skip 予算

学習の群が無い環境で torch を読むテストのファイル 28 本を回し、`tools/ci_skip_audit.py` で数えた。34 件だった。run 37367458459 の suite ジョブも 34 件で、手元と一致した。26 からの増分 8 件は、IKA-425 から IKA-433 で足した 8 ファイル（`test_value_stage2a`、`test_value_state_inputs`、`test_value_aux_targets`、`test_value_bind_inputs`、`test_value_attention_warm`、`test_q_state_inputs`、`test_q_bind_inputs`、`test_encode_join_streamed`）が 1 本ずつ skip する数と合う。

### deepen 系のテスト

`_SizedLeaf` は符号化した配列を、列の幅に応じた重みで足して値を作る。符号化の列が増えるたびに値が動き、深掘りのループが広げるセルの数が変わる。先頭 2 局面で広げたセルの数は次のとおり（手元、revision 4）。

| 予算 `deepen=` | 広げたセル |
|---|---|
| 300 | 2 + 4 = 6 |
| 1000 | 8 + 28 = 36 |

テストが守る性質は、先読みの有りと無しで答えが一致すること、旧い道と新しい道で答えが一致することである。しきい値 10 は「比べる中身がある」ことの確認なので、予算を上げて中身を増やした。

### test_port_threads

手元で再現し、`bindUs` が 1982.2 と 1949.1 で違うことを確認した。時計に足すと、次に `fills` の節点の `bindCache` が違った。プールの各スレッドが自分の符号器を持ち、命中数は符号器ごとの累積である。節点の配列は 1 スレッドと 4 スレッドでバイト単位に一致しており、本体の比較は残してある。

### learn ジョブの停止

run 37192062116 と 37367458459 の learn ジョブは、pytest の出力が無いまま 90 分で取り消された。手元で torch 入りの全体を回すと、終盤に止まるワーカーが出た。py-spy で止まっている場所を見て、2 つ見つけた。

1. `test_two_workers_at_once_get_what_they_would_get_alone` の 2 本のスレッドが、どちらも `rustnode._exchange`（`bind` 経由）で止まっていた。`RemoteValue.__call__` は符号化を呼び、IKA-429 から縛りの列をポートに頼む。ポートの子プロセスは 1 行ずつしか答えられず、モジュールの 1 本を 2 本のスレッドが共有していた。単独の再現（`C:/tmp/ika435/race.py`）では、共有だと 120 秒待っても 2 本中 0 本しか終わらず、`bind answered 40 of 12 positions` の再起動が出た。`own_node` を使うと 1.2 秒で 2 本とも終わり、答えの誤りは 0 件だった。生成では各ワーカーが別のプロセスで、ポートも別である。人と打つ・検討の先回りのスレッドは、既に `own_node` を使っている（`deepen.py`）。
2. `test_the_port_reads_the_same_order` は 1 本のスレッドで止まった。M-C の符号器に M-B の局面を渡しており、ポートは `position is ...regmb but the regulation is ...regmc` と拒む。`port.ask` は拒否も失敗として子プロセスを再起動して同じ要求を送り直すので、終わらない。単独で 150 秒待っても終わらなかった。直した後は同じファイルの 18 本が 2 秒で通った。

2 の `port.ask` が拒否を再起動で扱う点は、コードの側の弱さである。本番では別の形式の局面は渡らないので、今回は直していない（最後の節）。

## 確認

| 確認 | 結果 |
|---|---|
| 失敗していた 3 本と、deepen・port_threads の同ファイル（手元、`-n 0`） | 18 本通過 |
| `test_vocab_order.py` 全体 | 18 本通過（直す前は 150 秒で止まった） |
| 全体、torch 入り（CI の learn ジョブ相当、CUDA は隠した） | 3216 通過、18 skip、1 xfail、5 分 16 秒。`ci_skip_audit` の cuda 8、cpu-batch 1、standings 9 の内訳は予算内 |
| 全体、torch 無し（CI の suite ジョブ相当） | 3034 通過、43 skip、1 xfail、4 分 55 秒。`ci_skip_audit --absent standings=9 --absent torch=34 --absent cuda=0` が `every skip was one this run declared in advance` |
| ruff、`agent_drift.py --check`、`port_gate_audit.py --check`、`port_coverage.py --check` | 通過 |

対照は次のとおり。

- `test_port_threads` に、1 節点の `bindCache` を 1 つずらす不具合と、`fills` の節点の `leaves` を 1 つずらす不具合を入れた。どちらも落ちた（その後に戻した）。
- `test_deepen_batch::test_an_open_root_is_the_old_road` で「新しい道」だけ積み上げ採点にすると落ちた（その後に戻した）。
- スレッドの競合は、共有で止まり、`own_node` で止まらないことを `race.py` で対にして見せた。

## 確かめていないこと

- GitHub 上の CI は回していない（指示により push しない）。Linux の learn ジョブの停止は、手元（Windows）で同じ場所の停止を見たことと、2 つの run が同じ停止だったことから原因と見ている。直した後の learn ジョブの実時間は Linux では未確認である。
- torch 入りの手元の全体は、main の venv の torch 2.11.0+cu128 で走らせた。CI の CPU 版 torch ではない。
- 疑似の葉の値は今後も符号化の変更で動く。テストの予算を上げただけで、葉の作りは変えていない。
- `port.ask` が、局面の形式の違いのような決まった拒否を、再起動で終わりなく繰り返す点は直していない。本番の経路は変わらないが、別の形式の局面を渡すと止まる。直すなら別の課題にする。
