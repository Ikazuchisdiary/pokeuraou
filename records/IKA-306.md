# IKA-306: 葉 対 葉の対戦評価（`--baseline` でサーバに 2 つの腕）で worker が落ちる —— 原因は torch が 1 プロセスに 1 つのキャプチャしか許さないこと。全ての腕の CUDA グラフで 1 つのロックを共有して直した。生成の局は 600/600 バイト一致、速さも同じ

2026-09-25。担当 IKA-306（worker）。master 842fdc0 から切った `ika-306-graph-capture-two-arms`。

答えた問い: **`match_queue.py --served` で `--baseline` を渡し、サーバに 2 つの腕を載せると、worker が起動直後に落ちる
（IKA-292 §2.1）。何が原因か。局を変えずに直せるか。**
答え: torch の `torch.cuda.graph` は **1 プロセスに 1 つのキャプチャ** しか許さない。腕ごとのロック（IKA-291 の `_Graphs`）では、
2 つの腕が別々のスレッドで同時にキャプチャし、互いを壊していた。ロックをプロセス全体で 1 つにして直した（§2）。
再生の答えは eager とビットで同じなので、局は変わらない（§3）。

## 1. 原因

### 1.1 torch の側（torch 2.11.0+cu128 のソースで確認）

`torch.cuda.graph` は次のことをする。

* キャプチャの stream は、プロセス全体で 1 つ（クラス属性 `default_capture_stream`）。torch のコメントも、同時に進められる
  キャプチャはプロセスに 1 つだけだと明記している
* 入るときに `torch.cuda.synchronize()`（デバイス全体の同期）と `empty_cache()` を行う
* caching allocator は、1 度に 1 つの pool にしか記録できない（`beginAllocateToPool: already recording to mempool_id`）

腕が 1 つなら、キャプチャは腕のロックの中で 1 つずつ行われる。eager の順伝播がキャプチャと並んで走っても問題はない
（IKA-291 で確認済み。§1.2 の対照でも同じ）。腕が 2 つになると、2 つのロックが別々に取られ、2 つのキャプチャが同じ stream で重なる。
片方の `synchronize` が、もう片方のキャプチャ中に走ることもある。

IKA-107 までは、深さ 1 の単発の要求はグラフを通っていなかった。そのため、葉 対 葉の対戦評価でも、キャプチャは深さ 2 の
`score_segments` でしか起きなかった。IKA-107 で op `score` もグラフを通るようになり、どの対戦評価でも起動直後に
両方の腕が初見の大きさを次々にキャプチャする。IKA-107 §4 の計測は葉 対 hp-share（腕は 1 つ）なので、この形を通らなかった。

### 1.2 再現（直す前の master の src、`C:/tmp/ika306/probe_two_arms.py`）

単体のネット（テスト用の小さな `build`）を載せた `served_model` を 2 つ作り、各腕 6 スレッドで 1〜60 行の初見の大きさを、
順番を変えて同時に `block` に送った。

```
  形                                              結果
  2 腕 × 6 スレッド（master）            2 回とも落ちる。両腕ともグラフを諦める
                                                  （graph.failed: "beginAllocateToPool: already recording to mempool_id"）。
                                                  eager に戻った後も "Cannot copy between CPU and CUDA tensors during CUDA
                                                  graph capture" で 91 回エラー。1 回は答えが違う行があった。
                                                  2 回目はデバイス側の assert（gather の添字が範囲外）でプロセスごと落ちた
  1 腕 × 12 スレッド（master、対照）      3 回とも通る（キャプチャ 60、再生 720、エラー 0、答えは全部 eager と同じ）
  2 腕、腕ごとに別のキャプチャ stream     3 回とも落ちる（"beginAllocateToPool: already recording"・
                                                  "operation not permitted when stream is capturing"）
  2 腕、capture_error_mode="relaxed"      2 回とも落ちる（同じ 2 つのエラー）
  2 腕、ロックを 1 つに（この枝）         8 スレッド × 3 腕 × 120 通りの大きさ、block だけの形と eager を混ぜた形:
                                                  エラー 0、違う答え 0、各腕のキャプチャ 120・失敗 0
```

課題文の 2 つの候補のうち、`capture_error_mode` の変更では直らない。腕ごとにキャプチャの stream を分けても直らない。
直るのは、キャプチャをプロセスの中で 1 つずつにすることだけだった。

## 2. 変更

* `src/pokeuraou/inference.py`: モジュールに `_GRAPH_LOCK = threading.Lock()` を置き、`_Graphs.lock` はそれを指す
  （腕ごとの `threading.Lock()` をやめた）。ロックの範囲は IKA-291 のまま（キャプチャと、再生を積むところまで。デバイスを待つ間は
  持たない）。これで、他の腕のキャプチャ中は、別の腕のキャプチャも再生も積まれない。eager の順伝播は止めない
  （腕が 1 つのときと同じ。§1.2 の対照で、eager がキャプチャと並んで走っても答えは動かない）
  * 腕が 1 つのとき（生成・葉 対 hp-share の対戦評価）は、ロックが 1 つのままなので動作は変わらない
  * 腕が 2 つのときは、2 つの腕の再生を積む処理が 1 つのロックに並ぶ。積むのは短い処理（入力のコピー・再生・出力のコピーを
    stream に載せるだけ）なので、待ちは小さい見込み。2 腕の形の速さは、master が落ちるので比べていない
* `tests/test_inference.py`: `test_two_arms_capturing_at_once_answer_as_eager`（CUDA のみ）。サーバに 2 つの腕
  （`value`・`baseline`）を載せ、各腕 4 本の接続が、1〜48 行の初見の大きさを順番を変えて同時に送る（port と同じ int32）。
  見ること:
  * どの答えも、ローカルの eager `from_encoded` とビットで同じ
  * どの腕もグラフを諦めていない（`graphs.failed is None`）
  * **陽性対照**: どの腕も 48 通りをキャプチャし、4 × 48 回を再生した（グラフの道を実際に通った）
  * **陰性対照**: 直す前の src（master と同じ）で 3 回回し、3 回とも落ちた。エラーは 72・80・3 件で、対戦評価と同じ
    `operation failed due to a previous error during capture`。直した src では 5 回とも通った
* `.github/workflows/ci.yml`: learn ジョブの `--absent cuda=4` → `5`。新しいテストは GitHub の runner で「CUDA graphs need a card」
  として skip される。同じ段の注記の「three」も、今の数「five」に直した
* ローカルで回したテスト: `tests/test_inference.py` 全 27 本（CUDA のテストを含む。CI では skip される）、`test_line_endings`、
  `test_no_machine_specific_paths`。`ruff`・`agent_drift --check`・`port_gate_audit --check`・`port_coverage --check` はすべて rc 0

## 3. 確かめたこと

### 3.1 葉 対 葉の対戦評価（`C:/tmp/ika306/board.py`）

形は IKA-292 §2.2 の帰無対照と同じ。両腕とも value-mc0x2、深さ 1・幅 12、`--rank-leaf`、裏非公開、2 サーバ・24 ワーカー、
選出は IKA-292 の全 2,145 対の store の写し、種 29301、100 局/席（200 局）。木は m = master 842fdc0 の `git archive`、
w = この枝。「2 腕」は IKA-33 の形（`--baseline` で 2 つ目の腕を載せる）、「1 腕」は IKA-292 の形（`--baseline-inference-arm value`）。
グラフの数は、同じ設定の 2 本目（`-t`、`POKEURAOU_TIMING` つき）のサーバの報告から取った。

```
  本        木  形    rc  落ちた worker   局    グラフ（2 サーバの和）
  m-two     m   2 腕  1    3             200   —
  m-two-t   m   2 腕  1   13             200   キャプチャ 16、再生 24、失敗 2（両サーバとも eager に戻った）
  w-two     w   2 腕  0    0             200   —
  w-two-t   w   2 腕  0    0             200   キャプチャ 1,598、再生 9,629、失敗 0
  m-one     m   1 腕  0    0             200   —
  w-one     w   1 腕  0    0             200   —
```

master で落ちた worker のエラーは、どれも IKA-292 と同じ `RuntimeError: inference failed: AcceleratorError: CUDA error:
operation failed due to a previous error during capture`。局はキューに戻って打ち直され、200 局は全部書かれた（IKA-292 と同じ）。

局の一致（`same_games2.py --seat`: `gameIndex` × 2 + `seatIndex` で並べる。searchSeconds・engine・rankFill・benchDrop を除く）:

```
  w-two = m-two = w-two-t = m-two-t   200/200 局・2,174 決定
  w-one = m-one                       200/200 局
  w-two と m-one（2 腕 対 1 腕）        62/200 局。最初に違う決定は 1〜10 手目（0 手目で違う局は 0）
  対照（同じ席の局 i と i+1）           0（全組）
```

* **この修正は局を変えない**: 2 腕の形では、直した木と master の木の局が同じ。master ではグラフが途中で諦められ、残りを eager で
  答えたので、これは「再生と eager が同じ答え」ことの確認にもなる。1 腕の形でも、直した木と master の木で局が同じ
* **2 腕の形と 1 腕の形は、同じ種でも局が違う**。原因はこの修正ではなく、形そのものにある。1 腕の形では、`pool_match.build_leaves`
  が両方の agent に同じ `RemoteValue` を渡す。`play_game` は、葉が同じオブジェクト（`leaves[1] is leaves[0]`）でメニューも同じなら、
  局面のノードを 1 回だけ解き、両側で共有する（`same_menu`、IKA-282）。2 腕では葉が別のオブジェクトなので、側ごとに解く。
  葉に送る呼び出しの行の組み合わせが変わり、CUDA の答えは呼び出しの行数で最後の桁が動く（IKA-291 §1）
  * 最初に違う決定を見ると（`first_diff.py`）、違うのは方策と探索値の最後の桁だけ。差の中央値は方策 8e-9〜4e-8、探索値 3e-10〜4e-10、
    最大でも 6.7e-7。その後、手を引く乱数で局が分かれる
  * IKA-292 §2.1 は、1 腕の形の理由を「1 つのサーバの腕で答えは同じ」としていた。1 行ごとの答えは同じだが、葉の呼び出し方が違うので、
    局はビットでは同じにならない。IKA-292 の帰無対照（同じ腕どうし）と結果の読み方には影響しない（両席とも同じ形で打ち、
    腕の違いは 1 腕の形の中で測っている）

## 4. 判断

* 入れる。腕が 1 つの経路（生成・葉 対 hp-share）は局も速さも変わらない。腕が 2 つの経路（`--baseline` の葉 対 葉）は落ちなくなり、
  局は master（落ちた worker を打ち直した結果）と同じ
* 葉 対 葉の対戦評価で、1 腕の形（IKA-292）と 2 腕の形（IKA-33）のどちらを使うかは、この課題では決めない。どちらも正しいが、
  局はビットでは同じにならない（§3.1）。同じ重みの腕どうしなら 1 腕の形が安い（ノードを 1 回だけ解く）。
  重みの違う葉 対 葉では、2 腕の形しかない

## 5. 別課題の候補

* 2 腕の形の速さ: 2 つの腕の再生が 1 つのロックに並ぶ。葉 対 葉の対戦評価の壁時計を、1 腕の形（同じ重み）と 2 腕の形で並べて測る
  （局が違うので、同じ局数・同じ種で比べる。今回の 100 局/席では w-two 25 s、w-one 21 s（どちらもログの壁時計）。
  ただし 1 腕の形はノードを共有するので、差はロックの待ちだけではない）
* 別々の重みの葉 対 葉（例: 新しい世代の葉 対 出荷の葉）では、1 サーバのグラフが 2 腕分になる（IKA-107 §7 のメモリの注意）
