# IKA-350: port との行き来の JSON の残りを外す —— qfeatures の答えを float32 の塊に、交代のノードの行列を符号化の行で（`replacementsEncoded`）、再開したターンを重みと引いた 1 つだけに（`ResumedTurn.pick`）、スロットの行動を番号に（`acts`、1 プロセスに 1 回）、裏の決定化を土台の局面と差し替えたポケモンで保持。q-nocover の M-C データ生成で port の線の JSON は上り 1,177 → 340 KB/局・下り 870 → 283 KB/局、1 局の CPU 0.652 → 0.587 s（−9.9%）、1 分の局 969 → 1,027（+6.0%）。局は 3,000 局すべてバイト一致

ブランチ `ika-350-no-json`（ABBA は master 91683b5 と ce02a89。その後 master 2a16ac7（IKA-349、port と生成の道に触れない）を取り込み、
関係テストを回し直した）。

答えた問い: **IKA-302 の後にまだ JSON で port と行き来している口はどれで、いくら掛かっているか。効きの大きい順に二進・整数 ID・
取っ手に置き換えられるか（局はバイト一致のまま、遅くしない）。**

## 0. 答え

* 一覧にした（§1）。q-nocover の M-C データ生成（推論サーバ 2・ワーカー 24）の 1 局で、port の線は上り 1,177 KB・下り 870 KB が
  すべて JSON。大きい順に、局面の `hold`（548 KB 上り）、`qfeatures`（上り 282・下り 259 KB）、交代のノードの行列の `replacements`
  （下り 287 KB、局面を 36 枚）、行動の列（`fill_encoded`・`score` の上り 317 KB）、再開したターンの全分岐（`turn` の下り 72 KB）。
  port の側で JSON に使う時計は 1 局 38 ms（読み 12.5、書き 8.7、`Position::to_json` 14.9、`from_json` 2.1）
* 5 つ置き換えた（§2）:
  1. **`qfeatures` の答えを float32 の塊に**（ヘッダの行のあとに、行数 × 34 の little-endian f32）
  2. **交代のノードの行列を符号化の行で**（`replacementsEncoded`: 組ごとの交代の局面を port が符号化し、評価モデルの行を共有メモリで返す）
  3. **再開したターンを重みと、引いた 1 つだけに**（`ResumedTurn`: 重みを先に、引いた分岐か一時停止を `select` で 1 つだけ）
  4. **スロットの行動を番号に**（`acts` 行で 1 プロセスに 1 回だけ行動の JSON を渡し、以降の列は `[[3, 7], [3, 9]]`）
  5. **裏の決定化を土台と差し替えたポケモンで保持**（`hold` に `base`・`side`・`pokemon`・`megaCapableSlots`）
* 局は同じ（§3）。ABBA 2 組（300 局 × 2、1,200 局 × 2）で **3,000/3,000 局がバイト一致**（対照: 局 i 対 i+1 は 0 一致、
  worker の失敗 0）
* 速さ（§4、1,200 局の ABBA）: 1 局の CPU **0.652 → 0.587 s（−9.9%、両 B が両 A より下）**、ワーカー 0.332 → 0.293（−11.6%）、
  port 0.232 → 0.204（−11.9%）、推論サーバ 0.088 → 0.089。1 分の局 969 → 1,027（+6.0%）
* 残る JSON（§5）: 局面の正規形（`hold` の中身、`resolve` の選んだ分岐、本当の交代の相）と、`score` の答え、符号化したノードの
  見出しの小さな部分

## 2. 置き換えたもの

### 2.1 `qfeatures` の答えを float32 の塊に（`node::qfeatures_binary` ⇔ `RustNode.qfeatures`）

要求に `"binary": true`。答えはヘッダ `{"width": 34, "rows": [n0, n1], "bytes": B}` の行のあとに、side 0 の行・side 1 の行の順に
little-endian の f32 が B バイト。前は JSON の f64 の最短往復の文字列を Python が読み（その f64 に戻る）、float32 に丸めていた。
port は同じ f64 を `as f32`（最近接偶数）で丸めるので、同じビットになる（§3.2 のテスト）。候補の列は 2.4 の番号。JSON の答えは
`qhead.port_features(json_answer=True)` で残す（テストだけが使う）。

### 2.2 交代のノードの行列を符号化の行で（`commands::replacements_encoded` ⇔ `RustNode.replacements_encoded`）

`selfplay._do_replacement_node` の `matrix(at, evaluate)` は、裏の決定化 `at` から交代の組ごとに `replacements`（生成器なし）を
聞き、答えの局面を並べて `evaluate(flat)` していた。評価モデルに符号化の形（`from_encoded`、`port.encoded_leaf_plan`）がある
ときは、1 つの要求 `replacementsEncoded`（`position` と組の列 `pairs`）で port が組ごとに同じ相を解き（`phase_command` を
`phase_position` と書き出しに分けた）、その局面を符号化して、符号化したノードの行と同じ道（共有メモリ）で返す。行は組の順、
`decided` は局面の終わりの結果。Python は `from_encoded` を 1 回呼ぶ（`evaluate(flat)` と同じ 1 回・同じ行数なので、推論サーバの
一括も同じ）。評価モデルが無いとき（hp-share）は前のまま。

### 2.3 再開したターンを重みと、引いた 1 つだけに（`port.resumed` ⇔ `rustnode.ResumedTurn`）

`_self_switch_encoded` の最後の `port.resume(..., full=True)` を `port.resumed` に。まず重み（`full` なし）を聞き、
`_advance` が自分の生成器で引いた添字 k を `ResumedTurn.pick(k)` が `select=k` で聞く（分岐なら局面、一時停止なら pause）。
重みは同じ f64、選んだ分岐は full の答えの k 番目と同じ（port はターンをもう一度解く。ターンは pause と選択で決まる）。
`outcomes`・`pauses` を読む呼び手（`luck` の台帳、`humanplay`）には、そのとき full を 1 回聞いて渡す。

### 2.4 スロットの行動を番号に（`held::define_actions`・`parse_actions_list` ⇔ `_candidates`・`RustNode._defined`）

行動の列（`score` の候補、`qfeatures` の両側、`fill_encoded`・`fill` の `ours`・`theirs`、`resolve`・`turn` の `actions`、相の
`choices`、`replacementsEncoded` の `pairs`）を、スロットの行動の番号の列 `[[3, 7], [3, 9]]` で書く。番号は行動の JSON の文字列ごとに
プロセスの一生で 1 つ（`_ACTION_NUMBER`、同じ文字列は同じ番号、番号を別の文字列に回さない）。port は `acts` 行
（`{"kind": "acts", "acts": [[番号, {…}], …]}`、答えなし）で表を作り、`parse_actions_list` が数を表から読む。表はプロセスの一生
（`forget` で捨てない）で、セルのスレッドからも読む（`RwLock`）。Python は port ごとに渡した番号を覚え、要求の前に足りない分だけ
`acts` 行を送る（port を立て直せば渡し直す）。`score` の答えのメモ（IKA-264）は要求のバイトで引くので、同じ行動は同じ番号 ⇒ 同じ
バイトで、当たりは変わらない。

### 2.5 裏の決定化を土台と差し替えたポケモンで保持（`hidden.substitute`・`rustnode.note_completion` ⇔ `held::define_line`）

`hidden.substitute` は土台の局面から、1 つの側の裏のスロットのポケモンを作り直し、その側の `mega_capable_slots` を計算し直し、
他は写す。`hold_positions` のとき、作った物を `note_completion` で覚え、その決定の中で初めて port に渡すときは
`{"kind": "hold", "id": N, "base": B, "side": s, "pokemon": [[添字, {…}], …], "megaCapableSlots": [...]}` を送る（土台がまだなら
先に土台の `hold`）。port は土台の複製にそのポケモンと `megaCapableSlots` を入れる。`Position::from_json` は欄ごとに読むだけなので、
丸ごとの JSON を読んだ局面と同じになる。決定の終わりに覚えを捨てる（`hold_positions` の「決定の中で書き換えない」約束の範囲だけで
使う）。この形の物は文字列を持たないので、同じ中身の別の物と番号を分け合わない（`score` を 2 回聞くことがある。答えは同じ）。

### 2.6 計器

`timing` の数え（on のときだけ）: `port.qfeatures.binary`・`port.qfeatures.bytes`・`port.replacements.encoded`・`port.resume.picked`・
`port.acts.defined`・`position.delta`・`position.defined.delta`。`tools/legal_moves_cost.py` は要求を自分で書くので、`_defined` の行を
前に付けるよう直した。

## 5. 残る JSON と、その理由

* **`hold` の丸ごとの局面**（259 KB/局のほとんど、約 33 行/局）: `needed`・`weights` の本当の局面、`qfeatures` の局面など。局面の正規形
  （`position.ts` ⇔ `position.py`）で、正しさの契約。Python が作った物は Python が書くしかない。1 決定に 1 回（IKA-302）
* **port が返す局面**（`resolve` の選んだ分岐 84 KB/局、本当の交代の相 21 KB/局、先発 7.5 KB/局）: ゲームを進める本当の局面で、
  Python は `Position` を組む。同じく正規形
* **`score` の答え**（48 KB/局、スコアと内訳の小さな数の列）と**符号化したノードの見出し**（`fill_encoded` 103〜114 KB/局: `exact`・
  `folded`・`refused`・注記・`decided`）
* 前の決定で渡した局面と同じ文字列の `hold`（14%）は、Python が文字列を作らないと同じと分からないので、置き換えていない

> 引いた 1 つだけに／スロットの行動を番号に（1 プロセスに 1 回だけ行動の JSON を渡す）／裏の決定化を土台と差し替えたポケモンで
> 保持。JSON は上り −71%・下り −67%。ABBA 3,000 局すべてバイト一致、1,200 局の組で 1 局の CPU −9.9%（ワーカー −11.6%、port −11.9%）、
> 1 分の局 +6.0%。残る JSON は局面の正規形（Python が作った局面の hold、ゲームを進める局面）と score の答え・見出しの小さな部分。

## 8. 別課題の候補

* **`fill_encoded` の見出し**（103〜114 KB/局）: `exact` の真偽の行列、`folded` の木、`decided` の組。本体の二進の塊（IKA-302 の
  span と同じ形）に移せる
* **`score` の答え**（48 KB/局）: スコアと内訳（整数と f64）を二進に
* **`humanplay` の交代のノードの行列**（`humanplay.py` の `resolve_replacements` の組）: 生成と同じ `replacementsEncoded` にできる。
  IKA-344 が humanplay を触っているので今回は触らない
* `_with_deadline` のスレッドの受け渡し（要求 1 回に 2 回のスレッド切り替え、約 200 回/局）: JSON ではないが行き来の固定費
* IKA-339 のブランチは `qhead.port_features` に `rust.qfeatures` の段を足している。この課題で `port_features` は
  `RustNode.qfeatures`（同じ段の名前で計時）を呼ぶ形になったので、取り込むときは IKA-339 の包みを外す
