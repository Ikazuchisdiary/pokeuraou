# IKA-452: 生成の 1 決定の時間を段ごとに分けて測る

課題: Notion の Issues（ID IKA-452）。枝 `worktree-agent-a2cd698410aa0963e`。コードは変えていない。計測の駆動スクリプトは `C:/tmp/ika452/` に置き、コミットしていない。

## 0. 要点

問いは、今の本番のデータ生成の 1 決定で、実時間と CPU が何に使われているかである。`tools/profile_stages.py generation` を本番の形で 2,000 局回し、3 回繰り返した。

* ワーカーの実時間（21 過程の合計）の 96.8% を、段の行で説明できた。3 回の幅は 96.81〜96.83% である。残りの 3.2% は、タイマーのない部分である。名前は付けない。
* 過程木の CPU の 95.1% を説明できた。port の exe と推論サーバは、OS が数える過程全体の CPU である。ワーカーは、段の行の CPU とした。
* 実時間では、ワーカーが port の応答を待つ行が 39.9% で最大である。次が推論サーバの待ち（評価モデル 15.5%、Q 9.9%、受け渡し 1.6%、計 27.0%）である。
* CPU では、ワーカーの Python が 48.9%、port の exe が 37.0%、推論サーバが 14.0% である。
* 課題の判断の表では、推論サーバの往復と待ちが 2 割以上、port の解決と埋めが 2 割以上のどちらにも当たる（§6）。
* ただし、今の評価モデルを CPU で順伝播すると、1 局あたり 1.6〜1.7 CPU 秒かかった。サーバ付きの 1 局全体（0.68 CPU 秒）の 2.4 倍である。port の中で順伝播する案は、今の網では成り立たない（§5）。

### 3.1 埋め 1 回の固定費

`rust.fill@purpose` の行は、1 回の fill を呼ぶ側の実時間（応答の待ちと header・body・unpack を含む）で数える。同じ回の、子の時計（`rust.child@purpose`）と比べた（A1）。

| 用途 | fill の回数 | 1 回のセル数 | 1 回の葉 | 呼ぶ側の実時間（ms/回）| 子の時計（ms/回）| 差（ms/回）|
|---|---|---|---|---|---|---|
| 行列（matrix）| 17,585 | 124.7 | 240.8 | 13.46 | 10.65 | 2.81 |
| 差分（dirty）| 51,962 | 42.6 | 104.4 | 7.38 | 4.15 | 3.23 |

* 子の時計は、セル数にほぼ比例する。2 点（用途 2 つの平均）を通る直線のセルあたりの傾きは 0.079 ms、切片は 0.79 ms である。2 点の平均だけで引いた直線なので、固定費の見積もりとして荒い。
* 「差」は、呼ぶ側の実時間から子の時計を引いた値で、セル数が 3 倍近く違っても 2.8〜3.2 ms でほぼ同じである。2 つの測った値の差であり、内訳は測っていない。
* 固定費の中身のうち、直接測れたのは次の 3 つである。
  * 子の中: 要求の読みと応答の組み立て 0.15 ms/回、4 つの時計に入らない分 0.46 ms/回。
  * Python 側: header・body・unpack・ask の行。fill 以外の要求とも共有なので、fill 1 回あたりには切り分けていない（全体で 111.6 秒、実時間の 5.0%）。
  * 局面の受け渡し: 子の `hold` は 133,671 回で 0.08 ms/回。Python の `position.json` は 75,242 回で 4.3 秒（0.06 ms/回）。小さい。
* 行動リストの展開は、子の中の「セル解決」に含まれる。単独の時計は無く、分けていない。

## 6. 判断

課題の「判断」の表に当てはめる。

| 条件 | 測った値 | 当たるか |
|---|---|---|
| 推論サーバの往復と待ちが 2 割以上 | ワーカー実時間の 27.0%（評価モデル 15.5% + Q 9.9% + 複写 1.6%）| 当たる |
| port の解決か埋めの固定費が 2 割以上 | 手番の解決（子の時計）17.3%。port の応答を待つ行全体 39.9%。fill 1 回の固定費 2.8〜3.2 ms は計 209 秒で 9.4% | 当たる（待つ行全体で見たとき）|
| どれも 1 割未満 | | 当たらない |

* 表を文字どおり読むと、1 行目も 2 行目も当たる。
* ただし 1 行目の「port の中で順伝播する案」は、§5 の損益分岐から、今の網では成り立たない。1 局 0.227 CPU 秒以下（今の CPU 順伝播の 0.14 倍以下）の網が条件である。網を小さくする案の起票は、その条件を目標にした別の課題として判断する。
* 2 行目の「port の高速化」は、条件の言い方で当たりが変わる。子の時計の 13.2%（セル解決）と 4.7%（符号化）が子の仕事で、往復と待ちを含む行全体が 39.9% である。

### 一番大きい段の案（port の応答を待つ行、実時間 39.9%、port の exe は CPU の 37.0%）

1. **往復の回数を減らす。** 往復は 263,768 回で、1 回あたり呼ぶ側で 1.12 ms、空いた機械で 0.185 ms。`needed`（23,372）と `bind`（27,878）と `replacementsEncoded`（32,793）は、子の仕事が 0.02〜0.13 ms しかない。直後の要求に束ねると、約 84,000 回 × 約 1 ms で約 80〜90 秒、ワーカー実時間の 3.6〜4% が見込みの上限である。局の中身は変わらない。得られる局/分は、空きコア 16% の範囲で、2〜4% と見る（測っていない）。
2. **子のセル解決そのものを速くする。** セル解決は実時間の 13.2%、CPU の見積もりで 17.8% である。同じ決定の中の同じセルの再解決は、`--dupes` の 400 局（D1）で `port.cell` 873,179 回のうち 0 回だった。決定の中のセル再利用は効かない。解決の中の段（`profile` の phase 時計）を測ってから決める。10% 速くなれば、実時間 1.3%、CPU 1.8%（見込みの計算で、測っていない）。
3. **小さな評価モデルの要求をサーバに送らず、ワーカーの手元で CPU で順伝播する**（port ではなくサーバ側の案）。`replacement` の要求 32,793 回が葉 1.9 枚で 3.8 ms ずつ待つ。計 124.7 秒、実時間の 5.6%。CPU の順伝播は 1 葉 約 0.1 ms なので、葉 2 枚なら往復の十分の一以下である。GPU と CPU の浮動小数の差で局が変わりうるので、変化の大きさを記録して同じ費用で判定する。見込みの上限は実時間の 5.6%。

## 7. 対照

### 7.1 陽性対照: 既知の仕事を足した段が、その分だけ増えるか

`equilibrium._lp`（`lp`・`lp.q` の両方が呼ぶ）の頭に、環境変数で 1.0 ms の busy-wait を足した。worktree の `src/pokeuraou/equilibrium.py` を一時的に編集し、測ったあと `git checkout` で戻した（コミットしていない）。400 局、seed 45201、サーバ付き。C0・C2 は足さない。C1・C3 は足す。足した回数はワーカーが終了時に書き、2 回とも 30,008 回、足した仕事は 30.0 秒だった。

| 量 | C0 / C2（足さない）| C1 / C3（足す）| 増え方 | 足した量 |
|---|---|---|---|---|
| `lp` + `lp.q` の実時間（秒）| 42.6 / 44.5 | 75.7 / 76.4 | 平均で +32.5 | 30.0 |
| `lp` + `lp.q` の CPU（秒）| 34.6 / 35.6 | 64.1 / 64.5 | 平均で +29.1 | 30.0 |
| 段の和（秒）| 494.3 / 509.1 | 529.4 / 528.3 | 平均で +27.2 | 30.0 |
| タイマーのない部分（秒）| 14.4 / 15.0 | 14.7 / 14.9 | 変わらない | 0 |

* 足した段の行が、足した量とほぼ同じだけ増えた。タイマーのない部分は動かなかった。足した仕事が、別の行や「ない部分」に漏れていない。
* 足さない 2 回（C0 と C2）の差は、`lp` + `lp.q` の実時間で 1.9 秒、段の和で 14.8 秒だった。足した効果（+32.5 秒、+27.2 秒）より、`lp` の行では十分小さいが、段の和では同じ桁である。段の和の増え方は、機械の揺れを含む。`lp` の行の増え方が確かな証拠である。
* 段が互いを含まないこと（2 度数えが無いこと）は、`tests/test_timing.py` の `test_a_stage_excludes_what_it_nests`・`test_recursion_counts_once` が持つ。実際の生成では、段の和が実時間を超えない（96.8%）ことと、足した仕事が 1 回だけ数えられたこと（上の表）で確かめた。

### 7.2 値どうしの照合

* 3 回の割合の幅が 1 ポイント程度で、同じ局を 3 回打った結果が揃う。
* 子の応答時間（`wire`、子の中で別に実装された時計）の fill 437.1 秒は、`rust.child.*` の 5 つの時計の和 405.4 秒より大きい。差 31.7 秒は子の中の別の仕事である。また `wire` の回数（fill_encoded 69,547・resolve 34,276・needed 23,372・bind 27,878・qfeatures 27,878）は、Python 側の段の呼び出し回数と全部一致した。
* 子の応答時間の合計（605.4 秒）と、OS が数えた子の CPU（526.0 秒）は同じ桁で、子は応答中にほぼ CPU を使っている（0.87）。

## 8. 確かめていないこと

* 実時間の割合は、16 論理コア（物理 8）を 46 過程が取り合う状態の値である。待ち（サーバ・port）の行は、動けるのに順番を待った時間を含む。CPU を減らしたとき実時間が同じだけ減るとは限らない。
* port の exe の CPU を子の仕事の種類に割り当てた値は按分の見積もりである。種類ごとの CPU は測っていない（子に CPU 時計を足していない）。
* ワーカーの段の CPU は `thread_time` で、15.6 ms の刻みの和である。段の行に入らない CPU が 4.8% ある。HiGHS を別スレッドで走らせる分が入るかは確かめていない。
* 「port の応答を待つ行」の CPU が 146.1 秒ある理由は調べていない。
* 往復が 1.12 ms かかる原因（スケジューラの待ちか、パイプか、別の何か）は分けていない。
* 決定をまたいだセルの再利用は測っていない。`--dupes` は決定の中だけを数える。
* 評価モデルを port の中で順伝播する費用は、小さな網では測っていない。測ったのは、今の網（value-mc7、1 スレッド）の CPU 順伝播である。サーバ無しの形の `forward` の行に、Q の順伝播が入るかは確かめていない。
* サーバ無しの形は 600 局 × 2 回で、定常状態の幅が小さい（局あたり約 29 局/ワーカー）。サーバ付きと同じ局数ではない。
* 速さの ABBA は組んでいない。この課題は 2 つの構成の速さの比べではなく、同じ構成の内訳である。サーバ付きの 3 回は同じ構成の繰り返しで、サーバ無しはその前後に分けて走らせた（A1・A2、L0、A3、L1・L2）。サーバ付きとサーバ無しの比（0.25 倍）は桁の話で、比の信頼区間は出していない。
* 選出の store は value-mc7 を使った（本番の value-mc7x2 の store ではない）。選出は読み済みの store を引くだけで、局ごとの費用は 1.3% 以下（`selection`・`record`）なので、段の表には影響しないと見ているが、確かめていない。
* worktree の exe（77 秒でビルド）と本体の exe の同一性は確かめていない。生成はこの worktree の exe で走った。

## 12. 待ちの行の CPU は計時の偏りだった（2026-11-26、調整役）

問いは、§2 の「port の応答を待つ行」が CPU を 146.1 秒使った理由である。

### 12.1 わかったこと

* 段の CPU は `time.thread_time` の差で数える。Windows では、この時計は 15.6 ms の刻みで進む。
* この刻みの加算は、待ちの直後の短い行に偏って割り振られる。長く計算する行（LP・信念の補完）は少なく数えられる。
* スレッドのサイクル数（`QueryThreadCycleTime`）で数え直すと、待ちの行の CPU は約 3 分の 1 になった。待つ間に CPU を使ってはいない。
* 読み取りのスレッドへの受け渡し（`_with_deadline` の `submit` と `result`）は、1 回 5 µs ほどの CPU だった（`C:/tmp/ika452b/handoff.py`）。26 万回でも 1.3 秒で、原因ではない。

### 12.2 測り方

* ワーカー 1 つ（60 局、サーバ 1 つ）と、本番の形（21 ワーカー、サーバ 2 つ、600 局）を、時計だけ替えて 2 回ずつ回した。種 45201、value-mc7、q-mc6。
* サイクル数の時計は、`src/sitecustomize.py` に一時的に置いた差し替えで入れた（`IKA452_CYCLES=1` のときだけ `time.thread_time` を `QueryThreadCycleTime` ÷ 校正した周波数に替える）。測ったあとに消した。コミットしていない。
* 過程ごとの CPU（psutil）は、この差し替えの影響を受けない。

### 12.3 結果

ワーカー 1 つ（空いた機械）の 1 回あたり:

| 行 | 実時間 | `thread_time` の CPU | サイクル数の CPU |
|---|---|---|---|
| `rust.score` | 0.209 ms | 0.603 ms | 0.100 ms |
| `rust.bind` | 0.103 ms | 0.797 ms | 0.057 ms |

| `lp` | 0.988 ms | 0.734 ms | 0.991 ms |
| `belief` | 5.378 ms | 3.590 ms | 5.386 ms |
| 待ちの行（7 行）の CPU の和 | | 4.0 秒 | 0.7 秒 |

* `thread_time` では、1 回あたりの CPU が実時間を上回る行があった。1 本のスレッドでは起こりえない値で、計時の偏りを示す。
* サイクル数では、どの行も CPU が実時間以下になった。LP と信念の補完は、CPU と実時間がほぼ同じになった。

本番の形（21 ワーカー、600 局）のワーカーの段の CPU:

|---|---|---|
