# IKA-443: プールの 390 体の組み替えで強い構築を探す

2026-11-24 着手。枝 `ika-443-recombine`。課題: https://app.notion.com/p/4214b8acaa6c81449bdff6c03a7f7eae 。

## 要点

* プールの 65 構築の型を 1 体ずつ入れ替えた 6,491 候補（異なるもの 5,773）を、選出の値でふるい、上位を本物の局で確かめた。
* Ychu + Raptor (Ceruledge) のソウブレイズを、Mence + Sylv の型のヒスイウインディに替えた構築が、元の構築を上回った。別の種での確かめの局で +0.052 [+0.038, +0.066]（8,000 局ずつ）。§2 の 1 行目に当たる。
* 16 構築で解いた値は、65 構築の値と相関 0.943 で、第一段のふるいに使える。上位を選ぶと値は 0.023 高めに出る。
* 組み替えの構築でも、値は得点より楽観に偏らなかった（10 候補の得点 − 値の平均 +0.018）。値の差が 0.02 以内の候補は、値では並べ分けられない。

## 1. 何を確かめるか

プールの 65 構築の 390 体を組み替えて、プールのどの構築より強い構築を探す。IKA-442 で、選出の値は構築の強さの順位を当てると分かった（gen-6、構築の段の補正後の相関 0.944）。この課題は、その値を第一段のふるいに使う。入れ替えの単位は、技・持ち物・特性・性格・振り方まで決まった型で、型の中身は変えない。

## 2. 判定の目安（測る前に決めた。Notion の課題の本文と同じ）

| 結果 | 次にすること |
|---|---|
| 最上位の候補の得点が、プールの最上位の構築を有意に上回る | その候補を人と打つ道具の推奨構築にし、探索の範囲（入れ替えの数・プール外の型）を広げる課題を立てる |
| 候補の得点と値の差の平均が 0.03 を超える | 組み替えの構築では値が楽観に偏る。第一段の後に、安い探索の局で絞る段を足す |
| どちらでもない | 候補の数を増やすか、評価モデルの世代を待つ |

有意は、候補とプールの最上位の構築の得点の差の 95% 区間が 0 を含まないことにする。

## 3. 道具

`tools/team_search.py`（テストは `tests/test_team_search.py`）。

| 段 | 命令 | すること |
|---|---|---|
| base | `base --store <store>` | 解いた store から、プールの各構築の 65 構築への選出の値の平均を出す（ミラーは 0.5） |
| neighbors | `neighbors --base base.json --bases K --swaps 1` | 値の上位 K 構築から、1 体を別の構築の型に入れ替えた候補を作る。種族と持ち物の重複は `roster_from_data` が拒む |
| value | `value --candidates c.json --model M...` | 各候補を席 0 にして、65 構築との選出ゲームを解く。`--subset N` で N 構築だけにする |
| report | `report` | 候補を値の順に並べる |
| pool-with | `pool-with --ids ...` | プールの 65 構築と選んだ候補を持つプールのファイルを書く（本物の局の段に使う） |

正の対照として、プールの Ychu + Raptor (Ceruledge) を候補として `value` に通した。65 構築との値は、value-mc6x2 の store の値と最大 2.6×10⁻⁸ の差で一致した。平均は 0.6334 で、`base` の値と同じだった。

## 4. 方法

評価モデルは本番の value-mc6x2 である。

### 4.1 第一段: 選出の値でふるう

1. `base` で、プールの各構築の値を value-mc6x2 の store から出す。上位は Ychu + Raptor (Ceruledge) 0.6334、Dual Weather Screens (Swampert) 0.5951、Ttar + Raptor 0.5935、Gengar + Raptor 0.5737、Chicken SunRoom 0.5702 だった。
2. 上位 5 構築から 1 体を入れ替えた候補を作る。9,150 通りのうち 2,659 通りを規則が拒み、6,491 候補になった。
3. 全候補を、乱数で選んだ 16 構築（種 0）に対する値でふるう（1a）。65 構築すべてで解くと 1 候補 65 解で、全候補では 12 時間を超えるため。
4. 1a の上位 200 候補と、無作為に選んだ 50 候補を 65 構築すべてで解く（1b）。無作為の 50 候補で、16 構築の値と 65 構築の値の相関を出す。

### 4.2 第二段: 本物の局

1b の値の上位 10 候補と、プールの値の上位 3 構築を、65 構築と本物の局で打つ。打ち方は生成と同じ形（`match_queue.py --pool`、幅 12、q-nocover、value-mc6x2）で、1 構築あたり約 2,000 局にする。各構築の得点と選出の値を比べ、§2 で判定する。

## 5. 結果

### 5.1 第一段 1a（16 構築）

6,491 候補を 16 構築（種 0）に対する値で解いた。14 ワーカー・2 サーバで 10,017 秒（2.8 時間）だった。値の中央は 0.537、上位 200 番目は 0.626、最上位は 0.687 だった。

あとで、6,491 候補の中に、同じ型が技の並び順か性別だけ違う形で別の候補として入っていたと分かった。異なる候補は 5,773 個だった（`play_key` で数えた）。値はほぼ同じなので、1a の順位には影響しない。`neighbors` はこの重複を除くように直した（直した後は 5,771 候補）。

### 5.2 第一段 1b（65 構築）

1a の上位 200 候補と、残りから無作為に選んだ 50 候補（種 443）を、65 構築すべてで解いた（1,258 秒）。

### 5.3 第二段の打ち方

`tools/pool_match.py` に `--pairs-focus` と `--pairs-field` を足した。指定した構築が、指定した相手と当たる組だけを引く。10 候補とプールの上位 3 構築を focus に、元の 65 構築を field にして、ミラーを除くと 839 組になる。プールのファイルは `team_search.py pool-with` で 65 構築と 10 候補を並べた（`C:/tmp/ika443/pool-stage2.json`、75 構築）。両腕とも value-mc6x2・q-mc6・幅 12・q-nocover で、選出の探索はしない（ε 0）。13,000 組・種 44301 で打つ（`C:/tmp/ika443/stage2.py`）。

### 5.6 確かめの局の結果

8,000 組・16,000 局を 1,335 秒で打った。落ちたワーカーは 0 だった。

## 6. 判定

§2 の 1 行目に当たる。最上位の候補は、プールの最上位の構築を区間が 0 を含まずに上回った（第二段 +0.030 [+0.002, +0.059]、確かめの局 +0.052 [+0.038, +0.066]）。

| 何を | 分かったこと |
|---|---|
| 第一段のふるい | 16 構築の値は 65 構築の値と相関 0.943。上位 200 では 0.023 高めに出る |
| 組み替えの構築での値 | 10 候補の得点 − 値の平均は +0.018 で、楽観には偏らない。値の差 0.02 以内の候補は値では並べ分けられない |
| 見つかった構築 | Ychu + Raptor (Ceruledge) のソウブレイズを、Mence + Sylv のヒスイウインディに替えた構築。元の構築より得点が +0.03〜+0.05 高い |

次にすること（§2 の 1 行目）は 2 つある。

* 見つかった構築を、人と打つ道具の推奨構築にする。どこにどう出すかは、ユーザーと決める。
* 探索の範囲を広げる課題を立てる。2 体の入れ替え、上位 5 構築より外の土台、値の差が小さい候補を本物の局で絞る段を、費用と合わせて決める。
