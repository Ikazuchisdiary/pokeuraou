ブランチ `ika-302-no-json-hot-paths`（ABBA は master 77868a7 を取り込んだ上。その後 master 4f78dfb を取り込み、port を作り直して
関係テスト（§3.2）と検査を回し直した）。

## 0. 答え

* 測った（§1）。深さ 2 の 1 局で、port の線は上り 18.8 MB・下り 7.1 MB。port が JSON に使う時計は 402 ms/局
  （要求の文字列の読み 191、局面の組み立て `Position::from_json` 71、局面の書き出し `to_json` 72、答えの文字列 67）。
  上りの大半は、部分ゲームの局面（port が 1 つ前の `turn` で枝として書いたもの）を、`score` と `fills` で送り返す分だった。
  深さ 1 は 54 ms/局で、大きいのは符号化したノードの見出し（span の JSON）と、同じ局面の読み直し
* 2 つ置き換えた（§2）:
  1. **span を本体の二進の塊に**: 符号化したノードの見出しの大部分（セルごとの葉の番号と重み）を、共有メモリの本体の後ろに

## 2. 置き換えたもの

### 2.1 span を本体の二進の塊に（`encoded_node::span_block` ⇔ `rustnode._binary_spans`）

本体（共有メモリか管）の配置: 符号化の配列 → 葉の目的値（f64、今まで通り）→ **span の塊**。塊は、全 span の重み（f64）、
span ごとの行・列・長さ（u32 が各 span 数だけ）、全 span の葉の番号（u32）、すべてリトルエンディアン。見出しは `spans` の代わりに
`spanAt`（塊の始まり、本体の中の位置）・`spanCount`・`spanLeaves` を持つ。`fills`（多ノード）も各ノードの本体の中に同じ塊を持ち、
`bytes` はそれを含む。`alternativesEncoded` は span を持たない（塊なし、値の位置は今まで通り末尾から）。

Python は `numpy.frombuffer(...).tolist()` で読み、span ごとに Python のリスト `(i, j, [番号], [重み])` にする。重みは port の
f64 そのもの（JSON の最短往復の文字列も同じ double に戻っていた）で、下流（`_folded`・`beliefnode`）は今まで通り自分で
`np.asarray` を作るので、ドット積の入力の並びと整列も変わらない。

JSON の道は要求の `jsonSpans: true` で残す（テストだけが使う。本番の道は送らない）。

### 2.2 局面を番号で指す（`rust/src/held.rs` ⇔ `rustnode._Stored`）

`hold_positions`（生成のワーカーが入れる。IKA-264 の「1 決定のあいだ、局面をその場で書き換えない」約束の範囲）のときだけ:

* Python が初めて局面を使うとき、偶数の番号を振る（同じ文字列の別の物は同じ番号。`score` の答えのメモが要求のバイトで
  当たるのを保つため）。要求は `"position": {"held": 番号}` と書く
* その要求を port に送る直前、port がまだ持っていない番号なら、答えの無い行
  `{"kind": "hold", "id": 番号, "position": {…正規形の JSON…}}` を先に送る（`RustNode._defined`）。メモから答えた要求は何も定義しない
* 深さ 2 の `turn` の束（`turn_many`、full）は `refs: true` を付ける。port は各枝を奇数の番号で保持し、答えの枝に `held` を書く。
  同じ決定で等しい局面（`leaf_key` と `==`）を既に保持していれば、その番号を返す。Python は読んだ `Position` をその番号で登録するので、
  部分ゲームの `score`・`fills` は局面を書かずに番号だけを送る
* 決定の終わり（`timing.on_decided`）で Python は自分の表を捨て、次の要求の前に答えの無い `{"kind": "forget"}` を送る。
  port は保持を捨てる。番号はどちらの側も使い回さない。port を立て直したとき（`reset`）も Python の表を捨てる（新しい port は
  奇数の番号を 1 から振り直すため）
* port は知らない番号を黙って別の局面に読み替えない（panic → その要求は拒否）。セルのスレッド（IKA-32、2 本以上）は別スレッドの
  保持を見られないので、`many` をプールに回すときは番号を局面に書き戻し、`refs` を外す

`hold_positions` が切れているとき（道具・テスト）は、要求は今まで通り局面の JSON を運ぶ。

### 2.3 port の線の時計（`rust/src/wire.rs`）

要求の種類ごとの行数・上り下りのバイト・文字列の読み書きの時間と、`Position::from_json` / `to_json` の時間。
`POKEURAOU_PORT_THREADS_REPORT` のあるとき、終了時に `wire-<pid>.json` を書く（ない時は何も書かない）。
B 腕（このブランチの exe）は時計を積んだまま計時したので、下の速さはその分も込み。

## 5. 残る JSON と、その理由

* **`hold` 行の中身**（局面の正規形）: `position.ts` ⇔ `position.py` と共有する正しさの契約。1 決定に 1 局面 1 回になった
* **port が返す局面**（深さ 2 の枝 450 局面/局、`resolve` の選んだ枝、交代の相、先発）: Python は `Position` の物を組むので、
  二進にしても物を組む費用（`position.parse` 44 ms/局）は残る。port の `to_json` と書き（約 110 ms/局）と Python の `json.loads` は
  減らせる余地がある（別課題）
* **`score` の候補の列**（深さ 2 の `many` の上り約 5.7 MB/局の大半）: IKA-321 の手ごとの文字列。整数の手 ID と一度だけの文字列表にする余地（別課題）
* 見出しの小さな部分（`exact`・`folded`・`decided`・`refused`・注記）、`score` の答えの `detail`、一時停止の継続（`pause.raw`、まれ）
* 推論サーバとの往復は今回の測定の対象外（配列は共有メモリ。`serve.copy` 0.1 ms 程度）。起動時の大きな JSON（IKA-112）も対象外
  （1 プロセス 1 回）

## 8. 別課題の候補

* **port が返す局面の書き出し**: 深さ 2 で `Position::to_json` 76 ms/局と文字列の書き 36 ms/局、Python の `json.loads` の大半。
  `Value` を経ずに直接書く（または二進にして Python 側を C で読む）。Python の `Position.from_json`（44 ms/局）は形に依らず残る
* **`score` の候補を整数の手 ID に**: 深さ 2 の `many` の上り 5.7 MB/局の大半。手の文字列表を 1 決定に 1 回
* `rust.unpack` の span の読みを配列のまま下流へ（`_folded` を配列で）: 局が変わらないことを確かめてから（ドット積の入力の整列）
* 保持の上限 `_HELD_MAX`（512、1 決定の Python 側の表）を深さ 2 の決定が超えるかは数えていない。超えると表を捨てて番号を
  振り直し、同じ局面をもう一度 `hold` する（局は変わらない、費用だけ）。数えてから上限を決め直す
