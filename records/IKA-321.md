# IKA-321: `narrow` の Python を半分に —— 覆いの鍵を 1 回だけ作り、detail の文字列を読まれるときに書き、port への候補の列を手ごとの文字列から組む。メニューも port へのバイトも局も同じ

2026-09-26。担当 IKA-321（worker）。master 2442df3 から切った `ika-321-narrow-python`（取り込み後は master 5bdfb06 の上）。

答えた問い: **IKA-319 が測った `narrow` の Python の重い段（覆い 39%、port への要求の JSON 32%、detail の文字列 14%）を、
局を変えずにどれだけ削れるか。**

用語: 「裏」＝選出した 4 体のうち場に出ていない 2 体。「対戦評価」＝盤。

## 1. 変えたこと

* **覆い**（`narrow._cover`・`_option_ids`）: 貪欲法の各回で全候補の `_slot_key`（文字列）を作り直していたのをやめた。候補ごとの
  枠の選択肢を最初に 1 回だけ小さな整数にし（枠の手の物は組み合わせの間で共有されるので、物の id で引いて文字列は物ごとに 1 回）、
  「まだ覆っていない」は整数の bytearray で判定する。回の数・なめる順（`order`）・比べる利得は前と同じ。覆えなかった選択肢の
  名前（`_slot_label` と同じ文字列）は、残ったものだけ書く（前は全候補 × 枠で `describe` を呼んでいた）
* **detail**（`Candidate.detail`）: `Candidate` を手書きの類にし、`detail` を読まれたときに書く。port の答えの部品
  （`_PortDetail`）と、葉の順位付けの行（`_LeafDetail`: `leaf {値:+.4f}` の後にダメージの行）を持っておき、最初に読まれたときに
  前と同じ書式で文字列にする。`Candidate(action=…, score=…, detail=…)`・等価・hash・pickle（書き出してから渡す）は前と同じ。
  Python の点（`score_action`）は今まで通りその場で書く
* **並べ替えの鍵**（`narrow._choices`）: `to_choice()` の文字列を枠の手の物ごとに 1 回だけ作る。順は同じ
* **port への `score` 要求**（`rustnode._candidates`・`_payload`）: 候補の列を `json.dumps` の dict の列ではなく、枠の手ごとの
  JSON 文字列（手の値で引く表と、要求の中では物の id で引く表）をつないで作り、`_payload` は位置と同じやり方（`_Held`）で差し込む。
  **port の命令の形も、送るバイトも前と同じ**（§2 で全要求をバイトで比べた）
* `tools/legal_moves_cost.py`: `narrow` の本体を段ごとに書き写していた所を、`_cover`・`_choices`・`_candidates`・`_PortDetail`
  を呼ぶ形にした（写しと本物がずれない）。detail を全部書く費用は `t_detail_write`（`narrow` の外）として別に測る

detail を読む所を洗った（`grep` で `.detail`・`Candidate(`・`detail=`、src・tools・tests）:
* src で読むのは `narrow` の順位付けの付け足し（`leaf …` の行）だけ。CLI・`search`・`leaf_ranking`・記録（`selfplay` の JSON）は
  `detail` を読まない
* 読むのはテスト 3 本（`test_depth2_port_batch`・`test_exchange_repeats`・`test_rust_node` の port 対 Python の比べ）と
  `tools/legal_moves_cost.py`。どれも `c.detail` で、同じタプルが返る
