## 1. 主記憶の内訳（前のコード）

`tools/train_value.py` は `load_dataset(packed=True)` で読む。この詰め方はすでにあり、id を int16 にし、0/1 だけの浮動小数の列を uint8 にしていた。残りの列は float32 のままだった。
`C:/tmp/ika426/memprofile.py` で、読み込みの段ごとに commit（private bytes）と working set を psutil で読んだ。データは gen-4 の学習と同じ `data/selfplay-mc01234-encoded.npz`（12,436,572 行）。CPU だけで、学習はしていない。

| 段 | commit | working set | 経過 |
|---|---|---|---|
| 起動 | 0.52 GB | 0.03 GB | 0 秒 |
| torch と pokeuraou を読んだ後 | 1.41 GB | 0.51 GB | 1 秒 |
| `load_dataset` の後 | 20.73 GB | 15.76 GB | 114 秒 |
| 保留局の分割の後 | 20.83 GB | 15.86 GB | 116 秒 |

配列ごとの大きさは次のとおり。

| 配列 | 形 | 前の詰め方 | 今の詰め方 |
|---|---|---|---|
| mon | (N, 2, 4, 91) | 16.217 GB | 3.383 GB |
| side | (N, 2, 27) | 0.821 GB | 0.224 GB |
| field | (N, 24) | 0.410 GB | 0.075 GB |
| mask | (N, 2, 4) | 0.099 GB | 0.025 GB |
| species・ability・item | (N, 2, 4) | 各 0.199 GB（int16） | 同じ |
| moves | (N, 2, 4, 4) | 0.796 GB（int16） | 同じ |
| 合計（1 次元の配列を含む） | | 19.277 GB | 5.435 GB |

mon の 91 列のうち 67 列は 0 と 1 だけで、前の詰め方では 1 列 1 バイトだった。残り 24 列は float32 で 1 列 4 バイトだった。
24 列の値の種類を全行で数えた（`C:/tmp/ika426/distinct.py`）。最大は列 0 の 8,679 種で、ほかの 23 列は 100 種以下だった。side の列 14 だけが 71,348 種を超え、float32 のまま残る。

学習の commit が 21 GB を超えたのは、この配列をプロセスごとに主記憶に持つためだった。CUDA の初期化などで 2 GB ほど足され、学習 1 本の commit の最大は 23.0 GB になった（§4）。

## 2. 変えたこと

`src/pokeuraou/packed.py` の `PackedFloat` を作り直した。

- 浮動小数の列は、最初のチャンクで 4 つの形のどれかに入る。0.0 と 1.0 だけの列は 1 ビット、256 種以下は uint8 の符号、65,536 種以下は uint16 の符号、それ以外は float32 のまま。
- 符号の表は float32 のビット列で引く。-0.0 と 0.0 は別の値として扱い、NaN もビット列のまま残す。
- 後のチャンクで収まらない値が出たら、その列を広い形へ移し、それまでに書いた行も正確に書き直す。ビットから uint8、uint8 から uint16、uint16 から float32 の移動がある。
- バッチを作るときは、詰めた行だけを GPU に送り、ビットの展開と表の参照を GPU で行う（`PackedFloat.tensor`）。CPU で全幅に広げてから送る前の形より、送るバイトが約 11 分の 1 になる。
- id は前と同じ int16 で持ち、GPU に送ってから int64 にする。

`load_dataset` に `cache`（既定で有効）を足した。

- 最初の読み込みで、詰めた配列を `<データ>.npz.packed/<鍵>-v1/` に .npy で書き出し、それをメモリマップで読み直す。次の読み込みは解凍せずにマップする。
- 鍵は zip の中央ディレクトリにある各メンバーの CRC-32 と長さから作る。符号化をやり直したファイル（2b が `ENCODING_REVISION` を上げた後など）は別の鍵になり、古いキャッシュは読まない。古い鍵のディレクトリは、新しいキャッシュを書いた後に消す。マップ中で消せないものは残る。
- `.npz` の形式と列の意味は変えていない。前の形式のファイルはそのまま読める。`--no-cache` を付けると、詰めた配列をプロセスの中に持つ。
- メモリマップした配列は commit に数えられず、同じファイルを読む学習どうしで物理ページを共有する。
- `tools/encode_dataset.py` が断片を読むときはキャッシュを作らない（`cache=False`）。読んだ断片は前と同じように主記憶でつなぐ。

ほかに `Dataset.split_by_game` の Python のループを `np.isin` に替えた。返す添字は前と同じで、1,200 万個の bool のリストを作らない。

gen-4 のデータのキャッシュは 4.8 GiB、mc0123 は 3.0 GiB、mc1 は 175 MiB で、`data/` の下に残っている。2a と 2b の学習は、同じファイルなら書き出しを省ける。

## 3. 前と同じ結果か

### 3.1 学習の重み（CPU）

`C:/tmp/ika426/bits.sh`。mc1（444,842 行）で、gen-4 の学び方（`--init-from value-mc3.pt --lr 5e-4 --keep last`）を 1 エポック、CPU で回した。保存した重みを `compare.py` でテンソルごとにバイトで比べた。最終のコード（c9a32e5 の後）で回した。

| 比べたもの | 違うテンソル | 最大の差 |
|---|---|---|
| 前のコード 2 回目（空の対照） | 26 個中 0 | 0 |
| 今のコード、キャッシュを作る回 | 26 個中 0 | 0 |
| 今のコード、キャッシュをマップする回 | 26 個中 0 | 0 |
| 今のコード、`--no-cache` | 26 個中 0 | 0 |

比べ方が差を見つけられることは、GPU の同じ組で確かめた。GPU の学習は前のコードどうしでも 26 個中 25 個が違い、最大の差は 7.1e-4 だった。GPU の学習はもともと決定的ではないので、重みの比較は CPU で行った。

### 3.2 GPU に送るバッチ

`C:/tmp/ika426/gpucheck.py`。mc1 を、詰めずに読んだもの（`packed=False`）と今の形で読んだものから、同じ添字の入力を GPU で作って比べた。8 種の入力すべてで、無作為のバッチ 200 個と全 444,842 行がバイトで一致した。
対照として表の値を 1 つ変えると、比較は違いを返した。

### 3.3 テスト

`tests/test_packed.py` に次を足した。

- 4 つの形それぞれに入る列と、広い形への移動のすべての組（値の種類 2・3・256・257・65,536・65,537）で、全体と添字の行がビット一致すること。
- 2 回目の読み込みがメモリマップで、詰めない読み込みとバッチがビット一致すること。ファイルを書き直すと鍵が変わり、古いキャッシュが消えること。
- 比較が失敗しうること（表の値を 1 ulp 変えて、比較が落ちること）。

移動のコードに「書き直す値を 0 にする」誤りを入れると、その時点の 10 本のうち 8 本が落ちた。誤りを戻すと全部通った。値の学習に関わるテスト 18 ファイルは通った（worktree に `data/` が無いため、使用率を読むテスト 9 本は skip）。

## 4. 主記憶と速さ（gen-4 のデータ）

`C:/tmp/ika426/abba.sh`・`three.sh`・`memwatch.py`。`selfplay-mc01234-encoded.npz` で、gen-4 の学び方を 1 エポック、GPU で回した（`--no-save`）。commit と working set の最大は、OS が持つプロセスの最大値を 0.5 秒ごとに読んだ。venv の python.exe は起動役で、本体は子のプロセスなので、木の全体を読んだ。

| 実行 | commit の最大 | working set の最大 | 機械の空き（始め→最小） | 1 エポック | 壁時計 |
|---|---|---|---|---|---|
| 前のコード | 22.97 GB | 20.84 GB | 19.4 → 0.3 GB | 103.4 秒 | 231.0 秒 |
| 今のコード、キャッシュをマップ | 4.07 GB | 7.64 GB | 17.7 → 9.7 GB | 69.5 秒 | 87.1 秒 |
| 今のコード、`--no-cache` | 9.19 GB | 7.66 GB | 17.6 → 9.9 GB | 75.3 秒 | 211.3 秒 |
| 今のコード、3 本同時（1 本あたり） | 4.05〜4.09 GB | 7.62〜7.66 GB | 17.6 → 5.5 GB | 151.1〜151.2 秒 | 169.0〜169.6 秒 |

前のコードは機械の空きを 0.3 GB まで使い、ページングが起きた。このため gen-4 のデータでの 1 エポックの比べは公平ではない。速さの比べは、主記憶に収まる mc0123 で行った（§5）。

マップした実行の working set 7.6 GB には、共有しているキャッシュのページ約 5 GB が入る。3 本同時でも機械の空きの減りは 12.1 GB で、1 本の working set の 3 倍より小さい。

3 本同時のエポックは 151 秒で、1 本だけの 69.5 秒より遅い。3 本が 1 つの GPU と CPU を分け合うためで、3 本の合計の壁時計は 170 秒だった。1 本ずつ回すと 3 × 87 = 261 秒になる。

この実行で `--seed 1・2・3` の 3 本は、seed 0 の実行と 1 エポックの損失が 4 桁まで同じだった（train 0.3980、val 0.3949）。1,000 万行の平均なので同じ桁に揃っただけかもしれない。重みは保存しておらず、確かめていない。

## 6. 確かめていないこと

- 6 エポックの学習を最後まで回していない。1 エポックの結果がビット一致し、エポックごとの処理は同じなので、6 エポックも同じと見ている。
- GPU の学習の重みは、もともと実行ごとに違う。GPU では入力のバッチの一致だけを示した。
- 2b の新しい符号化のファイルでは回していない。新しい列があっても、列ごとに形を選ぶので、同じ規則で詰まるはずである。
- `--swap-slots`・`--drop-train-moves`・`--curve` は、`dataset.encoded` の配列を CPU で添字で読む。これらは前と同じ `__getitem__` を通るが、この課題では回していない。
- キャッシュのディレクトリは `data/` の下に残る。消すのは手で行う。
