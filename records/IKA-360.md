# IKA-360: 人と打つ打ち手の torch の OpenMP の待ち回しを止める（KMP_BLOCKTIME=0）—— 局は同じバイトのまま、CPU は 4.3 分の 1、同じ読みの壁時計は −17%

2026-09-27。担当 IKA-333 の worker（調整役の指示で別課題に切り出し）。master 954862c から切った `ika-360-omp-blocktime`。
見つけたのは IKA-333（持ち時間の対戦評価）の走行中。一時ファイルは `C:/tmp/ika333/`・`C:/tmp/ika360/`（コミットしていない）。

## 1. 見つけたこと

IKA-333 の 1 s 対 0.1 s の対戦評価（人と打つ打ち手 2 つ、局ごとの過程を論理 8 コアに固定、4 スレッド + 先読みワーカー 3）で、ユーザーが「計算資源の使い方が変だ」と指摘した
（調整役の測り: 対局の過程が CPU 185〜220% のうち system 43〜45%、先読みワーカーは system の方が user より多い、機械の 16 論理コアが 96〜100%、GPU 27%）。

スレッドごとの user/sys と、各スレッドが始まったモジュール（Win32 の開始アドレス → DLL、`C:/tmp/ika333/thread_modules.py`）を 5 秒ずつ測った（12:19、走行中）:

```
  過程                       スレッドの起点（数）              user s / 5 s   sys s / 5 s
  対局の過程（66 スレッド）   libiomp5md.dll（torch の OpenMP）7      2.17          1.94
                             python.exe（本体）1                     3.47          0.27
                             ucrtbase.dll（Python の threading）24   1.02          0.09
                             OpenBLAS（scipy）15 + 15                0             0
                             nvcuda64.dll 2・ntdll 2                  0             0
  先読みワーカー（46 スレッド）libiomp5md.dll 7                       0.98          1.78
                             python.exe 1                            0.59          0.03
                             OpenBLAS 30・その他                      0             0
  port の exe（別過程）        本体とスレッド                          user 13〜46%   sys ほぼ 0
```

system 時間の正体は torch の Intel OpenMP のスレッド池の待ち回し。並列領域が終わった後、各スレッドは `KMP_BLOCKTIME`（既定 200 ms）の間、yield しながら回り続ける
（Windows では yield が system 時間に数えられる）。人と打つ打ち手は 1 手の中で葉の塊を何度も点けるので（CPU 側の配列の詰め替え・複写が行の多い塊で並列化される）、
7 本が本体でも各ワーカーでもほぼずっと回り、読みそのものが使うはずのコアを食っていた。

## 2. 直したこと

* `src/pokeuraou/openmp.py`（新規）: `quiet_wait()` が `KMP_BLOCKTIME` を 0 にする（すでに値があれば残す）。torch が読み込まれる前でないと効かない（ランタイムは読み込み時に 1 回だけ読む）ので、
  呼んだ時点で torch が読まれていたかを `before_torch` に残す
* 呼ぶ場所は人が起動する入口だけ: `tools/play_human.py`・`tools/analyze.py`・`tools/play.py` の、`src` をパスに足した直後（ほかの import より前）。
  spawn の先読みワーカーは親の環境を継ぐので、ワーカーにも効く。`play.py` が別の過程で起こす検討モードも環境を継ぎ、自分でも呼ぶ
* データ生成と `match_queue` には入れない（§3.2: 効かない）

## 3. 測定（`C:/tmp/ika333/omp_ab.py`・`gen.py`、heavy.py `--exclusive`、IKA-333 の枝 3d9e499 取り込み後の木で）

### 3.1 人の局（`play_human --person random --quiet --clock count --seconds 2 --max-turns 5 --games 2 --seed 31`、4 スレッド、value-mc1x2 + q-nocover）

13:25〜13:27、ABBA:

```

  0A    200            27.3      88.9                  85.9    f0756b786baf
  1B    0              23.1      33.8                   7.0    f0756b786baf
  2B    0              22.2      31.8                   6.6    f0756b786baf
  3A    200            27.4      90.6                  85.7    f0756b786baf
```

* **局は 4 本ともバイト一致**（数えの時計なので読みの量は同じ。待ち方だけが変わり、数値は変わらない）
* CPU は 175 s → 40 s（**4.3 分の 1**）、system は 86 → 7 s（陽性対照: 設定が OpenMP に届いた）、壁時計は 27.35 → 22.65 s（**−17%**。同じ読みを、回るスレッドに取られていたコアで速く終えた）
* 実時間の打ち手（既定）では、同じ秒の中で読める深化のステップがその分増える見込み（IKA-333 の 1 s の手で、単独の IKA-343 の 94.6 に対し対戦評価の中は平均 75〜81 だった）
