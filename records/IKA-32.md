2026-09-26。担当 IKA-32（worker）。master 6986ae1 から切った `ika-32-measure-parallel`。この段は測るだけ。

答えた問い: **人と打つ持ち時間の対局（局は 1 つ、1 局はほぼ 1 コア）で、1 手の壁時計のうちどれだけを複数コアに割れるか。

## 1. 計器（既定 off、局は変わらない）

段の計時（`timing.stage`）は「何の仕事か」で切るが、同じ `rust.fill` がある所ではセルに割れる根の行列、別の所では決定化ごとに割れる
dirty の充填になる。割れるかどうかは **仕事の置き場所（部分）** の性質なので、段を部分で切る口を足した。

* `timing.region(name)`（`POKEURAOU_TIMING_REGIONS` があるときだけ。無ければ共有の no-op）: 部分の **自分の** 壁時計・
  メインスレッドの CPU（`thread_time`）・呼び出し数と、**Rust の子の CPU**（部分の境で kernel の累計を psutil で読む。
  `rustnode` が子の pid を `timing.child_process` で登録）。内側の部分は外側を止める（段と同じ扱い）。部分の境で走っている段は
  境で切って両側に付ける（段の合計は変わらない）。どの部分にも入らない時間は部分 `-`。数え（`count`）も部分ごとに持つ
* 決定ごとの差分（`decisions[kind]["regions"]`）に入るので、「move.hidden の 1 手」を部分で読める。例外で閉じられなかった部分は
  次の `decided` で閉じ、`region.unclosed` を数える（今回の本では 0）

## 4. Amdahl の上限（1 手の壁時計の倍率、コア 2 / 4 / 8 / 16）

`T(n) = 逐次 + Σ 仕事 / min(n, 幅)`。幅は: port の要求はどれもセルが多いので n（port の中でセルに割る）、Python の決定化は
min(n, K)（K = 決定化の数、1 手 5.4〜5.7）、Python の部分ゲームは min(n, 1 段の部分ゲーム数)、両側は 2（人と打つ局の LP は 1）。
段と段の間の待ち合わせ（ターン → メニュー → 充填 → 葉 → 畳み）と負荷の偏りは 0 と置いたので、上限。

* S1r: port の中でセルの resolve だけを割る（encode・葉の共有・JSON は子の中で逐次、局のバイトの並びをそのまま保つ）
* S1: port の子の CPU を全部割る
* S2: S1 ＋ Python の決定化ごと・部分ゲームごとの仕事を別プロセス（または別スレッド）で
* S3: S2 ＋ 両側（メニュー 2 つ、根の LP 2 つ）
* 「GPU 逐次」: 葉の呼び出しを今のまま待つ。「GPU 重ね」: 深さ 2 の葉の呼び出しを充填と重ねる（塊の区切りと行数は同じ。
  サーバは塊をその行数で採点するので、呼び出しをどう束ねても答えは同じ——IKA-291 §1）。根のノードの葉（`belief.score`・
  `open.node`）は、ノードの全部分を積んだ 1 回の呼び出しで行数がノード全体なので、重ねられない

  5.4 本にしか割れない。h48 の S2 は 16 コアで 3.6 倍、8 コアからほとんど伸びない
* 逐次で残るもの（16 コアでの 1 手の下限の中身）: 根のノードの葉の 1 回の呼び出し（`belief.score`・`open.node`、h48 で 31 ms）、
  局を進める・交代（部分の外、3〜10 ms）、要求の組み立て（`belief.ref`）、深さ 2 の外側の LP とオラクル（3.5〜4.4 ms）

### ビット一致の制約が上限をどれだけ下げるか

1. **葉の塊の区切りと行数**（IKA-291）: 深さ 2 の部分ゲームの塊を 1 回の順伝播に積めない。積めれば（局が変わる）
   S3 の 16 コアは d2h 4.39 → 5.68 倍、h48d2 4.68 → 5.56 倍（IKA-291 のローカルの測り 57 ms → 22 ms を GPU の待ちに掛けた見積もり）。
   ただし塊の行数を変えずに **呼び出しを充填と重ねる** のは制約の内側で、d2h 6.37 倍・h48d2 5.96 倍まで届く（上の「GPU 重ね」）。
   制約で失うのは主に「重ねる」ではなく「積む」ほうで、重ねれば積むより上に行く
2. **根のノードの葉の 1 回の呼び出し**: `belief_payoffs` は全決定化の塊を積んだ 1 つの `Encoded` を 1 回採点する（行数はノード全体）。
   決定化ごとに分けて先に送ると行数が変わるので、全決定化の仕事が終わるまで待つ待ち合わせになる。h48 で 1 手 31 ms（10%）が
   逐次に残り、16 コアの上限を約 3.6 倍に抑える主因の 1 つ
3. **答えを集める順**: 部分ゲーム・決定化の答えは今の順で畳む（`_fold_cell` の順、`jobs` の順、`waiting` の順）。順を保つこと
   自体の費用は小さいが、段ごとの待ち合わせになる（ターン → メニュー → 充填 → 葉 → 畳み）。1 段の部分ゲームは 14〜24 個なので、
   16 コアでは各段の最後の 1 個待ち（負荷の偏り）が上の表より上限を下げる（測っていない）
4. **port の葉の共有と encode の並び**: 同じ局面の葉を 1 つにする処理と配列の並びはセルの順で決まる。resolve をセルごとに割り、
   encode を順に行えばバイトは同じ（S1r）。encode も割るなら、セルごとに作ってから順に併合する形が要る。差は 16 コアで
   S1 と S1r の 0.3〜0.4 倍
5. **LP**: 部分ゲームの LP は HiGHS（scipy）。プロセスやスレッドに分けても同じ入力・同じ HiGHS なら同じ頂点（同じ版の scipy を
   使う限り）。port に移すなら HiGHS と同じ頂点を返さないと局が変わる（IKA-305）

## 6. Python の逐次の部分をどう割るか —— 3 つの道の材料

### (1) GIL の無い Python（free-threaded）

* 今の venv は 3.12.14。ワーカー（`--served`）は **torch を読まない**（「this worker holds no model」、torch はサーバだけ）ので、
  要るのは numpy・scipy（`linprog` と scipy の HiGHS の束縛 `_highspy._core`）・psutil（計器だけ）
* PyPI（2026-09-26 に JSON API で確かめた）: lock の版 **numpy 2.5.3・scipy 1.18.1 に cp314t の win_amd64 の wheel がある**
  （cp313t は無い。cp315t もある）。psutil 7.2.2 は cp313t・cp314t の win_amd64 がある。**3.14t なら依存は揃う**。torch は不要
* 入れて測ってはいない（ファイルのダウンロードは利用者の許可が要るため、この段では調べるだけにした）。1 スレッドでの遅さは
  CPython の案内で 3.14t が pyperformance で 5〜10%（3.13t は約 40%）とされるが、この仕事（小さな numpy の演算と dict・dataclass が多い）
  では測っていない
* 利点: 決定化ごとの塊（w48 で 1 本 150 MB）を複製せずにスレッドで共有できる。受け渡し（pickle）が無い
* 課題: port の子は 1 本のパイプで 1 要求ずつなので、スレッドごとに子を持つか、port が複数の要求を同時に受ける形が要る。
  numpy・scipy の free-threaded 対応はまだ「実験的」の扱いの所があり、HiGHS の束縛がスレッド安全かは確かめていない

### (2) プロセスで割る（multiprocessing）

### (3) 熱い部分を port（Rust）に移す

## 7. 判断（提案）

**実装の順:**

1. **port の中でセルを割る（S1r → S1）**。Python は変えない。`fill`・`fills`・`many`・damage の点の要求の中で、セルの resolve を
   スレッド（rayon など）で割り、セルの順に集め、encode と葉の共有は今の順で行う。局はバイトで同じになるはず（集める順が同じ）。
   人と打つ形（h48）で 16 コア 1.7 倍（S1r）、encode も順を保って割れば 2.1 倍。生成（24 ワーカーで CPU が埋まっている）では
   スレッドを 1 にする旗が要る
2. **深さ 2 の部分ゲームの Python を port へ**（IKA-303 の narrow、IKA-305 の LP、IKA-302 の JSON）。1 コアで速くなり、
   その仕事が 1. の割る道に入る。深さ 2 の 16 コアの上限が S1 の 1.7 倍から S2 相当の 4 倍台へ上がる
3. **深さ 2 の葉の呼び出しを充填と重ねる**（塊はそのまま、呼び出しを先に出す）。d2h の S3 で 4.4 → 6.4 倍
4. 幅 48 で遊ぶなら、決定化の `belief` の Python を一括の numpy か port へ（h48 の 1 手 300 ms のうち 68 ms。全部消えた場合が
   上限で −23%。どこまで消えるかは測っていない）

**持ち時間の対局で何倍になるか**（16 コア、1 手の壁時計）: 1. だけで 1.7〜2.1 倍、1.〜3. で深さ 2 が 4〜6 倍、幅 48 の深さ 1 が
3.5〜3.9 倍。ただし今の人と打つ形は 1 コアで 0.3 秒/手なので、**これは「同じ 45 秒でどれだけ大きな探索を回せるか」の倍率**で、
今の探索が遅すぎるから要るのではない。

**IKA-293（幅か深さかのキュー）との組み合わせと、キューの予算の単位:**
* 並列にすると、仕事の種類ごとに壁時計への効き方が変わる: port のセルの resolve は 1/n、部分ゲームの Python は 1/min(n, 段の部分ゲーム数)、
  決定化の Python は 1/min(n, K)、根のノードの葉の呼び出しと外側の LP は 1/1。1 コアでの「セル数」や「ms」は、16 コアでは
  同じ費用を表さない（S2 の 16 コアで、幅を足した h48 は 1 手が 1/3.6、深くした d2h は 1/4.1 になり、1 コアの ms の比が崩れる。
  崩れ方は仕事の混ざり方で決まる）
* だから **キューの予算の単位は「秒」でも「セル数」でもなく、本番のコア数での壁時計の見積もりを、数え（局を決めるもの）から
  作ったもの** にするのがよい: 予算 = Σ 種類ごとの数（解いたセル、部分ゲーム、LP、葉の呼び出し、決定化の仕事）× その種類の
  「n コアでの 1 件の ms」。数えは決定的なので局はビット一致のまま（IKA-33 の「予算はセル数」の性質を保つ）、係数だけを
  機械とコア数ごとに測って持つ。IKA-33 §9 の「セル + 精緻化 1 回あたり k セル」を、コア数の軸まで伸ばした形
* 係数の表はこの課題の計器（`--regions`）で、部分ごとに 1 件あたりを出せる（例: d2h の部分ゲーム 1 つは 1 コアで両側分
  約 4.8 ms、うち port 2.1・Python 2.3・GPU 0.5）

## 11. 実装の 1 段目: port の中でセルを並列にした（S1r）

2026-09-26。ブランチ `ika-32-port-parallel-cells`（master 03e90cd から）。§7 の「1.」の実装。Python の探索は変えていない。

### 11.1 入れたもの

* **`rust/src/par.rs`**: std だけのスレッドの池。クレートは足していない（rayon を入れると crates.io から落とすことになり、
  ダウンロードは利用者の許可が要る。池自体も小さく、難しいのは下の `Rc` の扱いで、これはどのクレートを使っても自分で考える所）。
  * スレッド数: `node <reg> --threads N`、無ければ環境変数 `POKEURAOU_PORT_THREADS`、無ければ **1（今と同じ）**。
    1 のときは池を作らず、各関数は前と同じループを通る
  * 池は最初に要るときに `N - 1` 本のスレッドで作り、終わらせない。要求を読むスレッドも仕事に加わる。
    項目は空いたスレッドが次の添字を取る形で配り、**集めた後に添字で並べ直す**（頼んだ順）
  * `Position` は `Rc` を持つので `Send` ではない。各スレッドは要求の JSON から **自分で局面を読み直し**（`Request.position_json`、
    池があるときだけ持つ）、解いたターンを `Rc` の木ごと、仕事の終わりに渡す（`par::Handoff`）。渡す側は仕事の間 `Rc` に触れず、
    受け取るのは全スレッドが「終わった」と言った後（mutex の後）。スレッドを終わらせないので、`Position::from_json` が配る
    スレッドローカルの空の blob も、仕事の外では触られない。`each` が要求の `Position` を掴めないことはコンパイラが見ている
    （`Sync` でないものは閉包に入らない）
* **割ったもの**（`node.rs`・`encoded_node.rs`）:
  * `fill`（目的関数の行列）: セルごとに resolve と `turn_value` まで。注記は集合なので合併の順は効かない。拒否は頼んだ順
  * 符号化ノード（`fill_shared`。`encoded` と `fills` の各ノード）: セルの `resolve_turn` と、そのターンの交代の中断の再開
    （`resume_all`。前は `Collector.turn_leaves` の中で 1 スレッドで再開していた）。**葉の共有（`add_leaf`）・符号化・spans と
    fold の組み立て・ヘッダは 1 スレッドで、セルの順**。中断は `turn_leaves_resumed` が再開済みの木を同じ順で歩く
    （再開は collector に触らないので、`add_leaf` に渡る葉の順は同じ）。`like` の読み取り（IKA-295）は前のノードの局面に触るので、
    要求を読むスレッドで先に行い、残りのセルだけを池に出す。セルは `32 × スレッド数` ずつの塊で出す（幅 48 のノードの全セルの
    ターンを一度に抱えないため）
  * `many`（IKA-295）: 要求ごと。各要求は自分で局面を読み、JSON で答えるので `Rc` は渡らない
  * 割っていないもの: 単独の `score`・`resolve`（1 ターン）・`alternativesEncoded`・単独のターンの命令（どれも 1 件）
* **encode は逐次に残した**ので、§4 の **S1r** の形（S1 ではない）
* **非決定の源の点検**:
  * port に乱数は無い（ターンは確率を列挙する）
  * HashMap は `Collector.seen`（引くだけ、要求を読むスレッドでセルの順に）と `Kept.cells`（引くだけ）。反復はしていない
  * 注記は BTreeSet
  * スレッドローカルは次の 3 つ。どれも答えは変えない
    * `LAST_RESOLVE`: `resolve` 専用で、要求を読むスレッドだけが使う
    * 空の blob: スレッドごとに持つが中身は同じで、`==` で比べる
    * `Encoder` の RefCell: 符号化は 1 スレッド
  * `Rc::ptr_eq` は近道だけで、外れたら `==` に落ちる（`same_mon`・`Like::turn`）。`strong_count` は数え（`UNSHARED`）に使うだけ
  * 数え（`CLONES` など）は atomic で、答えには出ない
* **口**:
  * Rust の旗と環境変数
  * `rustnode.set_port_threads(n)`（持っている port を閉じ、次を `--threads n` で立てる）と `RustNode(reg, threads=n)`
  * `cli.py --port-threads`（検討の道具）と `tools/match_queue.py --port-threads`（対戦評価。ワーカーの環境に入れる）。
    人と打つ道具はまだ無い（§2）ので、作るときは `set_port_threads` を呼べばよい
* **陽性対照の口**:
  * 要求 `{"kind":"parallel"}` は、スレッド数・池に出した map と項目の数・うち要求を読むスレッド以外が解いた数（`offMain`）を返す
  * `POKEURAOU_PORT_THREADS_REPORT=<dir>` があると、各 port が終わるときに同じ数を `port-<pid>.json` に書く
    （生成のワーカーには尋ねられないため）
  * どちらも既定では何も変えない
* **故障注入**: 機能 `ika32-control` は、集めた答えを添字で並べ直さず、終わった順のまま使う（「並べ直し忘れ」の形）

### 11.6 次の段の提案

   * 効くのは主に深さ 2（16 スレッドで上限の 87%）
3. **encode も割る（S1r → S1）**

   * 深さ 1 の上限が 1.70 から 2.10 に上がる。今回の実測は S1r の上限の 85% なので、得は +0.3 倍前後の見込み
4. **人と打つ道具**
   * `rustnode.set_port_threads(8)` を呼び、持ち時間から幅・深さを選ぶ口（§7、`cells_for_seconds`）
