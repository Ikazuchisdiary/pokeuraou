2. **(1) 往復の遅れか、塊の小ささか**: 依頼はまず小さい（O24 で 512 行以下が `score` の 91%）。1 つを他に誰もいないサーバで解くと 2.2 ms（うち CPU 1.76 ms・同期 0.29 ms、2,290 件。裏あり 4.5 ms・CPU 3.5 ms）。GPU の順伝播そのものは 0.3〜0.8 ms で、CPU が積む仕事（ピン留めした配列への写し・`from_numpy`・グラフの再生の積み・結果の写し）が費用の大半。ワーカー過程から見た 1 回（7.44 ms）とサーバの中の 1 回（7.28 ms）の差は 0.16 ms なので、ソケット・JSON・共有メモリの往復そのものは 2% で、往復の遅れではない。
3. **(2) サーバ過程の待ち行列**: 依頼の壁時計はサーバにいる依頼の数で伸びる（O24、入ったときの数 1 → 3 → 6 → 9 → 12 で 3.8 → 5.8 → 7.4 → 8.1 → 7.5 ms。ロックの待ちは 0.11 → 0.8 → 2.1 → 3.4 → 4.5 ms。CPU は 2.2 → 1.6 ms とむしろ減る）。ロックは 1 秒あたり 0.71 秒握られ（1 回の保持は `score` 0.56 ms・`q_batch` 1.12 ms）、稼働率 71% の 1 つの窓口の待ち時間（待ちは保持の約 ρ/(1−ρ) = 2.4 倍、実測 2.9〜3.6 ms）と合う。CPU は 1 つのサーバ過程で 1.8 コア使っており、GIL の飽和ではない（1 ms 眠るスレッドの遅れ: 実行中の平均 0.58 ms、p99 1.3 ms、何も無い過程でも平均 0.58 ms）。
4. **(3) ワーカー側の直列**: ワーカーは 1 つ出して答えを待つ（port が次の分を埋める重なりはある）。サーバの中の依頼の数の平均 6.7 は 15 × 0.45 = 6.8 と合う（リトルの法則）。つまり待ちの大半はサーバの中の時間で、ワーカー側の準備が遅くて依頼が出ない、ではない。依頼を出す側を速くしても、サーバの窓口が 71% なので待ちは縮まない。
5. **機械の側**: 全論理コアの使用は O24 で平均 71.5%（p10 60.6・p90 85.3）、H8 で 76.5%（p90 92.6）。私たちの過程は 9.0・10.2 コア、外の負荷 2.4・2.1（標本の過程を含む）で、平均 4.6・3.8 コアが空いている。port 16 過程の CPU は平均 5.7 コア（O24）・8.2 コア（H8）、ワーカー過程（Python）は 1.3・0.85 コア、読み手 0.24・0.09 コア。つまり 15 のワーカーのうち走っているのは O24 で約 6〜7、H8 で約 8〜9 で、O24 では約 7 がサーバの待ちで止まり（6.8）、その間 CPU は他の過程に使われず空いている（サーバ待ちで空いた CPU を使う仕事が無い）。
6. **上限の見積もり（§3）**: サーバ側の改善（依頼の待ち行列を縮める）は同じ段までの実時間で O24 1.10〜1.25 倍・H8 1.05〜1.15 倍。ワーカー過程の Python を全部消す B4 段 2〜4 は O24 1.06〜1.12 倍・H8 1.05〜1.10 倍で、しかもサーバの窓口が 71% なので、ワーカーが速くなるほどサーバの待ちが伸びて食われる。**B4 より先にサーバ側を測る価値がある**。
7. **測りの費用（null 対照）**: フックの無い同じ実行（O24N・H8N）でサーバ待ちの 1 回は 7.05・16.31 ms（フックあり 7.44・17.27 ms、+5.5・+5.9%）、`node/wall` は 15.91・11.64（15.30・11.95）。フックは往復を 5% ほど延ばす（1 回ずつなので実行ごとの揺れの中かもしれない）。内訳の割合（§1 の表）は 1〜2 ポイントの差で、結論は変わらない。
8. **機械（§5）**: 専有 9.1 分（承認 15 分以内）。

## 1. 測り方

* サーバ過程（`inference_server.py`）に `srv_site/sitecustomize.py` を読ませた（`IKA379_SITE`）。サーバの import が終わってから `inference._Handler._serve` を包み、依頼ごとに 1 行（操作・行数・局面数・壁時計・スレッドの CPU（`QueryThreadCycleTime`）・グラフのロックの待ちと保持・`torch.cuda.Event.synchronize` の待ち・入ったときと出るときにサーバにいた依頼の数）を書く。ロックは時計付きの入れ物に差し替え、答えは変えない。別のスレッドが 1 ms 眠ってどれだけ遅れて起きるか（GIL の待ちの目安）を 1 秒ごとに書く。

## 6. 確かめていないこと

* 各実行は 1 回ずつ。実行ごとの揺れ（IKA-388 の ±3〜5%）は見ていない。内訳の割合は 1〜2 ポイントの差でしか動かなかった（null 対照）が、絶対値はフックで 5% ほど延びている。
* eager の道の「その他」（GPU の順伝播・eager の関門・CPU の順番待ち）は分けていない。
* GIL の待ちは 1 ms の眠りの遅れでしか見ていない（実行中も何も無い過程も 0.58 ms）。サーバ過程の 1 スレッドごとの実行可能な待ちは測っていない。
* (c1)〜(c3) と (a) の倍率は推定で、どれも実装・測定していない。窓口の待ちを ρ/(1−ρ) で当てたのは事後の合わせで、他の分布では変わる。
* L6 は実時間を使い切るので、段 0 では同じ段までの実時間の比べをしていない。
