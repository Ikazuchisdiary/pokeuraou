2026-09-28。担当 IKA-373（worker）。master d63391a から切った `ika-373-cheaper-q`。
駆動と出力は `C:/tmp/ika373/`（コミットしていない）。

用語は用語集どおり（推論サーバ・評価モデル・候補集合・条件・実行・スモークテスト・ノード時間・実時間・裏・ABBA・ビット一致・陽性対照・A/A 対照）。

## 0. 問いと答え

1. **内訳を数え直した（§2）**: 16 スレッド・開いた 7 局面・実時間 8 s。ワーカー過程の中の Q の道を、関数ごとに実時間と CPU で数えた（`C:/tmp/ika373/prof_site/sitecustomize.py`）。
   - Q の子の候補集合づくり（`deepen._q_menus`）がワーカー過程の時間の 29%。うち推論サーバの Q の往復（`RemoteQ._post`）が 18.7%（1 往復 34 ms）。
   - **port の Q の特徴量（`qhead.port_features`）は 1.6%**。1 ノード秒 112 回で、port の読み 514 回の 2 割。1 回 0.54 ms のほぼ全部が python の CPU（依頼を作る側）で、port を待つ時間ではない。IKA-370 の「9 割（420 回）」は Q なしの条件との差から読んだもので、特徴量そのものの数ではなかった。
   - 推論サーバの `q_batch` は、手元で同じ依頼を流すと 1 回 3.5 ms の CPU（eager、約 150 カーネルの起動）で、算術は数 µs。依頼は中央 3 局面・候補 12×7 と小さい。
2. **(b) `q_batch` を CUDA graph にした（§1）**: `qrank.QBatchGraphs`。形 (B, N0, N1) ごとに、胴（B ごと）・各側の行動（側・B・N ごと）・対の頭（側の graph の組ごと）の graph を取る。eager と同じ形なので、答えはビット一致。
   - 手元の 400 依頼で、1 回の CPU 3.48 → 0.74 ms、3,836 行列すべてビット一致（graph を落として取り直す設定でも）。
   - 推論サーバの Q の 1 往復 34.2 → 7.7 ms（サーバの中）、ワーカー過程から見た往復 21.6 → 8.1 ms。サーバの CPU は 1.36 → 0.73 コア。
3. **速さ（§3）**: ABBA（`--exclusive --gpu`）、開いた 7 局面・実時間 8 s。
   - 16 スレッド: A 3.88・3.96・3.87・3.63、B 5.13・5.26・5.26・4.96（平均 3.84 → 5.15、1.34 倍）。
   - 8 スレッド: A 3.63・3.57・3.44・3.32、B 4.05・3.99・3.55・3.61（3.49 → 3.80、1.09 倍）。8 スレッドはもう port 待ち（47%）で詰まる。
   - 裏あり 7 局面・16 スレッド: A 5.65・6.01、B 7.57・7.40（5.83 → 7.49、1.28 倍）。
   - 16 スレッドが 8 スレッドを 1.36 倍上回るようになった（前は 1.10 倍）。
4. **カードのメモリ（§4）**: 最初の形では、裏ありの局面で graph の私用の pool が 2.1 GB まで育ち、推論サーバ（上限 3.5 GB、IKA-334）が評価モデルの依頼で OOM になった（実行 hB1・hB2、局面 5・6 で止まった）。パディングしたセル B×N0×N1 が 65,536 を超える依頼は eager に残す上限（`Q_BATCH_GRAPH_CELLS`）を置いた。裏ありの依頼の 94% を graph で、予約 +656 MiB（eager だけの山 +1,686 MiB より少ない）。開いた局面の依頼はすべて上限の内。
5. **一致（§5）**: 数えた時計（2 s、開いた 7 局面）で A と B の読みが、1 スレッド 7/7・16 スレッド 7/7 バイト一致。陽性対照: B の実行で graph の再生 154 回（1 スレッド）・418 回（16 スレッド）、A は 0 回。感度の対照: 1 スレッド対 16 スレッドは 0/7（推論サーバの塊の大きさで値の最後の桁が動く）、局面 i と i+1 は 6/6 で違う。候補集合は変わらないので、局面集の損失の判定は要らない。
6. **データ生成は通らない（§6）**: M-C gen-1 の設定の生成（深さ 1）で、推論サーバの Q の依頼 819 回はすべて 1 局面の `q`（既存の `QGraphs`）で、`q_batch` は 0 回。生成の道は変わらないので、生成の ABBA は回していない。
7. **(a)・(c) は入れなかった（§7）**: (a) は §2 のとおり上限 1〜2%。(c) は B の後で Q の往復がワーカー過程の時間の 6% で、しかも `q_groups` の約束（IKA-367、候補集合を前と同じに保つ）を変える。

## 1. 変えたもの

* **`src/pokeuraou/qrank.py`**:
  - `QBatchGraphs`: `qhead.q_matrices`（位置を積み、各側の候補をバッチの最長にパディング）を、形ごとの CUDA graph で。
    - 切り方は `QGraphs` と同じ（胴と文脈 / 各側の行動 / 対の頭）で、対の頭も graph にした（sigmoid と double への変換を含む）。
    - 部品ごとに私用の pool（胴・側 0・側 1・対）。1 依頼は各部品の graph を 1 つずつ順に再生するので、出力は同じ pool の他の graph が再生される前に読まれる。
    - 対の graph は 2 つの側の graph の出力を読むので、側の graph を落とすときはその上の対の graph も落とす（キーは側の graph の通し番号）。
    - パディングした候補は平たいバッファを (B, N, …) に見て渡す（eager と同じ連続のテンソル）。入力はページ固定のメモリを経る。グラフのロック（`inference._GRAPH_LOCK`）の下で積み、待ちはロックの外。
    - 上限: 局面 16（`POKEURAOU_Q_BATCH_GRAPHS`、`deepen.Q_MENU_CHUNK` と同じ。0 で off）、候補 256（`Q_GRAPH_POOL`）、パディングしたセル 65,536（`POKEURAOU_Q_BATCH_GRAPH_CELLS`）。超える依頼と、取り込みに失敗した後は eager（同じ答え）。
    - 保持: 部品ごとに 512 個（`POKEURAOU_Q_BATCH_GRAPH_CACHE`）、最近再生していないものから落とす。
  - `served_q` の `batch`（op `q_batch`）が `QBatchGraphs` を使う。計時の段 `server.qbatchgraph`・`server.qbatcheager`・`server.qbatchsync`、数 `q.batchgraph.captured`・`replays`・`evicted`。
* **`tools/inference_server.py`**: 起動の行に「q_batch by CUDA graphs」、計時の報告に `server.q.batchgraphed`・`server.q.batchcaptured`。
* **テスト** `tests/test_q_rank.py::test_the_batch_graphed_q_is_the_eager_batch_to_the_bit`（CUDA、CI では skip）:
  - 学んでいない Q で、20 依頼から作った 301 バッチ（大きさ 1〜8 と 16）を往復の順で流し、`q_matrices` とビット一致。保持 3 個にして graph を落とし・取り直す。対の graph が落ちた側の graph を読まないこと、17 局面とセルの上限を超える依頼は eager に回ること、推論サーバの `batch` が graph を通ること（`replays`）。
  - **故障注入**（`C:/tmp/ika373/mutate.py`。書き換え → テスト → バイトで戻し、ハッシュで確認）: パディングを 1 つ多くする・落とした側の上の対の graph を残す・pool を部品で分けない、の 3 つとも落ちる。何もしない文を足す（A/A 対照）は通る。pool を分けない故障は、実際の 400 依頼でも 3,836 行列のうち 2〜4 が最大 0.93 ずれた（`mutate2.py`）。
  - CI の skip の予算: suite ジョブの torch 21 → 22、learn ジョブの cuda 6 → 7（`.github/workflows/ci.yml`）。

## 7. 入れなかった候補

* **(a) 複数局面の Q の特徴量を 1 回の port の往復で**: §2 のとおり Q の特徴量はワーカー過程の時間の 1.6〜1.8%、しかもその時間は python で依頼（局面の JSON と候補）を作る側。Rust で束ねても、python の依頼づくりは残る。見込みは 1% 前後で、Rust の変更に見合わない。
* **(c) Q を段ごとに 1 回に積む**: B の後の Q の往復はワーカー過程の時間の 6%（3,682 回 × 8.4 ms）。積むとバッチが 16 局面を超え（graph の上限の外）、`q_groups`（IKA-367）の「束ねても子の候補集合を前と同じに」を変える（局面集の損失の判定が要る）。得は数 % 以下と見て入れなかった。

## 8. 別課題の候補
